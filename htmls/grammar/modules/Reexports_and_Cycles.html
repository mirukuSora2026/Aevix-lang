1. Reexport named public declarations explicitly

EXAMPLE MODULE · geometry

public import math.vector { Point };

public import forwards the explicitly named declaration under the same name. A normal import makes a name available to its importing module; it does not by itself make that name public to consumers. The source declaration must be public and accessible.

Reexporting Point does not reexport every other member of math.vector. The explicit list records the public surface intentionally. Reexport names cannot be aliases.

2. Use the path that the consumer actually imported

EXAMPLE CONSUMER · geometry publicly reexports Point

import geometry { Point };

geometry.Point make_origin() {
    Point value = Point { x = 0.0, y = 0.0 };
    return value;
}

Point and geometry.Point are allowed. The consumer did not import math.vector.Point, so the original defining path is not automatically authorized even though the compiler resolves Point to that original declaration.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import geometry { Point };

math.vector.Point unimported_original_path() {
    return Point { x = 0.0, y = 0.0 };
}

The original path requires its own import. Canonical identity and source-level access paths solve different problems: knowing where a declaration originated does not grant the programmer another lookup route.

3. Duplicate routes to one origin remain one declaration

import math.vector { Point };
import geometry { Point };

Point merged_origin() {
    return Point { x = 0.0, y = 0.0 };
}

Both imports lead to the same original Point declaration. They merge by canonical identity, so the short name is not ambiguous solely because it arrived twice. The declaration does not become two unrelated types, two overload origins, or two storage-owning copies.

The explicitly imported paths retain only their granted access. This example names both routes explicitly. Importing geometry alone would not gain math.vector as a side effect of deduplication. Additional paths are never synthesized from the chain of reexports.

The same identity principle applies to functions and constants. A same-origin overload set is not combined with a different module's unrelated overloads merely because the names match.

4. No wildcard forwarding or alias forwarding

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

public import math.vector { * };

Wildcard reexport is forbidden. A module must list the names it wants to expose. Ordinary import math.vector { * }; remains permitted for that module's own access, so these two forms must not be conflated.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

public import math.vector { Point as Vec2 };

Renaming a forwarded declaration is not allowed. The whole-module form public import math.vector; has not been decided; this reference does not present it as valid. Like other imports, chosen named public imports appear before declarations.

5. Module declaration cycles are allowed inside one package

EXAMPLE FILE · src/cycle/alpha.avx · module cycle.alpha

import cycle.beta { odd };

public bool even(i32 count) {
    if (count <= 0) return true;
    return odd(count - 1);
}

EXAMPLE FILE · src/cycle/beta.avx · module cycle.beta

import cycle.alpha { even };

public bool odd(i32 count) {
    if (count <= 0) return false;
    return even(count - 1);
}

The files refer to each other's public declarations. This same-package module cycle is allowed; a declaration need not become unavailable merely because another file is still being connected. Imports and access restrictions are nevertheless checked on every edge.

This example illustrates mutual declaration references, not a guarantee that arbitrary recursive calls terminate or that a compiler has executed them. A dependency cycle across packages is forbidden even when the modules would otherwise be a valid declaration cycle.

6. Declaration connection is separate from value initialization

Connecting a module establishes which declarations names refer to and checks their contracts. It does not require exposing a partly initialized value. Allowing a declaration cycle does not allow reading a persist value before it has been initialized.

All top-level persist declarations in modules transitively reached by following imports and reexports from the entry module are initialization targets before program entry. Confirmed value dependencies lead the initialization plan; managed dependencies discovered during execution follow the readiness and cycle rules in Persistent Storage.

Import line order is not the initialization order, and choosing a name from a module does not mean only that declaration's initialization is relevant. Private top-level persist declarations remain part of an included module's target set.

7. Recursive type declarations still need a finite layout

enum ListNode {
    End;
    Next {
        public i32 value;
        public Box<ListNode> next;
    };
};

The indirection is explicit in Box<ListNode>. It does not assert a stable ABI, automatic boxing or allocation by an enum declaration itself. Creating a heap owner uses the corresponding explicit Box API and its failure/cost contract.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

struct Endless {
    public Endless next;
};

A by-value recursive field requires an endlessly expanding layout and is rejected. The same requirement applies when the by-value cycle crosses files. Import cycles are allowed; infinite-sized value layouts are not. The compiler does not silently insert Box to repair the declaration.

8. A reexport cycle needs a real defining declaration

REJECTED EXAMPLE MODULE · redirects.first

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

public import redirects.second { Point };

REJECTED EXAMPLE MODULE · redirects.second

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

public import redirects.first { Point };

Taken together, these modules only forward Point around a closed redirect cycle. Neither provides an original definition. This is an unresolved reexport cycle and is rejected rather than manufacturing a placeholder Point type.

A module graph may have cycles while a particular reexport still resolves to a real original declaration. Track the requested name and original identity, not just whether a module was visited once. No private declaration may be promoted by a circular forwarding chain.

9. Constant initialization cycles are errors

REJECTED EXAMPLE MODULE · constants.left

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import constants.right { RIGHT };

public const i32 LEFT = RIGHT + 1;

REJECTED EXAMPLE MODULE · constants.right

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import constants.left { LEFT };

public const i32 RIGHT = LEFT - 1;

Each const requires the other's value before its own value can be computed. There is no initialized starting value. The compiler rejects the constant initializer cycle instead of solving simultaneous equations, substituting zero, or treating it as harmless declaration recursion.

persist initialization has its own dependency and runtime-readiness rules, including prevention of uninitialized access and diagnosis of initialization cycles. Those rules do not turn an unresolved const value into a valid runtime fallback.

10. Privacy and selection survive every cycle

A module in a cycle sees only the names granted by its imports. Selecting Point does not authorize a qualified access to dot in the same target module. A public reexport of Point does not reveal the source's private helpers or grant access through the original module path.

A parent/child filename prefix does not weaken these checks. math.vector.ops is independent of math.vector, and each must import the other's public declarations if it needs them. A cycle is not a friendship relation between files.

Likewise, a package dependency cycle is not legalized by the fact that the declarations could be connected. See package cycle boundaries.

11. SCC collection is a possible compiler organization

Collecting declarations across strongly connected components is a recommended way to organize a compiler for allowed module cycles. It can help separate name/type connection from value initialization analysis.

This is implementation guidance, not evidence of an existing parser, linker or SCC pass, and not a requirement that every backend use the same internal algorithm. AOT and JIT must preserve the selected name identity, access and initialization semantics.

Canonical declaration identity must survive reexport routes. The compiler must not make an extra type or an extra generic function storage instance merely because another module forwards the same declaration. The exact internal representation is not specified here.

12. Open forwarding and cycle details

  • The whole-module public import form; named explicit reexports are the chosen form.
  • Exact diagnostics and source-location reporting for long or ambiguous forwarding chains.
  • Complete module loading/build implementation, generated modules and incremental compilation mechanisms.
  • Filesystem indirection and package configuration details beyond the selected path rules.

Named same-origin reexport deduplication, forbidden wildcard reexports, same-package declaration cycles, finite layouts and rejected rootless redirect/constant cycles are already chosen. See Functions and Persistent Storage for their separate contracts.
