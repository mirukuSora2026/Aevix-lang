1. One .avx file defines one module

A source file is the module boundary. The .avx extension is the source-file extension. The module name is derived from the file path rather than repeated in a module declaration inside the source.

This design describes logical source identity and access. It does not prescribe an implemented filesystem resolver or promise that every future build environment uses a physical local directory. The mapping examples here use the selected default source root.

2. Derive full paths from the source root

Source file under the default rootFull module path
src/math/vector.avxmath.vector
src/math/vector/ops.avxmath.vector.ops
src/app/start.avxapp.start

src/ is the default source root and may be configured. The configuration file name, format and complete root declaration grammar are not yet selected. The source-root prefix and .avx extension are not included in the logical import path.

Dots separate module path components. A full path is a logical module path, not a quoted operating-system filename. Public import and ordinary import use the same full path spelling.

3. Do not repeat the module name in the file

EXAMPLE FILE · src/math/vector.avx

public struct Point {
    public f64 x;
    public f64 y;
};

public f64 dot(&Point left, &Point right) {
    return (*left).x * (*right).x + (*left).y * (*right).y;
}

f64 square(f64 value) {
    return value * value;
}

The path supplies math.vector. Point and dot are public declarations; square is private because no public modifier is written. Their module identity does not require a module math.vector; header.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

module math.vector;

public const i32 DIMENSIONS = 2;

A separate module declaration is not part of the chosen model. Do not treat the file path and an extra header as two competing sources of module identity.

4. Imports use full paths, even between nearby files

EXAMPLE MODULE · app.start

import math.vector { Point, dot };

f64 projection(&Point value) {
    return dot(value, value);
}

The full math.vector path is written from the module root. Moving the importing file to another directory does not turn this spelling into a relative path. Already borrowed parameters are passed directly to dot without an extra reference layer.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import .vector { Point };

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import ../math/vector.avx;

Leading-dot imports and parent-directory imports are rejected. Import paths do not use relative filesystem traversal or include the .avx extension.

5. A module file and a same-prefix directory may coexist

FileModuleRelationship
src/math/vector.avxmath.vectorIndependent file module.
src/math/vector/ops.avxmath.vector.opsAnother independent file module.

Both files are allowed at the same time. Each defines its own module. A directory path prefix does not replace, merge with, or inherit the declarations of the file module.

EXAMPLE FILE · src/math/vector/ops.avx

import math.vector { Point, dot };

public f64 length_squared(&Point value) {
    return dot(value, value);
}

The child-path module explicitly imports Point and dot. Its prefix does not make those declarations automatically visible. A file module does not automatically reexport all modules under a same-prefix directory.

6. Parent and child paths keep separate privacy and imports

import math.vector { Point };
import math.vector.ops { length_squared };

f64 use_operations() {
    Point value = Point { x = 3.0, y = 4.0 };
    return length_squared(&value);
}

The consumer selects the Point declaration from math.vector and the function from math.vector.ops. Importing one module does not automatically authorize access to the other, in either direction. Each file also has its own private declaration boundary.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import math.vector;

f64 child_is_not_imported() {
    math.vector.Point value = math.vector.Point { x = 3.0, y = 4.0 };
    return math.vector.ops.length_squared(&value);
}

The whole-module import grants qualified access to public names of math.vector. It does not import math.vector.ops. A longer spelling cannot synthesize a missing child import.

7. Match both logical and actual file casing

SituationChosen outcome
Only src/math/vector.avx exists; import uses math.vector.The casing matches.
The same file is requested as Math.Vector.Reject the casing mismatch; do not use filesystem case folding.
One package contains math.vector and Math.vector.Reject modules whose paths differ only by case.
A path component on disk has different casing from the import.Reject the mismatch even on a case-insensitive host filesystem.

Module paths are case-sensitive, and the written path must match actual file and directory casing. A package cannot place two modules that differ only by case. These checks prevent host filesystem behavior from silently changing which source is selected.

Unicode normalization, the complete identifier character set and treatment of filesystem indirection are separate open details. Case-sensitive matching itself is already chosen.

8. Standard and external paths use their actual roots

import math;
import io;
import pixel.filters;

These lines illustrate path forms, not a promise about particular functions supplied by those modules. Standard-library modules use top-level paths such as math and io; no std prefix is automatically added. Whether std is reserved has not been decided.

An external package includes its actual package name, such as pixel.filters for a filters module in package pixel. Import aliases are not available. See Package Boundaries for package identity and overlap rules.

9. A full-path collision is an error

If more than one candidate provides the same full module path, resolution fails rather than selecting a preferred source. For example, a project math module and a standard-library math module cannot be resolved by a project-first or standard-first rule.

This error is different from importing distinct modules that each expose a short name such as Point. Full-path collisions prevent identifying the module. Short-name collisions can remain unused and are diagnosed when an ambiguous short name is used; see import ambiguity.

10. Required path rejections

ConditionRequired outcome
Relative import spelling.Reject the import.
Mismatched actual file casing.Reject the module path.
Case-only module pair in one package.Reject the package source arrangement.
Several candidates for one full module path.Reject resolution; no priority fallback.
Child-path access without its own import.Reject access to the unimported module.
An extra module declaration.Reject syntax outside the chosen file-derived model.

These are source-level rejection requirements, not compiler error codes or verified output. The valid examples explain the selected grammar without claiming executed Aevix compilation.

11. Open path details

  • Configuration spelling for non-default source roots and package/build metadata.
  • The complete module identifier character set, escaping and Unicode normalization rules.
  • Symlink, generated-source and other filesystem indirection policies beyond exact casing.
  • Complete handling of entry-module selection, platform source variants and build targets.
  • Whether the identifier std is reserved; a std prefix is not currently required.

Full paths, .avx files, private module boundaries and simultaneous math.vector/math.vector.ops modules are already chosen. Their module identities and privacy boundaries remain independent of the open configuration details.
