1. Put every import before declarations

import math.vector { Point, dot };

f64 squared_length(&Point value) {
    return dot(value, value);
}

Imports are placed at the top of the file, before types, functions, constants and other declarations. This includes public import declarations. An import cannot be moved inside a function or after a declaration to delay name resolution or initialization.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

const i32 VERSION = 1;
import math.vector { Point };

The import follows a declaration and is rejected. All import examples use full paths and end with semicolons.

Default prelude and explicit library imports

The default prelude makes selected primitive and frequently used core type names available in every module. This is a name-availability rule: a library-defined type such as Vector can be available through the prelude without becoming a lexical keyword or a compiler primitive.

CategoryAvailable namesImport rule
Primitive scalar typesSelected integer and floating-point scalar types, including int and float aliases; bool, char, byte, unit, neverAutomatically available. This does not promote draft numeric formats to selected language types.
Return markervoidAutomatically available in return position; it is not an ordinary storable value type.
Text and common collectionsstring, string_view, Array, Vector, Slice, MutSlice, Tuple, RangeAutomatically available through the default prelude.
Absence and failureOptional, ResultAutomatically available through the default prelude.
Other library typesFor example Tensor, Map, Set, Box, Shared, Weak and synchronization typesRequire an explicit permitted import route.

For example, import tensor { Tensor }; grants the selected Tensor name and its permitted qualified route. Standard-library modules keep their ordinary full paths without a reserved std prefix. A type appearing in the catalog does not by itself grant access to its name, and imports do not allocate a Tensor value or instantiate a container.

Restricting automatic availability lets a module loader avoid eagerly analyzing unrelated specialist modules, but compiler-memory and build-time improvements require implementation and measurement. The chosen visibility, collision, reexport and persistent-initialization rules continue to apply to connected modules. Compiler import enforcement belongs to module loading and name resolution; the catalog is a design reference.

2. A whole-module import grants qualified public access

import math.vector;

f64 qualified_projection() {
    math.vector.Point value = math.vector.Point { x = 2.0, y = 3.0 };
    math.vector.Point axis = math.vector.Point { x = 1.0, y = 0.0 };
    return math.vector.dot(&value, &axis);
}

A whole-module import permits fully qualified access to the module's public declarations. It does not introduce Point or dot as short names. The qualification identifies the module and is still subject to public/private access.

The module namespace is a name-resolution boundary, not a dynamically allocated object. Qualifying a function call does not change its value or borrow parameter modes.

3. Select exactly the names to expose

import math.vector { Point, dot };

f64 selected_projection() {
    Point value = Point { x = 2.0, y = 3.0 };
    Point axis = Point { x = 1.0, y = 0.0 };
    return math.vector.dot(&value, &axis);
}

Selected names may be used with their short spelling or qualified through the explicitly imported path. In this example Point, math.vector.Point, dot and math.vector.dot are available. Selection does not rename them.

ImportShort namesQualified names
import math.vector;None introduced by this import.Public declarations of math.vector.
import math.vector { Point };Point only.math.vector.Point only.
import math.vector { Point, dot };Point and dot.The same selected names under math.vector.
import math.vector { * };The module's public names.Those public names under math.vector.

4. Qualification cannot recover an unselected name

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import math.vector { Point };

f64 unselected_function() {
    Point value = Point { x = 2.0, y = 3.0 };
    return math.vector.dot(&value, &value);
}

Point was selected but dot was not. The full module path does not bypass that restriction. Import dot explicitly, use a whole-module import, or use a wildcard import when all public names are intended.

The same rule applies to constants, types and callable overload sets. A type mentioned inside a selected declaration's signature does not automatically become another imported short or qualified name.

5. Wildcard imports expose public names without priority

import math.vector { * };

f64 wildcard_projection() {
    Point value = Point { x = 2.0, y = 3.0 };
    return dot(&value, &value);
}

The wildcard imports all public names offered by that module, including explicitly public reexported names. It does not import private declarations, automatically import same-prefix child modules, or expose all names of the module's dependencies.

Explicit imports do not outrank wildcard imports. Import order also gives no priority. If distinct original declarations contribute the same short spelling, the ambiguity is handled at a use of that short name. Wildcard reexports are a different operation and are forbidden.

6. Module-level declarations are private by default

EXAMPLE MODULE · math.vector

public struct Point {
    public f64 x;
    public f64 y;
};

public const i32 DIMENSIONS = 2;
const i32 INTERNAL_REVISION = 1;

f64 square(f64 value) {
    return value * value;
}

public f64 dot(&Point left, &Point right) {
    return (*left).x * (*right).x + (*left).y * (*right).y;
}

Point, DIMENSIONS and dot may be imported. INTERNAL_REVISION and square are private to this file module. Private defaults apply to module-level types, functions and constants; a public modifier is required to expose them.

A public type still enforces its own field and method visibility. Importing the type cannot authorize access to private fields or private payloads. Local variables keep lexical block scope; public/private do not turn them into globally accessible names.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import math.vector { square };

An explicit selection cannot import a private function, and a wildcard would not include it. A same-prefix child module gets no special exception.

7. Direct types, functions and constants share one name space

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

struct Item {
    public i32 value;
};

const i32 Item = 1;

These are two direct declarations in one module, not competing imported candidates. Their name collision is rejected at the declaration level. Types, functions and constants do not use separate module-level name spaces.

The exception is a permitted overload set of functions declared in the same module. Function overloads may differ by parameter types or counts, while a return-type-only difference is rejected. Those functions remain one named overload set for importing purposes.

public i32 add(i32 left, i32 right) {
    return left + right;
}

public f64 add(f64 left, f64 right) {
    return left + right;
}

These two functions are direct declarations in the same module and differ by their parameter types. They form one permitted overload set. Changing only a return type would not establish another overload.

Detailed call ranking, generic preference and default arguments are documented in Functions; import lookup must not invent a different overload system.

8. Ambiguous short names fail when used

EXAMPLE IMPORTS · both source modules export a distinct Point type

import drawing.left { Point };
import drawing.right { Point };

i32 unaffected() {
    return 1;
}

The competing imports are allowed to coexist when Point is not used as a short name. There is no source-order winner. The fully qualified selected names drawing.left.Point and drawing.right.Point distinguish the two original declarations.

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import drawing.left { Point };
import drawing.right { * };

Point ambiguous_point() {
    return Point { x = 0.0, y = 0.0 };
}

The short name Point is ambiguous. The explicit left selection has no priority over the right wildcard. The error is its ambiguous short use rather than the mere existence of both imports.

9. Local declarations do not outrank imports or merge remote overloads

EXAMPLE MODULE · app.settings · config.remote exports a distinct public LIMIT

import config.remote { LIMIT };

const i32 LIMIT = 3;

i32 selected_remote_limit() {
    return config.remote.LIMIT;
}

The local declaration and imported declaration are distinct origins. Neither receives a lookup priority. Their coexistence is not an ambiguous short use; referring to LIMIT alone would be ambiguous, while the selected remote qualified path identifies its declaration.

EXAMPLE SOURCE CONTRACTS · text.integer exports parse(i32); text.real exports parse(f64)

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import text.integer { parse };
import text.real { parse };

i32 ambiguous_parse() {
    return parse(1);
}

Overloads from different original modules are not combined. The short name parse is ambiguous before argument-based overload ranking could choose a remote origin. A matching argument type does not rescue the merged call; use a permitted qualified path.

When two paths actually lead to the same original declaration, canonical identity merges that duplicate instead. See canonical reexport identity.

Full paths must also identify one accessible declaration

Apply import-route grants and visibility before resolving a qualified use. If a parent module's type/member chain and an independently imported child module yield distinct accessible declarations at the same written full path, report ambiguity at that use. Do not silently prefer a module, member or longest module prefix. Parent files and child modules remain allowed to coexist. The programmer must remove the competing route or change an exposed name when the full path itself cannot distinguish the declarations.

10. Keep names unchanged

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import math.vector { Point as Vec2 };

Rejected example. This deliberately violates a chosen rule and is not valid Aevix source.

import math.vector as vectors;

Neither selected-name aliases nor whole-module aliases are chosen. Distinct origins with the same short name are distinguished using permitted full module paths rather than import precedence or renaming.

A public reexport also preserves the declared name. An imported value is not copied or moved merely because its name was introduced. A subsequent ordinary call or value operation follows its own ownership and cost contract.

11. Required checks and open details

ConditionChosen result
Private or nonexistent explicitly selected name.Reject the inaccessible or unresolved selection.
Distinct imported origins share a short spelling.Keep candidates; reject an ambiguous short use.
Direct type/function/constant name collision.Reject direct declarations, except valid same-module function overloads.
Selected name accessed through an unimported original or child path.Reject the unauthorized path.
Aliases or an import following a declaration.Reject syntax outside the chosen import model.

The 0.2 module loader uses ASCII path identifiers. Mixed wildcard-plus-named selection lists and special self-qualified lookup spellings beyond the examples remain outside that profile. Public signature exposure rules for private types also need their own complete contract.

These open details do not add aliases, import precedence, relative paths, or automatic transitive visibility. Examples are design requirements and not output from an Aevix compiler.
