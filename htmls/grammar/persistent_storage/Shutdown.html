1. Normal shutdown releases successfully initialized values

When the program completes normally, initialized persist values are automatically cleaned under their owning types' resource-release rules. A local persist whose declaration was never reached has no constructed value to release. Finishing the lexical scope that contains a local persist does not release that persistent storage.

persist Result<Box<i32>, InputError<i32>> owner = Box.new(7);

If this Result contains Ok, the stored Result owns the Box and its payload. If allocation produced the documented error value, the Result is still successfully initialized and owns its error payload under the normal type contract. Normal cleanup releases whichever complete value was actually stored.

This is a normal-shutdown guarantee. Forced process termination and execution-error stops are outside it. Releasing a handle also does not prove that external data was successfully saved or flushed.

2. Wait for tracked resource use before releasing persist

The shutdown procedure waits until language-tracked threads, Tasks and GPU work have finished their relevant resource uses before releasing persist resources those operations could access. Persistent storage must not be freed while a tracked operation may still use it.

Tracked useRequired condition before release
A thread still uses a persistent resourceIts use has finished before that resource is released.
A Task retains or borrows a persistent resourceIts tracked use has ended; discarding a result handle alone is not enough.
Accepted GPU work may still access a bufferDevice access is quiescent before the buffer can be released.
No such use remainsProceed to the persistent-value cleanup stage under the chosen ordering rules.

Waiting may last indefinitely when a relevant operation never finishes. A cancellation request, timeout or discarded Pending handle is not by itself proof of completion. Unknown completion cannot justify freeing memory that a device may still access.

This shutdown wait is a chosen lifecycle rule. It does not select hidden blocking for every ordinary destructor, settle outstanding borrowed-local exits in general, or claim to discover every use hidden in opaque foreign code. See ordinary resource cleanup and Pending.

3. Reverse successful initialization-completion order

Record successful completion of each persistent initialization. Clean initialized values in the reverse of that completed order. A declaration encountered earlier but completed later is cleaned earlier than the values that completed before it. Initialization start order alone does not decide shutdown order.

Successful completionsCleanup orderExplanation
A completes, then B completesB, then A.The latest successfully completed value is released first.
A starts, B starts and completes, A completesA, then B.Completion, rather than start time, sets the order.
Local C is never reachedNo C cleanup.C has no successfully initialized value.
Concurrent independent values complete in different orders across runsTheir reverse completion order may differ across runs.Concurrency does not imply a fixed declaration-order teardown.

The ordinary current-owner rules still apply within each stored value: cleaning a handle releases what that handle currently owns. Shared ownership and resource retention follow their own complete type contracts rather than being overwritten by a claim that every reachable payload is destroyed immediately.

4. Cleanup cannot access another persist

During cleanup of a persistent value, its cleanup logic may release its own owned resources but may not access another persist. The restriction includes indirect access through a function call, a stored reference or a helper. Merely knowing that another persist has not yet been cleaned does not grant permission.

OperationStatus
Release memory or resources owned by the value being cleanedPermitted under that type's cleanup contract.
Read a separate persistent logging registry directlyForbidden during persistent cleanup.
Call a helper that reads another persistForbidden indirect access.
Use a stored reference to another persistForbidden indirect access.
Perform an explicit application shutdown step before persistent cleanup beginsMay use live resources under ordinary access and error-handling rules.

Ending a shared reference, Slice or string_view descriptor without reading its target is not an access to that target. Releasing a Shared handle may update the bookkeeping of the allocation that handle owns, even if another persist also owns a handle to that allocation. In contrast, dereferencing a stored reference to another persist, running its cleanup callback, or unlocking a guard that acts on another persistent cell is an access and remains forbidden.

The reverse-completion order is not a license for arbitrary cross-persist destructor dependencies. Cross-resource saving, logging and coordination belong in an explicit application shutdown phase before persistent cleanup starts.

5. Handle fallible saves and flushes explicitly

If success of writing, flushing or committing matters, call and handle the relevant Result-bearing operation while the application can still choose recovery. Automatic release does not guarantee those external effects succeeded and cannot send a recoverable error back into an application scope that has already completed.

This chapter introduces no special shutdown annotation, destructor keyword, mandatory close method or new Result conversion. The exact custom cleanup declaration syntax remains open, and proposed type-level resource APIs retain their own status.

6. Termination and remaining shutdown work

Exit pathWhat this design guarantees
Normal completionFinish tracked uses, then clean successfully initialized persist in reverse completion order.
Initializer execution errorDiagnose and stop; normal-shutdown cleanup is not promised for this path.
Ordinary safety stop or external force killNo universal cleanup guarantee is introduced.
An operation never finishesWaiting can prevent normal shutdown from completing.
  • Creation of new Tasks, new GPU work or newly reached persist values during shutdown still needs a policy.
  • Custom cleanup syntax and the exact enforcement of indirect cross-persist access remain open.
  • Foreign-resource tracking, partial-construction cleanup and safety-stop unwinding details are not completed by the normal-shutdown rule.
