1. One thread initializes a local persist

i32 protocol() {
    persist i32 revision = 3;
    return revision;
}

If several threads reach revision before it is initialized, exactly one performs the initialization attempt. The others wait for that attempt to finish. After success, they all use the same complete stored value, provided their accesses satisfy the type and borrowing rules. The sample returns a Copy scalar, so it does not transfer a persistent owning resource to every caller.

StepInitializing threadOther threads
Claim first initializationBegins the initializer.Wait for the current attempt.
Construct the valueKeeps the incomplete value unavailable.Do not observe partial fields or a placeholder value.
Finish successfullyPublish the completed value and initialization success.Resume and access the initialized value safely.
Fail during executionProduce a diagnostic and stop program execution.Do not receive an uninitialized or fabricated replacement.

The language requires the synchronization needed for successful publication. No user-selectable memory-order API, storage-state inspection API or mandatory lock implementation is introduced by this rule.

2. Initialization coordination is not a lock around later use

Once initialization succeeds, the first-reach guard no longer protects arbitrary operations on the value. Sharing a value between threads must satisfy its ordinary safe-sharing contract. When shared state can change, modification requires an explicit synchronization type such as Atomic, Mutex or RwLock; marking an ordinary binding mutable does not make competing accesses safe.

Access patternChosen requirement
Read a suitably shareable immutable valuePreserve its type's safe concurrent-read and borrow requirements.
Update a scalar concurrentlyUse an explicit appropriate atomic or synchronization abstraction.
Modify a compound resource concurrentlyUse an explicit locking or synchronization abstraction with the needed access guarantee.
Use an ordinary mutable value with competing unsynchronized accessesReject unsafe shared modification; initializer coordination is not sufficient.
Access a stored owning valueBorrow it or copy a Copy value. Do not move out and leave the persistent place uninitialized; extraction requires a complete safe replacement.

The chosen rule makes synchronization costs visible. It does not certify every persist type as shareable, add new Sync/Send-like interface names, or choose the still-open policy for ordinary single-threaded or thread-local mutable persistent bindings.

See the separately proposed Atomic, Mutex and RwLock APIs. Their exact constructor and operation signatures are not finalized by this chapter.

3. A Result containing Err is a complete initialized value

persist Result<i32, i32> configuration_status = Result.err(7);

The initializer normally constructs a Result whose error payload is 7. Storage initialization has succeeded. Reading or handling that Result follows the existing ownership, borrowing and Result rules; there is no implicit retry of its initializer, and the stored Err alone does not stop the program.

SituationInitialization statusConsequence
A function returns a normally constructed Err for storageSuccessful initialization.The program may handle the stored error using its ordinary Result API.
An Optional value normally stores absenceSuccessful initialization.Absence is an ordinary value, not evidence of an unfinished initializer.
An initializer reaches a runtime initialization cycleExecution failure.Diagnose and stop; no incomplete value is published.
An ordinary safety failure occurs inside an initializerExecution failure.Follow the chosen initialization-error stop boundary rather than inventing a recoverable Result.

A Result-returning operation can deliberately make a resource-preparation error into a stored value. That API choice differs from an execution error that aborts initialization itself. Persist access has no new implicit Result wrapper.

4. Initialization cycles must not become indefinite mutual waiting

A statically confirmed value-initialization cycle is a compile-time error. For a dependency discovered only through execution, an Aevix-managed access that creates an initialization cycle is diagnosed as an initialization execution error and stops the program. The rule covers recursive first-reach initialization as well as cycles involving several managed persist values.

For example, if initializing A requires B and initializing B again requires the unfinished A, neither initializer may publish a partial value or simply wait for itself forever. If managed initialization on different threads forms that same circular dependency, ordinary waiting is insufficient; the cycle is an error.

Opaque foreign code and unrelated locking can introduce waits the language cannot infer from managed persist access alone. The chosen cycle rule must not be advertised as a detector for every external deadlock.

5. What the safety rule can cost

First reach can execute initialization and contend with another thread. A thread waiting for an initializer that never completes can remain blocked. Subsequent accesses must retain required safety and visibility while allowing a future compiler or runtime to remove redundant checks when that transformation is valid.

No benchmark, particular fast path or absolute zero-overhead promise follows from this specification. Explicit shared synchronization retains the real cost of its selected operation, including contention and memory ordering where required.

6. Failure and recovery boundaries

The chosen initializer execution-failure policy is diagnostic plus program stop. It does not give callers a retry token, choose an exception grammar or guarantee that ordinary shutdown cleanup runs after that stop. Handling expected preparation failures should use an explicit Result-bearing initializer API so the completed Result can be stored and examined.

  • Detailed failure diagnostics, partial-construction cleanup and safety-stop unwinding mechanics remain implementation and design work.
  • No general automatic-retry mode or new persistent-access recovery API has been approved.
  • Successful initialization does not validate later FFI races or extend borrowed data lifetimes.
