1. Use persist in a type-first declaration

persist i32 protocol_revision = 1;

i32 read_limit() {
    persist i32 limit = 64;
    return limit;
}

The declared type precedes the binding name. A module-level declaration has process-lifetime storage initialized before program entry; a declaration in a function retains its storage after that call returns and initializes on first reach. Retaining storage does not make an ordinary immutable binding writable.

This reference shows the chosen persist T name = value; form. It does not settle every combination or ordering of const, mut, visibility and persist modifiers.

2. One storage identity per declaration

SituationStorage rule
Two different persist declarationsEach has its own storage identity, even when its type, name in separate scopes and initial value match.
Repeated reach of one local declarationReuse the successfully initialized value belonging to that declaration.
A loop reaches one local declaration repeatedlyThe declaration is not a new persistent cell on each iteration.
Several threads reach one declarationCoordinate one initialization and share its resulting storage subject to access-safety rules.
The process exits and restartsA new process obtains newly initialized storage; disk restoration is not implied.

The stored value retains its type's ownership and borrowing requirements, with the additional rule that its persistent place cannot be left uninitialized by a move. Persist is not an implicit clone, reference-counted handle, serialization format or garbage collector.

Stored values must remain initialized

A persist place, including one of its fields or elements, cannot be moved out and left uninitialized. Reading a Copy value copies it; other accesses borrow the stored value. An operation that extracts ownership must install a complete replacement before exposing success and must satisfy the ordinary synchronization and borrowing requirements. This rule introduces no new replacement API or permission for unsynchronized mutation.

Rejected example. Returning this non-Copy Result would move the stored owner out of its persistent place.

Result<Box<i32>, InputError<i32>> take_owner() {
    persist Result<Box<i32>, InputError<i32>> retained = Box.new(7);
    return retained;
}

Initializers cannot propagate out of their enclosing function

A persist initializer must complete its stored value or follow the initialization-error stop policy. A postfix ? that returns from the surrounding function is prohibited inside the initializer, as are other nonlocal exits that leave the value unfinished. Store a Result itself to retain an expected error as a complete value. A function called by the initializer may use ? inside its own body: its returned Result is then an ordinary input to initialization.

Result<i32, IntegerError> invalid_initializer() {
    persist i32 saved = checked(2147483647 + 1)?;
    return Result.ok(saved);
}

The initializer cannot leave its first-reach guard in an initializing state by returning an Err from the enclosing function. This restriction adds no retry or poisoned-state recovery policy.

3. Long storage duration does not widen a name's scope

A local persist name is still visible only in its lexical block and nested scopes, and visible outer names cannot be shadowed. The value is not released at the end of that block, but its local identifier does not become accessible from arbitrary code afterward. Public/private apply at the already chosen module and type declaration boundaries, not as a way to export a local variable.

i32 read_revision() {
    {
        persist i32 retained_revision = 3;
        i32 observed = retained_revision;
    }
    return 3;
}

Rejected example. The following addition to that function would use a name outside its lexical scope.

i32 read_revision() {
    {
        persist i32 retained_revision = 3;
    }
    return retained_revision;
}

Persistent storage duration also does not extend the lifetime of data borrowed from somewhere else. A reference stored in persist must satisfy its full source-lifetime constraints. Returned-reference lifetime syntax remains a separate design question.

4. A local initializer cannot capture a call's inputs directly

A local persist initializer may not directly depend on runtime function parameters or ordinary local variables. The language rejects a first caller's input being permanently selected merely because it reached the declaration first. Under concurrent calls, this also avoids choosing an input by whichever thread wins initialization.

Rejected examples. Both initializers directly depend on call-local runtime values.

i32 from_parameter(i32 input) {
    persist i32 saved = input;
    return saved;
}

i32 from_local() {
    i32 ordinary = 10;
    persist i32 saved = ordinary;
    return saved;
}
i32 offset(i32 input) {
    persist i32 fixed_offset = 10;
    return input + fixed_offset;
}

The accepted example uses the parameter in the ordinary function result, outside the initializer. The direct-dependence restriction is not a promise of complete transitive purity analysis: effects hidden behind calls are handled by their own rules, including runtime persist initialization checks.

5. Generic function locals use the concrete type argument tuple

A persist inside a generic function has a separate storage instance for each concrete combination of that function's type arguments. Repeated calls with the same combination reuse the instance. A different combination selects another instance even if the persist's own type is identical.

i32 marker<T>(T value) {
    persist i32 stamp = 7;
    return stamp;
}

i32 first = marker<i32>(10);
i32 second = marker<i32>(20);
i32 third = marker<f64>(2.5);

The first two calls refer to the same i32-instantiated local declaration; the third refers to the f64 instance. All return 7 in this illustration, so the returned numbers are not a storage-identity inspection API. Unreached instantiations have no successfully initialized local value to clean.

With several type parameters, the full ordered tuple matters. Generic function type inference and explicit arguments retain their ordinary rules; this storage policy does not add const, Shape or lifetime generic parameter syntax.

6. AOT and JIT versions preserve one language-level identity

AOT compilation and selective JIT specialization may produce several code versions for one function and one concrete type-argument combination. They still access the same persistent storage. Generating or replacing a code version does not create another initializer run or reset an initialized value.

This is a semantic requirement. Symbol naming, runtime registries, code-cache implementation, dynamic-library loading and hot reload are not chosen mechanisms here.

7. Related rules and open boundaries

  • Generic type-member persist and thread-local storage rules are not selected.
  • The remaining modifier combinations and any persistent-storage inspection API are not introduced.
  • Borrowed field and returned-reference lifetime spelling remains separate from storage duration.
