1. A lifetime longer than one call

A persist declaration identifies one storage location whose successfully initialized value is retained across ordinary scope exits. It does not save the value to a file or restore it in the next process. The keyword changes storage duration, while lexical scope, public/private access, ownership and borrow validity remain separate rules.

Design reference. These pages describe chosen Aevix language rules and explicitly labeled open decisions. They do not claim an implemented compiler, runtime, scheduler or diagnostic system.

persist i32 protocol_revision = 1;

i32 revision() {
    persist i32 local_revision = 1;
    return local_revision;
}

The module value is prepared before program entry. The local value is prepared the first time execution reaches its declaration. Each later call reuses the same local storage rather than creating a new value. Both bindings retain the language's default immutability.

3. The chosen lifecycle

PhaseChosen behaviorBoundary
Declaration connectionResolve modules, declarations and static checks before running initializers.An import cycle alone is not a value-initialization cycle.
Before entryInitialize all top-level persist values in modules connected from the entry module.A statically known value dependency precedes its dependent value.
During executionInitialize each local persist when its declaration is first reached.Concurrent reaches wait for one initialization attempt.
Successful publicationMake only a complete value available to subsequent accesses.Initialization coordination does not protect later modifications.
Normal shutdownWait for tracked resource uses, then clean values in reverse initialization-completion order.Cleanup may not access another persist, even indirectly.

A runtime initialization error is diagnosed and stops execution. Normal-shutdown cleanup is not promised for that safety-stop path. A Result.err that is normally stored inside a persist is a complete value, with its ordinary Result behavior.

4. Visible costs and safety obligations

Persistent storage can retain memory, file handles and device resources for the lifetime of the process. A top-level initializer can add startup work even when a selectively imported declaration never uses that value. A first local reach can execute initialization and wait for another thread. Shared writes require explicit synchronization with its associated atomic or locking cost.

Persist places cannot be moved out and left uninitialized. Their initializers cannot propagate ? to the enclosing function before producing a stored value; expected errors can instead be stored as Result values. See stored-value rules.

The language must preserve safe access and observable initialization behavior across AOT and selective JIT execution. The chosen rules do not mandate an implementation technique or permit arbitrary reordering of observable side effects.

5. Chosen rules and remaining design work

Storage identity, initialization timing, dependency ordering, first-reach coordination, fatal initialization errors, explicit shared synchronization and normal-shutdown ordering are chosen. They are not optional runtime modes in this reference.

  • The exact custom cleanup declaration syntax and enforcement of indirect cross-persist accesses remain open.
  • Thread-local persist, generic type-member persist and the remaining modifier-combination grammar remain open.
  • Shutdown-time creation of new work or new persist values, and safety-stop cleanup mechanics, remain open.
  • Concrete Atomic, Mutex, RwLock, Task and GPU operation signatures remain separate type API proposals.
