1. Two chosen initialization times

DeclarationWhen initialization runsWhat later execution does
Module top-level persistBefore the program's entry function begins.Access the complete stored value under ordinary safety rules.
Local persistWhen execution first actually reaches its declaration.Reuse the already initialized storage.
Unreached local persistNo initializer executes.No successfully initialized value exists to clean.
persist i32 process_revision = 1;

i32 conditional_limit(bool enabled) {
    if (enabled) {
        persist i32 limit = 64;
        return limit;
    }
    return 0;
}

Calling conditional_limit(false) does not reach limit, so it does not initialize that local value. A later true call does. Program entry is reached only after the required top-level initializations complete successfully.

2. Every top-level persist in the connected module set is included

Starting from the entry module, follow imports and explicit reexports transitively. Every top-level persist in those connected modules belongs to startup initialization, including private declarations and values that ordinary program code never reads. A package merely installed on the machine, with no connection from the entry module, is not added by its presence.

import math.vector { Point };

This selective import grants access to Point and its permitted selected route. It still includes all top-level persist values in math.vector in the startup target set. The visibility selection does not filter that module's initialization to Point alone, and it does not grant access to other unselected names.

The same target-set rule applies when modules are reached by reexports. A module reached along several routes is one module identity, not several runs of its initializers. Package dependency cycles remain prohibited while module declaration cycles within one package are allowed.

3. Known value dependencies run before their dependents

persist i32 upper_limit = base_limit + 1;
persist i32 base_limit = 10;

Because upper_limit needs the initialized value of base_limit, base_limit is initialized first even though it is written later. Once that prerequisite succeeds, upper_limit becomes 11. Importing a declaration or referring only to a type or function signature does not by itself create such a value dependency.

RelationshipEffect
A module imports another moduleConnect declarations and extend the startup target set; it is not a command to execute an initializer at the import statement.
An initializer reads or borrows another persistRespect the target value's initialization prerequisite.
Two types or function declarations refer to one anotherResolve their declarations under module-cycle rules; no value cycle follows from signatures alone.
Known initializer values depend cyclically on each otherReject the value-initialization cycle at compile time.

Rejected example. No value can be initialized before its prerequisite in this known cycle.

persist i32 left = right + 1;
persist i32 right = left + 1;

4. Choose ready values by module path, then source order

After respecting known dependencies, choose among simultaneously ready top-level values by full module-path lexicographic order. Within one module, use their source declaration order. Dependency requirements always outrank this tie rule.

Ready declarationsChosen orderReason
alpha.cache.first and beta.cache.firstalpha.cache.first before beta.cache.first.alpha.cache precedes beta.cache lexicographically.
Two ready declarations in alpha.cacheEarlier declaration first.The full module path is equal, so source order breaks the tie.
alpha.cache.first depends on beta.cache.firstbeta.cache.first before alpha.cache.first.The value dependency outranks the path preference.

Renaming a module or moving a declaration can change its tie position. Initializers with observable I/O or logging therefore have an ordering contract. This design does not authorize the compiler to run them in arbitrary parallel order or erase side effects merely because a value is unused.

5. Runtime access checks complete the dependency plan

An initializer may call functions or use dynamic dispatch that accesses another persist without the compiler establishing that dependency in advance. These calls are permitted. Aevix-managed persist accesses are checked during initialization rather than exposing an unfinished target.

Target stateRequired behavior
Not startedPerform the needed target initialization first, then resume the requesting initializer.
Successfully initializedUse its complete value under the ordinary access rules.
Initializing on another threadWait for that initialization attempt to finish, subject to cycle detection.
Access creates an initialization cycleDiagnose the initialization error and stop program execution.

A newly discovered prerequisite can be initialized before the next value selected by the ready-value tie rule. That is dependency resolution, not a change to the default path/source ordering. Local persist values reached from initialization participate in their own first-reach coordination as well.

These checks cover Aevix-managed persist accesses. They do not promise to discover every deadlock or dependency hidden in opaque foreign code, external locks or arbitrary device behavior.

6. Only complete values are published

A persist initializer cannot use ? or another nonlocal exit to return from the enclosing function before constructing its value. A Result returned normally from a called function can be stored as a complete value; see initializer exit restrictions.

Successful initialization installs a complete value and makes that success visible to later permitted accesses. An execution error during initialization is diagnosed and stops the program; there is no published partially initialized substitute. A stored Result containing Err is instead a successfully initialized value.

The shutdown order records successful initialization completion, rather than declaration encounter or initialization start. A local persist never reached has no successful completion to record. See concurrency and failure and normal shutdown.

7. Implementation details remain separate

  • The exact initializer state representation, synchronization primitives and runtime registry are implementation work.
  • Diagnostic wording and safety-stop unwinding or abort mechanics are not selected.
  • Function-call dependency analysis need not claim perfect transitive purity or complete FFI visibility.
  • Runtime waiting can still be affected by operations that never finish; initialization checks are not a universal termination proof.
