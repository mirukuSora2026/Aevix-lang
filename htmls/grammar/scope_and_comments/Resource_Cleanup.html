1. Deterministic ownership cleanup

Aevix releases initialized values still owned by a scope in reverse initialization order when that scope exits normally. Each current owner is finalized exactly once under its type’s contract. Copy scalar values need no resource release; owning containers may destroy elements and release storage.

Design reference. Chosen language rules are stated directly. Open policies and recommendations are labeled separately. These examples do not claim an implemented compiler, runtime, or diagnostic system.

This is an ownership rule, not a tracing collection schedule or an unconditional guarantee that every reachable resource is released. Moved values, remaining Shared owners, persistent storage, strong cycles, and device leases have their own lifetime conditions.

2. Reverse initialization order

Only successful initialization creates an owned value that participates in cleanup. Partial constructors clean their initialized portions under their API contract. Local cleanup proceeds from the most recently initialized live owner toward earlier owners; an already moved-out owner is not finalized a second time.

{
    Result<Box<i32>, InputError<i32>> first = Box.new(1);
    Result<Box<i32>, InputError<i32>> second = Box.new(2);
}

The second Result is cleaned before the first. An Ok branch owns its Box; an error branch owns its documented recovery payload. This example does not assume allocation succeeded. Exact element destruction order inside a container belongs to that container’s contract rather than being invented by the local-variable order rule.

3. Block end and control-flow exits

void leave_loop() {
    while (true) {
        Vector<i32> scratch = Vector.new(i32);
        break;
    }
    return;
}

The scratch owner is released on the break path. Each case and default is also an independent scope: still-owned initialized locals are released in reverse initialization order when its branch exits. A value moved to an outer owner or returned follows that destination. The explicit case-ending break remains written even after an allowed return, enclosing-loop continue, divergence or Result ?. An unreachable required terminal break is not itself an error or warning and is not executed as a second cleanup action. Normal return/continue/Err exits clean up only the regions actually left; nontermination is not a normal exit and safety-stop cleanup remains separately open. See case exits.

4. Moves and returned owners

A move transfers the cleanup obligation. The old location becomes unavailable; the destination becomes the current owner. A returned payload is transferred into the result seen by the caller. Function cleanup must not destroy that same payload before the caller can use it.

Vector<i32> transfer_owner() {
    Vector<i32> original = Vector.new(i32);
    Vector<i32> destination = original;
    return destination;
}

Moving an owner does not clone its allocation. An explicit clone can create another cleanup obligation and may allocate or fail. Value semantics and observable release behavior must remain valid under AOT and JIT optimization.

In consuming enum switch, switch (move event) takes the directly owned enum. Value bindings can move owning payload fields to branch-local or outer destinations. Data remaining owned by the consumed variant is finalized once when the branch is left. Read and modification modes preserve the source owner. Custom cleanup combined with partial field moves remains an open design area.

5. Result errors are normal exits

A returned Err and the ? operator’s propagated error are ordinary function completion paths for cleanup. They do not rewind earlier assignments, completed callbacks, or external I/O. The checked arithmetic expression and Result type retain their separate error boundaries.

Result<i32, IntegerError> calculate(i32 left, i32 right) {
    Vector<i32> scratch = Vector.new(i32);
    rsn total = checked(left + right)?;
    return Result.ok(total);
}

Whether calculation succeeds or propagates IntegerError, scratch remains a local current owner until its normal scope exit. No raw trap or failure inside an unrelated called function becomes a recoverable Result merely because ? appears here.

6. Ending a borrow is not releasing its owner

A loan grants temporary access, not duplicate ownership. Ending a shared or exclusive loan makes the original owner available again under the remaining restrictions. It does not destroy the owner’s allocation. Last-use analysis concerns access permission; it does not silently replace an observable scope cleanup rule.

mut i32 number = 1;
{
    &mut i32 target = &mut number;
    *target = 2;
}
i32 observed = number;

Borrowed arguments, Slice, MutSlice, and string_view retain the same distinction. A borrowed view’s local binding can end without releasing the elements owned elsewhere. Returned or captured borrows remain subject to their complete lifetime constraints.

7. Reference-counted ownership

Releasing a Shared handle releases one strong reference. The payload is finalized when the last strong owner releases it, not whenever any one handle leaves a scope. Weak observers may retain control bookkeeping but cannot keep a destroyed payload alive or read it without successful promotion.

A strong ownership cycle can retain memory and external resources. Weak back-edges can break known cycles, but the language does not promise absolute leak prevention. A clone of a Shared handle and a clone of its payload have different ownership and cost contracts. See Shared and Weak.

8. Explicit fallible flush and close

Operations whose success matters to the program, such as committing data or flushing an external resource, need an explicit Result-bearing API before automatic cleanup. Handle that result while the caller can still choose recovery. Automatic finalization cannot return a recoverable Err to a scope that has already finished.

The cleanup contract does not permit a destructor to emit a recoverable error or unwind. This is a requirement for cleanup behavior, not a claim that every external device or I/O operation always succeeds. Custom destructor declaration syntax and the enforcement mechanism have not been designed; no new close, drop, or destructor function grammar is introduced here.

Do not rely on automatic cleanup as proof that buffered output was committed, a remote operation succeeded, or application state was transactionally restored.

9. In-flight GPU resources

A Pending result handle can end while its accepted device work remains tracked. The runtime must retain owned buffers, code, queue state, and required resource leases until the device can no longer access them. Dropping that user handle is not proof of completion and need not block on the device.

Borrowed local storage has a stronger exit constraint: its declaring scope cannot release or reuse that storage while device access may continue. Proven quiescence is required before borrowed locals can leave. Whether a language construct inserts a wait or rejects an outstanding borrowed exit is still open; neither policy is silently selected here.

A timeout, cancellation request, discarded Pending handle, or returned submission error does not by itself establish quiescence. Unknown completion cannot justify returning to safe code with potentially accessed borrowed memory freed.

See Pending and Task for completion tracking. Ownership retention and host memory visibility remain separate obligations.

10. Abort and persistent storage boundaries

An ordinary integer safety failure outside recoverable checked syntax is a safety stop, not a normal error return. This reference does not guarantee that local cleanup runs after such a stop, process abort, or external process termination. Normal scope-exit guarantees must not be advertised as universal termination guarantees.

Persistent storage follows its process-lifetime contract. At normal shutdown, language-tracked threads, Tasks and GPU resource uses finish before successfully initialized persist values are released in reverse initialization-completion order. Persist cleanup cannot access another persist. Fatal initialization errors stop execution and do not carry this normal-shutdown guarantee. These rules are detailed in Persistent Shutdown. Leaving an ordinary lexical scope does not release process-lifetime persist storage.

11. Design boundaries and related references

The chosen rules are reverse initialization order for current owners, exact transfer on moves and returns, cleanup on normal control-flow exits, and safe retention of device-accessed resources. User-defined cleanup syntax, partial-move restrictions for types with custom cleanup, ordinary borrowed-device exit behavior and safety-stop cleanup remain open. Normal persistent shutdown has its own chosen contract. Case-scope independence and the ordinary owner-transfer rules are chosen.
