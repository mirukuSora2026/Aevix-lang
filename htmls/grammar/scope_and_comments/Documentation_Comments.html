1. Metadata in ordinary block comments

Aevix uses ordinary /* ... */ comments for documentation metadata. A separate /** ... */ form is not required. Recognized tags at the start of a comment-content line describe the directly following declaration; the comment still introduces no executable statements.

Design reference. Chosen language rules are stated directly. Open policies and recommendations are labeled separately. These examples do not claim an implemented compiler, runtime, or diagnostic system.

/*
 * Return the supplied integer unchanged.
 * @parameter value The integer to return.
 * @return The same integer value.
 */
i32 identity(i32 value) {
    return value;
}

2. Line starts and optional leading stars

After removing the block-comment delimiters, a recognized tag starts a content line, allowing leading whitespace and an optional leading *. The star is presentation, not a distinct documentation-comment token. Ordinary descriptive lines remain prose.

/*
@parameter value The input integer.
@return The input value.
*/
i32 plain_comment_style(i32 value) {
    return value;
}

Tags embedded halfway through a prose sentence do not become new metadata entries. Both displayed layouts use the same ordinary comment delimiters. This reference does not add nested block comments, a markup language, or escaping rules for comment terminators.

3. Attach metadata to a declaration

Place the documentation block directly before the declaration it describes. Attachment is to that declaration, not to every later use of a name or an unrelated declaration discovered by scanning past statements and scope boundaries. A comment does not change lexical visibility or keep its declaration alive.

Maintained public library APIs use one directly attached lifecycle block. The source documentation checker rejects duplicate lifecycle tags and missing public declarations. A separate file-level @module block identifies an inventory module; it is tooling metadata and does not declare an Aevix module. Compiler behavior for other unknown or repeated tags remains separate.

4. The seven documentation tags

TagContentChosen meaning
@parameter name descriptionParameter name followed by descriptive text.Describe a named parameter; repeat for multiple parameters.
@return descriptionDescription of the declared return contract.Document the result; this is not a return statement.
@since versionThe first API version providing this declaration.Introduction history; independent of the documentation version.
@version versionAn API documentation version value.Metadata, not a runtime or language-mode switch.
@deprecated reason/replacementReason and/or replacement guidance.Mark and explain deprecation in documentation.
@deprecated_at version|noneThe first documented deprecation version, or no scheduled deprecation.Not a deletion version or automatic activation condition.
@removed_at version|noneThe documented removal version, or no scheduled removal.Compatibility metadata; not automatic compiler deletion.

The canonical deprecation tag is @deprecated. Tags describe the attached declaration; none changes its parameter types, return type, borrow permissions, or ABI.

5. Describe each parameter

Repeat @parameter for each parameter to document. The name identifies the parameter, and the remaining text explains its role, units, ownership expectations, or valid values. The tag does not declare another variable and cannot make an immutable parameter mutable.

/*
 * @parameter left The selected value when choose_left is true.
 * @parameter right The selected value otherwise.
 * @parameter choose_left Whether to select left.
 * @return The selected integer.
 */
i32 select_value(i32 left, i32 right, bool choose_left) {
    if (choose_left) {
        return left;
    } else {
        return right;
    }
}

Recommended, not settled: a documentation checker can compare tag names against the declaration’s parameter names. Unknown names, duplicates, missing tags, warning severity, and whether checks affect compilation have not been fixed.

6. Document return behavior

@return explains a function’s declared result. It never supplies a missing return statement, an implicit success wrapper, or an exception to return-path checking. Value-returning functions still explicitly return their values on normal paths, with the separately selected ? error-propagation shorthand retaining its own contract.

The unit value type and return-position void remain different. A tag cannot make void storable or remove the explicit value return required by a unit-returning function. A Result description should distinguish success and error meanings, and an Optional description should explain absence. Whether particular declarations require a return tag is an open validation policy.

7. Documentation version metadata

@version records version information for the attached API declaration. It does not choose a compiler version, enable a target instruction, select an overload, gate an import, or change runtime control flow. The library lifecycle checker accepts numeric major.minor or major.minor.patch versions, optionally followed by a prerelease suffix, for introduction, deprecation, and removal metadata. This does not redefine the existing @version value or select a compiler language mode.

8. Deprecation and replacement guidance

@deprecated marks the declaration as deprecated in its documentation and gives a reason or replacement guidance. It does not delete the declaration, rewrite calls, or imply that replacement preserves every ownership and error contract. A replacement name in prose is guidance, not a new executable alias.

Recommended, not settled: a compiler or tooling layer may warn when a deprecated declaration is used. Warning behavior, suppression, severity, enforcement across dependencies, and treatment of internal uses have not been selected. This reference therefore makes no claim that an implemented compiler already issues those warnings.

9. When the deprecation mark began

@deprecated_at records the API version at which the declaration started carrying its deprecation mark. It documents history. It is not the version where the API is removed and does not mean the marker only activates when a caller selects that version.

/*
 * @parameter value The integer to return.
 * @return The unchanged integer.
 * @version 2.0
 * @deprecated Prefer identity for new callers.
 * @deprecated_at 1.4
 */
i32 legacy_identity(i32 value) {
    return value;
}

Here the declaration’s sample metadata version is 2.0 and the deprecation mark began at 1.4. No automatic deletion or version-dependent warning rule follows. Active APIs write @deprecated_at none and @removed_at none when no end version is scheduled. A real deprecation records its actual version and should explain the replacement with @deprecated; inventing a future date for an active API is not permitted.

10. Library API lifecycle

Every public source module, type, enum variant, field, function, and method carries its own lifecycle values. Private declarations do not become public through a comment. The same rule applies to compiler-injected standard-library declarations; their inventory records the C++ provider and virtual source module separately.

/*
 * Return the input without changing ownership or its value.
 * @since 0.3
 * @deprecated_at none
 * @removed_at none
 * @version 1.0
 * @parameter value The input value.
 * @return The same value.
 */
public i32 identity(i32 value) {
    return value;
}

none means no deprecation or removal version is scheduled. It does not promise permanent compatibility. Introduction cannot follow deprecation or removal, and a scheduled removal cannot precede its documented deprecation. Existing 0.1 and 0.2 source API identities keep their verified introduction history when new 0.3 APIs are added.

The repository tool python3 tools/docs/library_api inventories signatures, updates attached blocks, checks missing or stale public entries, and renders a version table. It preserves existing prose, parameter descriptions, return descriptions, and @version. Annotating a catalog contract never changes its implementation status. Compiler-injected declarations describe intrinsic binding surfaces, so placeholder bodies are not ordinary Aevix implementations.

AreaChosenStill open or recommended
Comment formOrdinary /* ... */ with optional line-leading stars.Nested comment and rich-markup extensions are not introduced.
Recognized tagsSeven documentation tags; public library lifecycle blocks require since, deprecated_at, and removed_at.Compiler warning behavior and general unknown-tag policy remain separate.
Parameter metadataNames and descriptions can be written and repeated.Automatic name validation and diagnostic severity.
Deprecation metadataA marker, explanation, and historical API-version field.Compiler use warnings, suppression, and removal policy.

A comment never repairs a program with a type error, unsafe borrow, missing required return, or missing case-ending break. Documentation and executable semantics remain separate.

Public/private placement, lexical names, and resource lifetimes are governed by their language rules, not by a documentation tag. Complete module/type syntax, custom destructors, and annotation-driven compiler behavior are not added here.
