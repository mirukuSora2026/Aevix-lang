1. Scope, visibility, and lifetime

Scope determines where a name can be used. Visibility determines which declaration boundaries may expose it. Lifetime determines how long a value or resource remains valid. Aevix treats these as separate rules: public access cannot keep a local variable or a borrowed resource alive.

Design reference. Chosen language rules are stated directly. Open policies and recommendations are labeled separately. These examples do not claim an implemented compiler, runtime, or diagnostic system.

Local bindings use the established type-first syntax and are immutable unless declared mut. rsn performs static inference, not dynamic lookup. The chosen struct, enum, and interface forms refine type visibility. Module paths and imports are chosen in Modules and Imports; custom cleanup declarations remain open.

2. Local declarations and child scopes

A variable declared in a local lexical scope is available there and in nested scopes where the binding is visible. A declaration used as a conditional or loop body requires an explicit block; braces may be omitted only for a single ordinary executable statement. This creates no special scope for a lone unbraced declaration. Code outside that region cannot look up the local name. A nested region can read an enclosing immutable variable; changing it still requires the appropriate mutable binding or reference capability.

i32 outer = 10;
{
    i32 inner = outer;
    i32 observed = inner;
}
i32 still_available = outer;

The closing brace ends the inner local bindings. The outer binding remains in its enclosing scope. The following fragment deliberately tries to use a name after its declaring scope ends.

Rejected example. The local name is unavailable outside its lexical region.

{
    i32 inside = 10;
}
i32 escaped_name = inside; // Invalid: inside is out of scope.

3. public and private declaration access

public and private apply to module/type declaration interfaces. They do not decorate local variable declarations. Public permits externally visible access through the relevant declaration interface; private restricts access to its declaring boundary. Neither modifier supplies a writable reference, allocates storage, or extends a value lifetime.

Declaration contextChosen ruleBoundary
Module/type declaration interfacepublic and private are visibility controls.Type members follow the chosen struct, enum and interface rules; module lookup follows the chosen import paths and name-collision rules.
Local variableNo public or private modifier.The name is available in its declaring region and nested regions only.

Rejected example. Local visibility cannot be expanded with public.

void local_visibility() {
    public i32 count = 0; // Invalid: visibility modifier on a local.
    return;
}

Struct fields and enum payload fields are private by default; enum variant names are public by default within the visibility of their enum. Named-field initialization and case bindings respect access control. Type-internal factories may initialize private fields. Module-top-level types, functions and constants are private by default. Module qualification follows Imports and Visibility; defaults for other undecided member categories remain open.

4. No shadowing of visible variable names

A new variable declaration must not hide an already visible variable in an overlapping lexical region. Changing the type or adding mut does not make the redeclaration legal. A function parameter is a visible local binding in its function body, so an inner declaration cannot silently replace that parameter’s meaning.

Rejected example. The inner declaration hides the visible outer binding.

i32 count = 1;
{
    i32 count = 2; // Invalid: visible-variable shadowing.
}

Choose a distinct name when a second binding describes a different value. Assignment to an existing mutable binding remains assignment; it is not another declaration.

mut i32 count = 1;
{
    i32 next_count = 2;
    count = next_count;
}

Chosen case scopes. Every case and default introduces an independent implicit local scope. Different branches may use the same local name without body braces, provided that name does not hide a visible outer variable. Header bindings and body locals end on leaving their branch. Name reuse in other sibling-block categories remains a separate open policy.

Case-local names

i32 choose_value(i32 code) {
    mut i32 result = 0;
    switch (code) {
        case 1:
            i32 value = 10;
            result = value;
            break;
        case 2:
            i32 value = 20;
            result = value;
            break;
        default:
            break;
    }
    return result;
}

Each value binding belongs to a different branch. The result binding is shared from the enclosing function. A branch may not redeclare result. The lifetime of a legally retained reference continues to follow its source and uses; exiting a branch does not erase borrow obligations.

5. Visibility does not grant mutation

A binding can be visible and still immutable. The selected forms T value, &T value, and &mut T value distinguish value ownership, shared access, and exclusive target access. An immutable reference binding of type &mut T can write its permitted target; mutability of the reference binding instead controls rebinding that reference.

mut i32 count = 1;
&mut i32 target = &mut count;
*target = 2;
i32 observed = *target;

Taking &mut owner requires a mut owner binding. Public does not create this permission. Synchronized interior types such as Atomic and Mutex retain their own access contracts and do not authorize arbitrary mutable aliases.

6. Names and borrowed views

A reference or view can be available by name only while its source remains valid. A visible reference is not evidence that the owner can be moved, destroyed, or reallocated through another alias. Shared reads may coexist; conflicting exclusive access remains prohibited for the active loan.

Array<i32, 3> values = [1, 2, 3];
Slice<i32> view = Slice.from_array(&values);
usize count = Slice.len(view);

An existing Slice, MutSlice, string_view, or compatible reference is passed directly to a matching borrowed parameter. Local scope rules do not add another address-of layer. Last-use borrowing can end a loan before a textual block ends, but cannot extend the backing owner’s lifetime.

7. A binding ends; an owner may move

Ending a local scope removes its local binding and performs the cleanup owed by values still owned there. If ownership already moved elsewhere, the old binding does not destroy that value again. Returning an owner transfers it to the caller rather than destroying the returned resource at the function’s closing brace.

Vector<i32> make_values() {
    Vector<i32> values = Vector.new(i32);
    return values;
}

Shared ownership likewise permits the payload to outlive one handle’s local scope while another strong owner remains. A Weak observer does not retain the payload. The separate cleanup reference explains these release obligations.

8. Leaving a region

Block completion, break, continue, return, and propagated errors with ? leave the regions crossed by that control flow. Local cleanup follows the regions actually exited. A break inside a nested loop does not end an enclosing function; a return can leave several nested regions at once.

The ? operator is the selected shorthand for an error return in a compatible Result-returning function. It still obeys ordinary scope, ownership, and lifetime checks. It cannot make a borrowed local escape. See control flow and operators for their specific syntax.

Case-local scope is independent. A preceding return, loop continue, divergence or Result ? is allowed while the required final case break remains written. If that break is unreachable, unreachability alone is not an error or warning. Return/continue/Err clean up the regions they actually leave; this exception does not define general unreachable-code behavior or turn nontermination into a scope exit. See case-exit parsing.

9. Persistent storage and public access

persist gives per-declaration process-lifetime storage under its own contract. It does not grant an otherwise inaccessible local name global lookup, turn a declaration into a type member, or make shared mutation safe. Public also does not turn an ordinary local allocation into persistent storage.

Top-level initialization precedes program entry; local initialization occurs on first reach with one initializing thread. Generic-function storage identity and normal shutdown order are now chosen in Persistent Storage. Thread-local variants remain open. Name availability and storage duration must be checked separately. See Variable Declaration for the chosen declaration forms.
