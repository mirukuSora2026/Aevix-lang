1. One enum type, several variants

An enum names a type whose value is one of its declared variants. Empty variants and named-payload variants share one enum declaration and one parent type. A variant name is not an independent subtype.

These documents record chosen Aevix design rules, including ownership-aware switch patterns. They do not claim an implemented parser, compiler, ABI or runtime. Open layout, generic and cleanup details remain labeled separately.

3. A compact enum example

enum Direction implements Copy {
    North;
    South;
};

Direction choose_direction(bool northward) {
    return northward ? Direction.North : Direction.South;
}

Empty variants use qualified values such as Direction.North. Data variants use a named initializer such as Event.Move { x = 1, y = 2 }. Each required payload field is initialized explicitly; no implicit field default has been chosen.

AreaChosen rule
Variant namespublic by default; private is explicit.
Payload fieldsprivate by default; public fields are explicit.
OwnershipMove by default; built-in Copy checks every variant and every field.
Read switchswitch(event) borrows for reading and preserves the owner.
Modify switchswitch(&mut event) lends exclusive modification capability.
Consume switchswitch(move event) explicitly consumes an owned enum source.
Branch coverageEvery variant is covered by a case or by default; missing coverage is a compile-time error.
Case scopeEach case/default has an independent implicit lexical scope and ends with break;.

4. Connect enum rules to the rest of the language

Enums reuse the type-function and self receiver model of structs. An ordinary interface implementation applies to the whole enum, so Self denotes the parent enum rather than one variant. Static dispatch, default implementations and override rules follow the common interface contract.

See Interfaces, Generic Types and Copy. Numeric discriminants, memory layout, foreign ABI, derived equality, automatic cloning and custom enum cleanup remain open.
