1. One function model for construction and behavior

struct User {
    string name;
    i32 level;

    public User new(string initial_name, i32 initial_level) {
        return User { name = initial_name, level = initial_level };
    }

    public i32 get_level(&User self) {
        return (*self).level;
    }

    public void set_level(&mut User self, i32 new_level) {
        (*self).level = new_level;
        return;
    }

    public User into_user(User self) {
        return self;
    }
};

new has no receiver and is called through User.new(...). get_level reads through a shared receiver. set_level writes through an exclusive receiver. into_user uses ordinary value transfer. All ordinary non-void successful paths return explicitly; void may end normally or spell return;.

2. A factory is a receiverless type function

User make_user(string owned_name) {
    return User.new(owned_name, 1);
}

The word new is the chosen conventional function name, not a special constructor keyword. A type can define differently named factories using the same declaration and Type.function(...) call model. Their declared arguments and return types determine ownership and failures.

This example moves an already owned string argument into the factory. Under the existing text-literal draft, a literal is string_view; creating owning string uses an explicit fallible constructor. These examples do not add an implicit literal-to-owner conversion.

A factory inside the declaring type can initialize private fields. Its caller sees the returned complete value and the function’s access permission; the caller does not gain direct access to those private fields. The call spelling does not automatically allocate a heap object.

A constructor declaration without a return type and a separate allocation keyword are not introduced by this model. Function overload selection is chosen in Overloading; 0.2 rejects a field and method with the same direct member name, while distinct function signatures may form an overload set. More general wrapper forwarding and class inheritance remain outside this profile.

3. Return Result when construction can fail

enum ProfileError {
    NegativeLevel;
};

struct Profile {
    string name;
    i32 level;

    public Result<Profile, ProfileError> new(string initial_name, i32 initial_level) {
        if (initial_level < 0) {
            return Result.err(ProfileError.NegativeLevel);
        }
        return Result.ok(Profile { name = initial_name, level = initial_level });
    }
};

Result<Profile, ProfileError> build_profile(string owned_name) {
    return Profile.new(owned_name, 1);
}

The failure is an ordinary value in the declared Result, not a hidden constructor exception. On the rejected path, initial_name remains owned by the function and follows normal cleanup. On success, the already owned string argument moves into the initialized Profile and then into Result.

This is a user-defined example, not an added standard constructor API. The existing postfix ? rule can propagate matching Result errors in suitable Result-returning functions; successful return remains explicit.

4. Declare the receiver mode explicitly

Declaration Meaning Call effect
&User self Shared read loan of User. No owner move; conflicting write loans are excluded.
&mut User self Exclusive write loan of User. Requires existing write permission and a compatible exclusive loan.
User self Ordinary User value parameter. Copy if that type is Copy; otherwise move the complete owner.
No self receiver Receiverless type function. User.new(...) passes only the declared ordinary arguments.

self is the receiver variable; its type is written explicitly. A value receiver is not automatically changed into a borrow because the call uses member syntax. An ordinary immutable value parameter also does not grant arbitrary mutation merely by being a receiver.

5. Read calls allow automatic and explicit borrowing

i32 read_user_level(string owned_name) {
    User user = User.new(owned_name, 1);
    i32 automatic_read = user.get_level();
    i32 explicit_read = (&user).get_level();

    &User existing_read = &user;
    i32 reference_read = existing_read.get_level();
    return reference_read;
}

The first read call supplies the shared receiver loan indicated by get_level’s declaration. The second spells that loan explicitly. Both apply the same permission, lifetime, and conflict checks. The existing reference is passed or reborrowed directly rather than automatically wrapped in another reference layer.

The receiver expression is evaluated once. The method convenience does not deep-clone User, allocate a wrapper, or transfer it to another processor.

6. Write calls require an exclusive capability

void update_user_level(string owned_name) {
    mut User editable = User.new(owned_name, 1);
    editable.set_level(2);
    (&mut editable).set_level(3);

    &mut User existing_write = &mut editable;
    existing_write.set_level(4);
    return;
}

Automatic and explicit write calls require the same writable source and compatible exclusive loan. A shared reference cannot be upgraded into an exclusive reference. An ordinary owned User needs mut before a write loan can be taken; an already valid &mut User carries the referent’s write capability.

Rejected calls. The ordinary immutable owner and the shared loan do not provide write permission.

void invalid_writes(string owned_name) {
    User fixed = User.new(owned_name, 1);
    fixed.set_level(2); // Invalid: no owner write permission.
    &User read_only = &fixed;
    read_only.set_level(3); // Invalid: cannot upgrade shared access.
    return;
}

Last-use loan inference does not relax lifetime or overlap checks. A reference that escapes through a returned value continues to need its valid source; no blanket “all loans end at the semicolon” rule is assumed.

7. Value receivers follow Copy or move

User transfer_user(string owned_name) {
    User original = User.new(owned_name, 1);
    User destination = original.into_user();
    i32 retained_level = destination.get_level();
    return destination;
}

User owns a string and has not declared Copy, so the concrete value call moves original into self and returns that owner. The originating binding is no longer usable. Nothing about the member-call spelling silently borrows this declared value receiver.

Rejected use. original was consumed by a value receiver.

i32 invalid_reuse(string owned_name) {
    User original = User.new(owned_name, 1);
    User destination = original.into_user();
    return original.get_level(); // Invalid: original has moved.
}

For an explicitly Copy type, a value receiver follows the same value-copy rule as an ordinary value argument. This concrete-call rule does not make value receivers eligible through the current dyn callable surface; that surface is documented separately.

8. Access receiver fields with explicit dereference

struct Counter {
    i32 count;

    public Counter new(i32 initial_count) {
        return Counter { count = initial_count };
    }

    public i32 read(&Counter self) {
        return (*self).count;
    }

    public void write(&mut Counter self, i32 replacement_count) {
        (*self).count = replacement_count;
        return;
    }
};

A method in Counter can use its private count field. The reference receiver is explicitly dereferenced before selecting a field. Automatic receiver borrowing at a call site does not approve field automatic dereference inside an expression.

Initial or replacement parameter names are distinct from fields and visible outer variables. An initializer key identifies a field; it is not a new local binding. The exact broader namespace and reserved-name policy remains open.

9. Preserve ordinary evaluation, scope, and cleanup

Evaluate a receiver expression once and evaluate ordinary call arguments left to right once under the existing call rules. A factory or method body can have effects; calling it does not promise rollback on later failure. Required borrow conflicts must still be diagnosed regardless of evaluation order.

Parameters and receiver names are visible locals within the function body. A nested declaration cannot shadow them. Public/private apply to the method/type interface rather than its local variables. Returning an owner transfers it; scope cleanup releases initialized values still owned there.

Operation Retained rule
Shared method call The source must outlive every retained shared reference.
Exclusive method call No conflicting overlapping access during the active loan.
Value method call Copy or move follows the concrete type capability.
Failure from a Result factory Explicit error value; normal cleanup, no implicit recovery clone.
Public method External visibility; no owner lifetime extension.

10. Reuse the same model for enums and generic types

Enums use the same receiverless functions and typed receiver modes. A factory inside an enum can initialize its own private payload fields; a method can inspect its private variants within that type’s access boundary. It still needs the selected enum switch rules when behavior depends on the active variant.

Generic struct, enum, and interface declarations use the selected angle-bracket syntax and explicit where constraints. Generic function declarations and call inference are chosen. Generic methods use the same function template and static call rules. A type’s implements list precedes its where clause. Accessible methods can call later-defined methods; the compiler collects signatures before checking bodies. Read Enums and Generic Types.

The separate Box payload method-call convenience reuses declared receiver borrowing. Its explicit Box.as_ref/Box.as_mut views, dyn eligibility, collision policy, and ownership limitations belong to their respective references rather than a universal wrapper autodereference rule.

11. Open call policies

  • Method/field and wrapper-method collisions, and interface-specific interactions between overloads, default arguments and parameter names. Ordinary overload selection and default and named arguments are chosen.
  • General field automatic dereference and a general-purpose wrapper dereference capability.
  • Reference-return lifetime annotations, additional generic-method-specific rules, and advanced self forms. Ordinary generic function declarations and call inference are chosen.
  • The default visibility of every method category and the complete modifier ordering.
  • Custom destructor methods and special constructor protocols are not specified by ordinary factories.
  • Explicit-capture closures and concrete generic Fn/FnMut/FnOnce callbacks are implemented in 0.2. Owning dynamic callable wrappers, async/GPU method signatures and standalone forward-prototype syntax remain outside this profile. Qualified module lookup is described in Modules and Imports.
