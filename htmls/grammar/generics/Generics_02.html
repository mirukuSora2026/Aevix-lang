Trailing defaults and inference

Struct, enum, interface, and function generic parameter lists may provide trailing type and constant defaults. A default may use earlier parameters. Required parameters cannot follow a defaulted parameter; a default cannot refer to itself or a later parameter.

struct Pair<T = i32, U = T> {
    public T first;
    public U second;
};

T identity<T = i32>(T value) {
    return value;
}

i32 main() {
    Pair value = Pair { first = 20, second = 22 };
    i32 result = identity(value.first + value.second);
    return result;
}

Function arguments contribute to inference. Explicit function arguments may supply a leading portion of the generic list, with inference or trailing defaults completing it. Bare generic type names use their defaults; the compiler does not infer an arbitrary generic struct type from its field initializer values.

Compile-time constant extents

Value parameters use const usize N. The current compiler accepts usize constant parameters. Arguments must be nonnegative compile-time values fitting usize. Runtime variables, negative values, and larger unsigned values are rejected.

struct Buffer<T = i32, const usize N = 4> {
    public Array<T, N> values;
    public usize len(&Self self) {
        return N;
    }
};

usize width<T, const usize N>(&Array<T, N> values) {
    return N;
}

i32 main() {
    i32 items[4] = [1, 2, 3, 4];
    usize count = width(&items);
    Buffer buffer = Buffer { values = items };
    return buffer.len() == count ? 42 : 1;
}

The same extent can be written as an integer literal or a visible const name. The compiler normalizes their values, so 4 and a constant evaluating to 2 * 2 identify the same specialization. Zero-length fixed arrays are permitted. Defaults may contain constant expressions; parenthesize an expression containing a greater-than or shift operator to distinguish it from the closing angle bracket.

Array extents can be inferred through Array types, fixed array declarators, borrows, and generic container fields. A const parameter controls a static type or compile-time value; it does not create a runtime dimension-varying type.

Transparent type aliases

public type UserId = u64;
type Samples = Array<f32, 4>;

UserId identity(UserId value) {
    return value;
}

An alias is another spelling of the same type. It does not create a new nominal type or change ownership, representation, overload identity, interface satisfaction, or conversion rules. Alias cycles are compile errors. Imported aliases retain normal public/private access rules. Generic alias declarations are not part of this profile.

The sealed Floating contract

import numeric { Floating };

T twice<T>(T value) where T implements Floating {
    return value + value;
}

i32 main() {
    f32 result = twice(21.0f32);
    return result == 42.0f32 ? 42 : 1;
}

The actual numeric module exports Floating. It is a compiler-recognized scalar-format contract implemented only by builtin f16, bf16, f32, and f64. Transparent aliases of those formats satisfy it. Floating guarantees Copy behavior, arithmetic +, -, *, /, comparisons, and unary signs. It does not promise exact arithmetic, total ordering in the presence of NaN, bitwise operations, or new user-defined operator overloads.

Users cannot implement this sealed contract on a struct or enum. A custom interface named Floating remains an ordinary interface and receives no builtin numerical privileges. The compiler checks the imported contract's original identity, not just its spelling. Copy alone does not grant arithmetic, and an unbounded T still cannot use +.

Compiler scope

Concrete type and constant arguments determine a static specialization. AOT and JIT reuse canonical identities within a compilation. Inference errors and unsupported capability uses are diagnosed before machine code generation.

Shape parameters, arbitrary const-parameter types, associated types, lifetime parameter syntax, variance, and user-defined operator contracts remain outside this implemented profile. CPU SIMD and Complex use explicit imports and their own documented constraints.
