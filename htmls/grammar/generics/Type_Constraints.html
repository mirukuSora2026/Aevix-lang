1. Separate type parameters from requirements

struct Pair<T> where T implements Copy {
    public T first;
    public T second;
};

The chosen spelling places where T implements Copy after struct Pair<T> and before its body. The angle brackets introduce T; the where clause states a feature T must provide. This selects a requirement without using an inline T: Copy bound.

The same selected clause form applies to the approved generic type declaration families. These pages use one requirement at a time, because the grammar for multiple constraints has not been chosen.

2. Check the requirement for concrete arguments

Pair<i32> numbers = Pair<i32> {
    first = 10,
    second = 20
};

i32 satisfies the established Copy capability, so this concrete use meets the constraint. A compiler checks the supplied type’s actual capability rather than accepting it because the field values happen to be small or currently unused.

Rejected example. This intentionally violates a chosen rule.

// Rejected: owning string does not implement Copy;
Pair<string> invalid_words(string initial_first, string initial_second) {
    return Pair<string> {
        first = initial_first,
        second = initial_second
    };
}

Owning string is move-based and cannot meet this requirement. The rejected function receives already owned strings, so the intended error is the unsatisfied Copy constraint rather than an implicit literal-to-owner conversion. A reference can satisfy its own Copy rules while still retaining provenance; capability matching never extends the referent’s lifetime.

3. A Copy requirement does not mark the container Copy

Declaration propertyMeaning
where T implements CopyEvery permitted T must be Copy.
Fields of type TThe concrete fields have T’s checked value-passing behavior.
The enclosing struct or enumStill move-by-default unless it separately opts into Copy.
Whole-type CopyCompiler validates all fields, or all enum payloads, under a separate opt-in.
Pair<i32> original = Pair<i32> {
    first = 1,
    second = 2
};
Pair<i32> moved = original;

Even this constrained Pair moves in the assignment. The bound establishes a fact about T, not a declaration about Pair’s public value semantics. The exact combined header spelling for implements Copy plus a where clause is still open and is not assumed here.

Copy is a checked built-in capability, not a default body that a developer can override to allocate or deep-clone. Owning collections, Box and exclusive references cannot be made Copy merely by wrapping them in a constrained generic type.

4. A requirement may name an ordinary interface

interface Leveled {
    public i32 get_level(&Self self);
};

struct LevelHolder<T> where T implements Leveled {
    T item;
};

This requirement admits a supplied type only when it implements the selected Leveled contract. The interface’s typed receiver and return contract remain the source of its behavior. The private item field follows the normal struct access rules; the bound does not make it public.

Interface requirements state the behavior available for generic checking. They do not grant arbitrary field access, implicit deep cloning, Copy status, heap storage or dynamic method selection. Generic function bodies are checked using their declared requirements, as described in Generic Functions. Additional generic-method-specific rules remain open.

5. Use the selected clause on generic enums and interfaces

enum Snapshot<T> where T implements Copy {
    Empty;
    Present {
        public T value;
    };
};

interface Inspector<T> where T implements Copy {
    public T sample(&Self self);
};

The enum requirement restricts the payload parameter. Snapshot itself is still move-based without a separate Copy implementation. In Inspector, T is the constrained type argument while Self is the implementing receiver type; they are different names and different roles.

A constraint does not remove enum coverage checks or dynamic-interface method restrictions. Multiple parameters may be declared with <T, E>, but the chosen single-clause examples do not define how several parameter requirements are separated.

6. Requirements do not bypass access or borrowing

SituationResult
T implements an interfaceOnly its declared contract is promised; concrete private fields stay private.
T is CopyCopies follow T’s semantics; a copied shared reference still targets the same storage.
T owns resourcesNormal moves and cleanup remain; an interface bound does not clone them.
A value is immutableA where clause does not authorize ordinary mutation.
A value contains loansSource lifetime and conflicting-access checks remain active.

An interface bound and explicit dyn solve different needs: one states a static requirement on a type argument, while the other selects an eligible implementation at runtime through an erased view. No conversion between them is inferred by this syntax.

7. Reject missing capabilities without runtime fallback

A concrete instantiation that does not satisfy a chosen requirement is rejected during static checking. There is no automatic clone fallback for Copy, no runtime method-name lookup fallback for a missing interface and no implicit adapter implementation.

Rejected example. This intentionally violates a chosen rule.

struct Token {
    public i32 value;
};

// Rejected: Token has not opted into Copy;
Pair<Token> tokens = Pair<Token> {
    first = Token { value = 1 },
    second = Token { value = 2 }
};

This example uses Pair from the first section. Primitive Copy fields do not automatically make a user-defined Token Copy. Exact error wording and diagnostic identifiers remain compiler work; this page records the semantic reason for rejection.

8. Open constraint grammar and related reference

  • Function requirements use where T implements Copy, T implements Leveled: repeat the subject, separate with commas and require every bound. No additional inline-bound syntax is selected.
  • The exact order for combining a type’s implements list with where clauses remains open.
  • Conditional implementations, negative constraints, associated-type equalities and structural constraints remain open.
  • Generic function placement and call inference are chosen in the function reference; additional method rules and specialization behavior remain open.
  • Const/Shape values, lifetime constraints and generic-interface dynamic conversion remain open.
