0.2 implementation update. Const generic extents, trailing defaults, transparent aliases, and numeric.Floating are implemented. The sections below distinguish these implemented features from the remaining design limits.

1. Type parameters belong to the declaration

A generic declaration names type parameters after its type name. Field and method signatures may use those types within the declaration. A concrete use replaces each parameter with a supplied type; it does not change a variable’s type during execution.

struct Pair<T> {
    public T first;
    public T second;
};

Pair<i32> numbers = Pair<i32> {
    first = 10,
    second = 20
};

The left declaration supplies the variable’s type before its name. The right constructor explicitly identifies the same concrete struct and uses the already selected named-field initialization grammar. Fields are checked for name, type, presence, duplication and access permission.

2. A generic struct retains field rules

Pair<f64> coordinates = Pair<f64> {
    first = 1.5,
    second = 2.5
};

Pair<string> make_words(string initial_first, string initial_second) {
    return Pair<string> {
        first = initial_first,
        second = initial_second
    };
}

This fragment uses the unbounded Pair in the preceding section. T is f64 for coordinates and string in make_words. The concrete, non-generic function receives existing owning strings and moves them into the returned Pair. It does not convert a literal or borrowed string_view into an owner. The owning string fields move when their struct moves; merely sharing a generic name does not turn them into Copy fields.

Struct fields remain private by default. Public fields are explicit in this example to permit external named-field construction. A generic type with private required fields uses internal factory logic under the same access restrictions as a non-generic struct. Generic method parameters follow the method name, using the same placement as free generic functions.

3. An enum may parameterize each variant payload

enum Outcome<T, E> {
    Success {
        public T value;
    };

    Failure {
        public E error;
    };
};

Outcome<string, i32> make_success(string initial_value) {
    return Outcome<string, i32>.Success {
        value = initial_value
    };
}

Outcome<string, i32> failure = Outcome<string, i32>.Failure {
    error = 7
};

T and E are distinct type parameters. make_success is a concrete, non-generic function that moves its existing owning string parameter into the Success payload. Both variants produce the parent concrete enum type Outcome<string, i32>. Variant names remain public by default, payload fields private by default; these payloads are explicitly public so external construction is valid.

Normal exhaustive switch, partial payload binding, per-case scope and ownership rules still apply. This declaration does not extend the builtin Result/Optional ? operator to Outcome merely because its variants look similar. Generic enum Copy checks, when opted into, must cover every variant payload.

4. An interface may parameterize its contract

interface Reader<T> {
    public T read(&Self self);
};

struct Reading implements Reader<i32> {
    i32 stored;

    public Reading new(i32 initial_value) {
        return Reading { stored = initial_value };
    }

    public i32 read(&Reading self) {
        return (*self).stored;
    }
};

Reading reading = Reading.new(42);
i32 value = reading.read();

In Reader<i32>, T resolves to i32. Independently, Self resolves to Reading in this implementation. T describes a contract type argument; Self identifies the concrete receiver type. The public implementation supplies the required ordinary method, without override because no default body exists.

The ordinary call is statically selected. Concrete generic interfaces use the ordinary dyn method-eligibility rules. Type arguments may be omitted only where declared trailing defaults complete the type; this does not add interface inheritance. Function-call inference and overload rules are defined separately in Functions and Calls.

// Rejected: second resolves to i32 and a string_view literal cannot initialize it;
Pair<i32> invalid = Pair<i32> {
    first = 1,
    second = "two"

No implicit conversion between different concrete instantiations is introduced. Exact variance and subtyping policies remain open. Untyped numeric literals can resolve to the already declared numeric field type under the existing literal rules.

6. A container is still move-by-default

Pair<i32> original = Pair<i32> {
    first = 10,
    second = 20
};
Pair<i32> moved = original;

The unbounded Pair declaration has no whole-type Copy opt-in. Although its concrete i32 fields are Copy, assigning the struct transfers its ownership. Generic substitution does not silently make the container Copy.

Rejected example. This intentionally violates a chosen rule.

// Rejected: original was moved in the preceding example;
Pair<i32> reused = original;

If a container opts into Copy, the compiler must verify its relevant concrete field types under the chosen Copy rules. The combined header is struct CopyPair<T> implements Copy where T implements Copy: the container opts into Copy before its field-type constraint. Conditional implementation declarations remain outside this profile.

7. Borrowing and mutability remain explicit

mut Pair<i32> editable = Pair<i32> {
    first = 10,
    second = 20
};
editable.first = 30;

&Pair<i32> view = &editable;
i32 observed = (*view).first;

The ordinary owning binding needs mut for assignment. A shared reference reads the same struct without cloning it, and cannot write its fields. Replacing a type parameter does not add permission to an immutable binding or hide an allocation needed by its concrete type.

Generic values containing borrowed fields must preserve the lifetime of each source. Lifetime parameter syntax and generic returned-reference lifetime notation are open; angle-bracket type arguments are not blanket permission to escape references.

8. Static specialization preserves source contracts

The 0.2 compiler checks generic bodies against their contracts and creates canonical concrete specializations for type and const arguments. AOT and JIT share those checks. This implementation does not promise a stable generic ABI, a fixed dictionary layout, or a future shared-code compilation strategy.

No generic declaration by itself guarantees GPU eligibility, packed layout, vectorization or runtime-free behavior. Operations and concrete representation retain their real costs; explicit allocation, copying and device transfers remain explicit.

9. Open generic decisions and related reference

  • Generic functions and methods put parameters after their names. Calls support a leading explicit list completed by inference or defaults, as described in Generic Functions.
  • Generic type arguments may omit declared trailing defaults. Arbitrary field-based container inference, wildcard arguments, and variance extensions are unsupported.
  • const usize parameters, trailing type/value defaults, and transparent non-generic type aliases are implemented. Shape parameters, lifetime parameter syntax, generic alias declarations, and associated types remain outside this profile.
  • A type’s implements list precedes where. Type and function constraints use comma-separated requirements with the subject repeated; conditional implementation declarations remain unsupported.
  • Dyn views expose eligible nongeneric methods. Generic methods remain static; generic ABI/FFI layout guarantees remain outside this profile.
