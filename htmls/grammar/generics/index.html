1. Reuse declarations across concrete types

A generic type declaration introduces type parameters in <...>. A concrete use supplies type arguments in the same angle-bracket form, such as Pair<i32> or Outcome<string, i32>. The supplied type fixes the fields and method contracts; it is not a runtime string naming a type.

Chosen scope. Generic structs, enums and interfaces are approved. Generic function declarations and calls are also chosen. Constant shape parameters, lifetime parameters and generic-type inference extensions remain open.

3. A constrained generic struct

struct Pair<T> where T implements Copy {
    public T first;
    public T second;
};

Pair<i32> numbers = Pair<i32> {
    first = 10,
    second = 20
};

The condition admits i32 because it satisfies Copy. Owning string does not satisfy Copy, so Pair<string> is rejected for this declaration. The Pair itself remains move-by-default because a requirement on T is not a Copy declaration for Pair.

4. Chosen forms at a glance

FormPurpose
struct Pair<T>Parameterize a product-like user-defined value.
enum Outcome<T, E>Parameterize the payload types of enum variants.
interface Reader<T>Parameterize a behavior contract’s types.
Pair<i32>Use the generic declaration with a concrete type argument.
where T implements CopyRequire a selected capability after the generic declaration head.

The where clause separates the type argument list from a feature requirement. This type reference does not add inline bounds or decide combined type implements/where ordering. The function reference defines comma-separated requirements and call inference.

5. Generic types keep the same ownership rules

Concrete fields follow their supplied type’s Copy, move, read-borrow and write-borrow contracts. Type parameters do not grant cloning, mutability, field access or lifetime extension. Public/private fields and the whole-type Copy opt-in apply just as they do to ordinary structs and enums.

An instantiated interface still describes behavior. Generic parameters alone do not introduce runtime dispatch, dynamic boxing or data transfers. The static-dispatch default remains separate from the still-open backend strategy for compiling generic bodies.

6. Open generic design and related reference

  • Generic function syntax, complete explicit call-site type lists and function inference are chosen in Generic Functions; additional method rules remain open.
  • Function bounds use repeated subjects separated by commas. Combined type implements/where heads and conditional implementations remain open.
  • Constant/shape arguments, lifetime parameters, variance, associated types and default type arguments remain open.
  • Monomorphization versus shared-code strategies, JIT specialization and generic-interface dynamic coercion remain open.
