1. Compile ahead of time and selectively at runtime

Aevix combines ahead-of-time compilation with selective just-in-time compilation. AOT is the baseline for native code. Selected portions may be compiled or specialized at runtime through JIT. This choice establishes the execution direction, not a complete runtime architecture.

Confirmed scope. The AOT/JIT combination is selected. Initial CPU/OS targets and LLVM/ORC implementation direction are selected below. Trigger policy, hotness thresholds, cache storage format, complete fallback behavior and deployment packaging remain open; GPU and parallel-language work are deferred. No JIT or AOT engine has been demonstrated by this documentation.

2. AOT is the native baseline

Ahead-of-time compilation prepares executable code before its normal execution. The source is statically typed and checked under the selected ownership and borrowing model. Baseline work does not require every source operation to become a mandatory runtime compilation request.

The initial native target matrix and platform object/linking route are chosen below. Standard-library packaging, optimization levels and whether a deployment includes a JIT component remain to be chosen. The phrase AOT baseline does not settle those distribution choices.

3. JIT is selective, not a second language

Runtime compilation can provide an additional specialization or execution path for selected work. It must remain subject to the same source rules and supported target capabilities. Source does not gain a different safety mode merely because the code is compiled later.

Question Possible design work, not an approved policy
What triggers compilation? Explicit requests, measured hotness, runtime type/shape facts, or another selected policy.
What can be specialized? Only facts whose use preserves the language’s type, error, effect, and cost contracts.
When is compiled code installed? Compilation scheduling, publication, and concurrent call behavior need defined semantics.
What happens when compilation is unavailable or fails? Fallback, explicit failure, retry, or another policy has not been selected.
How is compilation time exposed? Startup, latency, profiling, and runtime resource accounting require design.

4. Keep the same static contract

struct Point {
    public i32 x;
    public i32 y;
};

i32 sum(&Point point) {
    return (*point).x + (*point).y;
}

Point input = Point { x = 10, y = 20 };
i32 output = sum(&input);

The selected type-first syntax, explicit return, named initialization, reference permission, and integer safety behavior are the same on either compilation path. JIT is not permission to reinterpret a moved binding, upgrade a shared reference, or allow an invalid field type.

Required static typing and ownership diagnostics must not be deferred into unchecked execution. The exact implementation of front-end reuse, intermediate validation, and JIT code verification remains open.

5. Preserve observable evaluation and errors

Area Selected rule that remains in force
Evaluation Operands, initializer values, receivers, and ordinary call arguments evaluate once under their selected ordering rules.
Arithmetic Ordinary checked integer safety and explicit checked Result recovery keep their distinct semantics.
Errors Result/Optional contracts remain explicit; postfix ? propagates matching Result errors.
Ownership Move defaults, explicit Copy, source lifetimes, and conflicting-loan checks are preserved.
Scope cleanup Normal exits clean only currently owned initialized values under the selected scope model.
Dispatch Static default and explicitly selected dyn calls do not change implicitly based on compilation stage.
Cost boundaries Compilation cannot insert an unrequested deep clone, ownership box, or CPU/GPU transfer.

Compilation may change generated instructions when it preserves the required observable behavior. It may eliminate a redundant check only with valid proof, not by assuming that earlier observed inputs cover every future call. No blanket relaxed-floating-point or build-mode safety exception is selected.

6. Specialize only under a valid contract

The selected compiler-first direction encourages using type, shape, ownership, effect, and target information for valid optimization. AOT can use facts available before execution; JIT can potentially use additional runtime facts when their validity is established.

Guards, recompilation, deoptimization, speculation limits, specialization budgets, and invalidation are mechanism questions still open. Naming them here does not choose an implementation. Generic compilation may use specialization or another strategy; the user-defined generic grammar does not settle that strategy.

7. A unified CPU/GPU model still needs explicit target rules

The language direction is one programming model across CPU and GPU, with explicit transfer and copy costs. The AOT/JIT choice does not prescribe which processor runs JIT compilation, which code is eligible for device execution, or whether device code is compiled before or during execution.

Target availability, device module format, kernel launch syntax, data placement, transfer APIs, synchronization, and target-specific unsupported operations remain open. Unifying syntax is not a promise of shared physical memory or of cost-free migration.

Pending device access must not outlive released backing storage. Borrowed local storage needs a valid completion/lifetime contract before its scope can end; hidden waits versus explicit structured completion have not been finalized.

8. Support extensible backend architecture

The compiler should be extensible to backends such as LLVM and MLIR, preserving enough language information to lower the same semantics to different targets. This is an architectural goal, not a claim that a particular frontend, IR chain, code generator, or backend plugin already exists.

The initial route is shared frontend and AIR, then target-aware LLVM lowering for AOT and ORC execution. Exact AIR schemas, pass interfaces and backend APIs remain open; device backends are deferred. No source-level semantic guarantee should depend on an undocumented backend optimization accidentally occurring.

10. Validate correctness before making performance claims

An implementation will need appropriate semantic checks for both paths: type and ownership rejection, checked arithmetic failures, Result exits, evaluation order, dispatch, cleanup, target capability handling, and resource lifetime preservation. Runtime specialization also needs evidence that the assumptions supporting its generated code stay valid.

Representative benchmarks must account for native throughput, compilation latency, warm and cold execution, memory use, synchronization, data movement, and supported devices. No comparative speed claim follows from the AOT/JIT spelling alone.

Current evidence. These pages are HTML design documentation. There is no Aevix compilation, execution, GPU run, benchmark, or FFI validation result here.

11. Open mechanisms at a glance

  • Selection triggers, compilation scheduling, thresholds, and profiling controls.
  • Runtime fact validation, guards, specialization limits, and invalidation or replacement mechanics.
  • Complete fallback/error policy, deployment packages, runtime inclusion, cache storage and eviction.
  • Deferred GPU/parallel work: CPU/GPU division, device support and launch/transfer/completion syntax.
  • Detailed generic lowering, AIR schema, backend interfaces, target ABI implementation and versioned runtime ABI.
  • Safe-stop cleanup and custom cleanup declarations remain open; normal persistent shutdown order is already chosen.

12. ARM64 and x86-64 execution architecture

Chosen initial target scope: ARM64 (AArch64) and x86-64, each on macOS and Linux. Windows is a later target; ARM32 is outside the initial scope. These are implementation requirements, not demonstrated execution support. GPU and parallel-language design are deferred while the CPU core is completed.

The exact minimum OS versions, initial Linux libc baseline and required SDK/toolchain versions remain release-matrix choices. A target description includes architecture, OS, environment/ABI, CPU features and data layout. Frontend checks may consult this target information for size, alignment and FFI decisions; a shared frontend does not imply target-independent pointer sizes or calling conventions.

Shared checks, target-specific generated code

  1. Parse and check Aevix source using one frontend, type system and ownership model. Preserve language-level semantics in AIR.
  2. Lower AIR through the initial LLVM backend using the selected target's data layout and call ABI. LLVM IR with a target layout is not automatically a portable bytecode bundle.
  3. For AOT, emit target object code and link the matching runtime and system libraries using an appropriate target linker and sysroot. Use the operating system's executable loader.
  4. For execution from source, the proposed aevix-run tool uses the same checks and an ORC JIT targeting its executor process. It cannot directly execute incompatible CPU instructions or another OS ABI.
  5. Use shared runtime startup and normal shutdown, including the existing persist initialization and cleanup contracts. Retain needed JIT code through cleanup callbacks.

LLVM code generation and ORC are the initial implementation route. The existing Backend/Native architecture-specific encoder folders remain later extension points. A custom native encoder, custom executable loader, emulator and remote executor are not required for the first implementation. Cross-compiling an object file does not establish that it can be linked or executed on the compiler's machine.

Native execution and cache compatibility

AOT distribution uses an explicit portable CPU baseline for each target. Optional CPU instructions require an explicit target requirement or a validated runtime dispatch path; do not silently compile distributed code for the build machine's features. JIT feature selection is based on the executor's usable capabilities.

Before installing or loading code, check the target, ABI and required CPU features. Cache identity must include source and dependencies, compiler/LLVM versions, language/runtime ABI, target triple, data layout and code-generation options. Cache paths and file format remain open. Cache hits do not create a second persist instance.

OS-specific executable-memory allocation, write/execute transitions and required instruction-cache synchronization belong behind the platform/architecture interfaces. On macOS, apply the supported JIT memory and code-signing rules for the chosen deployment and Hardened Runtime configuration; do not solve compatibility by globally disabling protections.

The initial code-retention policy keeps superseded JIT code and required metadata until orderly process shutdown, after callbacks and language cleanup can no longer use them. Reject incompatible function-signature or live-data-layout replacement. More precise code reclamation, hotness triggers and speculative deoptimization remain later work.

An explicit initial entry contract

The default executable entry module is src/main.avx, resolved under the configured source root. Selection of a different entry module belongs to the future project/driver configuration. The initial entry function is exactly one receiverless, non-generic, non-overloaded i32 main(). It does not need public visibility: the executable startup adapter selects that entry rather than importing a private declaration from an ordinary language module.

i32 main() {
    return 0;
}

All required top-level persist initialization succeeds before main begins. The i32 result goes to the platform exit adapter, with zero representing success; the operating system's observable exit-status representation is not promised to preserve every i32 bit. Command-line argument parameters, Result-returning main and async main are not initial entry forms. Libraries do not require main.

A shared runtime startup wrapper supplies the platform ABI entry and calls the checked language entry using its matching generated ABI. Keep the compiler/runtime C ABI distinct from the operating-system entry ABI. The CMake toolchain builds a compiler/runtime for a selected host or cross-build environment; it must not accidentally determine the target of every Aevix program that compiler later emits.

Evidence required before declaring support

Run native AOT and JIT tests on all four architecture/OS combinations. Check arithmetic and Result behavior, ownership rejection, evaluation order, struct/enum calls and returns, C ABI round trips, persist identity and cleanup, CPU-feature rejection and platform JIT permissions. Cross-build and emulation checks can supplement this matrix but do not replace native execution evidence. No such Aevix execution evidence exists yet.

Primary implementation references: LLVM target triples, Clang cross-compilation and sysroots, LLVM ORC architecture, CMake toolchains and Apple silicon JIT requirements. These sources guide the architecture; they do not validate an Aevix implementation.
