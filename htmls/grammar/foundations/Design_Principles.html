1. Read these principles as design commitments

The following 15 principles preserve the substance of the selected Aevix direction. The overall goal is C++-class native speed with safety at least at the level targeted by Rust, approachable syntax, and built-in GPU/parallel support. These describe desired behavior, not completed performance, security, interoperability, or backend validation. Concrete syntax is shown only where it has already been selected.

Evidence boundary. A design goal, a selected source rule, a proposed standard API, and a verified implementation are different kinds of evidence. This document identifies the first two; it does not claim the last.

2. 01 · Simplicity

Prioritize syntax that is simple and easy to read. Reuse one type-first declaration style, one ordinary function model, named-field aggregate initialization, and explicit ownership modes instead of requiring unrelated forms for equivalent work.

Selected forms include T name = value;, static inference with rsn, condition parentheses, optional braces for a single executable statement, and explicit successful return. Simplicity does not remove meaningful cost, error, or lifetime boundaries.

3. 02 · Static typing

Check type errors at compile time before the affected source executes. Typed numeric values do not silently change to another numeric type; unconstrained literals retain the selected defaults and contextual literal typing remains available.

i32 count = 10;
f64 ratio = 0.5;
rsn enabled = true;

rsn performs compile-time inference and fixes the resulting type; it is not a runtime dynamic-type declaration. JIT compilation must not bypass the source’s required static type checks.

4. 03 · Memory safety

The compiler is intended to prevent incorrect resource management, avoidable memory leaks, and data races through checked ownership, borrowing, and resource lifetimes. Safe code must not access released storage, duplicate an exclusive owner, or retain an invalid loan.

i32 owner = 42;
&i32 read_view = &owner;
i32 observed = *read_view;

Normal cleanup of currently owned initialized values is deterministic; ownership transferred elsewhere is not released twice. Strong Shared cycles or deliberately retained ownership can keep resources alive, so ownership checking is not a claim that every possible leak is automatically prevented. Whole-program behavior, foreign boundaries, and the complete compiler safety guarantee still require implementation and validation. Process termination and custom cleanup failure behavior are not settled by this principle.

5. 04 · Zero-cost abstraction

Abstractions should not introduce unnecessary runtime overhead. Static interfaces, ownership checks, and shape facts should give the compiler opportunities to remove bookkeeping when correctness is proved.

This does not erase the real work of copies, allocation, synchronization, bounds checks that cannot be proved redundant, or explicitly selected dynamic dispatch. The source contract and target behavior constrain optimization; zero-cost is an objective rather than a universal benchmark result.

6. 05 · AI-native

Support Tensor, Shape, and data processing at the language-engine level. Their element types, shapes, ownership, and device placement should be part of the compiler’s understanding rather than opaque accidental conventions.

The Tensor and Quantized catalogs describe the intended value/API surface. This principle does not introduce an unselected tensor literal, automatic differentiation syntax, or final training/runtime API.

7. 06 · CPU / GPU Unified

Use one programming model for CPU and GPU computation. Values, ownership, errors, and parallel operations should remain understandable across target boundaries, with backend-specific capability limits made explicit.

A unified model does not promise shared physical memory, identical device instruction sets, automatic migration, or cost-free launches. Kernel syntax, target selection, supported device operations, scheduling, and completion rules remain separate compiler/runtime decisions.

8. 07 · Shape-aware programming

Check Tensor Shape compatibility at compile time wherever the source and type information make that compatibility statically knowable. Reject incompatible operations before executing them instead of discovering avoidable shape failures deep in a computation.

Symbolic shape parameters, constraints, inference, and dynamic-shape check spelling remain open. Runtime facts must not be treated as compile-time proof simply because a JIT observes one execution. Any specialization must preserve the selected failure and validation semantics.

9. 08 · Explicit cost

Represent data copying and GPU-transfer costs clearly. Distinguish value moves, allowed Copy values, explicit allocated duplicates, borrowed views, device transfers, and synchronization that may wait for work.

Operation category Meaning Cost boundary
Move Transfer an owner. No implicit deep clone or processor transfer; physical movement may remain.
Copy Duplicate an eligible value. Large values may still move real bytes; references keep the same backing storage.
Borrow Use a valid source under access restrictions. No ownership extension or hidden resource clone.
Allocated duplication Explicitly create another owning allocation. API work, allocation, and errors must remain visible.
CPU/GPU transfer Move or copy data across a device boundary. Do not infer it from ordinary assignment or type erasure.
Completion/synchronization Ensure pending accesses are finished. Potential waiting and resource retention must not be presented as free.

10. 09 · Errors as values

Express absence and failure safely through Optional and Result. A caller must account for whether a value exists or an operation succeeded under those contracts.

Result<i32, IntegerError> add_checked(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    return Result.ok(sum);
}

Postfix ? explicitly propagates an Err from a compatible Result-returning function. Successful return remains written out. The 0.2 profile also supports postfix ? on an owned Optional, forwarding None only to an Optional-returning function or explicitly typed closure. None-to-error conversion is unsupported. Ordinary unrecoverable integer arithmetic and an explicitly checked Result operation retain distinct approved failure behavior.

11. 10 · Immutable by default

Allow data modification only through an explicit mutable declaration or an already valid write capability. Ordinary owners are immutable by default, which makes local intent and shared read access easier to inspect.

i32 fixed = 10;
mut i32 editable = 10;
editable += 1;

public visibility is not write permission. &mut T carries exclusive target access even if the reference binding itself is immutable. Synchronized interior types have explicit specialized contracts; they do not authorize unrestricted writes to ordinary immutable data.

12. 11 · Data-oriented design

Favor contiguous memory and high cache efficiency. Fixed arrays, growable contiguous vectors, slices, scalar/SIMD elements, and tensor storage should make bulk operations and their layout costs understandable.

Concrete layout guarantees, automatic record layout transformations, cache behavior, vectorization results, and backend storage choices require explicit contracts or measurement. A struct declaration alone is not a stable foreign ABI or a promise of a particular cache layout.

13. 12 · Safe parallelism

Block data races through ownership and borrowing. Shared reads can coexist; conflicting write access needs a valid exclusive capability or the explicit synchronization protocol of a concurrency type.

The catalogs for Atomic, Mutex, Task, and Pending describe intended contracts. Scheduling, task syntax, memory ordering details, GPU access completion, and structured-lifetime mechanisms still need their respective specification and implementation.

14. 13 · FFI First

Provide smooth binding to C, C++, and Python ecosystems. Interoperability should describe ownership, initialization, errors, resource release, and representation at each boundary rather than silently weakening safe-language checks.

Binding generators, calling conventions, supported foreign types, allocator ownership, callback lifetimes, and target-specific ABI coverage remain implementation decisions. The goal does not claim an existing universal foreign interface or automatically safe arbitrary foreign code.

15. 14 · Extensible compiler

Use a compiler architecture that can expand to different backends, including LLVM and MLIR. Preserve enough type, shape, effect, ownership, and target information to support those backends without changing source semantics.

The exact frontend pipeline, intermediate representations, backend interface, lowering passes, extension format, and supported target set remain open. LLVM and MLIR are named architectural directions, not evidence that either has been integrated.

16. 15 · Compiler-first optimization

Favor automatic compiler optimization over requiring developers to perform complex manual tuning. Type, shape, layout, ownership, and effect information should help choose valid native and parallel transformations.

The compiler must preserve observable evaluation order, errors, value results, ownership checks, and explicit cost boundaries. Removing a safety check requires proof that the check cannot fail on that path. Floating-point, synchronization, and target-specific transformations need their own correctness contracts.

AOT and selective JIT provide possible optimization stages. Which transformations run, what runtime facts are specialized, and how optimization effectiveness is measured remain open.
