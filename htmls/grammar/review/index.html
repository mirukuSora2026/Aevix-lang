1. Scope and evidence

Historical design review. The inventory and review counts below describe the initial documentation snapshot. Subsequent 0.2 work implements partial explicit generic inference, trailing defaults and const usize parameters, explicit-capture closures, and scoped CPU parallelism. The current implementation profile records supported behavior and platform evidence.

Two independent reviewers examined declaration, grammar and data-type references. The initial snapshot contained 134 HTML pages and 485 Aevix code blocks, totaling 2,990 code lines including blank lines and comments. One review focused on syntax, examples and parser boundaries; the other on ownership, borrowing, types and cross-reference contracts. Findings were cross-checked before integration.

Review records distinguish actual conflicting statements, missing integration rules and topics already explicitly marked open. The counts above describe the initial snapshot, before corrective examples and new reference pages were added. They are not a claim that a parser accepted every block.

3. Chosen integration rules

  • Array suffixes map to complete Array/Vector types, including mixed fixed/dynamic nesting. Parameter context reserves the final single empty bracket for variadic arguments; whole dynamic-array parameters use complete types.
  • Dynamic array literal construction has a CollectionError Result. Nested sublists participate in one recursive construction, while ordinary Result elements are never silently unwrapped. Context-free nonempty literals default to fixed arrays.
  • Variadic packs copy Copy values and move other values into call-frame temporary ownership. The callee receives read-only access; pack loans cannot escape. Zero arguments are allowed, while spread and named variadics are outside the initial surface.
  • Known mutable-reference/view formal parameters automatically reborrow. Variadic pack elements and ordinary generic T value inputs do not gain that exception after substitution. Explicit consuming intrinsics keep their own contract: the implemented Slice.slice_mut consumes its MutSlice input descriptor.
  • Typed locals may be declared before initialization, with definite-assignment checks and exactly one initialization per immutable path. Const, persist and rsn require initializers.
  • Postfix propagation and ternary selection use one whitespace-independent syntax policy: a unique complete parse is used; multiple complete parses require parentheses. Operator precedence and generic-angle/shift-token handling are centralized.
  • A dangling else attaches to the nearest unmatched if. Unbraced executable single statements remain supported, while declaration bodies require braces.
  • Every case/default still requires its written final break. An earlier return, continue or propagated error may exit normally; the syntactically required unreachable trailing break alone is not diagnosed.
  • Type operands are compile-time operands only for documented built-in intrinsics. They are not general runtime values. This intrinsic rule is separate from function generic arguments, which in 0.2 may be inferred, supplied as a leading explicit portion, or completed by trailing defaults.
  • After import and visibility checks, a full path resolving to distinct module/member declarations is ambiguous at use. No hidden module or longest-prefix priority is introduced.

4. Remaining design work

The initial audit did not count intentionally open features as accidental contradictions. At that snapshot, remaining policy choices included returned/stored reference lifetime notation, custom cleanup hooks and partial-move restrictions, and the minimum OS/libc/deployment matrix. Current release requirements and qualification evidence are now tracked by the implementation profile and installation information; unresolved general lifetime and custom-cleanup design remains separate.

The initial review also listed identifier/literal grammar, numeric annotations, visibility, interface conflicts, generic-method/dynamic eligibility, project/package metadata and backend schemas for further work. Later 0.2 implementation resolved concrete portions of that list: explicit-capture generic callbacks, const usize parameters and trailing defaults are supported. Broader catalog callback APIs, Shape parameters, general Task APIs and GPU execution remain outside the current profile; explicit CPU SIMD and scoped named-worker parallel.for_each are implemented.

No let, auto, fn, uppercase String, old static storage declaration, actual name:Type local declaration or definite statement-semicolon omission was found in the initial positive-example scan. Candidate literal annotations such as 127:i8 are not name-first variable declarations and still need a separate lexical policy.

5. CPU execution requirements

The original selection was AArch64 and x86-64 on macOS and Linux, with Windows deferred at that time. The 0.2 implementation now also includes a Windows x86-64 target; its object/link checks are distinguished from native execution in the current platform status. The shared frontend/AIR pipeline, target-aware LLVM AOT generation and ORC JIT are implemented. Direct Native code generators remain later extension points; current internal runtime interfaces do not constitute a published stable ABI.

Target, Execution, Runtime/ABI, runtime platform/architecture/startup, toolchain, aevix-run and portability-test folders were added without source/header placeholders. Native execution, cross-compilation, target ABI compatibility and foreign-CPU emulation remain separate capabilities. See the execution architecture and the initial i32 main() contract.

6. Validation boundaries

Corrections are checked for HTML structure, duplicate identifiers, local links and anchors, code markup and statement terminators. Independent reviewers rechecked the new ownership rules. Shared CSS and JavaScript remain unchanged. Documentation and folder structure do not constitute a compiler, borrow-checker proof, CPU execution result, GPU result or benchmark.

The original review required native AOT/JIT and ABI checks for every intended CPU/OS combination. Current qualification evidence is recorded separately in the implementation profile. Static HTML checks, cross-generated object files and emulated runs must retain their distinct evidence boundaries.
