1. while and three for forms

Aevix supports while and three forms of for: Range traversal with in, C-style initialization/condition/update, and enhanced traversal with a colon. Every loop header has parentheses. A single executable body statement may omit braces; multiple body statements require braces.

FormHeaderBinding model
Rangefor (int index in indices)Fresh immutable binding for each yielded value.
C-stylefor (mut int index = 0; index < 10; index++)One mutable control binding throughout the loop.
Enhancedfor (char scalar : text)Fresh immutable scalar binding during text traversal.

2. while checks a bool condition before each iteration

int count_to(int limit) {
    mut int count = 0;
    while (count < limit) count++;
    return count;
}

The condition is evaluated on entry and before each later iteration. A false first condition executes the body zero times. The condition must have type bool. Body effects can change values used by the next condition evaluation.

int count_even(int limit) {
    mut int candidate = 0;
    mut int count = 0;
    while (candidate < limit) {
        candidate++;
        if (candidate % 2 != 0) continue;
        count++;
    }
    return count;
}

continue leaves this iteration body and immediately resumes the while condition test. It does not repeat the remaining statements of the interrupted body.

3. Use the existing Range type directly

int sum_indices() {
    Range<int> indices = Range.new(0, 10);
    mut int total = 0;
    for (int index in indices) total += index;
    return total;
}

The loop receives the Range descriptor itself. It does not require converting the range to an array or Vector. The descriptor supplies bounds, direction, inclusion and step magnitude; traversal creates independent cursor state.

The descriptor is a small Copy value with no owned allocation. Copying it does not deep-copy a sequence or secretly mutate another descriptor. No full element count is needed merely to advance through a range.

4. 0..10 and 0..=10 construct Range values

LiteralAPI correspondenceValues
0..10Range.new(0, 10)0 through 9: start inclusive, end exclusive.
0..=10Range.closed(0, 10)0 through 10: both endpoints eligible.
int sum_closed() {
    Range<int> inclusive = 0..=10;
    mut int total = 0;
    for (int index in inclusive) total += index;
    return total;
}

int sum_literal() {
    mut int total = 0;
    for (int index in 0..10) total += index;
    return total;
}

A range literal constructs a descriptor, not a materialized container. The bounds are evaluated once when the descriptor expression is evaluated. Already typed endpoints must agree on the supported integer type; an untyped literal uses its compatible context or the default int type.

Ascending reversed bounds are empty rather than automatically reversed. The half-open 0..0 has no values; the closed 0..=0 has one value.

5. Direction and positive steps come from Range APIs

Result<int, RangeError> sum_every_four() {
    u32 magnitude = 4;
    Range<int> strided = Range.with_step(Range.closed(0, 10), magnitude)?;
    mut int total = 0;
    for (int index in strided) total += index;
    return Result.ok(total);
}

int count_down() {
    Range<int> descending = Range.descending_closed(3, 0);
    mut int total = 0;
    for (int index in descending) total += index;
    return total;
}

The strided range yields 0, 4 and 8; an inclusive bound is included only if it is reachable. The step magnitude is the same-width unsigned type corresponding to the range integer. Zero step is a RangeError; descending direction is represented separately from the positive magnitude.

At an integer maximum or minimum boundary, the range cursor must decide that traversal is complete without an overflowing final increment. An inclusive range ending at the integer maximum is valid. This safe cursor contract does not make ordinary user-written i++ infallible.

The Range API catalog supplies these construction contracts. Full iterator protocol syntax, user-defined stepping and new stride literal notation remain open.

6. C-style for has dedicated initialization and update slots

int c_style_total() {
    mut int index = 0;
    mut int total = 0;
    for (mut int cursor = 0; cursor < 10; cursor++) {
        total += cursor;
        index = cursor;
    }
    return total + index;
}

Initialize the header binding once, evaluate the bool condition, run the body when true, run the update, and repeat the condition test. The loop control binding is visible in its condition, update and body, but unavailable after the for statement ends.

Updating an ordinary header variable requires mut. int cursor = 0 declares an immutable binding just as it would elsewhere; a later cursor++ or cursor += 1 is invalid without mutation permission.

The initialization and update slots may contain the approved declaration or assignment/increment forms. This dedicated use does not make = or += value expressions in general. Empty clauses, comma-separated declarations/updates and declaration-free initializer syntax are not finalized here.

7. Prefix and postfix ++ and -- have different values

FormStored changeExpression value
++valueIncrease by one.The new value.
value++Increase by one.The previous value.
--valueDecrease by one.The new value.
value--Decrease by one.The previous value.
int observe_increment() {
    mut int value = 4;
    int previous = value++;
    int next = ++value;
    return previous + next;
}

These operators require a writable integer place. They are value expressions, including in a for update. Ordinary increments and decrements check overflow and safely stop on arithmetic failure. A failing increment does not store a wrapped value.

Result<i8, IntegerError> checked_increment() {
    mut i8 value = 127;
    i8 previous = checked(value++)?;
    return Result.ok(previous);
}

Here the checked increment returns Err, keeps value at 127, and ? returns that error from the function. Effects completed earlier in a larger expression are not rolled back. This is a design example, not a claim of an executed compiler.

8. Enhanced for reads text as Unicode scalars

int count_scalars(string_view text) {
    mut int count = 0;
    for (char scalar : text) {
        count++;
    }
    return count;
}

char final_scalar(string_view text) {
    mut char last = ' ';
    for (char scalar : text) last = scalar;
    return last;
}

char scalar : text visits Unicode scalar values from a string or string_view. A scalar is not necessarily a user-perceived character or a UTF-8 byte. The final_scalar example deliberately returns a space for an empty input; it is a loop example rather than an absence-handling API.

Text traversal keeps the source owner with its existing owner and reads through a borrow. An existing string_view is already borrowed and is passed directly; no extra & is inserted by the example. Structural mutation or another conflicting access to the traversed storage is disallowed while the traversal loan is active.

This confirmed text behavior does not settle all collection traversal modes. Read-borrow, write-borrow and consuming headers for generic collections need explicit contracts before they are treated as chosen syntax.

9. Bindings, evaluation and source lifetimes

Range and enhanced traversal bind a fresh immutable iteration value on each iteration. A changing iteration value is not reassignment of one immutable binding. The C-style control binding is instead one binding deliberately updated over time.

A header binding exists only inside its loop. It cannot shadow a visible outer local name. A source borrow remains valid only while the source is alive; escaping references to loop-local values or invalidating an active source loan is rejected. Loop-local owning resources are released when their iteration scope ends unless they have moved to a new owner.

Whether mut can qualify a Range/enhanced iteration binding, and how mutable references are exposed for other collections, remain open. This page does not infer write permission from the mere presence of a mutable source.

A Range or enhanced-loop source expression is evaluated once before iteration. Range bounds are not reevaluated each time. The C-style condition and update are different: the condition is evaluated before each body entry and the update after each completed body or continue.

The current Range cursor and text cursor are iteration state; creating or copying a descriptor is not a hidden allocation of all values. A body still pays for the work it explicitly performs, and text traversal decodes scalars from its underlying representation.

These loops express sequential execution. GPU submission, parallel scheduling, Tensor broadcasting or automatic task creation are not implied by ordinary for syntax. AOT and JIT must preserve the same observable control-flow and ownership behavior.

10. Structured exits, update steps and cleanup

Constructbreak;continue;
whileExit the nearest enclosing loop, unless an inner switch is the nearer break target.Leave the body and test the condition again.
Range / enhanced forExit the nearest eligible loop or inner switch target.Leave the body, advance the cursor and begin the next iteration if present.
C-style forExit without running its update clause.Leave the body, run the update clause, then test the condition.
int sum_until_five() {
    mut int total = 0;
    for (mut int index = 0; index < 10; index++) {
        if (index == 2) continue;
        if (index == 5) break;
        total += index;
    }
    return total;
}

break targets the innermost enclosing loop or switch. continue targets the innermost enclosing loop, ignoring an intervening switch as a loop target. Neither keyword uses a numeric depth or label in the accepted grammar. continue outside any loop is invalid.

On continue, resources still owned by the current body scopes are cleaned up in reverse initialization order before the next iteration step. The C-style control binding survives continue. On break, the scopes being exited, including the loop header scope, are left and their current owners cleaned up.

Result<int, IntegerError> sum_checked() {
    mut int total = 0;
    for (int index in 0..10) {
        int next = checked(total + index)?;
        total = next;
    }
    return Result.ok(total);
}

return and Err propagation with ? leave the function scopes, perform normal ownership cleanup, and skip any pending C-style update clause. Only resources actually initialized and still locally owned are cleaned up. An owning returned payload has moved to the caller rather than being destroyed at the exit.

Automatic cleanup is not rollback and is not a new error-return channel. GPU-borrowed resources must remain alive until use completes. Forced safety-stop cleanup remains open. Normal process-lifetime persist cleanup follows reverse successful initialization-completion order after tracked resource uses finish.

11. Rejected loop examples

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

int invalid_immutable_counter() {
    mut int total = 0;
    for (int index = 0; index < 3; index++) total += index;
    return total;
}

The C-style index is immutable, so its update has no write permission.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

int invalid_shadowing(int index) {
    mut int total = 0;
    for (int index in 0..3) total += index;
    return total;
}

The loop binding attempts to hide the visible parameter index. A different name is required.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

void invalid_continue() {
    continue;
}

There is no enclosing loop to continue. These examples specify intended compile-time rejection rather than observed compiler diagnostics.

12. Open loop design decisions

  • do/while, a dedicated infinite-loop keyword, labels and multi-level break/continue.
  • Empty C-style clauses, comma expressions and multiple initializer/update entries.
  • General collection iterator protocol, iterator trait/bounds, consuming iteration, write iteration and user-defined iteration.
  • Inference spelling in loop bindings, destructuring headers and optional mutable Range/enhanced bindings.
  • Borrowed collection header spellings; a future form such as for (&i32 value : &values) is only a proposal.
  • Future slicing syntax remains open. Parsing Rules now specifies range precedence, numeric token boundaries and mixed conditional parsing.

A declaration used as a loop body requires braces. A single ordinary executable body statement may omit them. This is a chosen rule; see body scopes.

The descriptor construction, endpoints, positive steps and costs are documented in Range. Switch explains why an inner case break may exit a switch while its surrounding loop keeps running.
