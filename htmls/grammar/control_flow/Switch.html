1. switch selects a statement branch

Aevix uses switch and case for multi-way statement control flow. Every written case branch and every written default branch must end with an explicit break;. Omitting that terminal break is a compile-time error; automatic fallthrough is excluded.

The switch itself is a statement, not a value-producing expression. Use the ternary operator for conditional value selection and explicit return to deliver a function result. The examples here assign a result inside the selected case, then return it after the switch. Enum payload patterns, ownership modes and exhaustive coverage are specified in Enum Switch.

2. A parenthesized selector and case labels

int score_for_mode(int mode) {
    mut int score = 0;
    switch (mode) {
        case 1:
            score = 10;
            break;

        case 2:
            score = 20;
            break;

        default:
            score = 0;
            break;
    }
    return score;
}

The shown selector is an integer value and the case labels are integer constants. A colon introduces each case body. The switch container uses braces; its branch contents are delimited by labels and the required terminal break. These labels are syntax boundaries, not expression statements requiring a semicolon.

This form establishes numeric case dispatch. Enum selectors additionally support typed named payload patterns and explicit read, modification or consuming modes; see Enum Switch. The empty and payload variant declarations belong to one parent type, documented in Enums.

3. Evaluate the selector once and run the selected branch

The switch selector is evaluated once when execution enters the switch. Its value selects a matching case. If no case matches and a default branch is written, default executes. Only the selected branch body executes; source order does not create a chain of ordinary if conditions.

For scalar dispatch without a matching case or default, the exact accepted behavior remains under the open scalar default policy. These scalar examples include default. For enum dispatch, every variant must instead be covered by a case or by default; missing coverage is a compile-time error.

Automatic numeric promotion, duplicate-label acceptance, range labels, user-defined equality and overlapping patterns are not introduced here. Case constant typing and duplicate diagnostics need a complete selector/type contract.

4. Every branch explicitly ends with break

Branch formChosen requirement
case constant:The branch ends with an explicit break;.
default:If written, the branch also ends with an explicit break;.
Omitted breakCompile-time error; no implicit fallthrough.
Break inside a nested constructExits that inner eligible construct and does not replace the outer branch terminal break.
Branch ending with return or postfix ?Permitted before the required written break; the break remains mandatory, even when unreachable.

The terminal break belongs to the switch branch. A preceding return, a continue targeting an enclosing loop, divergence or Result ? keeps its own control-flow contract. The written terminal break is always required. If it is unreachable, that fact alone produces neither an error nor a warning; no general unreachable-code policy follows. The successful path of ? continues normally to the branch break. There is no chosen fallthrough marker, continue-as-fallthrough behavior or labeled case jump. See case-exit parsing.

5. default handles the fallback when it is written

int small_category(int value) {
    mut int category = 0;
    switch (value) {
        case 0:
            category = 1;
            break;
        default:
            category = 2;
            break;
    }
    return category;
}

default has no case value. Its body follows the same explicit-break requirement as an ordinary case and has its own implicit lexical scope. Scalar default requirements remain open. Enum switches may omit default only when all variants are explicitly covered; external code requires default when hidden private variants cannot be named. Default covers future added variants as well, so those additions do not produce missing-variant diagnostics.

Multiple adjacent empty case labels used to share one body are also open. A label without its own terminal break is not treated as an already approved grouped-case shorthand.

6. break targets the nearest loop or switch

int count_modes() {
    mut int count = 0;
    for (mut int mode = 0; mode < 3; mode++) {
        switch (mode) {
            case 1:
                count += 10;
                break;
            default:
                count += 1;
                break;
        }
        count += 100;
    }
    return count;
}

Each case break exits the inner switch, so count += 100 still runs and the outer loop proceeds. The same keyword outside the inner switch would instead target the nearest loop. The lexical nesting of eligible constructs decides the target.

int inner_loop_then_case_break(int mode) {
    mut int total = 0;
    switch (mode) {
        case 1:
            for (int index in 0..3) {
                if (index == 1) break;
                total += index;
            }
            total += 10;
            break;
        default:
            total = 0;
            break;
    }
    return total;
}

The inner break exits for, then the selected case continues to total += 10 and its own terminal break. An inner-loop break cannot be used as evidence that the surrounding case meets its terminal-break requirement.

7. continue still targets an enclosing loop

continue is a loop operation. If a switch is nested inside a loop, a continue targets the nearest enclosing loop rather than the switch. For C-style for, it performs the loop update before the next condition test; for while it resumes the condition test.

A valid continue inside a case is allowed before its required written terminal break. Its loop resume action and cleanup occur as usual; the now-unreachable terminal break is retained without a diagnostic solely for that unreachability. A return or diverging path follows the same written-break requirement. A successful ? continues through its branch; an Err leaves the function. Neither path removes the source-level terminal-break requirement.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

void invalid_switch_continue(int value) {
    switch (value) {
        case 1:
            continue;
            break;
        default:
            break;
    }
}

Even though a terminal break is shown, continue has no enclosing loop to target. A switch alone is not a loop.

8. Each case has an independent lexical scope

int branch_local_value(int mode) {
    mut int selected = 0;
    switch (mode) {
        case 1:
            int local = 12;
            selected = local;
            break;
        default:
            int local = 3;
            selected = local;
            break;
    }
    return selected;
}

Every case and every default branch has an independent implicit lexical scope. The two local names are allowed because their sibling branch scopes do not overlap. A binding is available in its own branch and nested blocks, but not in another case or after the switch. No binding may shadow an already visible outer local.

An explicit nested block still introduces a deeper ordinary scope. Enum pattern bindings belong to the corresponding case scope along with its body locals. Leaving the branch cleans up resources still owned there in reverse initialization order.

Name scope and loan lifetime remain separate. A reference that escapes a case must still satisfy the source provenance and lifetime rules; a loan of a longer-lived source is not automatically invalid merely because its pattern binding name leaves scope. Case-local owned storage cannot be borrowed past its own lifetime.

Ownership must remain valid on all paths reaching a later use. Moving an owner in one branch does not permit an unconditional use after switch that assumes it remained owned. See enum case scopes for payload binding examples.

9. Leaving switch scopes performs ordinary ownership cleanup

break cleans up resources still owned by the scopes it leaves, in reverse initialization order, exactly once. An explicit nested block that ends before break has already cleaned up its own remaining owners; the switch break must not clean them a second time.

A switch nested inside a loop does not destroy the enclosing loop control binding when the case break exits only the switch. A borrowed view ending does not release the original owner. Moved payloads follow their destination owner.

Result<int, IntegerError> selected_checked_sum(int mode, int value) {
    mut int increment = 0;
    switch (mode) {
        case 1:
            increment = 1;
            break;
        default:
            increment = 2;
            break;
    }
    int result = checked(value + increment)?;
    return Result.ok(result);
}

The checked calculation and error propagation occur after the switch, so every branch clearly keeps its terminal break. The normal return explicitly constructs Ok. Error propagation with ? cleans up function scopes without undoing earlier assignments.

Forced safety-stop cleanup and persist shutdown ordering remain separate. Ordinary switch dispatch does not imply allocation, GPU synchronization or hidden copying.

10. Missing terminal breaks are rejected

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

int invalid_case_break(int mode) {
    mut int value = 0;
    switch (mode) {
        case 1:
            value = 1;
        default:
            value = 2;
            break;
    }
    return value;
}

case 1 has no terminal break. The next label is not an implicit exit or an invitation to fall through.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

int invalid_default_break(int mode) {
    mut int value = 0;
    switch (mode) {
        case 1:
            value = 1;
            break;
        default:
            value = 2;
    }
    return value;
}

default is present but has no terminal break. The closing switch brace does not satisfy the explicit requirement.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

int invalid_inner_break_only(int mode) {
    mut int total = 0;
    switch (mode) {
        case 1:
            for (int index in 0..3) {
                total += index;
                break;
            }
        default:
            total = 0;
            break;
    }
    return total;
}

The shown break belongs to the inner for. case 1 still lacks its own terminal break. These are deliberately invalid design examples, not observed compiler output.

11. Open switch design decisions

  • Scalar default requirements and behavior when no scalar label matches without default; enum exhaustiveness is already required.
  • Additional scalar selector families, scalar constant typing, duplicate constant labels and numeric range labels.
  • Specific built-in Result/Optional pattern spelling beyond the documented enum pattern forms.
  • Guarded patterns, grouped labels, wildcard spelling and richer nested patterns.
  • General unreachable-code policy remains open. The required terminal case/default break is permitted without an error or warning solely because a preceding exit makes it unreachable.
  • A future explicit fallthrough feature, if any; none is currently chosen.
  • Detailed temporary enum selector lifetimes, borrowed-source mode inference, Copy consumption details, and custom cleanup with partial moves.

The accepted enum modes, named field patterns, omitted field patterns, tag-only cases, privacy checks and coverage are collected in Enum Switch. Each case/default scope is already independent. Those chosen rules must not be presented as open.

The chosen C++-style exit behavior is the nearest loop/switch target of break and nearest loop target of continue. See Loops for their loop-specific resume steps. These contracts specify the language design without claiming an implemented compiler or dispatch lowering.
