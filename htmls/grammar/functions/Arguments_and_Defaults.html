1. Ordinary parameters may have trailing defaults

i32 add_offset(i32 value, i32 offset = 1) {
    return value + offset;
}

void use_default() {
    i32 implicit_offset = add_offset(7);
    i32 explicit_offset = add_offset(7, 3);
    return;
}

Omitting offset uses the declared constant 1; supplying it uses the provided value. The first parameter remains required. A default is part of the declaration’s call contract and does not make an ordinary argument an Optional value.

2. After the first default, later ordinary parameters need defaults

i32 encode(i32 first, i32 second = 0, i32 third = 0) {
    return first * 100 + second * 10 + third;
}

void use_trailing_defaults() {
    i32 first_only = encode(1);
    i32 first_two = encode(1, 2);
    i32 all_three = encode(1, 2, 3);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: a required ordinary second parameter follows a default;
i32 invalid_trailing_default(i32 first = 0, i32 second) {
    return second;
}

The rule concerns ordinary parameters. A defaulted ordinary parameter before a variadic parameter is unsupported in the initial rule; required ordinary prefixes remain allowed. An explicit self receiver may not have a default. Default syntax does not create a new implicit receiver.

3. Defaults must be Copy-compatible compile-time constants

const i32 DEFAULT_OFFSET = 3;

i32 configured_offset(i32 value, i32 offset = DEFAULT_OFFSET) {
    return value + offset;
}
RequirementMeaning
Compile-time constantThe value must satisfy the chosen compile-time constant requirement; arbitrary runtime computation is not accepted.
Copy-compatible valueSupplying an omitted argument cannot consume one shared owning default object.
No hidden clone or allocationA default is not a request to allocate a string/container or call an implicit cloning function.
Normal Copy cost remainsCopying larger permitted values can still require work; optimization must preserve behavior.
Complete expression grammarThe full set of admitted constant expressions remains open; simple numeric and named const examples do not define a const-function facility.

The rule does not make Copy an overridable deep-clone hook. Owning string and other non-Copy resource values must be supplied under their explicit ownership APIs rather than silently created by default.

4. Do not execute an arbitrary function to obtain a default

Rejected example. This intentionally violates a chosen rule.

i32 compute_offset() {
    return 1;
}

// Rejected: an ordinary function call is not an allowed default here;
i32 invalid_runtime_default(i32 value, i32 offset = compute_offset()) {
    return value + offset;
}

Even this simple ordinary function body does not acquire compile-time-call status merely because its result looks constant. A future constant-function facility would need a separate decision. Default selection must not introduce an arbitrary runtime side effect or a hidden failure-producing allocation.

5. Use parameter_name = expression at the call site

void use_named_arguments() {
    i32 positional = encode(1, 2, 3);
    i32 named = encode(first = 1, second = 2, third = 3);
    i32 reordered = encode(third = 3, first = 1, second = 2);
    i32 mixed = encode(1, third = 3, second = 2);
    i32 skipped_default = encode(first = 1, third = 3);
    return;
}

This uses encode from the trailing-default example. The first four calls bind first = 1, second = 2 and third = 3. The final call omits second, so it uses 0. Named arguments can appear in any parameter order, but all positional arguments must appear before the first named argument.

Call-site names are parameter bindings, not local assignments or named-field construction. They do not declare local variables, change parameter mutability or bypass the function’s receiver/borrow contract.

6. Evaluate explicit expressions in written source order

i32 record_digit(&mut i32 trace, i32 digit) {
    *trace = *trace * 10 + digit;
    return digit;
}

void demonstrate_source_order() {
    mut i32 trace = 0;
    i32 result = encode(
        third = record_digit(&mut trace, 3),
        first = record_digit(&mut trace, 1),
        second = record_digit(&mut trace, 2)
    );
    return;
}

The written expressions run in the order third, first, second: trace becomes 312. Their results are matched to parameter names, so result is 123. These numbers illustrate the specified behavior; they are not an observed Aevix execution result.

Each expression runs once. Mapping happens at compile time and does not reorder side effects into declaration order. Each record_digit call finishes its temporary exclusive loan before the next begins. Named arguments do not weaken ordinary overlapping-borrow checks.

7. Argument labels do not change value passing

string relay(string value) {
    return value;
}

string move_named_string(string original) {
    string result = relay(value = original);
    return result;
}

The owning string moves whether passed positionally or by name. No literal-to-owner conversion or automatic clone occurs. Compatible borrowed arguments are likewise passed with their existing reference/view contracts.

If evaluating an earlier argument has effects and a later operation fails, naming arguments does not create rollback. The established failure and Result propagation boundaries still govern the enclosing expression.

8. Reject unknown, duplicate and misordered arguments

Rejected example. This intentionally violates a chosen rule.

// Rejected: fourth is not a parameter of encode;
void unknown_name() {
    i32 result = encode(first = 1, fourth = 4);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: first is already supplied positionally;
void positional_and_named_duplicate() {
    i32 result = encode(1, first = 2);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: a named argument is followed by a positional one;
void positional_after_named() {
    i32 result = encode(first = 1, 2);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: the same named parameter is supplied twice;
void repeated_named_argument() {
    i32 result = encode(first = 1, second = 2, second = 3);
    return;
}

Every required ordinary parameter must also be supplied. All mapping and type checks happen before execution of a valid call; the compiler does not run malformed calls and then discover missing names.

9. Public parameter names are part of the API

Callers can depend on a public function’s parameter names. Renaming a public parameter can break named callers even if its type and positional order stay unchanged. Documentation and compatibility decisions must therefore treat those names as part of the callable API.

Importing a function does not rename its parameter names. The language currently provides no import aliases. Re-exporting the same original function preserves the underlying declaration and its call contract. Ordinary public parameter names remain part of named calls; the variadic pack itself is not a supported named argument.

10. Defaults and names do not add a hidden ranking score

Defaults can make a candidate callable, and named arguments can rule out candidates with incompatible parameter names. But the number of omitted defaults is not a ranking criterion. Two otherwise equally suitable candidates remain ambiguous even if one uses fewer defaults.

Return types do not distinguish duplicate parameter signatures. Different original modules’ function sets remain separate before argument matching. See default-count ambiguity and module-origin boundaries for complete examples.

11. Default and variadic boundaries

Rejected example. This intentionally violates a chosen rule.

// Rejected: defaults before a variadic pack are unsupported;
void invalid_default_then_pack(i32 prefix = 0, i32 values[]) {
    return;
}

A required ordinary prefix may precede the final pack. Repeated arguments use positional expressions; supplying the pack by name and spreading an array are unsupported initially. Ordinary named arguments still follow the positional-first rule. A mutable variadic binding is also unsupported; use explicit mutable array or MutSlice parameters for modification.

  • The complete constant-expression grammar and a possible compile-time function facility remain open.
  • Generic type-parameter defaults and further field-default policies are not introduced by ordinary function parameter defaults.
  • Variadic storage/ownership and fixed-versus-variadic ties are now chosen; see their dedicated references rather than treating them as open.
