1. Share a function name only through valid overloads

i32 select(i32 value) {
    return value;
}

i64 select(i64 value) {
    return value;
}

i32 select(i32 first, i32 second) {
    return first + second;
}

void use_selection() {
    i32 small = select(10);
    i64 wide = 20;
    i64 retained = select(wide);
    i32 sum = select(1, 2);
    return;
}

Within one original module, parameter types or counts distinguish overloads. The i32 literal default selects the first one-argument form, an already typed i64 selects the second, and two arguments select the third. Ordinary parameter permissions remain part of matching; overload resolution cannot manufacture a write capability.

2. Types, functions and constants share one module namespace

Rejected example. This intentionally violates a chosen rule.

// Rejected: a constant and a function cannot share this module name;
const i32 scale = 2;

i32 scale(i32 value) {
    return value;
}

Function overloading is a specific exception for differing parameter signatures. It does not permit a type or constant to occupy that same declaration name. Public/private affects access, not the existence of a distinct namespace for these three declaration categories.

Parameter names help named calls but do not create a different parameter type/count signature. An otherwise identical function cannot be redeclared merely by renaming its arguments.

3. Return type alone cannot distinguish declarations

Rejected example. This intentionally violates a chosen rule.

// Rejected: these parameter signatures are identical;
i32 convert(i32 value) {
    return value;
}

f64 convert(i32 value) {
    return 1.0;
}

Writing a receiving variable with type i32 or f64 does not make this overload set legal. Return-context generic inference fills unresolved type parameters of an otherwise matching candidate; it does not authorize return-only overloading or replace an argument-inferred type.

4. Apply the chosen preferences in order

StageChosen behavior
Resolve declaration originDifferent original modules remain separate overload families. Ambiguous imported short names must be qualified first.
Map argumentsCheck argument names/positions, ordinary counts, available defaults, passing modes, generic substitutions and declared requirements.
Use typed inputsNarrow candidates using already typed argument information without implicit numeric conversion.
Compare untyped numeric literalsPrefer a compatible candidate matching i32 integer or f64 real defaults before the generic/non-generic tie rule.
Break an otherwise equal generic tiePrefer a non-generic candidate when suitability is otherwise equal.
Break an otherwise equal pack tieAfter the preceding type, literal and generic/non-generic preferences, prefer a fixed-parameter candidate over a variadic one.
Reject a remaining tieNo source-order, import-order, guessed-width or default-count fallback selects a winner.

Explicit type arguments request generic candidates. This is compile-time selection; expressions are not run speculatively to discover which overload would succeed. No additional numeric conversion ranking or arbitrary weighted matching score is introduced.

5. Typed evidence precedes a literal’s default

i32 choose_pair(i32 first, i32 second) {
    return first;
}

i64 choose_pair(i64 first, i64 second) {
    return first;
}

void use_later_typed_argument() {
    i64 wide = 40;
    i64 result = choose_pair(10, wide);
    return;
}

wide rules out the i32 candidate because typed i64 does not implicitly convert. The remaining i64 parameter context accepts the untyped integer literal. The earlier source position of 10 cannot force a wrong i32 decision.

This selection order changes no evaluation order: the first argument is evaluated before the second. Static type information is available to the compiler independently of those runtime side effects.

6. Prefer default numeric types before genericity

i32 numeric(i32 value) {
    return value;
}

i64 numeric(i64 value) {
    return value;
}

f32 real_numeric(f32 value) {
    return value;
}

f64 real_numeric(f64 value) {
    return value;
}

void use_literal_defaults() {
    i32 whole = numeric(10);
    f64 real = real_numeric(0.5);
    return;
}
i64 prefer_literal_default(i64 value) {
    return value;
}

T prefer_literal_default<T>(T value) {
    return value;
}

void default_before_generic_tie() {
    i32 selected = prefer_literal_default(10);
    return;
}

The last call chooses the generic T = i32 candidate because it matches the integer default. The non-generic i64 candidate does not win merely for being non-generic; that preference applies only after literal suitability is otherwise tied.

7. Prefer a concrete function only for equal suitability

i32 identity(i32 value) {
    return value;
}

T identity<T>(T value) {
    return value;
}

void use_generic_ties() {
    i32 concrete = identity(10);
    i32 generic = identity<i32>(20);
    return;
}

The ordinary call has an equally suitable concrete i32 function and a generic i32 specialization, so the non-generic form wins. The explicit angle-bracket call chooses the generic family directly. In 0.2, an explicit function generic argument list may supply a leading portion; inference or trailing defaults must resolve the remaining parameters. See the implemented generics profile.

8. Do not guess when no default candidate wins

Rejected example. This intentionally violates a chosen rule.

i8 small_number(i8 value) {
    return value;
}

i16 small_number(i16 value) {
    return value;
}

// Rejected: both accept 10, neither matches the i32 default;
void ambiguous_numeric_literal() {
    rsn result = small_number(10);
    return;
}

There is no smallest-width preference. Supply an already typed argument or otherwise remove the ambiguity. If only one compatible non-default candidate remains, contextual literal typing can use that candidate; the rule does not forbid every non-i32 numeric parameter.

void resolve_with_a_type() {
    i8 value = 10;
    i8 result = small_number(value);
    return;
}

9. Omitting fewer defaults is not a preference

Rejected example. This intentionally violates a chosen rule.

i32 choose_default(i32 value) {
    return value;
}

i32 choose_default(i32 value, i32 offset = 0) {
    return value + offset;
}

// Rejected: both match equally; the omitted-default count is not ranked;
void ambiguous_default_count() {
    i32 result = choose_default(10);
    return;
}

Both functions have distinct declared parameter counts and may coexist, but the one-argument call is ambiguous. No rule prefers the candidate that uses zero default arguments. A two-argument call can select the second function directly. See Arguments and Defaults.

10. Resolve a module family before overload matching

Assume these independent modules each expose a public function named choose. The code blocks are separate module fixtures, not declarations to concatenate into one module.

Module calculations.integer

public i32 choose(i32 value) {
    return value;
}

Module calculations.real

public f64 choose(f64 value) {
    return value;
}

Consumer: qualification identifies the intended family

import calculations.integer { choose };
import calculations.real { choose };

void use_qualified_calls() {
    i32 first = calculations.integer.choose(10);
    f64 second = calculations.real.choose(0.5);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected in that consumer: different originating modules share choose;
void invalid_pooled_set() {
    i32 result = choose(10);
    return;
}

The argument cannot make the ambiguous short name legal by selecting one module’s function. The two original overload families are never pooled. A local family and a different imported family follow the same rule; the local name does not silently absorb or outrank the imported family.

Repeated access to the same canonical original declaration through re-export routes does not create competing copies of that declaration. Type and function identity follow the original declaration; qualification permission still follows the chosen import and re-export routes.

11. Names participate in candidate matching, not signature identity

Each candidate maps named arguments to its declared parameters. Unknown names, duplicate bindings and a positional argument after a named one invalidate that call form. Public parameter names are part of the callable API because changing them changes valid named calls.

Functions with the same parameter types/count cannot become distinct overloads merely through different parameter names. The source evaluation order of named argument expressions is preserved even when their selected parameter positions differ.

12. Apply fixed-versus-variadic preference only as the final tie-break

i32 choose_pack(i32 value) {
    return 1;
}

i32 choose_pack(i32 values[]) {
    return 2;
}

void fixed_wins_equal_tie() {
    i32 selected = choose_pack(10);
    return;
}

Both candidates accept the i32 argument and both are non-generic. The final pack tie-break prefers the fixed-parameter function, so selected is 1 in the specified design. This is not an observed Aevix execution.

T generic_or_pack<T>(T value) {
    return value;
}

i32 generic_or_pack(i32 values[]) {
    return 2;
}

void generic_preference_still_runs_first() {
    i32 selected = generic_or_pack(10);
    i32 explicit_generic = generic_or_pack<i32>(10);
    return;
}

The ordinary call chooses the non-generic pack candidate before the final fixed-versus-variadic tie-break is reached; selected is 2. The explicitly typed call selects the generic function and returns 10. Numeric literal preferences also remain earlier than either tie-break.

The count of omitted ordinary defaults remains unranked. Different originating modules remain separate overload families, canonical duplicate re-exports do not create extra candidates, and a remaining tie is still a compile-time ambiguity.

  • Implicit user-defined conversions, extension-method lookup and further interface method conflicts are not introduced by these free-function rules.
  • The pack rule does not enable aliases, expose private declarations, import unselected siblings, permit named/spread packs or settle foreign varargs ABI.
