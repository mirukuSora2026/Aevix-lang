1. Build on the existing function contract

Aevix writes the return type before the function name and the parameter type before each parameter name. Values copy when their type is Copy and otherwise move; shared and exclusive borrows remain explicit capabilities. These pages extend that contract with the function features chosen after the initial declaration reference.

Design reference. Chosen rules are documented here; open details are explicitly separated. The examples are language-design illustrations, not results from an implemented parser, compiler, borrow checker or runtime.

3. Chosen rules at a glance

FeatureChosen rule
Generic declarationT identity<T>(T value); type parameters follow the function name.
Constraintswhere T implements Copy follows the parameter list and precedes the body; comma-separated requirements all apply.
InferenceUse argument information first; a declared destination may fill only still-unresolved type parameters.
OverloadingParameter types or counts must differ; return type alone cannot distinguish overloads.
Default argumentsTrailing ordinary parameters may use Copy-compatible compile-time constants.
Named argumentsUse name = expression; positional arguments precede named ones.
Variadic argumentsOne final T values[] parameter; zero or more homogeneous arguments copy or move into a call-frame-owned pack.

Module-level types, functions and constants share a declaration namespace. Different originating modules do not contribute a combined overload set merely because their imported functions have the same short name.

4. Read the type and call intent directly

T identity<T>(T value) {
    return value;
}

i32 add_offset(i32 value, i32 offset = 1) {
    return value + offset;
}

void receive(i32 values[]) {
    return;
}

void demonstrate() {
    i32 inferred = identity(10);
    i32 explicit_type = identity<i32>(20);
    i32 adjusted = add_offset(offset = 3, value = 7);
    receive(1, 2, 3);
    return;
}

The two identity calls select T = i32. add_offset maps named arguments at compile time; their source order need not match parameter order. The variadic example uses a read-only Slice-like view over a temporary pack. Elements follow ordinary Copy-or-move passing; the callee cannot grow, consume or export the pack storage.

5. Keep ownership, cost and evaluation visible

Function features do not add implicit numeric casts, owner clones, boxing or device transfers. Ordinary owning arguments still move. Default values cannot allocate or call arbitrary runtime functions. A Copy value can still have a real copy cost; compile-time selection does not make every operation free.

Explicit argument expressions run once, left to right in source order. Reordering named arguments changes that evaluation order, not which parameter name each result supplies. Overload resolution and generic checking do not execute argument expressions to decide which candidate works.

6. Closed variadic rules and remaining decisions

Variadic packs allow zero or more same-typed arguments, use ordinary Copy/move ownership and provide a call-bounded read-only view without hidden heap allocation for the pack. Mutable pack binding, named variadic binding, spread and ordinary defaults before a pack are unsupported initially. An otherwise tied fixed-parameter overload wins only after the existing type/literal/generic preferences.

  • Ordinary dynamic array parameters, returns and generic arguments use canonical Vector types; fixed value parameters move Array owners and whole-array borrows use explicit &Array/&Vector types.
  • The complete constant-expression grammar, generic type-constructor inference, lifetime/Shape parameters and further method/dynamic eligibility rules remain open.
  • Physical ABI, frame limits and detailed general element-cleanup ordering need separate specification. Dynamic array literal allocation errors use the selected CollectionError carrier.
