0.2 implementation update. Function generic lists now support trailing defaults, const usize parameters, and partially explicit argument lists completed by inference or defaults. See the implemented generics profile.

1. Name the function before its type parameters

T identity<T>(T value) {
    return value;
}

void use_identity() {
    i32 first = identity(10);
    i32 second = identity<i32>(20);
    return;
}

Capital T is a type parameter declared by the function’s name-following angle brackets. Its scope includes the return type, parameter types, requirements and body. A call may infer its generic arguments, explicitly supply a leading portion, or supply the complete ordered list. Remaining parameters must be resolved by argument information, compatible destination context, or declared trailing defaults. The normal successful return is still written with return; the body’s final expression is not an implicit return.

2. Match multiple type parameters in order

T first_of<T, U>(T first, U second) {
    return first;
}

void use_first_of() {
    i32 inferred = first_of(10, true);
    i32 explicit_types = first_of<i32, bool>(20, false);
    i32 partial_types = first_of<i32>(10, true);
    return;
}

T corresponds to the first explicit type argument and U to the second. Each type parameter must have one uniquely determined, consistent type. The second value parameter is an ordinary value argument: its ownership follows its type even though this simple function does not return it.

In first_of<i32>(10, true), the explicit prefix fixes T as i32 and the second value argument infers U as bool. Writing a shorter list is valid when its remaining parameters can be resolved. Wildcard placeholders and skipping a middle parameter are unsupported. Trailing generic defaults are also supported; they fill parameters that remain unresolved after inference.

T keep<T, Marker = bool>(T value) {
    return value;
}

void use_generic_default() {
    i32 result = keep<i32>(10);
    return;
}

Marker has no value argument in this declaration, so its declared bool default completes the call. Defaults do not override types fixed by explicit arguments or inference.

3. Place where after ordinary parameters

T copy_value<T>(&T value) where T implements Copy {
    return *value;
}

void use_copy_value() {
    i32 original = 7;
    i32 duplicate = copy_value(&original);
    i32 retained = original;
    return;
}

The where clause comes after the closing parenthesis of the parameter list and before the function body. Copy applies to T, not merely to the shared reference &T. This permits returning a copied pointee without moving it out of borrowed storage. original remains usable.

The receiver and parameter access contracts still matter: a requirement does not grant mutation through a shared borrow, create a clone operation or prolong the source lifetime.

4. Every comma-separated requirement must hold

interface Leveled {
    public i32 get_level(&Self self);
};

i32 copied_level<T>(&T value)
    where T implements Copy, T implements Leveled {
    T duplicate = *value;
    return duplicate.get_level();
}

T copied_first<T, U>(&T first, &U second)
    where T implements Copy, U implements Copy {
    U inspected = *second;
    return *first;
}

Repeat the subject for each requirement: where T implements Copy, T implements Leveled, or separate subjects such as T and U. Commas express conjunction; they are not alternatives and do not imply a default implementation. Newlines in the examples do not move the where clause from its selected position.

The same known Copy distinction applies to generic containers: a requirement on T does not automatically make a containing struct or enum Copy. A type may combine its own capability list with constraints, as in struct Pair<T> implements Copy where T implements Copy. The implements list precedes where; the two clauses apply to different types.

5. Check the body against its declared contracts

A generic body may use the operations valid for every permitted argument: ordinary ownership transfer and borrowing, statically known types, and the capabilities guaranteed by its declared requirements. It cannot rely on an extra method merely because one concrete caller happens to provide it.

Rejected example. This intentionally violates a chosen rule.

// Rejected: no Leveled requirement makes get_level available on T;
i32 missing_contract<T>(&T value) {
    return value.get_level();
}

AOT or JIT specialization must preserve these source-level validity rules. The same declaration cannot become legal only because one compilation path happens to know a convenient concrete type. The 0.2 compiler creates canonical concrete specializations after checking the generic contract. AOT and JIT use that same source validity check; specialization cannot supply a capability absent from the declaration.

6. Resolve typed arguments before literal defaults

T first_of_same<T>(T first, T second) {
    return first;
}

void use_typed_evidence() {
    i64 wide = 40;
    i64 first = first_of_same(10, wide);
    i64 second = first_of_same(wide, 20);
    return;
}

The typed i64 argument supplies T = i64 in either source position. The untyped integer literal can then match that expected numeric type. The compiler must not fix the earlier literal to i32 before collecting the later typed argument’s information.

This is type checking, not expression evaluation order. Argument expressions still execute left to right in source order. The compiler does not execute later arguments early to obtain their static types.

7. Use a destination only to fill unresolved parameters

enum ExampleError {
    Invalid;
};

Result<T, E> success<T, E>(T value) {
    return Result.ok(value);
}

void use_destination() {
    Result<i32, ExampleError> result = success(10);
    return;
}

The input fixes T as i32. E has no argument source, so the declared destination Result<i32, ExampleError> supplies ExampleError. The function’s own declared return type provides the constructor context for Result.ok; there is no implicit wrapping return.

Rejected example. This intentionally violates a chosen rule.

// Rejected: rsn supplies no destination error type for unresolved E;
void unresolved_error_type() {
    rsn result = success(10);
    return;
}

No arbitrary default error type is invented. A declared destination can complete success<i32>(10) with E = ExampleError; success<i32, ExampleError>(10) supplies both explicitly. A declaration may instead provide a trailing default, such as success<T, E = ExampleError>.

8. A destination cannot replace an inferred type

Rejected example. This intentionally violates a chosen rule.

// Rejected: identity(10) has T = i32 before destination checking;
void incompatible_destination() {
    f64 result = identity(10);
    return;
}
void explicit_numeric_context() {
    i64 result = identity<i64>(10);
    return;
}

Explicit i64 gives the untyped integer literal its parameter context. It is not an implicit conversion of an already typed i32 variable. If input evidence has already established a type, a different receiving variable type cannot revise it. Borrowing and move checks also remain unchanged.

9. Copy, move and borrows stay type dependent

string relay_string(string original) {
    string transferred = identity(original);
    return transferred;
}

The existing owning string argument moves into identity and moves back through the returned value. This example receives an already owned string; it does not silently allocate from a text literal. A text literal is a string_view under the current text contract, and making an owning string requires its explicit fallible constructor.

The absence of a Copy bound does not prohibit an ordinary value transfer. It prevents assuming that T can be duplicated. Borrowed T values retain the source permissions and lifetime; generic code does not erase those facts.

10. Reject missing arguments and conflicting evidence

Rejected example. This intentionally violates a chosen rule.

// Rejected: Missing has no argument source, destination source, or default;
T keep_with_extra<T, Missing>(T value) {
    return value;
}

void unresolved_remaining_parameter() {
    i32 result = keep_with_extra<i32>(10);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: already typed arguments disagree about the same T;
void conflicting_arguments() {
    i32 narrow = 1;
    i64 wide = 2;
    i32 result = first_of_same(narrow, wide);
    return;
}

Rejected example. This intentionally violates a chosen rule.

// Rejected: owning string is not Copy;
string invalid_copy(string original) {
    return copy_value(&original);
}

These blocks use the earlier declarations on this page. The rejected cases were checked with the 0.2 compiler; the messages may change without changing the stated failure reason. A partial list alone is not an error: first_of<i32>(10, true) is accepted.

11. Keep function inference separate from type construction

The selected inference rules apply to generic function calls. Generic type uses may omit trailing arguments that have declared defaults, according to the generic type reference. This is distinct from inferring an arbitrary container type from named-field initializer values.

  • Leading explicit function arguments, inference, trailing generic defaults, and const usize parameters are implemented. See the 0.2 generics profile.
  • Wildcard placeholders, arbitrary const-parameter types, Shape parameters, lifetime parameter syntax, higher-ranked bounds, and associated-type constraints remain outside this profile.
  • Generic functions and methods specialize statically. A generic method is not callable through a dyn view. Generic FFI layout and future shared-code strategies are not guaranteed by this syntax.
