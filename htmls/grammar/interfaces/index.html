1. One contract, several implementing types

An interface declares behavior. A struct or enum declares implements to satisfy that contract. Required methods, shared default bodies, receiver permissions and explicit ownership remain visible in the source.

Design reference. These pages record chosen Aevix rules. Open language policies are identified separately; examples do not demonstrate an implemented compiler or runtime.

3. Chosen rules at a glance

FormMeaning
interface LeveledA behavior contract; it does not declare the layout of every implementing value.
implements LeveledA struct or enum supplies the contract’s required methods and may use defaults.
&Self selfA shared receiver whose Self resolves to the implementing type.
overrideRequired when replacing an existing interface default body.
&dyn LeveledAn explicit shared dynamic view; ownership stays with its source.
Box<dyn Leveled>An owning dynamic interface value retaining the concrete payload’s cleanup information.

Implementing several interfaces uses a comma-separated implements Named, Leveled list. Conflicting same-name, same-signature default methods require an explicit replacement; interface order never selects a winner.

4. A required method and a replaced default

interface Leveled {
    public i32 get_level(&Self self);

    public bool is_beginner(&Self self) {
        return self.get_level() < 10;
    }
};

struct User implements Leveled {
    i32 level;

    public User new(i32 initial_level) {
        return User { level = initial_level };
    }

    public i32 get_level(&User self) {
        return (*self).level;
    }

    public override bool is_beginner(&User self) {
        return self.get_level() < 5;
    }
};

User user = User.new(7);
bool beginner = user.is_beginner();

User implements the required read method and explicitly replaces the default predicate. The call uses the concrete User implementation, so beginner is false at level 7. The method call automatically creates the shared borrow demanded by its self parameter; it does not clone user.

5. Choose the access and dispatch mode

Receiver formDispatchOwnership and cost
Concrete user.method()Static by default.Receiver declaration determines read borrow, write borrow or value passing.
&dyn InterfaceRuntime selection for eligible methods.Shared loan; no allocation or clone introduced by creating the view.
&mut dyn InterfaceRuntime selection for eligible methods.Exclusive loan; ordinary mutable storage and compatible borrows are required.
Box<dyn Interface>Runtime selection for eligible payload methods.Owns the concrete value; explicit Box construction accounts for allocation.

Static dispatch is the language default, not a guarantee that every interface abstraction is free on every backend. Dynamic calls are a deliberate runtime selection mechanism. No CPU/GPU transfer or automatic GPU support follows from implementing an interface.

6. Open decisions and related reference

  • 0.2 supports static generic methods and dynamic calls to eligible nongeneric methods with a borrowed self receiver. Methods requiring a concrete Self value and generic methods remain unavailable through dyn. Dynamic by-value receivers, associated types and interface inheritance remain outside the profile.
  • Concrete generic interfaces such as &dyn Reader<i32> are supported when their methods are dynamically eligible. A stable interface ABI, downcasting and device execution are outside this profile.
  • Generic function syntax and comma-separated where requirements are defined in generic functions. The 0.3 override plan hardens invalid modifier placements without adding class inheritance.
