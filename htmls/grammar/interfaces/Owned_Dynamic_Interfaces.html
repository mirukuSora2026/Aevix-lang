1. Own a value behind a dynamic contract

0.2 availability: the owning wrapper requires import memory { Box }; before declarations. The interface itself must also be visible under the normal module rules. Box is not an automatically provided type; see the implemented value profile.

Box<dyn Interface> owns a concrete implementing payload. Dynamic method selection is independent of that ownership: the box keeps the payload alive, while the interface restricts the visible method contract.

Explicit cost. Creating a Box accounts for allocation through its Result-returning constructor. Converting an existing Box to dyn moves its ownership without another allocation or payload clone.

This uses the established Box API; it does not introduce a special infallible allocation syntax. Hidden references inside the payload retain their source lifetime restrictions.

2. Use the existing fallible Box constructor

Result<Box<dyn Leveled>, InputError<User>> make_user(i32 requested_level) {
    Box<User> concrete = Box.new(User.new(requested_level))?;
    Box<dyn Leveled> owner = Box.into_dyn(concrete);
    return Result.ok(owner);
}

User and Leveled are the declarations in Interface Contracts. Box.new(User.new(...)) returns Result<Box<User>, InputError<User>>. The enclosing function uses that exact error type, so ? can forward allocation failure. The normal successful path explicitly returns Result.ok(owner).

On the documented constructor failure, InputError retains the unused User input. The conversion runs only after construction succeeds. The owning allocation is explicit; neither Type.new nor an interface default silently introduces it.

Rejected example. This intentionally violates a chosen rule.

// Rejected: Box.new returns Result, not a bare Box;
Box<User> concrete = Box.new(User.new(7));

3. Convert with Box.into_dyn explicitly

PropertyRule

TargetThe declared destination Box<dyn Interface> supplies the interface in this chosen form.
OwnershipThe source box moves; its binding cannot be reused afterward.
Allocation and copyingNo additional allocation or payload clone is introduced.

Borrow provenanceHidden payload references keep their original lifetime restrictions.
// This fragment assumes a valid owned Box<User> named concrete;
Box<dyn Leveled> owner = Box.into_dyn(concrete);

The explicit call replaces an implicit target-type conversion. It does not make a non-implementing T compatible. This documented conversion is not an automatic CPU/GPU transfer. Exact metadata representation is left to a later ABI decision.

An untyped destination such as rsn owner does not provide the selected interface by itself. Additional generic arguments or inference routes for choosing among multiple interfaces have not been designed.

4. Call through the owner or an explicit view

// This fragment assumes a valid Box<dyn Leveled> named owner;
bool automatic = owner.is_beginner();

&dyn Leveled view = Box.as_ref(&owner);
bool explicit_view = view.is_beginner();

The default call reaches the owned payload and creates the borrow required by the method’s self parameter. The explicit form uses Box.as_ref to obtain a shared interface view first. Both preserve ownership in owner and use the same eligible dynamic implementation.

The owner expression is evaluated once. There is no hidden cloning, ownership extraction or additional box allocation. Automatic payload method access does not separately settle general field auto-dereference, wrapper forwarding or name-collision rules.

5. Mutable calls need an exclusive payload loan

// This fragment assumes Counter and CounterState from the borrowed-view page;
Result<Box<dyn Counter>, InputError<CounterState>> make_counter(i32 initial_value) {
    Box<CounterState> concrete = Box.new(CounterState.new(initial_value))?;
    mut Box<dyn Counter> owner = Box.into_dyn(concrete);

    owner.write(2);
    {
        &mut dyn Counter view = Box.as_mut(&mut owner);
        view.write(3);
    }

    return Result.ok(owner);
}

The owner’s mut binding grants the ordinary write permission needed for automatic exclusive borrowing and Box.as_mut. Each call still obeys overlapping-loan checks. The view mutates the existing boxed payload; ending its loan does not destroy it.

Inside an active borrowed view, extracting, moving or replacing the owner in a way that invalidates the view is rejected. Shared access cannot be upgraded simply because the outer container supports a write API.

6. Preserve the actual payload’s cleanup obligation

Moving into a dynamic box transfers the existing ownership obligation. When the final owner ends normally, the actual concrete payload is cleaned up exactly once and its matching storage is released. An interface view does not replace that obligation with only the statically visible interface methods.

Returning the box transfers its responsibility to the caller. Borrowed interface views never keep a dropped owner alive by themselves. Normal cleanup uses the established reverse-initialization rule for current owners, including Result error returns; borrowed device work must also satisfy resource-completion contracts.

Owning a struct containing borrowed fields does not make those fields process-lifetime references. The compiler must preserve their source constraints through the erased owner. Box ownership is not a way to evade borrow escape checks.

7. Ownership does not make every method dynamically callable

A Box-owned interface has the same explicitly limited dynamic method surface. Merely owning the payload does not turn a value-returning Self method into a dynamically available operation or authorize a by-value self method through a shared payload view.

The generic Box.into_inner API for a known T cannot be assumed to yield an unknown erased concrete value from every Box<dyn Interface>. Extracting the hidden type, downcasting and dyn-consuming self methods still need separate rules.

8. Reject a reused moved box

Rejected example. This intentionally violates a chosen rule.

// Rejected: concrete was moved by into_dyn;
Result<Box<dyn Leveled>, InputError<User>> invalid_reuse(i32 requested_level) {
    Box<User> concrete = Box.new(User.new(requested_level))?;
    Box<dyn Leveled> owner = Box.into_dyn(concrete);
    &User stale_view = Box.as_ref(&concrete);
    return Result.ok(owner);
}

Other ordinary errors remain: a missing interface implementation, a live incompatible loan, a non-mutable owner used for an exclusive view, a mismatched Result error type or a payload containing an escaping reference. These are design-level rejections; diagnostic codes are not claimed.

9. Open owning-dynamic rules and related reference

  • Concrete metadata layout, allocator/ABI representation and downcast operations remain open.
  • Erased payload extraction, consuming dyn receivers and their interaction with partial moves or custom cleanup remain open.
  • Shared/Weak dynamic ownership, wrapper call collisions and generalized automatic forwarding remain open.
  • Dynamic conversion to a concrete generic interface is supported when the owned type implements that specialization and its called methods are eligible. Device eligibility and a stable foreign representation remain outside the 0.2 profile.
