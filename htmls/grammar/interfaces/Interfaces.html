1. Declare a contract explicitly

An interface groups callable behavior rather than a concrete field layout. Its signatures specify argument types, return types and receiver passing modes. A declaration with no body is a required method; a declaration with a body is an available default.

interface Leveled {
    public i32 get_level(&Self self);

    public bool is_beginner(&Self self) {
        return self.get_level() < 10;
    }
};

Interface methods in these examples are explicitly public. Complete omitted-visibility rules for interface members are not established here. Non-void bodies use an explicit return, just like ordinary functions.

2. Self is a type; self is a parameter

DeclarationMeaning
&Self selfRead borrow of the actual implementing type.
&mut Self selfExclusive write borrow of the actual implementing type.
Self selfBy-value receiver: Copy values copy, other values move.

Capital Self resolves to the whole implementing struct or enum. In a User implementation, &Self self matches &User self. Lowercase self is the receiver variable. Matching checks the resolved argument and return types as well as the borrowing mode.

A receiverless type function and a self method remain distinct. Interface use does not automatically add a self parameter or rewrite a value receiver into a read loan. The scope of Self outside interface declarations is still open.

3. Implement required methods normally

struct User implements Leveled {
    i32 level;

    public User new(i32 initial_level) {
        return User { level = initial_level };
    }

    public i32 get_level(&User self) {
        return (*self).level;
    }
};

User user = User.new(7);
bool beginner = user.is_beginner();

This User supplies the required method and inherits the default is_beginner, so level 7 is beginner here. A required method implementation uses the ordinary method declaration; it does not require override because no existing body is being replaced. Missing a required implementation or changing its receiver/return contract is a compile-time error.

Inside the concrete type, private fields may be accessed through (*self).field. Callers use the public contract and do not gain access to those private fields.

4. Default bodies depend on the contract

A default may call behavior declared by its interface, including required methods, and use values available under its parameter permissions. It cannot assume a particular implementing struct field exists. This keeps the default meaningful for both structs and enums.

Rejected example. This intentionally violates a chosen rule.

// Rejected: an interface has no concrete level field;
interface InvalidDefault {
    public i32 read_level(&Self self) {
        return (*self).level;
    }
};

For the valid Leveled default, self.get_level() calls the actual implementation under the selected static or dynamic call mode. A default body does not bypass an override or secretly clone its receiver.

5. Replacing a default requires override

struct User implements Leveled {
    i32 level;

    public User new(i32 initial_level) {
        return User { level = initial_level };
    }

    public i32 get_level(&User self) {
        return (*self).level;
    }

    public override bool is_beginner(&User self) {
        return self.get_level() < 5;
    }
};

The explicit marker makes replacement intentional. A matching default must exist, and the complete resolved method signature must agree. A misspelled or unmatched override is rejected. The chosen replacement applies to concrete calls and eligible dynamic calls alike.

Rejected example. This intentionally violates a chosen rule.

// Rejected: get_level is required but has no default body;
struct InvalidOverride implements Leveled {
    public override i32 get_level(&InvalidOverride self) {
        return 0;
    }
};

These blocks are independent illustrative definitions. The repeated User name is not a permitted redeclaration in a single module.

6. Implement several independent contracts

interface Leveled {
    public i32 get_level(&Self self);
};

interface Enabled {
    public bool is_enabled(&Self self);
};

struct Device implements Leveled, Enabled {
    i32 level;
    bool enabled;

    public Device new(i32 initial_level, bool initial_enabled) {
        return Device { level = initial_level, enabled = initial_enabled };
    }

    public i32 get_level(&Device self) {
        return (*self).level;
    }

    public bool is_enabled(&Device self) {
        return (*self).enabled;
    }
};

Each listed interface contributes a contract. Listing one first does not grant it priority. The implementation must satisfy all chosen obligations. Distinct methods compose directly; same-name methods require the conflict and signature rules described below.

7. Resolve conflicting defaults explicitly

interface Calm {
    public i32 priority(&Self self) {
        return 1;
    }
};

interface Urgent {
    public i32 priority(&Self self) {
        return 9;
    }
};

struct Ticket implements Calm, Urgent {
    public override i32 priority(&Ticket self) {
        return 5;
    }
};

Both defaults have the same name and resolved signature. Without Ticket’s explicit override, the conflict is a compile-time error. The replacement resolves the shared behavior for both contract views; it does not call one original default implicitly.

Open conflict cases. Required-only duplicates, a default mixed with a required declaration, incompatible signatures, overload sets and qualified calls to original default bodies still need separate decisions.

8. An enum implements the whole contract

interface Leveled {
    public i32 get_level(&Self self);
};

enum LevelState implements Leveled {
    Beginner;
    Experienced;

    public i32 get_level(&LevelState self) {
        mut i32 result = 0;

        switch (*self) {
            case LevelState.Beginner:
                result = 1;
                break;

            case LevelState.Experienced:
                result = 20;
                break;
        }

        return result;
    }
};

Self here resolves to LevelState, not to an individual variant. The interface implementation belongs to the enum as a whole; variants do not receive independent automatic implementations. The existing enum switch borrowing, coverage and explicit break rules continue to apply. Here switch (*self) selects the enum referent as a place for the default read loan; it does not move the enum out of self.

Inside enum methods, the type’s private payload fields are accessible subject to receiver permissions. Public methods do not expose their fields automatically. See Enums for private factories and payload binding.

9. Concrete calls remain static by default

User user = User.new(7);
bool automatic = user.is_beginner();
bool explicit_view = (&user).is_beginner();

This fragment uses User from the override example. Both calls use its declared read receiver. The ordinary call performs automatic borrowing; the explicit reference form requests the same access directly. Receiver evaluation occurs once. Passing a value receiver follows Copy-or-move behavior instead.

An implements declaration alone neither allocates an interface box nor changes all calls to runtime dispatch. Explicit dyn values select runtime implementations. The compiler’s optimization and backend strategy are separate from this semantic default.

10. Copy remains a checked built-in capability

implements Copy is the established opt-in for implicit value copying. It is compiler checked rather than an ordinary clone method supplied in an interface body. Every struct field or every enum variant payload must meet the Copy requirements.

Using an ordinary behavior interface does not imply Copy. Owning string, Box and dynamic collection fields keep the ordinary move behavior. Generic where T implements Copy constrains the argument T and does not automatically make its containing type Copy.

Custom cleanup compatibility with Copy remains open. See struct ownership and type constraints.

11. Open decisions and related reference

  • Interface inheritance, associated types, interface constants, receiverless interface obligations and general Self scope remain open.
  • Overloads, duplicate required methods, mixed required/default conflicts and original-default qualified calls remain open.
  • Generic functions and their call inference are chosen. Generic-interface-method-specific rules, generic-type inference and backend specialization policies remain open.
  • Dynamic-call eligibility beyond the documented chosen boundaries is addressed separately; no ABI or GPU compatibility is promised.
