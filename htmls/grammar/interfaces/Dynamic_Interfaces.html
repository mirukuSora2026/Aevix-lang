1. A view borrows; it does not take ownership

&dyn Interface is an explicit shared view over a concrete implementation. &mut dyn Interface is an exclusive write view. The concrete owner stays responsible for the value and cleanup; the view selects eligible methods according to its runtime concrete type.

User user = User.new(7);
&dyn Leveled view = &user;
bool beginner = view.is_beginner();

This fragment uses the User and Leveled declarations in Interface Contracts. The chosen User override is used through the view as well. Creating this shared view introduces no allocation, clone or CPU/GPU transfer.

2. Receiver permissions still govern calls

TypeBorrow capabilityMethod access
&dyn IShared read loan.Eligible read-receiver methods; no upgrade to an exclusive receiver.
&mut dyn IExclusive write loan.Eligible write-receiver methods and compatible read access under the borrow rules.

A method’s typed self parameter determines its permissions. dyn changes selection of the implementation; it does not grant mutation to an ordinary shared reference or turn a by-value self into a borrowed call. A directly owned value needs a mut binding before an ordinary write borrow can be created.

3. An exclusive view changes the original value

interface Counter {
    public i32 read(&Self self);
    public void write(&mut Self self, i32 next_value);
};

struct CounterState implements Counter {
    i32 value;

    public CounterState new(i32 initial_value) {
        return CounterState { value = initial_value };
    }

    public i32 read(&CounterState self) {
        return (*self).value;
    }

    public void write(&mut CounterState self, i32 next_value) {
        (*self).value = next_value;
    }
};

mut CounterState counter = CounterState.new(1);
{
    &mut dyn Counter view = &mut counter;
    view.write(2);
}
i32 updated = counter.read();

The view writes the same counter storage, so updated is 2. Its reference binding need not itself be mut to exercise its exclusive referent capability. The explicit nested block bounds the view in this example; no conflicting access is made while it is used.

4. Concrete provenance survives the view

Type erasure hides the public concrete type at the call site. It does not erase the source of a loan. A view cannot outlive its owner or borrowed data stored within that owner. Moving, consuming or cleaning up an owner while a conflicting live view remains is rejected.

Rejected example. This intentionally violates a chosen rule.

// Rejected: the view is used after its owner is moved;
User user = User.new(7);
&dyn Leveled view = &user;
User moved = user;
bool beginner = view.is_beginner();

A view’s last use participates in the existing borrow analysis. Variable scope and the proven extent of a loan are related but different: leaving one branch does not make an escaped reference valid. An exclusive view cannot coexist with an overlapping loan that would create a conflicting read or write.

5. A dyn view may expose only part of a contract

interface Rebuildable {
    public i32 level(&Self self);
    public Self rebuild(&Self self);
};

void inspect(&dyn Rebuildable view) {
    i32 observed = view.level();
}

The interface may contain methods that require knowledge of its concrete Self. A dyn view is still allowed, but only eligible methods are callable through it. A value-returning Self result such as rebuild remains a concrete-type operation in the chosen model.

Rejected example. This intentionally violates a chosen rule.

// Rejected: a dyn view cannot produce an erased concrete Self value;
void invalid_rebuild(&dyn Rebuildable view) {
    view.rebuild();
}

No automatic Box allocation or clone is inserted to make an unavailable method callable. The compiler reports the call as unsupported on that dynamic view rather than rejecting the entire interface view because of one such method.

6. Defaults and overrides retain their meaning

An eligible default method uses the interface contract’s behavior. If an implementing type supplies an override, a dynamic call observes that override. If the default calls a required method, the concrete implementation supplies that operation.

A shared dynamic view cannot call a default whose receiver needs exclusive access. Conflicting same-signature defaults still require a concrete override before that type is a valid implementation. Dynamic dispatch does not invent a priority based on the interface list order.

7. Make runtime selection and access costs visible

OperationChosen contract
Create a borrowed viewNo new allocation, clone or data transfer.
Call an eligible methodSelect the implementation at runtime; method body costs remain real.
Access concrete fieldsThe interface view offers its contract, not arbitrary hidden field access.
End a viewEnding a loan does not destroy the owner’s payload.
Device useNo automatic GPU support or transfer is inferred from dyn.

A particular backend may optimize a dynamic call when it can prove the concrete implementation. That is an implementation opportunity, not a change to the language’s explicit runtime-selection model. Metadata layout, pointer count and size are not specified by this reference.

8. Rejected permission and compatibility changes

Rejected example. This intentionally violates a chosen rule.

// Rejected: this owner does not grant ordinary write permission;
CounterState counter = CounterState.new(1);
&mut dyn Counter view = &mut counter;
view.write(2);

Rejected example. This intentionally violates a chosen rule.

// Rejected: a shared view cannot invoke Counter.write;
mut CounterState counter = CounterState.new(1);
&dyn Counter view = &counter;
view.write(2);

The source must implement the requested interface. A dyn conversion does not make a missing implementation valid, relax private-member access, extend hidden borrow lifetimes or authorize consumption of a borrowed owner.

9. Open dynamic rules and related reference

  • The full eligibility rules for generic methods, associated types, Self reference results and Self argument positions remain open.
  • By-value self through a dynamic owner, extracted values, interface downcasting and multiple-interface dynamic combinations remain open.
  • The exact syntax and rules for generic-interface dynamic coercion remain open.
  • Interface ABI, metadata representation, FFI boundaries and supported GPU dynamic operations remain open.
