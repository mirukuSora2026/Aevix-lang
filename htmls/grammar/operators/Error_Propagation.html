1. Postfix ? and the first complete example

0.2 implementation boundary. Owned Result and Optional propagation are implemented, including inside explicitly typed closure bodies. Result forwards Err only to a Result return with the same error type; Optional forwards None only to an Optional return. The checked-arithmetic and broader catalog APIs below retain their separate design scope; see the implementation profile.

For a Result<T, E> operand, postfix ? yields its T payload on success. On error it immediately returns a Result error from the current Result<U, E>-returning function. The success type T may differ from the enclosing success type U; the error type E must match exactly.

Operand outcomeExpression resultControl flow
Ok(value)Extracted T value.Continue evaluating the surrounding code.
Err(error)No success value is produced on this path.Return an Err carrying E from the current function.

This language design adds one explicit error-return marker to the existing return rule. Successful normal non-void exits still use return; a final expression never implicitly returns. The Result examples below explain the selected contract; an example using a catalog-only API does not establish that API as implemented.

Use the extracted value in a typed declaration

Result<i32, IntegerError> calculate(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = checked(sum * third)?;
    return Result.ok(value);
}

If the addition fails, calculate returns that error immediately and multiplication is skipped. If multiplication fails, its error is returned. If both succeed, value is explicitly wrapped and returned. Result.ok constructs success; it does not itself perform a return.

rsn can infer an extracted payload too: rsn sum = checked(first + second)?; resolves to i32 in this context. Inference does not change the error type or return rules.

2. The enclosing error type must match

Result<bool, IntegerError> positive_sum(i32 first, i32 second) {
    i32 sum = Integer.checked_add(first, second)?;
    return Result.ok(sum > 0);
}

The operand has success type i32 while the function has success type bool. This is valid because IntegerError matches exactly. There is no implicit error conversion, automatic From-like mechanism, error hierarchy coercion or clone. A developer must explicitly map an error through a documented Result API before propagating a different error type. The planned 0.3 common Error interface adds borrowed reporting; implementing it does not change this exact-error-type rule or automatically box an error.

A literal or Result constructor must already resolve to a complete Result<T, E> before ?. The operator cannot supply arbitrary missing success/error type meaning or turn an ordinary number into a Result.

3. Direct Result return and ? serve different paths

Result<i32, IntegerError> direct_sum(i32 first, i32 second) {
    return checked(first + second);
}

Result<i32, IntegerError> extract_sum(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    return Result.ok(sum);
}

direct_sum returns the compatible wrapper directly. extract_sum consumes the wrapper to obtain a scalar, then constructs and explicitly returns success. Both retain errors as values. Choose direct return when no subsequent work needs the payload.

Rejected example. This block intentionally violates a chosen rule.

// Rejected: ? extracts i32 on success, but the function returns Result;
Result<i32, IntegerError> missing_success_wrapper(i32 first, i32 second) {
    return checked(first + second)?;
}

Propagation never silently wraps an otherwise incompatible explicit return expression in Ok. The ordinary type rules still apply to the successful path.

4. checked creates Result; ? forwards it

Result<i32, IntegerError> partly_checked(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = sum + third;
    return Result.ok(value);
}

Result<i32, IntegerError> fully_checked(i32 first, i32 second, i32 third) {
    i32 value = checked(first + second + third)?;
    return Result.ok(value);
}

In partly_checked, the second addition is ordinary arithmetic and a runtime failure safely stops execution. In fully_checked, both additions are directly within checked and their first failure becomes a Result error before ? forwards it. The propagation operator does not extend a preceding checked boundary.

A helper's ordinary failure is not captured by an outer checked call. Likewise, ? does not catch safety termination, arbitrary thrown foreign exceptions, allocation failures without a Result, or GPU work errors that have not been observed through an explicit Result-producing API.

5. One evaluation, no rollback and owned payloads

Result<i32, IntegerError> increment_then_add(&mut i32 counter, i32 amount) {
    i32 previous = checked((*counter)++)?;
    i32 value = checked(previous + amount)?;
    return Result.ok(value);
}

The operand of each ? runs once. If increment fails, later addition never runs. If increment succeeds but the addition fails, the already stored increment remains. Returning an error is not a transaction or automatic rollback.

The ? operator returns from the current function or explicitly typed closure body, not only the nearest loop or switch. It neither means break nor continue. Work later in the same statement, later arguments, and subsequent statements on that path is skipped.

Payload extraction preserves ownership

Result<string, TextError> create_text(string_view source) {
    string owned = string.from_view(source)?;
    return Result.ok(owned);
}

string.from_view performs its explicitly documented copy/allocation operation and returns an owning string on success. ? moves that payload out of the owned Result. Returning owned transfers it into the returned Result; it does not deep-clone the bytes.

On Err, the error payload moves into the enclosing function's error result. For Copy payloads, scalar copying may be implemented without heap work, but the language does not implicitly clone an owning payload or its error. A loan in a payload retains the original lifetime restrictions and may not escape past its source.

Result propagation consumes an owned Result. Optional propagation likewise consumes an owned Optional. Applying ? to borrowed carriers, automatic dereference, error borrowing and generalized propagation traits remain outside the 0.2 profile.

6. Scope cleanup and unit-valued success

Result<unit, TextError> prepare_texts() {
    string first = string.from_view("first")?;
    string second = string.from_view("second")?;
    return Result.ok(Unit.value());
}

If the second operation returns Err, first is cleaned up before the error leaves the function. On successful return, second then first are cleaned up in reverse initialization order. Only initialized, still-owned resources are cleaned up; a moved resource belongs to its new owner.

This is ordinary function exit through a Result value, so the chosen scope-cleanup contract applies. It does not promise cleanup after forced safety termination. Automatic cleanup does not override the returned error with a new cleanup error. Tasks and GPU loans must respect resource lifetime and completion contracts rather than implicitly freeing in-use buffers.

Functions without a success payload use unit

Result<unit, IntegerError> check_addition(i32 first, i32 second) {
    i32 verified = checked(first + second)?;
    return Result.ok(Unit.value());
}

unit is a normal sole-value type, so Result<unit, IntegerError> is meaningful. The function still explicitly returns its success unit. Return-position void is not a storable payload type. A plain void, integer or never function does not gain a carrier return route merely because ? appears inside it. An Optional-returning function may propagate None from an owned Optional; it cannot implicitly convert None to a Result error.

7. Propagation and ternary selection differ

Result<i32, IntegerError> choose_result(bool choose_first, i32 first, i32 second) {
    i32 selected = choose_first ? first : second;
    i32 increased = checked(selected + 1)?;
    return Result.ok(increased);
}
FormPurposeEvaluation
result?Extract success or return error.Evaluates the Result once; may exit the function.
condition ? first : secondSelect a value.Evaluates the bool condition and exactly one branch.

Whitespace does not select propagation or ternary selection. Postfix ? belongs to the postfix chain; ternary selection is right-associative at the lowest expression level. Use the unique complete syntactic interpretation. If several interpretations remain, reject the expression and require explicit parentheses instead of choosing from operand types. See Parsing Rules for mixed forms and a genuine ambiguous token sequence.

8. Intentionally rejected uses

Rejected example. This block intentionally violates a chosen rule.

// Rejected: this function has no Result error return type;
i32 invalid_context(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    return sum;
}

Rejected example. This block intentionally violates a chosen rule.

// Rejected: IntegerError does not match TextError;
Result<i32, TextError> wrong_error_type(i32 first, i32 second) {
    i32 sum = Integer.checked_add(first, second)?;
    return Result.ok(sum);
}

Rejected example. This block intentionally violates a chosen rule.

// Rejected: a plain integer is not a Result operand;
Result<i32, IntegerError> wrong_operand(i32 value) {
    i32 extracted = value?;
    return Result.ok(extracted);
}

Rejected example. This block intentionally violates a chosen rule.

// Rejected: the final expression is not an explicit success return;
Result<i32, IntegerError> missing_return(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    Result.ok(sum);
}

These are chosen semantic rejections, not implemented error codes. Missing success returns, moved payload reuse and borrow escape remain errors independently of ?.

9. Open propagation decisions

  • Optional propagation is implemented: Some yields its payload and None exits the current Optional-returning function or closure. None-to-error conversion and additional carrier types are unsupported.
  • Automatic error conversion, borrowed-Result propagation and user-extensible propagation protocols remain unselected.
  • The 0.2 parser gate checks the selected postfix and conditional parsing rules in closure bodies, including nested closures, and rejects genuinely ambiguous question-mark expressions.
  • Syntax and detailed effects of ? inside checked(...) are open; a checked boundary is not a function-return catcher.
  • In 0.2, a closure requires a written -> Result<T, E> or -> Optional<T> return annotation to provide the corresponding propagation route. Postfix ? exits that closure body, not the function that created it. Async/GPU declaration grammar and additional carrier protocols remain outside this profile.

The implemented core consumes an owned Result or Optional once and returns early through the same carrier kind. Result requires the same E; Optional forwards None without an error conversion. Successful normal non-void exits still use an ordinary explicit return.
