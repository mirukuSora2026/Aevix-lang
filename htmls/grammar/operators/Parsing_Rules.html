1. Precedence and comparison boundaries

These selected source rules complete the interaction of the existing operators. A smaller rank binds more tightly. Evaluation remains left to right where the operation evaluates both operands; precedence does not permit reordering effects.

Design specification. These are chosen parsing requirements. A future parser must validate them with a grammar corpus; the examples are not evidence of an implemented parser.

RankOperatorsGrouping
1. () [] ? ++ --Left-to-right postfix chain; each form retains its operand/place rules.
2& &mut * + - ! ~ ++ --Right to left.
3* / %Left to right.
4+ -Left to right.
5<< >>Left to right.
6< <= > >=No unparenthesized comparison chain.
7== !=No unparenthesized comparison chain.
8&Left to right.
9^Left to right.
10|Left to right.
11&&Left to right; short-circuit.
12||Left to right; short-circuit.
13.. ..=Nonassociative; group endpoints when needed.
14condition ? first : secondRight to left; one selected branch.

Assignment and compound assignment are statements, with a dedicated C-style for update-action slot; they never become value expressions. A range does not chain: group a deliberately nested expression rather than writing a..b..c. Relational and equality operators have different levels, but unparenthesized comparison chains remain prohibited across those levels. Write (a < b) == expected when comparing an explicitly grouped comparison result. Integer ++ and -- require a writable primitive integer place; their result is a value, so chaining another update onto that result does not create a writable place.

Comparison binds more tightly than bitwise operations. A mask test therefore needs grouping such as (flags & mask) != 0. Parentheses override grouping while retaining the chosen evaluation and failure contracts.

2. Postfix propagation and conditional selection

Postfix ? belongs to a postfix chain. Ternary ? : belongs to the lowest conditional-selection level. Parse the same token sequence independently of whitespace: if one syntactically complete interpretation remains under these rules, use it; if more than one remains, reject the expression and require explicit parentheses. Operand types are checked after this decision and must not be guessed to select a parse.

Written formGroupingMeaning
checked(a + b)? + c(checked(a + b)?) + cPropagate the checked sum before ordinary addition of c.
result? ? first : second(result?) ? first : secondThe extracted result must be bool; only the selected value is evaluated.
flag ? make_result()? : fallbackflag ? (make_result()?) : fallbackCall and propagate only on the selected true branch.
flag ? +x : yflag ? (+x) : yThe question mark starts conditional selection; + is unary.
Result<i32, IntegerError> choose_from_result(Result<bool, IntegerError> result, i32 first, i32 second) {
    i32 selected = result? ? first : second;
    return Result.ok(selected);
}

The branch forms must still have the same type and propagation must still use the enclosing function's exact error type. A unique parse does not excuse a type, borrow or return error.

Ambiguous token sequence: a ? + b ? + c : d. It permits both ((a?) + b) ? (+c) : d and a ? ((+(b?)) + c) : d. The ungrouped spelling is rejected even if type checking would happen to reject one interpretation. Write the desired grouping explicitly. This policy is an acceptance requirement for the future grammar, not a claim that an ambiguity checker has already been implemented.

3. Generic angles and shift tokens

In a type context, <...> encloses type arguments. Nested closing >> is split into two closing angle delimiters when closing nested type argument lists; the same token spelling remains a right-shift operator in expression context.

FormInterpretation
Vector<Vector<i32>>Nested generic type; two closing delimiters.
identity<i32>(value)Generic call when a well-formed type argument list, following call parentheses and the statically resolved callable name agree.
a < bOrdinary relational comparison in expression context.
value >> amountOrdinary right shift in expression context.

Recognizing a generic call uses type-argument syntax, call context and the static kind of the resolved name. It does not reinterpret arbitrary runtime values as types or choose a different parse from runtime values. If the type/callable path remains ambiguous, require explicit grouping or an unambiguous accessible type path; do not invent a conversion or an import. Explicit function type-argument lists still supply every declared type parameter. Generic type construction retains its separately documented explicit type-argument rules.

4. Narrow compile-time type operands

A documented built-in intrinsic may designate an argument position as a compile-time type operand. Only that catalog-defined position accepts a type such as i64 in the call's ordinary parentheses. The operand is resolved at compile time and has no runtime first-class type-value representation.

Intrinsic callType operand
Integer.convert(i64, source)The destination integer type i64.
Vector.new(i32)The vector element type i32.
Array.from_copy(i32, 4, &fill)The array element type i32; other operands retain their documented contracts.
Box.payload_size(i32)The queried payload type i32.
i32 source = 12;
Result<i64, IntegerError> widened = Integer.convert(i64, source);
usize payload_bytes = Box.payload_size(i32);

The type-operand markers in an intrinsic catalog are metadata for that intrinsic, not ordinary value-parameter declarations. This rule also covers other documented built-in catalog entries only when they explicitly designate such a position; it does not treat every identifier as a type operand. User functions keep normal value parameters and full <...> function type-argument lists. Passing i32 to an ordinary parameter expecting an integer value is invalid. This is not partial generic argument inference, general reflection or a way to allocate or clone an owner implicitly.

5. Range and numeric token boundaries

The lexer recognizes ..= before ... A decimal real literal using a decimal point requires digits on both sides of that point; 0.5 and 1.0 have that form, while .5 and 1. do not. Consequently 0..10 is integer 0, range .., integer 10, and 0..=10 uses the inclusive range token.

A signed minimum literal is checked using its sign and magnitude against the expected signed type. i8 minimum = -128; is valid without first requiring positive 128 to fit i8. Negating an already typed minimum value is a separate arithmetic operation and retains its overflow contract.

These minimal token rules do not finalize all numeric bases, suffixes, separators, exponent forms, Unicode identifiers or string/character escapes. Candidate numeric annotations elsewhere in the API catalog are not adopted automatically by this page.

6. Statement bodies and else attachment

An else attaches to the nearest unmatched if. Parenthesized bool conditions remain required. A single ordinary executable statement may omit body braces; a declaration used as the body requires an explicit block. No special scope is invented for a lone unbraced declaration.

For example, if (outer) if (inner) action(); else fallback(); attaches the else to inner. Use braces to attach it to outer. Write if (ready) { i32 value = 1; } for a declaration body. The declaration's name and cleanup follow that explicit block.

Every executable declaration, assignment, call statement and return ends with a semicolon. A function or control-flow block closing brace does not acquire an extra semicolon. Type declarations retain their established closing };.

7. Case exits keep a written break

Every written case and default still ends with an explicit break;. A preceding return, loop continue, divergence or Result ? is permitted under its own control-flow and ownership contract. It never replaces the written terminal break. If that mandatory break is unreachable, its unreachability alone produces neither an error nor a warning. This narrow exemption does not choose a general unreachable-code policy.

i32 first_or_zero(i32 value) {
    switch (value) {
        case 1:
            return 10;
            break;
        default:
            break;
    }
    return 0;
}

A ? takes an early return only on Err; its successful path continues to the branch's written break. Return, continue and propagated Err clean up the regions they actually leave exactly once. Nontermination is not a normal scope exit; safety-stop cleanup remains separately unsettled. These rules apply equally to scalar and enum switches. See Switch and Enum Switch.

8. Implementation and remaining limits

A parser implementation must test positive, negative and ambiguous token sequences against these selected rules, including nested generic closers, comparison-chain rejection and mixed question marks. A formal grammar and its executable corpus are future implementation work.

The full literal/identifier grammar, general casts, Optional propagation, user-defined operator overloads, complete shift failure contracts, indexing failure policy and detailed ? effects inside checked(...) remain open. This page does not expand GPU or parallel execution.
