1. The explicit mixed arithmetic model

0.2 boundary. Ordinary guarded integer operators are implemented. The checked(expression) syntax and named checked-arithmetic APIs on this page are selected design contracts, not executable 0.2 features. The implemented Integer.convert and Float conversions retain their own explicit Result contracts; see the numeric profile.

The selected design combines convenient ordinary integer arithmetic and recoverable checked arithmetic. The syntax selects the failure mode before evaluation. A return type, optimization setting or inference result never silently switches between them.

FormSuccessful resultArithmetic failure
a + bA scalar T.Static guaranteed failure is diagnosed; runtime failure safely stops execution.
Integer.checked_add(a, b)Ok(T) in Result<T, IntegerError>.Returns Err.
checked(a + b * c)Ok(T) in Result<T, IntegerError>.First direct arithmetic failure returns Err from this checked expression.

checked is language syntax, not a catch-all runtime function. Its Result describes this expression; returning that error from a containing function is a separate explicit operation. All examples are design examples and have not been compiled by an Aevix compiler.

Ordinary arithmetic returns the declared number type

i32 add(i32 first, i32 second) {
    return first + second;
}

For representable inputs, add returns an i32. If the mathematical sum exceeds the i32 range, a runtime safety failure stops execution. Debug and release builds must agree. Unrecoverable termination details are open: this page does not promise stack unwinding or resource cleanup on a forced stop.

Unsigned subtraction below zero is overflow under the same checked policy. A signed minimum divided by -1 cannot fit the signed result. Division or remainder by zero is arithmetic failure. The signed minimum remainder by -1 edge is still tracked as a candidate in the Integer API draft and is not newly finalized here.

2. checked(expression) and covered operations

Result<i32, IntegerError> calculate(i32 first, i32 second, i32 third) {
    return checked(first + second * third);
}

The checked boundary transforms directly written supported integer arithmetic failures into IntegerError values. Success contains the final expression value of type i32. Returning the Result directly is valid; no unwrap or propagation operator is needed when the wrapper already matches the function return type.

The initial examples use a same-type integer scalar result. General result-shape rules for checked around non-integer or mixed-domain expressions remain open. Parentheses define the expression boundary; this version does not introduce a checked statement block.

Unary plus preserves a supported numeric value. Bit operations do not become arbitrary error capture, and the final relationship between lexical checked and shift failures is still open. The proposed Integer API catalog also contains explicit conversions, parsing, wrapping and saturating functions. Those functions keep their own contracts.

i32 first = 10;
i32 second = 20;
Result<i32, IntegerError> explicit_sum = Integer.checked_add(first, second);
Result<i32, IntegerError> expression_sum = checked(first + second);

3. Evaluation order and intermediate failures

Result<i32, IntegerError> combine(i32 first, i32 second, i32 third) {
    return checked(first + second * third);
}

Evaluate first, then second, then third, each once. Compute second * third, then add first. If multiplication fails, addition does not execute. The first failure is determined by the chosen evaluation order; the implementation must not select an arbitrary later failure because a different schedule is faster.

A failure skips the remaining work of the checked expression. It does not automatically return from the containing function. Bind the Result, return it directly, inspect it with explicit APIs, or use the separately approved postfix question mark.

Intermediate overflow still counts

i8 first = 120;
i8 second = 10;
i8 third = 10;
Result<i8, IntegerError> outcome = checked(first + second - third);

The first addition would create 130, outside i8. The expression therefore produces Err even though an unbounded mathematical rearrangement could end at 120. Subtraction never runs. Neither optimizer reassociation nor JIT specialization may turn this defined failure into a success.

Operands do not widen implicitly. To calculate in a wider integer type, perform documented explicit conversions before entering the expression. Choosing rsn for outcome only infers the Result type; it does not change the arithmetic width.

4. Static checking preserves Result failures

i8 first = 120;
i8 second = 10;
rsn outcome = checked(first + second);

If the compiler determines this calculation in advance, outcome is a normal Err value of Result<i8, IntegerError>. A proven overflow inside checked is part of that expression's value contract rather than an ordinary-arithmetic rejection.

Rejected example. This block intentionally violates a chosen rule.

// Rejected: ordinary statically guaranteed i8 overflow;
i8 invalid_sum = 127 + 1;

Rejected example. This block intentionally violates a chosen rule.

// Rejected: the literal itself cannot be an i8 operand;
Result<i8, IntegerError> invalid_literal = checked(128);

checked does not repair an invalid typed literal, type mismatch, unresolved name, syntax error or illegal borrow. Such errors remain compile-time diagnostics. Folding an explicit named checked API likewise preserves its Result contract.

5. The boundary is lexical, not a trap catcher

i32 ordinary_add(i32 first, i32 second) {
    return first + second;
}

Result<i32, IntegerError> outer(i32 first, i32 second) {
    return checked(ordinary_add(first, second) + 1);
}

Only the + 1 directly written inside checked is covered. If ordinary_add fails during its own ordinary addition, the safety termination is not converted into Err by outer. This remains true if the optimizer inlines the call. Source-level boundaries cannot move because of a code generation choice.

An explicitly checked function call returns its own Result. checked does not implicitly unwrap that Result or flatten arbitrary nested wrappers. Use error propagation outside the checked expression as a separate step.

6. Increment validation and no rollback

mut i8 counter = 127;
Result<i8, IntegerError> outcome = checked(counter++);
i8 unchanged = counter;

outcome is Err and unchanged is 127. Postfix increment returns the previous value only after a successful validated update. Overflow cannot produce Ok(127) while declining to perform the requested mutation.

mut i8 counter = 4;
Result<i8, IntegerError> before = checked(counter++);
Result<i8, IntegerError> after = checked(++counter);

before contains 4, after contains 6, and counter is 6. Prefix decrement returns the newly stored value; postfix decrement returns the old value. A writable place is evaluated once. Exclusive references can grant referent mutation even when their local reference bindings are immutable.

Successful earlier work is not rolled back

mut i8 counter = 1;
i8 large = 127;
Result<i8, IntegerError> outcome = checked(counter++ + large);
i8 retained_update = counter;

The increment succeeds and stores 2. The later addition of old value 1 and large 127 overflows. outcome is Err, but retained_update is 2. checked is an arithmetic error boundary, not a transaction. Earlier function calls, completed mutations and ownership moves remain in effect.

A failed operation performs no result store of its own. That guarantee is local to the failed update; it does not rewind an earlier successful operation. Automatic resource cleanup on leaving a scope remains a separate ownership rule.

7. Expected type does not choose the failure mode

Rejected example. This block intentionally violates a chosen rule.

// Rejected: ordinary addition returns i32, not Result;
Result<i32, IntegerError> wrong_mode(i32 first, i32 second) {
    return first + second;
}
Result<i32, IntegerError> explicit_mode(i32 first, i32 second) {
    return checked(first + second);
}

A Result return annotation must not reinterpret ordinary + as recoverable checked syntax. Similarly, assigning a Result to a plain integer does not implicitly extract it. An explicit postfix ? or Result API is required in an appropriate context.

8. Floating-point behavior stays separate

f64 first = 1.0;
f64 second = 2.0;
f64 ordinary = first + second;
rsn finite_result = Float.checked_add(first, second);

Floating-point NaN and infinity follow the Float contract. Integer checked syntax does not make all floating-point exceptional values arithmetic errors. Use the explicit finite-result checked Float APIs when their contract is needed, and use functions such as Float.fmod for real remainder.

The generic-looking word checked does not import floating-point traps, aggregate Tensor error handling, allocation failure capture or GPU synchronization. Those behaviors must be chosen through their own APIs.

9. Combine checked with explicit propagation

Result<i32, IntegerError> calculate_stepwise(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = checked(sum * third)?;
    return Result.ok(value);
}

Each checked expression returns a Result. Postfix ? extracts the successful scalar or returns the same IntegerError from the containing function. The success path still explicitly returns Result.ok(value).

Result<i32, IntegerError> calculate_whole(i32 first, i32 second, i32 third) {
    return checked((first + second) * third);
}

Syntax and detailed effect rules for a ? written inside checked(...) remain open. None of these examples relies on that nesting. A checked boundary is never specified to catch a ? that returns from a function.

10. Costs, ownership and compilation

  • A scalar Result can be represented without a separate heap allocation; final ABI and layout are not settled by this syntax.
  • Necessary checks, tags and error branches can cost instructions. The compiler removes a check only when doing so preserves values, side effects and failure behavior.
  • AOT and JIT use the same semantic contract. Optimization does not authorize wrapping, skipped failures or an altered lexical checked boundary.
  • Normal scope exits and Err propagation clean up still-owned initialized resources in reverse initialization order. Moved values are managed by their new owners.
  • Safety termination cleanup remains open. Recoverable checked arithmetic does not promise rollback or hidden GPU waits.

A Result-returning operation without a success payload uses Result<unit, E>, not a container of return-position void. Refer to unit and void.

11. Open decisions and related reference

  • Final IntegerError enum representation, payloads and public diagnostic names. Overflow and DivisionByZero identify failure concepts, not an approved enum declaration syntax.
  • The proposed checked remainder edge and lexical checked treatment of shift failures remain separate design work. Ordinary 0.2 shifts already validate counts, discard high left-shift bits, and distinguish signed/unsigned right shifts; see implemented shifts.
  • Unsigned unary-minus applicability and full literal grammar beyond the chosen sign-and-magnitude range check.
  • General checked expression result shapes, nested checked flattening, checked statement blocks and ? inside a checked operand.
  • Termination, unwinding and forced-stop cleanup, plus user-defined overloaded arithmetic.
