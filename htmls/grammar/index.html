1. Grammar reference

Aevix documents its expression, control-flow, declaration, and lifetime rules as an original language design. These pages separate chosen behavior from unresolved syntax and policies. They do not claim a working parser, optimizer, runtime, GPU backend, or diagnostic implementation.

Type-first declarations, immutable defaults, explicit mut, static rsn inference, explicit numeric conversion, and ownership-aware borrowing provide the common foundation. No comparison language silently supplies missing rules.

3. Start with declarations

Syntax foundationDeclarations

Variables, functions, value/reference parameters, explicit returns, unit, and void.

Value foundationData Types

Primitive values, collections, ownership, synchronization, and CPU/GPU resource contracts.

A local owner, a borrowed reference, and a returned value have different lifetime effects. The grammar pages preserve the linked types’ established contracts rather than inventing implicit copies or allocations.

4. Shared syntax across the reference

i32 size = 128;
mut i32 count = 0;
rsn inferred = 128;
const i32 LIMIT = 100;
&i32 reference = &size;
i32 observed = *reference;

These declaration fragments use semicolons and fixed static types. Expressions and control flow operate within the same ownership and borrowing rules. The detailed pages label intentionally rejected examples rather than silently repairing them.

5. Semantic boundaries

Boundary Design rule
Names and storage Public visibility cannot extend lifetime or turn a local into process storage.
Mutation and aliases Mut and writable references do not permit conflicting access.
Errors and normal exits Recoverable Result propagation follows normal cleanup; an ordinary safety stop is not the same exit.
Device work Accepted in-flight resources remain retained, and borrowed locals require quiescence before release.
Documentation Metadata describes declarations and does not rewrite executable semantics.

6. Open design and implementation status

Each reference labels its remaining questions. Custom cleanup functions, partial moves with user-defined cleanup, enum representation, full dynamic-call eligibility, reference-return lifetime notation and project configuration formats remain open. Module paths and imports, generic function calls, overload selection, named/default arguments and persist initialization and normal shutdown now have chosen rules in their focused references. Structs, interfaces, enums, type generics and independent switch-case scopes are documented as chosen rules. Documentation describes a design; it does not establish a working compiler or backend.

Read declarations first, then operators, control flow, and scope rules. Use the type reference whenever an operation depends on ownership, placement, or an error contract.
