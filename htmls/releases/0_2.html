Scope and status

This is the implementation profile for the 0.2V preview. It is separate from the larger type and API design catalogs. The compiler packages retain their 0.2.0-dev filenames; the compiler and VS Code extension report 0.2.0. The prior 0.1 line is preserved on release/0.1. The current macOS ARM64, Linux ARM64 and emulated Linux x86-64 builds each pass all 43 CTest gates. Relocated per-user installer, PATH, AOT/JIT and removal checks also pass on those hosts. The Windows artifact is AOT-only and has nine COFF/static-link probes plus package inspection; native execution remains unverified. Performance-changing optimization is held pending the final external review.

Memory uses native values and explicit owners. There is no tracing garbage collector or JVM-style reserved heap. Ownership and loan checks apply to the supported language; arbitrary foreign code and abnormal process termination are outside normal cleanup guarantees.

Numeric values

Signed and unsigned integers extend through i128 and u128. Floating formats include f16, bf16, f32 and f64. int aliases i32; float aliases f64. Typed literal suffixes select the exact numeric type. Integer arithmetic retains runtime safety checks in optimized builds. This does not implement the catalog's checked(expression) or general named checked-arithmetic APIs. Unsupported casts and implicit narrowing are rejected.

Integer.convert<T> returns Result<T, IntegerError>. Float.convert<T> permits rounding; Float.convert_exact<T> and Float.to_integer_exact<T> reject inexact values. Half formats have 16-bit storage and portable rounding helpers. The external C ABI does not accept 128-bit scalar values in this profile.

Result<i8, IntegerError> narrow(i64 input) {
    return Integer.convert<i8>(input);
}

i32 main() {
    u128 bit = 1u128 << 100;
    return bit > 0u128 ? 0 : 1;
}

Text, tuples and arrays

String literals are allocation-free UTF-8 string_view values. Owned string creation and mutation return explicit TextError results. Byte lengths, Unicode scalar counts and grapheme counts are different concepts. The implemented text calls are byte_len, scalar_count, is_empty, view, as_bytes, equals, from_view, from_utf8, slice_bytes, append, push_char and clear. Views keep their source storage borrowed.

Tuple.make owns its inputs; get<I> and get_mut<I> borrow a constant field index. Tuples move by default; Tuple.copy requires every field to support Copy. A repeated fixed array evaluates its source once, including zero length, and requires a Copy element. Slice.slice and Slice.slice_mut return checked views or BoundsError.

Result<usize, TextError> count_text() {
    string owner = string.from_view("Aé한🙂")?;
    return Result.ok(string.scalar_count(&owner));
}

void arrays() {
    i32 zeros[128] = [0; 128];
    Tuple<i32, bool> status = Tuple.make(200, true);
    &i32 code = Tuple.get<0>(&status);
    return;
}

Generic and callable foundations

Transparent aliases preserve type identity. Trailing type defaults and const usize parameters support statically sized user-defined containers. Constant arguments are normalized by value, not spelling. Required parameters cannot follow defaulted parameters. General const functions and arbitrary constant-parameter types are not part of this profile.

Explicit-capture closures use stack environments and static calls, with Fn, FnMut and FnOnce constraints. Capture and borrowing restrictions are checked; this profile does not implicitly allocate a boxed callback. Closure return-type inference and owning dynamic callable wrappers remain outside the initial implementation.

struct Buffer<T = i32, const usize N = 4> {
    public Array<T, N> values;
};

i32 main() {
    i32 factor = 3;
    rsn multiply = [factor](i32 value) -> i32 { return value * factor; };
    return multiply(14) == 42 ? 0 : 1;
}

Complex<T = f64> and complex = Complex<f64> require an explicit complex import. Seventeen public type functions cover construction, component arithmetic, magnitude, conjugation, comparison and Result-returning division. ComplexError.ZeroDivisor reports a zero divisor. The numeric.Floating capability is sealed to built-in floating formats; user structs cannot claim primitive numeric operations by implementing it.

CPU SIMD and parallel execution

The implemented SIMD profile requires an explicit simd import and limits numeric vectors to 128 bits. It preserves per-lane integer checks and ordered sums. It promises lane semantics rather than a particular instruction count or speedup.

parallel.for_each works on a scalar MutSlice and a validated named worker. Workers receive disjoint elements, and the call waits for all workers. Captured closures, general task APIs, detached work and GPU execution are not supported by this profile.

Execution and tools

The LLVM ORC JIT supports verified modules, static host symbols, optimization levels, cached entry lookup and tracked module removal. Referenced modules and modules owning exit callbacks cannot be unloaded. Invocations run inside the host process; JIT is not a sandbox or a promise of automatic tiering, OSR or speculative deoptimization.

@bench reports per-function wall time and sampled process RSS. RSS includes the process, not just allocations owned by one function. Instrumentation perturbs short calls. Unannotated code does not reference profiler hooks.

Run aevixc --check-deps to probe native build requirements without executing the probe. Installers register PATH and carry the matching runtime; they do not install a platform SDK. See the installation guide for platform setup and removal.

Release boundaries

Targets are macOS ARM64, Linux ARM64/x86-64 and Windows x86-64. The current Linux artifacts were qualified on Ubuntu 24.04.5 LTS with glibc 2.39; wider distribution compatibility needs separate checks. The current macOS development installers require macOS 26.0 or newer and check that requirement before installation changes. Their code signatures are ad hoc; the PKG is unsigned and not notarized. The PKG payload was inspected without a system installation; actual installation tests used the per-user .run. Module filename stems and folders below the source root currently use [A-Za-z_][A-Za-z0-9_]*; Unicode module names and hyphenated stems are outside this profile. JIT runs on its host CPU. Windows native execution and MSVC remain unverified; an object file or cross-linked executable alone does not establish native behavior.

GPU/Tensor execution, the complete library catalogs, user-defined destructors, a formatter and a debugger remain outside 0.2. Self-hosting is scheduled for 0.5. Source and runtime evidence take precedence over broad design-page API lists.
