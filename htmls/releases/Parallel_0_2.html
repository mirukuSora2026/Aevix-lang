Start with a mutable slice

Import parallel explicitly, provide a named worker, and pass an exclusive slice. The function finishes all element work before returning to its caller.

import parallel;

void transform(&mut i32 item) {
    *item += 3;
    return;
}

i32 main() {
    mut i32 values[1025] = [1; 1025];
    parallel.for_each(Slice.from_array_mut(&mut values), transform);
    for (i32 value : values) {
        if (value != 4) return 1;
    }
    return 0;
}

Slice.from_vector_mut(&mut owner) can provide the same kind of view over a vector. The owner remains protected by the exclusive loan while parallel work is using its storage.

Implemented API

CallResultContract
parallel.for_each(MutSlice<T> items, worker)unitProcess each element exactly once on normal completion, using a validated void worker(&mut T item).
parallel.worker_count()usizeReturn the runtime worker limit, between 1 and 32, based on available logical CPUs.

T is limited to supported scalar numeric types, bool, char and byte. A shared Slice cannot be passed where a MutSlice is required. The writable view is passed directly; callers do not take an additional address of the view.

The reported worker count is an upper bound. Actual worker use is also bounded by the slice length, and thread creation failure can reduce it. A nonempty call includes work performed by the calling thread.

Worker safety is checked transitively

A worker must be a named, module-level, non-generic function with exactly one exclusive scalar reference parameter and a void return type. Overloaded or captured callable values do not serve as workers in this profile.

The checker follows calls made by the worker. Each reachable helper needs an inspectable Aevix body and must obey the same restrictions.

  • No access to module variables, persist storage or captured storage, including reads of global values.
  • No external C functions, dynamic calls, nested parallel work or unvalidated compiler intrinsics.
  • Local variables and parameters are limited to scalars and scalar borrows.
  • Helper return values are limited to scalars, scalar borrows, unit, void or never.

These restrictions provide a bounded 0.2 safety model. They do not claim general Send/Sync checking for arbitrary user-defined owners or foreign code.

import parallel;

void add_three(&mut i32 item) {
    *item += 3;
    return;
}

void transform(&mut i32 item) {
    add_three(&mut *item);
    *item *= 2;
    return;
}

Disjoint work and scoped completion

The runtime partitions the slice into contiguous, nonoverlapping chunks. Each worker receives elements from its own chunk, so safe worker code cannot obtain a second alias to another worker’s element.

Element execution order is unspecified. The caller must not depend on a particular thread identity or on one index finishing before another. For an empty slice, the worker is not called.

All started worker threads are joined before a normal return. No work is detached, and the call does not extend the slice loan into a background task. Once the loan is no longer live, normal owner access can resume.

Completion is not rollback. A worker that never returns prevents completion. A checked arithmetic trap or another fatal runtime failure terminates the process; it does not undo elements already modified.

Thread creation failure and cost

If the operating system refuses a new worker thread, the calling thread processes only the chunks that have not started. Already started threads continue and are joined. This fallback avoids duplicate element calls and requires no ParallelError result.

The runtime uses bounded stack bookkeeping rather than allocating a collection of tasks. The operating system still supplies thread resources. Creating and joining threads has a real cost on each call, so small or inexpensive workloads can be slower than a sequential loop.

There is no guaranteed speedup, reusable task pool, user-selected scheduling policy or GPU dispatch in this API. SIMD is a separate explicit module; see the implemented SIMD reference.

Checked behavior

Native runtime tests check exactly-once processing, multiple worker participation, scalar strides, empty and single-element slices, and a forced thread-creation-failure fallback. Compiler integration tests execute the same element transformation through AOT at two optimization levels and through ORC JIT.

Negative compiler checks cover missing import, a shared slice, the wrong worker signature, direct and indirect global access, persist access and external calls. Final native validation of each release platform is tracked in the 0.2 implementation profile.
