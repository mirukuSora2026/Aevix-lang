A closure is a value

A closure combines a function body with explicitly captured values. Its parameters use the normal type-first syntax, and the arrow introduces an explicit return type. Use rsn to infer the closure’s unique concrete type.

i32 main() {
    i32 factor = 3;
    rsn multiply = [factor](i32 value) -> i32 {
        return value * factor;
    };
    return multiply(14) == 42 ? 0 : 1;
}

An empty capture list is written []. Outer local variables must appear in the capture list before the body can use them. A closure declaration ends with a semicolon because the closure expression initializes a variable.

Implemented profile. These examples describe compiler-supported 0.2 behavior. The larger collection API catalogs contain additional proposed callbacks and algorithms.

Choose how each value is captured

CaptureMeaningEffect on the source
[value]Capture by value. Copy values are copied; other values move.A moved owner cannot be used through its previous binding.
[&read]Capture a shared borrow.Conflicting mutation is rejected while the loan remains live.
[&mut write]Capture an exclusive borrow.Requires mutable source storage and excludes conflicting access.
[value, &read, &mut write]Combine explicit capture modes.Each captured value keeps its own move or loan rules.

Inside the body, a borrowed capture is used by its original name; the compiler handles access through the stored reference. It does not require an extra dereference just because the value was captured.

i32 main() {
    i32 base = 10;
    rsn add_base = [&base](i32 value) -> i32 {
        return value + base;
    };
    return add_base(2) == 12 ? 0 : 1;
}

Captured references cannot outlive their source storage. Returning a reference into an environment consumed by its own call is also rejected. Moving an environment preserves the lifetime restrictions carried by its captured fields.

Fn, FnMut and FnOnce

ContractCall receiver0.2 classification
Fn<Tuple<Args...>, Output>Shared borrow: &F.Read-only closures with Copy value captures or shared borrowed captures.
FnMut<Tuple<Args...>, Output>Exclusive borrow: &mut F.Closures that need mutable capture access, including explicit exclusive captures.
FnOnce<Tuple<Args...>, Output>Value: F.Closures that own a non-Copy captured value; calling consumes the environment.

An Fn closure satisfies FnMut and FnOnce requirements. FnMut satisfies FnOnce. The reverse directions are rejected. Argument and result types must match the contract.

The 0.2 classifier is conservative: any non-Copy value capture makes the closure FnOnce, even if the body only reads it. Calls on a captured object may also require mutable environment access. This profile does not infer every reusable closure accepted by other languages.

i32 main() {
    mut i32 total = 1;
    mut rsn change = [&mut total](i32 delta) -> i32 {
        total += delta;
        return total;
    };
    i32 first = change(2);
    i32 second = change(4);
    return first == 3 && second == 7 ? 0 : 1;
}

A mutable closure needs a mut binding when called directly. Mutability of the source value alone does not make the closure binding mutable.

Pass closures to generic functions

The contracts are available in the basic type environment. The argument tuple describes the callback signature; the caller still passes ordinary arguments rather than constructing a runtime tuple.

T map<T, F>(T value, &F callback)
    where F implements Fn<Tuple<T>, T> {
    return callback(value);
}

i32 update<F>(&mut F callback, i32 value)
    where F implements FnMut<Tuple<i32>, i32> {
    return callback(value);
}

i32 main() {
    i32 factor = 3;
    rsn multiply = [factor](i32 value) -> i32 {
        return value * factor;
    };
    return map(4, &multiply) == 12 ? 0 : 1;
}

The generic body is checked against its declared contract. A function receiving F callback under an FnOnce constraint may call it once; a second call is a move error. To call a reusable callback without consuming it, take &F or &mut F with the matching contract.

usize consume<F>(F callback, usize extra)
    where F implements FnOnce<Tuple<usize>, usize> {
    return callback(extra);
}

Result<usize, TextError> owned_example() {
    string text = string.from_view("abc")?;
    rsn once = [text](usize extra) -> usize {
        return string.byte_len(&text) + extra;
    };
    return Result.ok(consume(once, 2));
}

Storage, calls and current limits

The compiler builds a concrete environment record from the capture list and generates a statically selected invoke function. The environment uses ordinary value storage; creating a closure does not itself allocate a hidden heap object. A captured string or vector can still own a separate buffer, and copying a large Copy capture has its normal value-copy cost.

Specialization and ordinary LLVM optimization can remove environment fields or inline calls. Such transformations depend on the program and optimization level; the language does not promise that every closure disappears from machine code.

  • Capture lists and parameter types are explicit; the return type after -> is required.
  • The current callback contracts describe concrete generic callbacks. Owning dynamic callable wrappers and dyn Fn dispatch are outside this profile.
  • The closure parameter list is fixed-arity. self is reserved for the generated receiver.
  • CPU parallel workers must be validated named functions. Closures are not accepted by parallel.for_each in 0.2.

Checked behavior

The closure integration gate exercises AOT and ORC JIT calls, actual generic Fn/FnMut/FnOnce specialization, shared and exclusive captures, and owned string capture. Negative checks reject implicit local capture, writing through a shared capture, calling an immutable FnMut binding, conflicting source mutation, repeated FnOnce use, an escaping environment reference and a closure used as a parallel worker.

These compiler checks are separate from final native qualification of every release platform. See the implementation profile for the platform status.
