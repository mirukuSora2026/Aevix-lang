Selected scope and status

Selected 0.3 scope: an explicitly imported system module exposing print, println, printf, and input. This adds console IO to the existing resource/FFI and library foundation goals.

Not implemented in 0.2. The examples below are proposed 0.3 source forms, not programs accepted by the shipped 0.2 compiler. Selecting the four names does not finalize their signatures, formatting grammar, buffering, or error variants. Those details are recommendations for the 0.3 API review.

Selected functionPlanned purposeRecommended result
system.print(text)Write text without appending a newline.Result<unit, system.IoError>
system.println(text)Write text and append a newline.Result<unit, system.IoError>
system.printf(format, values...)Write formatted output, with no automatic newline.Result<unit, system.IoError>
system.input()Read one UTF-8 line from standard input.Result<Optional<string>, system.IoError>

The table shows call shapes, not variadic function declarations. A no-argument println() overload, other printable value types, and additional stream operations require separate review.

Imports and call forms

A whole-module import system; uses qualified calls such as system.print(...) and the exported error name system.IoError. IO types are not added to the automatic prelude.

import system;

Result<unit, system.IoError> write_summary(string_view label, i32 count) {
    system.print("Summary: ")?;
    system.println(label)?;
    system.printf("%s: %d\n", label, count)?;
    return Result.ok(Unit.value());
}

This is a proposed helper returning Result. It does not change the selected i32 main() convention or make ? valid in an incompatible integer-returning main.

Selective imports retain the existing rules. In a separate file, the following form exposes only the selected names; unrelated system exports still require their own import. Name collisions use imported module-qualified paths, with no new alias or overload-merging rule.

import system { println, IoError };

Result<unit, IoError> announce() {
    println("ready")?;
    return Result.ok(Unit.value());
}

Output and errors

The recommended initial text parameter is string_view. Callers borrow an existing string explicitly when a view is needed; the API does not silently move or clone an owning string. The operation must not retain a caller's borrow after returning. Formatting and internal buffering copies or allocations must have documented costs and failure behavior.

Output returns Result<unit, system.IoError> because writes and resource operations can fail. An Err can follow a successfully written prefix; it cannot roll back terminal output. Lower-level short writes should be handled under a documented write-all policy, without promising that a caller can blindly retry the entire message after an error.

Recommended error categories include read, write, and flush failures; invalid UTF-8; input-size limits; allocation failure; and unavailable or closed standard streams. These are categories for review, not frozen enum variant names. Preserve an OS error code when meaningful, without making callers interpret EOF as an OS error. Broken-pipe and signal handling also need an explicit per-platform policy; the convenience API must not silently install a process-wide handler.

Checked printf without C varargs

The recommended initial printf uses familiar percent-style conversions while checking the format, argument count, and argument types at compile time. Its format should initially be a literal or supported compile-time string. The sample uses %s for a string_view, %d for i32, and %% for a literal percent; the complete conversion, width, and precision grammar remains a review item. Forbid unsafe conversions such as %n.

Mixed-type arguments need a 0.3 intrinsic design. The string_view and i32 arguments in the example are intentionally heterogeneous. They are not an extension of the existing homogeneous i32 values[] variadic parameter syntax. Keep that syntax and its ownership rules unchanged, and approve a separate compiler-checked intrinsic or typed argument representation before implementing printf.

Do not lower this interface to unchecked C varargs or rely on C's default argument promotions. No implicit ownership move, deep clone, or arbitrary printable-type conversion is introduced by a format string. Invalid static formats should be compile errors; actual output/resource failures remain Result values.

Line input, EOF, and UTF-8

The recommended input() result is Result<Optional<string>, system.IoError>. The outer Result reports failure; the inner Optional distinguishes a line from EOF. Returning an owned string makes the allocation and ownership transfer part of the contract.

Observed inputRecommended result
A line containing text followed by a terminatorOk(Some(text)), with the terminator removed.
An empty lineOk(Some("")); it is not EOF.
EOF before any bytes of another lineOk(None).
A final line without a terminator, followed by EOFOk(Some(text)), then None on the next successful read.
Invalid UTF-8, an IO failure, a size-limit failure, or allocation failureErr(...) under the reviewed error policy.

The table uses outcome notation rather than constructor syntax; the empty-line payload is an owned empty string. Review terminal input and redirected-byte encodings separately on each OS rather than assuming every native console stream already supplies UTF-8.

Recommend recognizing LF and CRLF line endings, removing the full terminator, and never replacing invalid UTF-8 silently. The treatment of a lone CR, maximum line size, interrupted reads, already consumed bytes after failure, and recovery after malformed input must be finalized before implementation.

import system;

Result<Optional<string>, system.IoError> read_next_line() {
    return system.input();
}

Buffering, flushing, and resource boundaries

Separate writing, flushing a library buffer, and releasing a resource. A successful buffered write need not mean the terminal has displayed the text. Appending a newline should not imply an undocumented flush.

Recommended additional operation: an explicit system.flush() returning Result<unit, system.IoError>, particularly before waiting for input after printing a prompt. Its name and inclusion are not part of the four confirmed functions and still need API approval.

Define standard-stream ownership, redirection, and closure behavior on each supported OS. Automatic cleanup cannot guarantee a successful fallible flush. Recommend thread-safe, call-level stream serialization while leaving the relative order of racing calls unspecified; several calls do not automatically form one output transaction.

The public system surface should be a convenience layer over the reviewed text/format and io/resource facilities. It must not bypass bounded byte loans, ownership, OS error translation, or safe FFI rules. This plan does not add async IO, GPU behavior, shell execution, or a complete general IO library to 0.3.

Review and implementation gates

  1. Approve exact parameter/result types, error categories, newline policy, and the explicit flush stage.
  2. Approve the heterogeneous printf intrinsic and its checked format grammar without changing homogeneous variadics.
  3. Finish the resource/FFI, byte, UTF-8, allocation, and error foundations needed by synchronous standard streams.
  4. Implement and test empty input, empty lines, CRLF, final unterminated lines, malformed UTF-8, size limits, allocation failure, short/interrupted writes, partial output, broken pipes, redirected streams, flush errors, and concurrent calls.
  5. Verify the same language and ownership behavior in AOT and JIT on the supported targets. Only then describe these functions as implemented.

Library foundations records the wider implementation order. The 0.2 executable profile remains unchanged by this planning document.
