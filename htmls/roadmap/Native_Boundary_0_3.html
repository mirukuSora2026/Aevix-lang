Selected scope

The user selected a small C++ native connection layer for the complete CPU library target in 0.3. GPU-only work remains deferred. The user has approved CPU library implementation and execution checks; GPU-only work remains outside the approved scope.

The development tree now includes move-only io.File and process.Child source owners backed by separate generational file/process registries. Registered private operations connect file IO, UTF-8 path/fs/environment calls, clocks, sleep, and argv-based process spawning/waiting through checked compiler bindings and AIR lowering. Compiler-managed system intrinsics provide bounded standard-stream IO separately. This is a closed library subset, not general native-handle syntax, arbitrary FFI permission, or complete CPU catalog coverage. The published 0.2 profile is unchanged.

Typed native owners

A native owner is move-only and carries its resource kind in its C++ type. Moving transfers cleanup responsibility. Empty and moved-from owners do not release a resource. Cleanup is noexcept and runs once for a current owner. There is no public raw-address accessor, integer conversion, clone, or ownership-detaching raw release.

C++ type identity prevents mixing different resource tags. It does not establish that a handle may cross threads. The current source owners do not grant thread transfer or sharing; those permissions require separate compiler contracts.

Bounded byte loans

The source file APIs accept Slice<byte> and MutSlice<byte>; the mutable buffer is exclusively reborrowed for the private native call. The internal C++ adapters use bounded byte views. Input is read-only; output is exclusively mutable during the synchronous call. Empty buffers are valid. A nonempty buffer cannot have null data, and lengths and address-range arithmetic are checked for overflow.

A pointer-plus-length check cannot prove the allocation size of an arbitrary C++ pointer. Prefer views constructed from actual arrays or spans. The registered compiler path carries the typed slice and preserves its loan during the synchronous call; the raw ABI remains restricted to trusted native adapters.

Closed operation contracts

The earlier generic C++ descriptor foundation defines Release, ReadBytes, and WriteBytes; the current OS library uses a separate closed, typed operation registry. Release consumes the owner and takes no byte loan. ReadBytes exclusively borrows both mutable native state and its output buffer. WriteBytes exclusively borrows mutable native state and reads its input buffer. Reading bytes can still mutate a file cursor.

Every operation is synchronous. Retained or returned loans, Aevix callbacks, asynchronous work with borrowed buffers, and access to Aevix globals or persist storage are forbidden. Unknown IDs or altered effects are rejected. Only Release has cleanup permission; ordinary IO does not acquire that permission.

Compiler bridge symbols and private source helpers are unavailable to ordinary source callers. A source extern declaration, import path, module name, type name, or user annotation cannot grant native privileges. The loader marks only known private declarations from trusted standard modules; semantic checking verifies the closed signature and actual module identity. Arbitrary public C extern signatures retain their scalar-only restriction.

The separate compiler-managed console intrinsic does not reuse these native-handle operation IDs. It is a known synchronous operation that cannot retain Aevix loans, invoke Aevix callbacks, or inspect Aevix persist storage. General native-handle cleanup permissions are unchanged.

Errors and partial progress

Internal results carry a status, a native error code, and completed byte progress. The runtime checks that progress does not exceed the supplied buffer. An error may follow partial progress; it does not imply rollback. The error module defines public IO errors with OS codes and byte progress. Current File and OS source wrappers translate registered runtime outcomes into explicit Result values without a universal implicit error conversion.

Automatic resource release cannot report successful flush or close. Fallible persistence and explicit close need separate Result APIs. The existing conservative rejection of unknown external effects in persist cleanup remains until a real compiler-managed binding proves the required effects.

The trusted C++ boundary

Native adapters are reviewed C++ runtime code. A descriptor validator verifies the declared contract, not an arbitrary C++ implementation. It cannot prevent malicious native code from retaining a pointer or writing outside an allocation. Keep adapters small, use bounded operations, and test partial failures and resource release.

These foundations are independent of the AOT or JIT execution mode. Source and native fixtures cover registered file, path/fs, environment, time, and process operations. Each supported OS/CPU pair still requires its own execution checks; cross-target object generation alone is not execution evidence.

Source integration gates

The current registered source calls bind by trusted declaration/module identity, validate exact signatures and resource roles, carry their operation into AIR, and reject ordinary calls to private helpers. New native resource kinds still need complete ownership, cleanup, construction, loan, effect, and AOT/JIT checks. A matching user name or path is insufficient authorization. Filesystem iteration, lossless native paths, process capture/redirection/timeouts, general synchronization, and the remaining CPU catalog are not supplied by this subset.
