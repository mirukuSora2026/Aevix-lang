Existing behavior and new work

This adds to the existing 0.3 milestone. The common error interface is new library work. Calls to later-defined functions and interface default overrides already work in the current 0.2 compiler; 0.3 retains those contracts and strengthens their documentation and rejection checks.

Calls before function definitions

A module-level function may call another function defined later in the same module. Type methods follow the same declaration-first model within their accessible type. A separate forward prototype is not required.

i32 main() {
    return add(1, 2) - 3;
}

i32 add(i32 left, i32 right) {
    return left + right;
}

main can resolve add even though add's definition appears below it. Collect declaration names, generic parameters, parameter types, return types, and constraints before checking function bodies. Resolve calls from the resulting declaration set rather than from the functions already visited in the file.

bool is_even(i32 value) {
    if (value == 0) return true;
    return is_odd(value - 1);
}

bool is_odd(i32 value) {
    if (value == 0) return false;
    return is_even(value - 1);
}

This mutual-recursion example assumes nonnegative inputs. Declaration collection does not guarantee termination or eliminate call-stack costs.

  • Normal visibility and import rules still determine which declarations a caller can use. Another file is not visible merely because it is compiled first.
  • Overload selection and generic constraints remain the same; source order does not choose a winner.
  • Local variables become available under ordinary block declaration and initialization rules. They cannot be read before declaration or initialization.
  • Statements still execute in their written control-flow order. Persist initialization keeps its separate dependency and lifetime rules.
  • This rule concerns module and type declarations, not a new nested-function or standalone-prototype grammar.

Explicit override

Use the existing override keyword when a struct or enum replaces a matching default method from an implemented interface. The marker is required for replacement.

interface Scored {
    public i32 score(&Self self) {
        return 1;
    }
};

struct Player implements Scored {
    public override i32 score(&Player self) {
        return 2;
    }
};

Match the resolved method name, parameter and receiver contract, return type, and generic requirements. Interface implementation methods remain public. A concrete call uses the selected implementation statically by default; an eligible dyn call uses the same replacement through its dynamic view.

SituationRule
Replace one matching default bodyWrite public override and satisfy the complete method contract.
Implement a required method with no default bodyWrite an ordinary public method; override has no body to replace.
Multiple matching defaults conflictSupply one explicit override. Interface listing order grants no priority.
Unknown name or incompatible signatureReject the override; do not silently introduce an unrelated method.
Free function, field, local declaration, or method without a matching defaultReject the marker.

Known hardening work: the current 0.2 frontend accepts an override modifier on a module-level function, a field, or a method declared in an interface without rejecting its missing target. The 0.3 rejection gate must close these gaps. Existing positive interface examples do not establish that every modifier misuse is already diagnosed.

This retains the chosen interface model. It does not introduce class inheritance, virtual-by-default calls, a super expression, or Java's annotation syntax.

A common error interface

Selected goal: one handling function can receive different recoverable errors. The recommended 0.3 library surface is an explicitly imported error.Error interface, received by a shared dynamic borrow.

The proposed minimal interface has allocation-free code and message access. The code identifies the error kind; the message is a human-readable summary. A view may borrow from the error owner or static storage and must not outlive that storage.

public interface Error {
    public string_view code(&Self self);
    public string_view message(&Self self);
};

This is the proposed public declaration in error.avx, not an automatic prelude type. Standard recoverable error types can implement it without losing their concrete fields or enum variants. A user-defined error opts in with implements Error under the existing interface rules.

import error { Error };
import system;

Result<unit, system.IoError> report(&dyn Error e) {
    system.println(e.code() + ": " + e.message())?;
    return Result.ok(Unit.value());
}

Here Error describes the common behavior and e is the received error variable. The handler borrows the existing error; it does not clone, box, or consume it. The output can itself fail, so report returns the planned console IO Result.

Accessing code or message must not format a new owning string on every call. Implementations may use static summaries or borrow stored text. Detailed formatting, causes, context, and optional backtraces are separate APIs with explicit storage and failure contracts. This interface is not a promise to catch compiler diagnostics, process termination, or unrecoverable safety stops.

Owning and propagating errors

A borrowed &dyn Error is useful for immediate reporting. It cannot own a temporary error, escape its owner's lifetime, or be stored as though it were a complete concrete Error value. An interface name alone is not the sized error carrier in Result<T, E>.

Retain concrete error types and explicit application enums for owned propagation. The existing ? rule still requires the same E at the propagation boundary. Implementing Error does not make different Result error parameters interchangeable.

A future owning erased carrier, including a Box-based design, requires a separate explicit conversion. Allocation failure must be represented without losing the original error. It must be possible to report allocation failure without allocating another wrapper recursively. A fallible boxing operation cannot be hidden as an infallible map_err callback or automatic ? conversion.

The 0.3 error-mapping foundation remains explicit. Finalize any owning carrier only after its layout, allocation, ownership-on-failure, lifetime, and thread-transfer rules are reviewed.

Relationship to try and catch

The common error goal is included in 0.3. The exact Java-like catch spelling and control-transfer model remain a separate decision; the existing 0.4 try work is retained. A shared error interface does not silently add throw statements, exception inheritance, runtime stack unwinding, or catching across functions.

The preferred 0.4 direction remains local handling of Result failures. If Java-style unwinding is selected later, specify which operations can transfer control, catch ordering, cleanup, propagation across FFI, and the relationship to Result before changing the compiler.

0.3 implementation gates

  1. Keep shared cases for later free functions, methods, overloads, generic functions, and mutual recursion. Reordering independent declarations must not change accepted calls.
  2. Reject local use before declaration, missing imports, private access, duplicate signatures, and ambiguous overloads.
  3. Retain positive override and dyn-dispatch cases; reject stray modifiers, missing defaults, mismatched receiver/result contracts, and unresolved default conflicts.
  4. Finalize the error module's public code/message contracts, implement recoverable standard error adapters, and reject escaping error/message borrows.
  5. Test reporting without mandatory allocation, failed output, and explicit error mapping. An owning carrier, if adopted, must preserve the input error on failed conversion.
  6. Keep current Result/? behavior and the separate 0.4 try decision. Compare language behavior in AOT and JIT before relying on these rules in the compiler port.
