Proposal and current scope

The dependency order below is a proposal pending final external review; the linked pages record the user-selected 0.3 goals. The 0.2 profile already implements built-in collection/text/error subsets plus the numeric.Floating and Complex source libraries. Map, general IO, Process, and the remaining broad catalog APIs are future work. See the current implementation boundary.

The first blocker is the scalar-only FFI and missing user-defined native-resource cleanup. A long function list cannot replace those ownership contracts.

0.3 system convenience layer

The selected 0.3 console scope includes import system; and the four functions system.print, system.println, system.printf, and system.input. They are not implemented in 0.2. The console IO plan also covers direct text/scalar output and output-only + composition, while separating these goals from exact signatures, error handling, UTF-8/EOF rules, and the explicit flush stage that still need API review. The convenience plan retains return-only bool-to-integer adaptation, explicit Boolean conversion, field shorthand, and raw literals.

Place system above the text/bytes/convert and io foundations below as a public convenience layer. It reuses their formatting, bounded-buffer, stream, resource, and error contracts rather than adding unchecked C varargs. Mixed-type printf arguments require a reviewed 0.3 intrinsic; the existing homogeneous values[] variadic syntax remains unchanged. The existing resource/FFI goals and implementation order remain in force.

Useful additions to the existing catalogs

  • Source spans and typed IDs for source/AST/type tables that grow.
  • Structured IO errors and explicit error mapping into compiler diagnostics. The planned Error interface supports borrowed inspection; the concrete owning AnyError carrier supports Result<T, AnyError>. Neither is shipped in 0.2. Conversions remain explicit, and fallible packing preserves the original error on failure. The inline subset is limited to selected fixed-size errors; concrete typed errors retain their payloads.
  • Bounded readers, write-all and documented partial progress after failure.
  • Lossless OS paths and environment values.
  • Temporary-output transactions with no-overwrite publication.
  • Stable content hashes distinct from randomized collection hashing.
  • Allocation-failure injection, test/fuzz helpers and deterministic fixtures.
  • Versioned AIR/cache serialization and streaming formatting writers.

API sketches

The confirmed console names and proposed signatures are documented in System console IO in 0.3. These resource and collection sketches are proposed signatures, not current executable programs. Resource cleanup and exact error/type names belong to the 0.3 contract review.

Result<usize, IoError> read(&mut File self, MutSlice<byte> output);
Result<usize, IoError> write(&mut File self, Slice<byte> input);
Result<unit, IoError> flush(&mut File self);
Result<ExitStatus, ProcessError> wait(&mut Child self);
Optional<&V> get(&Map<K, V> self, &K key);
Result<T, ParseError> parse_integer<T>(string_view input, u32 radix);

Borrowed-key lookup must not secretly clone a key. Iterator/callback APIs need explicit item ownership and reference lifetimes. Add associated-type machinery only if a required API cannot use the existing generic contracts.

Keep outside bootstrap requirements

Regex, networking/TLS, locale collation, full grapheme/normalization tables, broad serialization formats, async executors, general thread pools, package registries and GPU can follow the compiler subset. Existing small CPU SIMD/parallel profiles can remain independent.
