Selected milestone and current boundary

Friendly compiler diagnostics are an additional 0.5 deliverable. They supplement the existing stage0 → stage1 → stage2 → stage3 self-hosting objective; they do not postpone or replace bootstrap reproducibility. The current compiler reports source locations and error text, and the editor consumes diagnostics. The richer labels, stable diagnostic codes, structured fixes, JSON schema, and recovery policy described here are planned work, not a claim that the published 0.2 compiler implements them.

A diagnostic explains a compiler finding. It is separate from a runtime Result error, a safety stop, or a line written by system.log. Messages must be derived from checked source facts; speculative generated explanations must not substitute for a real type, ownership, or control-flow reason.

One structured diagnostic model

Introduce an internal record with a stable diagnostic code, severity, short primary message, primary byte span, zero or more related labels, causal notes, and optional structured fixes. Store stable source identifiers and byte offsets; render line numbers and display columns from the original source text. The C++ stage0 and Aevix compiler port should share diagnostic fixtures and the same semantic categories.

Use error, warning, note, and help deliberately. A note explains an existing finding; it must not masquerade as a separate fatal error. Give stable codes to semantic categories, rather than to the English wording or compiler-internal line. Avoid machine consumers having to match sentences.

Related labels need their own source IDs because declarations, imports, generic constraints, and callers may live in different modules. Source versions must be explicit when an editor buffer changes; a fix for an older version must not be applied to a newer buffer silently.

Readable source excerpts and locations

Terminal output should show the file and line, a concise message, a source excerpt, and an underline for the primary range. Show nearby related ranges when they explain the cause. Keep the location meaningful when the range is empty, crosses lines, touches EOF, or points to an imported declaration. Long lines need bounded excerpts and a visible truncation marker.

Keep byte offsets as the canonical source coordinates. Decode UTF-8 only for presentation and the documented editor conversion. Tabs, combining marks, wide characters, CRLF, and malformed source bytes must not cause an underline to point at another token. A display-width policy and tab width must be chosen and tested. VS Code positions use its expected line/character encoding, independently of terminal cell widths.

Color is optional and never carries the only distinction between an error and a note. Plain output must remain usable when redirected or when color is disabled. Escape terminal control characters from source, symbol names, paths, and OS messages; showing an untrusted source line must not execute a terminal escape sequence.

Explain types, overloads, and constraints

A type mismatch should state the expected type, actual type, and the context that imposed the expectation. Prefer argument 2 requires &mut Vector<i32> to a bare “no matching overload.” If multiple overloads fail, give a bounded list of the most relevant candidates and the specific rejected parameter or constraint. Distinguish no viable candidate from several equally valid candidates.

Generic diagnostics should retain the original declaration, concrete substitutions, failed where requirement, and a bounded instantiation chain. A failure in a generated specialization should still point back to editable source. Do not print unbounded recursive type names or thousands of nearly identical candidate notes.

Import diagnostics should name the full module path, the colliding origins, and the permitted qualification. Missing selected names, private declarations, case-only spelling mistakes, and missing module roots have different causes and should have distinct messages.

Show ownership and borrow causes

For use after move, label the move and later use. For a live-borrow conflict, label the original loan, conflicting access, and the later use that keeps the loan live. For a returned dangling view, show the local owner, creation of the view, and return boundary. Distinguish a shared loan from an exclusive loan and identify the overlapping field or index region when the analysis knows it.

Explain Copy, Drop, capture modes, and partial-initialization cleanup through their actual rules. A partial move from a Drop owner should identify the enclosing Drop contract. A closure escape should identify its captured owner and escaping use. A persist initialization or shutdown restriction should identify the relevant storage declaration rather than just the internal runtime guard.

Offer a fix only when the compiler can justify it: use the moved destination, shorten a borrow, introduce a disjoint scope, pass a read borrow to an available borrowing overload, or explicitly clone through a fallible API. Do not propose cloning as a universal ownership repair or remove required cleanup.

Actionable fixes and recovery

A fix contains a source span, replacement bytes, a short explanation, and an applicability level. A machine-applicable fix must be local, unambiguous, and safe under the same source version. Examples include an exact misspelled keyword or a clearly missing delimiter; broad API redesigns belong in help text. Conflicting edits need a selection policy rather than being applied together blindly.

Parser recovery should synchronize at a justified delimiter or declaration boundary, preserve useful source ranges, and emit several independent errors in one run. It must suppress cascades caused by one missing token. Type and ownership passes should stop using invalid placeholder facts when doing so would produce misleading downstream errors.

Apply explicit limits to the number of diagnostics, candidate notes, nested causes, source excerpt size, and generic traces. Emit a final truncation note when a limit is reached. Recovery must make forward progress on malformed or adversarial source and must not loop, exhaust the stack, or produce quadratic diagnostic output.

Plain output, JSON, and the editor

Render the same record to human terminal output and a versioned machine format. The JSON representation should carry stable codes, severity, source identity, canonical byte ranges, related locations, notes, and structured edits. Keep the schema independent of terminal color, wording, and locale. The command-line mode and final field names require implementation review.

The VSIX should translate canonical locations into editor positions, show related information, and expose only justified quick fixes. Preserve an existing document version check so a late compiler response cannot replace newer diagnostics. A compilation failure or malformed JSON response should become one clear tool failure, not a list of invented language errors.

Deterministic ordering should use explicit source and span rules, with stable tie-breaking for the same input and configuration. Parallel compilation must not let worker completion order randomize the final list. Resolve paths according to an explicit project-root policy; avoid leaking home directories, environment values, credentials, or build-server paths into public diagnostics and artifacts. Relevant OS errors may retain an error code without exposing unrelated sensitive context.

Keep library logging separate

The requested system.log(level, message, optional code) belongs to the 0.3 CPU library work. Its exact available overloads and runtime result must be documented from the implemented system module and tests. A library log entry is ordinary program output; it is not a compiler diagnostic and must not change compilation status or create an exception.

Use a typed level and make an optional code distinct from free-form message text. Preserve the established output evaluation and ownership rules, explicit IO failure handling, call-level serialization, and explicit flushing. No disabled-log optimization may skip an argument with side effects unless that evaluation contract is separately chosen. A timestamp, output destination, filtering policy, and structured log encoding are additional explicit API decisions; their presence must not be inferred from the function name.

Compiler diagnostics should use the structured model above even if the compiler also logs internal debugging information. Do not route user-facing source errors through a generic printf or a log message and lose their source spans, related locations, or machine-readable codes.
