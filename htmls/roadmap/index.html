Planning status

Self-hosting is scheduled for 0.5. This provisional plan combines source-based reviews by the implementing agents and the existing language decisions. The requested Claude Opus 5.5 review stopped at an account limit before its final answer. This is not a completed cross-model consensus. See review status.

GPU is excluded from 0.2. CPU SIMD and scoped parallel execution remain in scope. The full library catalog is not a bootstrap prerequisite.

Additional 0.3 and 0.4 work

The following additions supplement the existing roadmap. They do not replace the native resource/library work in 0.3, the compiler port in 0.4, or the self-hosting target in 0.5. New APIs and syntax are plans, not features of the current 0.2 compiler. Calls before definitions and valid interface overrides already exist; their 0.3 work documents and strengthens the existing contracts.

Prerequisite order

Safe native resources come before collection/text/hash/IO/process libraries. Introduce the system console layer on the audited byte/error boundary; keep broader File and Process ownership work. Land the approved 0.3 convenience rules without broadening general implicit conversions, then freeze the compiler subset. New 0.4 syntax must land in stage0 and its shared regression fixtures before the Aevix port depends on it. Port source storage and syntax before semantic passes, then ownership and AIR verification before native execution.

Use SourceId, NodeId, TypeId and byte spans as long-lived identities, with short borrows during lookup. Growing a Vector cannot preserve long-lived element loans. A direct translation of stable C++ object addresses into Vector references would conflict with borrowing.

Current C FFI accepts 32/64-bit numeric parameters/results and void returns. Design audited C shims with opaque owning handles and bounded nonescaping byte loans before ordinary File/Process wrappers. Passing an address as u64 is not a safe substitute.

Self-hosting boundary

The frontend, semantic analyses, AIR construction and compiler driver must be written in Aevix. A launcher around the C++ frontend does not meet the goal. LLVM, audited platform shims, native runtime and linker may remain external dependencies.

A bespoke CPU backend, GPU, speculative JIT tiers/OSR, a network package registry, async executor, regex and full locale/Unicode stacks do not need to block bootstrap.

Decisions before 0.3 implementation

User-defined cleanup syntax, native FFI resource/buffer contracts and any stable public layout/ABI promise need a focused design decision. Keep these open until implementation instead of granting unchecked pointer or callback privileges.

Version serialized AIR and persistent caches. Include source/dependency content, compiler/runtime/LLVM versions, target features/layout and options in cache identity. Mutable AST addresses are not persistent IDs.

The system console functions and do-while/try work are additional targets. The precise formatting-call contract and try error model need focused review; adding try does not by itself approve throw/catch exception unwinding. See the linked version plans for confirmed scope versus proposed details.
