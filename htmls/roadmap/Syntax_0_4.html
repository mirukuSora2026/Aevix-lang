Relationship to the existing roadmap

The 0.4 plan includes syntax research and implementation for try and do ... while. This work supplements the existing milestones: 0.3 still establishes native resource and library foundations, 0.4 still ports the compiler to Aevix, and 0.5 still performs the self-hosting bootstrap.

This is a future work plan. These additions are not claims about the current 0.2 implementation. The syntax sketches below are not executable 0.2 examples.

Type-first declarations, immutable defaults, explicit non-void returns, mandatory condition parentheses, and the existing ownership and visibility rules remain in force. A new convenience construct must have a defined translation into the compiler's control flow and cleanup model.

Post-test loops

Add do ... while (condition); as a 0.4 work item. Execute the body before testing its bool condition. Normal completion of the body and continue; both lead to the condition; break; exits without evaluating that condition. An earlier return or propagated error can also leave the loop before the test.

i32 repetitions() {
    mut i32 count = 0;
    do {
        count++;
    } while (count < 3);
    return count;
}

The trailing semicolon and condition parentheses are required. A single statement can omit its body braces under the existing statement-body rules; declarations still require a block. Locals declared inside the body block are not visible in the later condition.

Test definite initialization, loop-carried moves and loans, cleanup on each exit, nested loops, and a condition that returns an error. The Java and C++ post-test loop specifications are comparison material, not permission to adopt their implicit conversions. Aevix conditions remain bool-only.

Local error handling

Include try in the 0.4 design and implementation work. Its precise grammar and error model need a focused decision before parser changes. The preferred direction is local handling of Result values, preserving the established ? and explicit-error model.

The confirmed 0.3 common-error and Result model plans Error for borrowed inspection and AnyError for owned Result propagation. This keeps try as 0.4 design work rather than adding try/catch to 0.3. It does not add implicit conversion between Result error types or select Java-style unwinding.

ApproachBenefitAevix decision
Result-based local error scopeGroup fallible operations and handle their error without returning from the entire function.Preferred design to develop. Specify the destination of each ?, success completion, and nesting before accepting a grammar.
Throw/catch exception unwindingTransfer a thrown error through calling frames to a matching handler.Requires an explicit user decision because it changes error and cleanup policy. It is not implied by adding the name try.
Finally or deferred cleanupAttach work to an exit path.Review against 0.3 resource cleanup first; avoid two independent owners trying to release the same resource.

Rust's official try-block documentation describes a local scope for ? under an unstable feature. Java's try statement instead handles thrown exceptions and has separate finally/resource rules. These are different designs; the Aevix plan does not claim stable Rust availability or silently import Java's unwinding semantics.

Preserve explicit normal returns and do not introduce implicit final-expression returns. A closure remains its own return/propagation boundary. Normal exits must release initialized owners exactly once; local recovery must not catch safety stops, invalid foreign behavior, or process termination as ordinary Result errors. Existing direct-return behavior outside a new error scope must remain compatible.

Other syntax to review

The following are research candidates, not additional confirmed features or new 0.5 prerequisites.

CandidateUseCompatibility check
Labeled break and continueLeave or continue a chosen outer loop.Keep ordinary break/continue behavior. Define label scope, forbid shadowing, prohibit jumps across functions or closures, and preserve cleanup.
Guarded switch casesApply a bool condition after a variant or pattern matches.Keep case scopes and written break;. A guard that can fail cannot by itself prove an enum variant is fully covered.
Pattern-based conditional bindingUse Optional or enum payloads with less nesting.Retain type-first binding, private field access, explicit move/borrow rules, and the selected statement-only if model.
DeferRun an explicitly registered action at scope exit.Hold until the resource cleanup contract settles. Define capture lifetimes, order and failure behavior before adding another cleanup mechanism.

Adopt a candidate only when it solves a demonstrated compiler or library problem without weakening the current rules. Researching a feature does not approve its exact spelling or promise to ship every candidate.

Integration and exit gates

  1. Record the accepted grammar and its control-flow, ownership and cleanup semantics.
  2. Implement and test it in the C++ stage0 compiler before relying on it in compiler source written in Aevix.
  3. Run shared acceptance, rejection, normalized AST/IR and execution fixtures through stage0 and the Aevix compiler port. Include early exits and failed operations.
  4. Freeze the added syntax before the 0.5 bootstrap comparison. If a candidate is delayed, write the port using the existing subset rather than silently weakening a bootstrap gate.

The new work does not remove any existing 0.3, 0.4 or 0.5 exit gate. The self-hosted frontend must still perform parsing, typing and ownership analysis itself.
