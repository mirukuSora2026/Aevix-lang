1. Three distinct failure channels

ChannelMeaningHandling
Result<T, E>Recoverable failure is a normal typed value. Optional absence is a separate success/absence model.Inspect an exhaustive switch, return the Result, or use postfix ?.
Guarded runtime stopAn unsafe operation is rejected before an invalid access or overflowing integer instruction executes.Fix the precondition or choose a separately implemented checked/optional API; ? cannot catch a trap.
Compiler / tool diagnosticSource syntax, type, ownership, module, backend or host-tool failure.Repair the diagnostic or environment; no program error value is constructed.

Aevix currently has no language-level throw / try / catch exception mechanism. C++ exceptions inside the compiler are implementation details and are not Aevix exception types.

The planned 0.3 common Error interface provides opt-in borrowed inspection. It does not make Error a sized Result payload, require every E to implement the interface, implicitly box or convert errors, or add exception unwinding. The separate try/error-scope design remains 0.4 work.

2. Error-type catalog

Browse 69 catalog error names and their referenced API signatures. The catalog covers numeric, text, collection, ownership, reference-counting, synchronization, Tensor/SIMD, task and device errors. The 0.2 working profile supports explicitly imported CPU SIMD and scoped CPU parallel.for_each with named, validated scalar workers. General Task APIs, Tensor and GPU execution remain unsupported; their catalog error records remain design contracts.

3. Implemented 0.2 error carriers

The 0.2 profile implements the following error subsets. These carriers do not make every API associated with the same catalog name executable. The implementation profile records the current platform scope; native Windows execution remains outside its established evidence.

InputError<T>AllocationFailure and SizeOverflow, each carrying public T input.Vector.push and Box.new preserve the unused input on documented preflight failure.

TextErrorAllocationFailure; SizeOverflow; InvalidUtf8; InvalidBoundary.Implemented UTF-8 owner construction/mutation and text boundary checks.

ComplexErrorZeroDivisor.Imported Complex.div and Complex.reciprocal reject a zero denominator.

The seven core carriers above are automatically available. ComplexError is supplied by the imported complex module; it is not a prelude error. Box requires import memory { Box };, and import memory { Box, InputError }; re-exports the canonical InputError type. AllocError and AllocationError remain distinct design names, not aliases for CollectionError. See the 0.2 implementation profile for supported operations.

Dynamic-allocation example, implemented minimum profile:

Result<Vector<i32>, CollectionError> make_values() {
    i32 values[] = [1, 2, 3]?;
    return Result.ok(values);
}

The literal allocates an owned Vector. Postfix ? propagates exactly CollectionError on failure; success moves values into the returned Result. This example does not introduce implicit allocation for fixed Array literals or promise the full Vector API catalog.

4. Explicit handling and propagation

Result<i32, i32> fetch(bool available) {
    if (available) return Result.ok(42);
    return Result.err(404);
}

Result<i32, i32> compute(bool available) {
    i32 value = fetch(available)?;
    return Result.ok(value + 1);
}

Result.ok and Result.err infer their carrier types from the return context. The error type is exactly the same in both functions. The successful branch explicitly returns its value. A bare integer is not a valid ? operand, and a different error type is not silently converted.

5. Cleanup and owner recovery

Ordinary error propagation follows scope cleanup for fully initialized owned values. The implemented array/Box paths clean constructed owned values and preserve unused inputs on their documented failures. Broader collection designs also require initialized-prefix cleanup, but those contracts do not establish implementation of every catalog API. Owner-preserving errors such as InputError<T> explicitly carry accepted inputs on preflight failure; this is a per-API guarantee, not universal rollback. Values already moved into completed callbacks cannot be reconstructed automatically.

Normal ownership cleanup does not promise successful flushing, saving or closing. Such fallible operations need explicit Result-returning APIs before destruction. Trap, abort, process kill and forced termination do not guarantee normal scope or persist cleanup.

6. Runtime and compiler failures

Read all failure categories, compiler-internal exception types, CLI exit behavior and persist initialization failures. Diagnostic text and operating-system signal numbers are not a stable public error enum or portable ABI.
