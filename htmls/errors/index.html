1. Three distinct failure channels

ChannelMeaningHandling
Result<T, E>Recoverable failure is a normal typed value. Optional absence is a separate success/absence model.Inspect an exhaustive switch, return the Result, or use postfix ?.
Guarded runtime stopAn unsafe operation is rejected before an invalid access or overflowing integer instruction executes.Fix the precondition or choose a separately implemented checked/optional API; ? cannot catch a trap.
Compiler / tool diagnosticSource syntax, type, ownership, module, backend or host-tool failure.Repair the diagnostic or environment; no program error value is constructed.

Aevix currently has no language-level throw / try / catch exception mechanism. C++ exceptions inside the compiler are implementation details and are not Aevix exception types.

2. Complete error-type catalog

Browse all 69 error names and every associated API signature. The catalog covers numeric, text, collection, ownership, reference-counting, synchronization, Tensor/SIMD, task and device errors. GPU and parallel application execution remain deferred; their error records remain design documentation.

3. Minimum 0.1 error carriers

The promoted array/Range/Box implementation uses these canonical core types. Their minimum operations passed the macOS ARM64 Release/sanitizer, Linux ARM64 and QEMU-emulated Linux x86-64 working-profile suites (24/24 each). Native Windows qualification remains pending. Other catalog APIs and error names remain design/example records.

CarrierVariants and payloadMinimum meaning
CollectionErrorAllocationFailure; SizeOverflow; no payload.Minimal dynamic-array allocation/size failure.
InputError<T>AllocationFailure { public T input; }; SizeOverflow { public T input; }.Minimal Vector.push and Box.new return the unused owned input on preflight failure.
RangeErrorInvalidStep; CountOverflow; no payload.Invalid zero step magnitude or unrepresentable count query.

These errors are automatically available core types. Box itself requires import memory { Box };; import memory { Box, InputError }; re-exports the same InputError type. AllocError and AllocationError remain distinct design names and are not aliases for CollectionError. See the required 0.1 profile for the exact boundary.

Dynamic-allocation example, implemented minimum profile:

Result<Vector<i32>, CollectionError> make_values() {
    i32 values[] = [1, 2, 3]?;
    return Result.ok(values);
}

The literal allocates an owned Vector. Postfix ? propagates exactly CollectionError on failure; success moves values into the returned Result. This example does not introduce implicit allocation for fixed Array literals or promise the full Vector API catalog.

4. Explicit handling and propagation

Result<i32, i32> fetch(bool available) {
    if (available) return Result.ok(42);
    return Result.err(404);
}

Result<i32, i32> compute(bool available) {
    i32 value = fetch(available)?;
    return Result.ok(value + 1);
}

Result.ok and Result.err infer their carrier types from the return context. The error type is exactly the same in both functions. The successful branch explicitly returns its value. A bare integer is not a valid ? operand, and a different error type is not silently converted.

5. Cleanup and owner recovery

Ordinary error propagation follows scope cleanup for fully initialized owned values. The collection design requires a partially constructed owner to clean its initialized prefix exactly once; the minimum array/Box implementation is covered by the refreshed macOS/Linux ARM64 and QEMU-emulated Linux x86-64 working-profile tests. This does not claim implementation of every collection API in the catalog. Owner-preserving errors such as InputError<T> explicitly carry accepted inputs on preflight failure; this is a per-API guarantee, not universal rollback. Values already moved into completed callbacks cannot be reconstructed automatically.

Normal ownership cleanup does not promise successful flushing, saving or closing. Such fallible operations need explicit Result-returning APIs before destruction. Trap, abort, process kill and forced termination do not guarantee normal scope or persist cleanup.
