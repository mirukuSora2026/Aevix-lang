1. Function declarations: the agreed contract

A function names a computation, declares how inputs are received, and states what normal completion returns. Aevix puts the return type before the function name and the parameter type before each parameter name. Parameter bindings are immutable by default. Ownership transfer and borrowing are visible at the call site.

This page describes the implemented 0.2 declaration and closure rules, with remaining design limits listed separately. Linked data-type catalogs can include future APIs; no stable foreign ABI is promised by ordinary function syntax. The chosen condition and loop forms are documented in Control Flow. Remaining features are identified in the scope section.

2. Return type first, then name and parameters

i32 identity(i32 value) {
    return value;
}

i32 use_identity() {
    i32 source = 12;
    rsn result = identity(source);
    return result;
}

identity receives and explicitly returns an i32 value. Empty parentheses declare no parameters. A call supplies arguments in their parameter positions. Every statement, including a declaration, assignment, call statement or return, ends with a semicolon. Braces delimit function and control-flow blocks; no extra semicolon is required after a function body.

rsn statically infers result as i32 from the call. It does not request a dynamic type. Return and parameter types in these declarations are explicit. Local inference does not settle a future shorthand for inferred function signatures.

The same return-type-first declaration applies inside structs and enums. A function without a self receiver is called through its type, such as User.new(...). The ordinary new function name does not request hidden heap allocation. An instance method explicitly declares &User self, &mut User self, or User self; receiver borrowing may be automatic or written explicitly at the call.

3. Parameter forms and matching calls

Parameter declaration Call argument Permission and ownership
T value x Copy values are copied; an owning non-Copy value moves into the function.
&T value &x Shared read borrow; caller retains ownership and compatible read aliases.
&mut T value &mut x Exclusive write borrow; an ordinary writable owner needs a mut binding.
mut T value x Mutable callee-local value; no new right to change caller storage.
&T value or &mut T value existing_reference Pass an already compatible reference directly, without another &.
Slice<T>, MutSlice<T> or string_view existing_view The view already carries its borrowing capability; pass it directly. A declared MutSlice parameter reborrows an existing exclusive view under the rules below.

T is explanatory type notation, not a generic-function declaration. Concrete examples use i32, string and existing containers. mut T and &mut T distinguish which storage may change, independently of compiler inlining.

4. Value inputs copy scalars and move owners

string relay_owned(string value) {
    return value;
}

string transfer_once(string original) {
    string moved = relay_owned(original);
    return moved;
}

i32 is Copy, so identity(source) leaves source usable. An owning string moves when passed by value. In transfer_once, original becomes unavailable after relay_owned receives it; moved receives the returned owner and is then returned to this function's caller. No string contents are silently deep-cloned.

An immutable owner may move. Immutability forbids ordinary mutation or reassignment; it does not pin ownership in place. Borrow when temporary access should preserve caller ownership. An independent duplicate requires an explicit copy/clone operation and its cost and error contract.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: original has already moved into relay_owned.
string use_after_move(string original) {
    string moved = relay_owned(original);
    return original;
}

5. Parameter bindings are immutable by default

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: value is an immutable by-value parameter.
i32 overwrite_parameter(i32 value) {
    value = 0;
    return value;
}

A function may read or move value according to its type, but cannot reassign that binding without mut. The rule applies inside the function regardless of caller mutability. Passing a mutable i32 still supplies a separate copied scalar; the caller's mut permission does not transfer through a value argument.

An owning argument instead moves. Mutating that moved owner does not create an alias to a caller binding that has lost ownership. Reference binding mutability and access to the referenced storage are separate concerns.

6. mut changes the callee-local value

i32 reset_copy(mut i32 value) {
    value = 0;
    return value;
}

i32 keep_original() {
    i32 original = 10;
    i32 changed = reset_copy(original);
    return original;
}

reset_copy may replace its local copy. changed is 0, while original remains 10. The caller needs no mut binding because the call requests no write borrow. Assignment is used here instead of arithmetic, avoiding any assumption about overflow or arithmetic-error handling.

For an owner, mut allows callee-local mutation after the move. It does not automatically return ownership: returning, storing or destroying the owner follows the function body and resource contract.

7. Shared read parameters use &T

i32 read_value(&i32 value) {
    return *value;
}

i32 read_original() {
    i32 number = 10;
    &i32 reference = &number;
    i32 first = read_value(&number);
    i32 second = read_value(reference);
    return second;
}

&number creates a shared read borrow. *value accesses the borrowed i32, and returning it copies that scalar. The function does not acquire ownership of number. Compatible read borrows may coexist, including reference and the temporary borrow supplied for first.

reference already has type &i32. read_value(reference) passes the requested capability directly; adding & would introduce another reference layer. A shared reference does not authorize ordinary writes through its target. Interior synchronized types follow their separately declared contracts.

8. Exclusive write parameters use &mut T

void set_value(&mut i32 target, i32 value) {
    *target = value;
}

i32 update_original() {
    mut i32 number = 10;
    set_value(&mut number, 20);
    return number;
}

*target = value changes caller storage, so number must be declared mut to create this ordinary write borrow. After the call's loan ends, the caller reads number and observes 20.

The target binding is immutable, yet its &mut i32 capability permits writing the referent. Reassigning target to another reference would change the binding and is not allowed here. Making a shared &i32 binding locally mutable cannot upgrade its referent permission.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: number is not a mutable owner binding.
void borrow_immutable_owner() {
    i32 number = 10;
    set_value(&mut number, 20);
}

9. Forward references and borrowed views directly

void forward_write(&mut i32 target, i32 value) {
    set_value(target, value);
}

usize count_values(Slice<i32> values) {
    return Slice.len(values);
}

usize forward_view(Slice<i32> values) {
    return count_values(values);
}

forward_write already receives an exclusive reference. Passing target directly forwards the requested access; it does not manufacture a second independent write capability. Overlap and lifetime checks remain active. Adding & mechanically is not a conversion rule.

Slice<T>, MutSlice<T> and string_view already carry borrowing capabilities. count_values receives a slice descriptor directly, not ownership of its element allocation. Vector<i32> by value instead moves the owning container, while &Vector<i32> borrows that owner. The signature must express the intended boundary; a plain view is not automatically wrapped in another reference.

Reborrow known exclusive parameters; move ordinary values

After type normalization, a formal parameter whose known outer form is &mut U or MutSlice<U> automatically reborrows a compatible existing exclusive reference or view passed directly. U may itself be a generic type parameter. This lends a derived capability; it does not move the source binding or copy an exclusive loan. Conflicting use of the parent capability is suspended until that derived loan ends.

The same distinction applies when an API returns a borrowed reference, view or iterator. Loans nested inside Optional, Result or another returned value remain connected to the parent. The parent does not become available merely because the call returned: every remaining derived loan must have ended, including any possible referent access during cleanup. A compatible shared-reference or read-view argument still preserves its original source lifetime.

void reverse_twice(MutSlice<i32> values) {
    Slice.reverse(values);
    Slice.reverse(values);
    return;
}

Each reverse call declares a MutSlice parameter and finishes its temporary reborrow before the next call. values need not be a mut binding: its existing exclusive referent capability permits the reborrow, while reassigning the descriptor would require separate binding mutability.

A formal parameter declared as an ordinary generic T value keeps value passing. Even when T is later instantiated as &mut i32 or MutSlice<i32>, the non-Copy capability moves. Generic instantiation does not change that declaration into a borrowed parameter. Ordinary value assignment, initialization and return follow the same move rule. Passing a non-Copy view to the generic value parameter of Optional.some, Result.ok or identity<T> likewise moves it. These operations do not gain automatic reborrowing solely from their eventual concrete type. This rule adds no general move expression.

Borrowing behavior follows the declared parameter and API contract; automatic method receiver borrowing is not a universal wrapper conversion or delayed activation of an exclusive loan. See generic function contracts and the Slice parameter modes.

10. Loans follow overlapping storage and last use

For overlapping regions, ordinary safe access allows compatible shared reads or one exclusive write borrow. A write borrow conflicts with another live access when their permissions and regions overlap. Different variables can still view the same allocation. A collection API must establish disjointness before dividing exclusive access.

i32 last_use_example() {
    mut i32 number = 10;
    &i32 observed = &number;
    i32 snapshot = *observed;
    set_value(&mut number, 20);
    return number;
}

observed is last used before set_value, so its read loan no longer conflicts with the later write. If that reference is used afterward, the loan spans the write and causes a conflict:

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: reader remains live across the exclusive write.
i32 conflicting_borrow() {
    mut i32 number = 10;
    &i32 reader = &number;
    set_value(&mut number, 20);
    return *reader;
}

Last-use analysis never extends owner storage. A borrowed result cannot outlive its source, and a function cannot return a borrow of a destroyed local. A single borrowed input gives an obvious semantic source; multiple inputs need an unambiguous relationship. Exact annotation and elision policies for reference-returning signatures remain open, so no guessed lifetime grammar is presented here.

11. Every normal non-void path returns explicitly

i32 choose_value(bool outer, bool inner, i32 left, i32 middle, i32 right) {
    if (outer) {
        if (inner) {
            return left;
        } else {
            return middle;
        }
    } else {
        return right;
    }
}

Every normal path in this illustrative conditional structure explicitly returns an i32. A return completes the current function with its declared value. A final expression is not an implicit return. Reachable non-void fallthrough must be rejected rather than supplied with a default result.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: evaluating value does not return it.
i32 no_implicit_return(i32 value) {
    value;
}

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

// Rejected: the false path falls through without a result.
i32 missing_path(bool enabled, i32 value) {
    if (enabled) {
        return value;
    }
}

Genuinely diverging paths have no normal completion and need no impossible return. That exception follows the actual operation contract; expecting a branch never to happen does not justify a reachable missing return.

12. unit, void and never have different contracts

Return spelling Normal completion Return requirement
i32, string and other value types Produces the declared value. Explicit compatible value on every normal path.
unit Produces its sole value. Explicit return Unit.value(); on every normal path.
void Completes without a value. Fallthrough or bare return; is permitted.
never Cannot complete normally. No fabricated value or impossible return is required. 
unit complete_value() {
    return Unit.value();
}

void complete_without_value() {
    return;
}

void empty_action() {
}

unit is an ordinary value type usable in containers and Result. A unit-returning function is non-void. void is a return-position marker, not a storable value or container element. Calling empty_action as a statement does not implicitly produce a unit value.

never has no valid values. There is no default constructor, implicit zero or fake result for it. Divergence can mean endless work, termination or another genuinely non-returning operation; the resource behavior belongs to that operation's contract. A never declaration alone does not promise cleanup.

13. Errors and absence are ordinary returned values

Result<i32, i32> require_available(bool available, i32 value) {
    if (available) {
        return Result.ok(value);
    }
    return Result.err(404);
}

Optional<i32> maybe_value(bool present, i32 value) {
    if (present) {
        return Optional.some(value);
    }
    return Optional.none<i32>();
}

Err is normal completion carrying an error payload. None represents absence. The examples explicitly return their wrapper values. A Result-returning function may propagate Err, and an Optional-returning function may propagate None, with postfix ?; ordinary successful returns still require return. The declared return type provides constructor context for Result.ok and Result.err; constructing a variant alone does not transfer control.

The caller receives the declared Result or Optional. Postfix ? extracts Ok or Some, or explicitly returns Err or None from a compatible Result- or Optional-returning function. checked(expression) makes directly written integer calculation failures into Result values. No implicit unwrap, error conversion or exception-catching syntax is introduced. Owning payloads still move; borrowed payloads remain constrained by their source lifetimes.

14. Diagnostic categories and rejected examples

These categories describe required semantic rejection, not implemented error codes or exact compiler messages. Intentionally rejected blocks carry data-expected="compile-error" metadata. Their statements still use semicolons.

Immutable binding Assignment to an immutable parameter or reference binding. Use mut only when local rebinding is intended.
Moved owner Use of an owner after its by-value move. Borrow it, return ownership or explicitly clone.

15. Calls preserve ownership and cost contracts

Inlining, eliminating redundant scalar copies and optimizing move representation preserve observable values, ownership, alias restrictions and declared failures. By-value input never silently authorizes a deep clone. A shared borrow never authorizes ordinary mutation merely because generated machine code could write through its address.

AOT and JIT preserve the same function-level meaning. This syntax alone does not schedule a Task, submit GPU work or transfer a buffer. Atomic and Mutex operations can expose synchronized interior mutation under their own rules; an arbitrary &T does not gain those permissions. Function declarations do not promise a stable foreign calling convention.

16. Explicit closures and callable contracts

A closure declares its capture list, typed parameters, an explicit -> ReturnType, and a block body. Captures are explicit: [value] transfers or copies a value, [&read] borrows shared storage, and [&mut write] borrows exclusive storage. Names outside the closure are unavailable unless captured.

i32 apply<F>(&F callback, i32 value)
    where F implements Fn<Tuple<i32>, i32> {
    return callback(value);
}

void use_closures() {
    i32 base = 40;
    rsn add = [base](i32 value) -> i32 {
        return base + value;
    };
    i32 answer = apply(&add, 2);

    mut i32 total = 0;
    mut rsn set = [&mut total](i32 value) -> void {
        total = value;
        return;
    };
    set(answer);
    return;
}

The closure expression ends with the enclosing declaration’s semicolon. A non-void closure must explicitly return a value on every normal exit, just like a named function. A void closure may use return; or fall through. The return type after -> is required; a final expression is not an implicit return.

ConstraintReceiverCurrent profile
Fn<Tuple<Args...>, Output>&FShared calls; read-only captures and unambiguously shared captured-receiver methods.
FnMut<Tuple<Args...>, Output>&mut FCalls may mutate the captured environment; the closure binding must permit mutation.
FnOnce<Tuple<Args...>, Output>FThe call consumes the environment. The current compiler classifies a by-value non-Copy capture this way, including an owned string used only for reading.

Fn closures also satisfy FnMut and FnOnce requirements; FnMut closures satisfy FnOnce requirements. Captured borrows retain ordinary lifetime and exclusivity checks. These callable constraints use static specialization and do not introduce function-pointer conversion, dyn callable erasure, implicit captures, or hidden boxing.

Rejected example. A non-void closure cannot fall through.

void missing_closure_return() {
    rsn invalid = [](i32 value) -> i32 {
        value;
    };
    return;
}

17. Implemented additions and remaining limits

Generic functions, overloads, trailing constant defaults, named arguments and i32 values[] variadic parameter spelling are chosen in Functions and Calls. Full module paths and import lookup are chosen in Modules and Imports. Closures with explicit captures and typed signatures, plus the static Fn/FnMut/FnOnce contracts above, are implemented. Generic function calls may provide a leading explicit argument list completed by inference or trailing defaults. Const functions, function-pointer types, standalone forward-prototype syntax, and async/GPU declaration grammar remain outside this profile. The initial executable entry is i32 main() in the selected entry module. Reference-return lifetime annotation and elision remain open as well. The chosen public/private visibility rules are documented in Scope and Visibility. These free-function examples do not establish a forward-prototype form. Interface requirements use bodyless method declarations; default methods may provide bodies and require override when replaced.

mut, rsn, const and persist are chosen declaration concepts documented in Variable Declaration. const does not establish a const-function qualifier; persist specifies storage duration rather than static methods or function members. An ordinary immutable binding may receive a runtime result.

The primary sources below were read as comparison material. Aevix follows the choices stated on this page; foreign implicit-return, prototype, default-argument and ABI rules are not imported automatically. The implemented generic-call and closure examples are checked against the 0.2 compiler; linked design catalogs do not expand that executable scope.

Variable Declaration · Data Type Reference · Vector · Slice

User-defined type generics use <T>, and type constraints use where T implements Copy. Generic functions put <T> after the function name and where after the parameter list. Multiple requirements use commas and repeat their subject, as detailed in Generic Functions. Enums reuse struct type functions and self methods and can implement ordinary interfaces.
