1. Variable declarations

A declaration binds a name to a statically typed value. Aevix places the type before the name and makes an ordinary binding immutable by default. A declaration therefore answers separate questions: what type is stored, whether this binding may change, whether an initializer is a compile-time expression, and how long its storage exists. Ownership and borrowing add access rules without merging these questions.

Language design reference. This page records decisions made for Aevix; it is not evidence of an implemented parser or compiler. Positive examples illustrate those decisions. Blocks marked as expected compile errors are deliberately invalid. Initializer and function-call details follow their linked type contracts; unresolved policies are listed explicitly below.

Examples are declaration fragments inside a suitable enclosing scope. They introduce no entry-point, visibility, or function-definition keyword. See Function Declaration for parameters and returns.

2. Canonical declaration forms

The following are canonical spellings for the selected forms. T stands for an explicit type, name for a binding identifier, and expression for an initializer. This table is not a complete grammar for every modifier combination. It does not declare every alternative ordering illegal.

Canonical form Type and mutability Evaluation or storage
T name = expression; Explicit T; immutable binding. Initializer may depend on runtime values.
mut T name = expression; Explicit T; mutable binding. Runtime initialization is permitted.
rsn name = expression; Inferred fixed type; immutable binding. Inference is static, not dynamic typing.
mut rsn name = expression; Inferred fixed type; mutable binding. Later assignments keep the inferred type.
const T name = expression; Explicit T; always immutable. Initializer must be compile-time evaluable.
const rsn name = expression; Inferred fixed type; always immutable. Compile-time evaluation is still required.
persist T name = expression; Explicit T; ordinary immutable binding. Per-declaration process-lifetime storage; startup or first-reach initialization follows declaration context.

Every shown declaration ends with a semicolon. The inference keyword is rsn. No additional declaration introducer or colon-separated name/type form is needed.

3. Explicit types and ordinary initialization

An explicit type fixes the binding’s representation and operations. The initializer must satisfy that type’s rules. A literal can use the destination’s permitted literal context, but a value already assigned a numeric type does not silently become another numeric type. The alias int denotes i32; it does not follow the machine’s pointer width.

i32 size = 128;
f64 ratio = 0.5;
char marker = 'A';
unit completed = Unit.value();

These bindings cannot be reassigned merely because their initializers are simple. Ordinary immutable bindings may also receive runtime results. Immutability is an access rule, not a promise of compile-time evaluation, read-only hardware pages, global lifetime, or recursive freezing of every reachable resource. unit is a value type; void is a return-position choice and cannot replace it in a variable declaration.

4. Mutable bindings

Prefix mut when the binding needs permitted writes. It allows replacing the bound value and taking an exclusive borrow of an owned variable, provided type, ownership, and active-borrow rules permit the operation. It never changes the binding’s static type or authorizes conflicting aliases. An immutable owner can still move into another owner; a move is not an implicit clone.

mut i32 count = 0;
count = 1;
count = 2;

Expected rejection: assigning a new value to an ordinary immutable binding is invalid, even if the replacement has the same type.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

i32 count = 0;
count = 1; // Invalid: this binding is immutable.

For an owning aggregate, mutability permits operations through an exclusive owner borrow. Any displaced owning value still follows its destruction contract. Making a binding mutable does not bypass bounds checks, allocation errors, or synchronization requirements.

5. Static inference with rsn

rsn asks the compiler to determine the type from the initializer and available static context. Once determined, that type remains fixed for the binding. An unconstrained integer literal defaults to i32 and an unconstrained real literal to f64. Inference does not create a runtime tagged numeric slot or permit a value to alternate between unrelated types.

rsn size = 128;
rsn scale = 2.0;
mut rsn count = 0;
count = 1;

Here size and count have type i32; scale has type f64. The mutable inferred binding accepts another i32 value, not a different inferred type on each assignment.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

mut rsn amount = 3;
amount = 4.5; // Invalid: amount remains i32.

An inference declaration with no initializer or other permitted type source cannot determine its type. Explicit typed locals can instead use the chosen definite-assignment rule. Inference also retains ownership and borrow lifetimes; it cannot erase them.

Typed locals may be initialized later

An ordinary explicitly typed local may be declared without an initializer. It has no implicit zero/default value. Every reachable read, borrow, address-taking or move must be preceded by a complete successful initialization on that path. An immutable local may be initialized exactly once on each path; a later assignment after initialization requires mut. Const and persist declarations require initializers, and rsn requires an initializer to infer its type.

i32 choose(bool first) {
    i32 value;
    if (first) value = 10;
    else value = 20;
    return value;
}

Both branches initialize value exactly once, so the return is valid. A path that reaches the return without initialization is rejected. Ordinary partial-field initialization is not introduced by this rule: use a complete struct, enum or array value. Cleanup only applies on paths where an owned value was successfully initialized and remains owned.

i32 invalid_initialization(bool ready) {
    i32 value;
    if (ready) value = 10;
    return value;
}

6. Numeric context and explicit conversion

Literal context and conversion of an already typed value are different. A small literal can initialize a compatible fixed-width type when its value is in range. After a variable has type i32, assigning it to i64 is a typed conversion even though every i32 value would fit. Such conversion is explicit, preserving the same semantics across CPU AOT, JIT, and supported device code.

i8 small_literal = 12;
i32 source = 12;
Result<i64, IntegerError> wider = Integer.convert(i64, source);

The explicit conversion keeps the operation’s Result contract visible. A narrower conversion may fail; declaring its result does not automatically extract the success value.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

i32 source = 12;
i64 destination = source; // Invalid: no implicit typed numeric conversion.

Use the Integer and Float references for range, rounding, overflow, and conversion policies. rsn does not relax them.

7. Compile-time constants

const requires an immutable constant whose initializer is evaluable at compile time. const rsn infers its type without weakening that requirement. Ordinary immutable declarations can depend on runtime input; a const declaration cannot use an input available only at runtime. Optimizer constant propagation does not by itself turn arbitrary runtime work into a valid constant initializer.

const i32 LIMIT = 100;
const rsn SCALE = 2.0;
const i32 BLOCK_BYTES = 4 * 32;

Combining mut and const is invalid. Constants also reject later reassignment. The following block demonstrates the forbidden combination, rather than defining another accepted modifier order.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

const mut i32 LIMIT = 100; // Invalid: const and mut conflict.

In this contextual example, runtime_value is an i32 input supplied by the enclosing runtime interface. The first declaration is ordinary immutable initialization; the second requires unavailable compile-time data.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

i32 snapshot = runtime_value;
const i32 CAPTURED = runtime_value; // Invalid: runtime-only initializer.

The 0.2 profile evaluates its supported constant expressions and normalizes const usize generic arguments by value, so equivalent extents identify the same concrete specialization. User-defined constant functions and arbitrary const-parameter types remain outside the profile. Parameter defaults are restricted to Copy-capable compile-time constants; see Arguments and Defaults. A const value does not imply one addressable process-lifetime object.

8. Persistent process storage

persist gives a declaration process-lifetime storage. Visibility, mutability and constant evaluation remain separate. It does not preserve data across process restarts or extend a borrowed source's lifetime.

persist i32 protocol_revision = 1;

At module top level, this value is initialized before program entry. Inside a function, initialization begins when execution first reaches the declaration; subsequent reaches reuse the same completed value. A local initializer cannot directly depend on runtime function parameters or ordinary local variables. In a generic function, each concrete type-argument combination has separate storage shared by that combination's AOT and JIT code versions.

A persist place cannot be moved out and left uninitialized; use borrowing or an explicit operation that safely installs a complete replacement. Its initializer cannot propagate ? to return from the enclosing function before initialization completes.

One thread performs a first initialization while other callers wait. Unfinished values are never exposed. A stored Err is a completed Result value; an initialization execution error is diagnosed and stops the program. Shared modification requires explicit synchronization types, such as Atomic, Mutex or RwLock.

Normal shutdown waits for language-tracked resource users before releasing successfully initialized persist values in reverse initialization-completion order. Cleanup cannot access another persist. See Persistent Storage for dependency order, runtime checks, shutdown boundaries and the remaining open policies.

9. Copies, moves, and owning values

Copy scalar values duplicate their value when initialized from another scalar. Owning non-Copy values transfer ownership by default. This includes Array, Vector, and lowercase string under the selected aggregate rules. An immutable source binding can be moved; afterward it cannot be read, borrowed, or destroyed as a second live owner. Mut does not turn an owning value into a Copy type.

i32 first = 7;
i32 second = first;
Array<i32, 3> original = [1, 2, 3];
Array<i32, 3> duplicate = Array.copy(&original);
Array<i32, 3> moved = original;
usize count = Array.len(&moved);

Even an Array of Copy elements uses explicit Array.copy for aggregate duplication. That operation differs from the ownership transfer into moved. Declaring a second name does not silently clone the first owner.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

Vector<i32> original = Vector.new(i32);
Vector<i32> destination = original;
usize old_count = Vector.len(&original); // Invalid: original was moved.

Explicit Clone may allocate and fail, and need not recursively isolate nested Shared resources. See Array, Vector, and string.

Structs and enums also move by default. implements Copy opts a type into compiler-checked copying: all fields, including every enum variant, must qualify. A type parameter constrained by where T implements Copy does not automatically make its containing type Copy.

10. Fallible initializers

A declaration preserves its initializer’s result type and ownership contract. It does not hide an allocation, unwrap Result, or convert failure into an empty collection. A Result binding can itself own either a success value or recovery information. Handling that result is a separate operation; general propagation and pattern syntax are outside this declaration reference.

Result<Vector<i32>, CollectionError> reserved = Vector.with_capacity(i32, 64);
Array<i32, 3> values = [1, 2, 3];
Result<Array<i32, 3>, CollectionError> cloned = Array.clone(&values);

Fallible clone and allocation remain explicit even when the destination binding is immutable. When an API promises preflight recovery of moved inputs, its error carrier retains those owners. This is the function’s contract, not a universal rollback property supplied by declaration syntax. A callback’s earlier external effects are not undone by naming its Result.

11. Shared and exclusive reference declarations

&T declares a shared read reference; &mut T declares an exclusive writable reference. Creating one borrows an existing value instead of duplicating its ownership. The referent must remain valid for every permitted use. Reading a scalar through *reference copies that scalar value; dereferencing an owning value does not authorize an implicit owner copy. 

i32 value = 10;
&i32 reference = &value;
i32 observed = *reference;
Array<i32, 3> values = [1, 2, 3];
Slice<i32> view = Slice.from_array(&values);
usize count = Slice.len(view);

Calls distinguish x, &x, and &mut x when passing owned values. Existing references and borrowed Slice, MutSlice, and string_view values are passed directly where that borrowed type is expected; do not add an extra address-of operator by rote. Borrowed views retain the owner’s lifetime constraints and never become owners of the backing elements. See Slice.

12. Binding mutability versus target mutability

A reference has both a binding and an access capability. An immutable binding of type &mut T cannot be rebound to another reference, but can write its permitted referent. Conversely, a mutable binding of type &T can select another shared reference while still lacking write access to either target. The location of mut therefore matters.

mut i32 count = 1;
&mut i32 target = &mut count;
*target = 2;
i32 observed = *target;
i32 left = 1;
i32 right = 2;
mut &i32 selected = &left;
selected = &right;
i32 observed = *selected;

Taking &mut owner requires a mut owner binding. That requirement is about the owned variable; using an existing writable reference or view does not require adding another mutable-reference layer.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

i32 fixed = 10;
&mut i32 forbidden = &mut fixed; // Invalid: immutable owner.

In a function parameter, mut T value makes the callee’s by-value local binding mutable. It does not grant access to the caller’s original value. &mut T value grants an exclusive caller-target borrow; the function reference explains the distinction.

13. Last use, overlap, and synchronized interior state

Borrow checking follows active uses and ownership paths, rather than treating every textual reference name as live until the closing brace. A new exclusive borrow can begin after the last use of a conflicting shared borrow. Destructors, captured references, and returned views can keep obligations live; an unused-looking alias must not be assumed dead when cleanup can still access it.

mut i32 number = 10;
&i32 reader = &number;
i32 saved = *reader;
&mut i32 writer = &mut number;
*writer = 20;
i32 after = number;

The next fragment instead uses reader after creating writer, so their conflicting borrows overlap.

Rejected example. This intentionally violates a chosen rule and is not valid Aevix code.

mut i32 number = 10;
&i32 reader = &number;
&mut i32 writer = &mut number; // Invalid: reader remains active.
i32 saved = *reader;

Multiple readers may coexist; conflicting writers or a reader with an exclusive writer may not. Proven disjoint subranges can have separate writable views. Interior synchronization is a distinct contract: Atomic and Mutex may perform their defined operations through shared object references without granting arbitrary &mut aliases. Storage duration alone establishes no synchronization. See Atomic and Mutex.

14. Diagnostic guide

These are required diagnostic conditions and suggested explanations, not implemented compiler error codes. A diagnostic should identify the declaration, conflicting use, and relevant type or loan; it should not silently add clones, widen numeric types, or discard failures.

Condition Explain Typical correction
Assignment to an immutable binding The binding lacks write permission. Use mut when mutation is intended.
Different type assigned after rsn inference Inference fixed one static type. Use a separate appropriately typed binding.
Typed numeric value crosses types implicitly No implicit numeric cast is defined. Call the explicit conversion API.
mut combined with const A constant cannot be mutable. Choose one intended evaluation/access contract.
Runtime-only initializer required by const The value is unavailable to compile-time evaluation. Use ordinary immutable initialization or a true constant.
Exclusive borrow of an immutable owner The owner binding cannot supply writable access. Use mut if that owner should be mutable.
Conflicting active loans Later uses keep an overlapping loan live. End the conflicting use or prove disjoint storage.
Use of a moved owner Ownership transferred to another binding. Use the destination, borrow earlier, or explicitly clone.
rsn with no available type source No static type can be inferred. Supply a type-bearing initializer or explicit type.
void used as a variable value type void is a return-position choice. Use unit when a no-payload value is required.

The correction must preserve the intended ownership and cost model; automatic recovery is not implied.

15. Open decisions and related references

Typed local declarations without initializers are allowed under the definite-assignment rule. Explicit annotations for globally borrowed references remain open. Top-level persist initialization order is now defined by value dependencies, then module-path and declaration-order tie breaking. The fragment T name; is a supported explicitly typed local declaration, but cannot be used until definitely initialized. When rsn has no initializer or other type source, inference cannot succeed. Shadowing of an already visible variable is now forbidden; public/private apply to module and type declarations, while local variables retain lexical block scope. See Scope and Visibility.

The complete modifier-order grammar, combinations involving persistent storage, a constant-function facility and thread-local storage remain open. Const usize generic identity is already normalized by value in 0.2. Function calls now define default arguments and overload ranking; persist defines initialization timing, fatal execution failure and normal shutdown. Visibility and normal-scope resource cleanup are documented in Scope and Comments; no function introducer or implicit final-expression return is added.

The external sources below are comparison material for terminology and design tradeoffs. They do not define Aevix syntax or import another language’s initialization, shadowing, lifetime-annotation, or storage rules. Continue with Function Declaration, the data type index, or the declaration index.

Named-field initialization, private field access, enum variant visibility and type parameter declarations are chosen in the user-defined types, enum, and generic type references. Field default values and custom cleanup declarations remain open.
