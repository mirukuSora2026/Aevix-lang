1. Basic Information

The existing Float8 page documents an extension proposal. Aevix has not assigned an unqualified f8 alias. The candidate code names f8_e4m3fn and f8_e5m2 identify distinct encodings; their final spellings remain under review.

An eight-bit width alone does not determine the exponent bias, NaN encoding, infinity support, or signed-zero behavior. Always record the encoding in tensor and FFI metadata.

FN means finite encodings plus NaN, with no infinity. FNUZ variants are different encodings and are not aliases of the formats on this page.

3. Bit Representation

E4M3FN repurposes encodings that a conventional IEEE-like interpretation would reserve for infinity. Do not apply the ordinary exponent-all-ones rule from f16/f32/f64. E5M2 uses the familiar all-ones exponent special-value structure.

Both formats expose their numeric bit word through u8 in Float.to_bits / Float.from_bits, while byte serialization uses Array<byte, 1>. These are distinct APIs and types. Bitcasting between the two FP8 formats changes the numerical interpretation, so serialized bytes must be accompanied by a format tag. There is no implicit byte/u8 conversion; use Byte conversions explicitly.

4. Precision & Rounding

FP8 has very few significant bits. Most real-valued inputs are rounded on conversion, and spacing grows quickly with magnitude. Use explicit rounding and an explicit overflow policy. E4M3FN cannot produce infinity as the destination encoding; checked conversion must report out-of-range values or a named saturation policy must be selected.

Round-to-nearest, ties-to-even is the candidate baseline. Exact conversion is available only for values the selected encoding can represent.

5. Conversion & Special Values

Finite FP8 values are exactly representable in f32. Converting back to FP8 may lose precision. Signed zero, NaN payloads, non-finite inputs, and finite-range overflow require separate rules.

The proposed API uses Float.convert_exact, Float.convert, Float.to_bits, and Float.from_bits. No implicit conversion between different FP8 encodings is permitted. 

Float.convert(f8_e4m3fn, source, rounding);
Float.convert_exact(f32, fp8_value);
Float.to_bits(fp8_value);
// FP8 type spellings and conversion policy are proposals.

6. Arithmetic & Accumulation

Storage support does not imply native scalar arithmetic, transcendental functions, or atomics. A backend may compute in an explicitly selected wider format and round into FP8 at declared boundaries.

For dot products, specify f32 or another supported accumulator rather than treating repeated FP8 rounding as equivalent. Promotions, transfers, materialization, and emulation costs remain visible.

At the E4M3FN boundary, Float.checked_next_up(448) and Float.checked_next_down(-448) return a range error. They do not manufacture infinity or silently clamp. Interior neighbors follow the selected encoding’s grid. E5M2 unchecked neighbors may reach infinity, while checked neighbors report a non-finite result.

The complete definitions belong to Float. Unsupported instantiations are rejected instead of silently choosing another encoding.

8. string, Bytes & Interoperability

Little-endian and big-endian byte arrays are identical for a one-byte value. A byte stream still needs the exact FP8 format identity. Numeric text and raw-bit transport are different operations; shortest round-trip formatting must round back to the chosen encoding.

Model-import conversion verifies dtype, scale metadata when present, rounding, tensor layout, and storage ownership. FP8 alone is not an integer quantization type and does not imply a scale or zero point.

9. CPU & GPU Support

FP8 is a capability-gated extension proposal. Storage, conversion, matrix operations, scalar arithmetic, and special functions have separate support flags. An explicit emulation path may be offered; native performance is not guaranteed by this page.

Strict and relaxed execution profiles must document flush-to-zero, saturation, NaN handling, and accumulator precision. AOT and JIT cannot choose different semantics for the same requested profile.

10. Float8-Specific Functions

No independent Float8 function namespace is introduced. Encoding-specific metadata specializes the common Float API. An unqualified f8 default, additional FNUZ encodings, and native backend coverage remain explicit design decisions.
