1. Basic Information

Aevix provides binary floating-point values through f16, bf16, f32, and f64. The convenience alias float is exactly f64. Scalars copy their value without heap allocation. Owning arrays and tensors retain their own ownership contracts.

Design draft. This reference records proposed contracts and a comprehensive function catalog. It does not claim compiler implementation, final grammar, or verified hardware support. Every function uses the Float. namespace; instance methods are excluded.

Reference Type Format Status

See the 16-bit, 32-bit, 64-bit, and FP8 candidate references. bf16 and f16 are different formats despite equal storage width. FP8 formats can differ in infinity and NaN support, as documented by ONNX.

2. Numerical Model & Literals

Proposed baseline: round ordinary core arithmetic to the destination format using nearest, ties to even; retain signed zeros and gradual underflow. AOT and JIT must preserve this contract. Reassociation, reciprocal substitution, fused contraction, and subnormal flushing require an explicit alternative numerical profile. Wider internal instructions are permitted only when observable results match the specified operation.

IEEE formats encode finite values, +0, -0, infinities, and NaNs. Overflow may produce infinity; tiny results may become subnormal or zero. These are numeric results, not memory-safety failures. For supported IEEE formats, Float.sqrt(-1.0) yields NaN while Float.checked_sqrt(-1.0) returns a recoverable error under the proposal below. Finite-only formats need their own out-of-range contract.

NaN compares unequal to every value, including itself; ordinary ordering is partial. Arithmetic need not preserve NaN payloads. Explicit bit and byte operations preserve representations. Strict core arithmetic does not establish identical transcendental-library results across devices: each math profile must publish its accuracy and reproducibility guarantees. These distinctions reflect the LLVM floating-point model and Rust f32 guarantees. 

float ordinary = 3.25;       // float aliases f64
f32 small = 3.25;     // contextual literal rounding
f64 value = 0.1;      // nearest representable approximation
Float.is_nan(Float.sqrt(-1.0)); // true under the draft IEEE contract

Decimal literals describe mathematical values and are rounded directly to their contextual type. Typed values never acquire implicit numeric casts. Explicit NaN and infinity constructors avoid silently accepting an overflowing finite literal. Hexadecimal floating-point literals remain a grammar proposal.

3. Function Notation & Error Contracts

API names and format parameters remain descriptive; T value, &T value, and &mut T value are chosen parameter forms. T denotes a supported floating format; arguments marked x, y, or a have that same T unless stated otherwise. D is a destination float, I an integer type, U the same-width unsigned bit type, and B the storage byte count. Type arguments are explicit namespace parameters, such as Float.epsilon(f32).

FloatClass, RoundingMode, Ordering, FloatError, ParseError, FormatError, ByteError, FloatParts, and capability descriptors are proposed support types. They are not additions to the approved scalar list. Rounding modes are TiesEven, TiesAway, TowardZero, TowardPositive, and TowardNegative.

The checked arithmetic proposal rejects nonfinite operands, invalid domains, zero divisors, and finite-result overflow. Rounded finite values, subnormals, and gradual underflow remain successful results; it does not promise exact arithmetic or detect every underflow. Checks are ordinary Result values and must not silently inherit host errno, exceptions, or global rounding state. Functions unsupported by a format or selected backend produce a compile-time capability diagnostic.

Proposed FloatError.OutOfRange reports a requested adjacent value that has no finite encoding. Proposed FormatError variants include InvalidSpecification, BufferTooSmall, and AllocationFailed. string-producing formatting functions return allocation failure through Result; caller-buffer formatting validates capacity separately and performs no heap allocation.

min and max propagate NaN. Their _number counterparts prefer the non-NaN operand; both choose signed zeros consistently. Approximate equality requires caller-selected finite nonnegative tolerances and is not a valid equivalence relation for map keys. total_compare instead follows IEEE total ordering, including signed zeros and NaN representation distinctions, as discussed by Rust total_cmp.

The proposed finite comparison checks |x-y| ≤ max(abs_tol, rel_tol × max(|x|, |y|)), using scaled evaluation when needed to avoid intermediate overflow. Equal infinities return true; NaN and unequal infinities return false after tolerance validation.

Proposed format boundary contract: plain next_up, next_down, and next_after instantiate only for infinity-capable formats. They are unavailable for finite-only E4M3FN. The three checked variants may instantiate for every supported finite floating format whose backend exposes representation-neighbor operations; they reject nonfinite operands with NonFiniteInput and an absent or nonfinite adjacent result with OutOfRange. They never saturate silently.

For proposed E4M3FN, checked_next_up(448) is an OutOfRange error. For E5M2, stepping above the greatest finite value would reach infinity and the checked operation also returns OutOfRange. For checked_next_after, numerically equal operands succeed immediately with the target representation: a -0 source and +0 target return +0, and the reverse returns -0.

17. Explicit Numeric Conversion

Converting a number is different from reinterpreting its bits. Exact float-to-float conversion preserves mathematical value and signed zero; NaN payload conversion requires a separate encoding policy. Float-to-integer conversion maps either signed zero to integer zero, because integers have no separate negative-zero representation. Rounded conversion exposes its rounding mode. Integer conversion checks the rounded integer against exact integer bounds; comparing against a rounded floating representation of I.MAX is insufficient.

18. Byte Representation & Buffer Access

Raw serialization uses byte, the opaque octet type documented in Byte, rather than the numeric integer u8. There is no implicit conversion between them: use Byte.from_u8 or Byte.to_u8 explicitly for each octet when a numeric value is needed. Numeric bit-word APIs retain their documented unsigned integer types.

Fixed-width encodings return stack-friendly Array values; they do not allocate a Vector. Byte order is explicit. Native order is useful for local interop, while portable storage uses little or big endian. Reading signaling NaN bits must not promise subsequent arithmetic preserves signaling state.

19. Parsing & Formatting

Proposed parsing is locale-independent ASCII: optional sign, decimal point, and exponent. It consumes the complete input; whitespace, separators, and special-value spellings require explicit options. Finite overflow is an error. Default formatting round-trips finite values and preserves signed zero; ordinary text need not preserve NaN payloads. Decimal precision limits and parsing resource limits must be documented.

20. Accurate Reductions — Optional Numeric Library

Reduction order affects results. These candidates accept borrowed finite sequences and return a Result; accumulation type is explicit. Parallel versions must expose the selected reproducibility policy. Empty sums and products use zero and one; an empty mean is an error.

21. CPU, GPU, AOT & JIT

Backend capabilities cover storage, core arithmetic, conversion, subnormals, math functions, and atomic operations separately. A format may be storable without native arithmetic. Unsupported operations require an explicit fallback choice or a compilation diagnostic; they must not silently lower precision, flush subnormals, or move a tensor between CPU and GPU.

Low-precision tensor storage does not imply low-precision accumulation. Select an accumulation type explicitly. JIT specialization retains the same selected numerical profile as AOT. Parallel reductions use a documented order or an explicit nondeterministic profile. An opt-in fast-math profile can improve throughput, but the allowed changes to NaN, infinity, signed zero, fusion, and reassociation must be individually stated.

Global floating-point environment mutation, host-specific exception flags, unbounded-precision floats, decimal arithmetic, arbitrary random generation, complex arithmetic, and tensor allocation are outside this scalar namespace. Safe bit conversion is included; unchecked float-to-integer conversion is not proposed as a safe default. These remain separate design decisions.

22. Examples & Edge Cases 

Float.sqrt(9.0);                  // 3.0
Float.is_nan(Float.sqrt(-1.0));   // true: IEEE-style result
Float.checked_sqrt(-1.0);         // Result error: Domain
Float.round_ties_even(2.5);       // 2.0
Float.round_ties_away(2.5);       // 3.0
Float.is_sign_negative(-0.0);     // true
Float.total_compare(-0.0, 0.0);   // Less
Float.fmod(-5.5, 2.0);           // -1.5
Float.remainder(5.5, 2.0);        // -0.5
Float.frexp(6.0);                 // (0.75, 3)
Float.from_integer_exact(f32, 16_777_217); // precision-loss error
Float.approx_equal(0.1 + 0.2, 0.3, 1e-12, 1e-12); // successful true

Approximation checks must handle nonfinite values before subtraction: equal infinities compare approximately equal, NaN never does, and unequal infinities compare false. Tolerances remain explicit. Hashing and map-key equality need a separately selected representation policy; ordinary NaN-sensitive numeric equality is insufficient.

The external references explain their own languages and libraries. They inform this independent Aevix draft; they do not certify Aevix behavior or performance. The catalog spans core functions and optional library candidates rather than asserting universal implementation of every function.
