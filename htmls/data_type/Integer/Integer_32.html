1. Basic Information

i32 is a signed, fixed-width integer. “Int32” names this reference; the page does not introduce another code alias.

The approved int alias denotes i32 and has the same representation, range, and arithmetic rules.

Design draft. Function names and examples describe intended Aevix behavior. They do not establish final grammar, a working compiler, or runtime validation.

PropertyType behavior
Code typei32
Width32 bits; 4 bytes
Range-2147483648 through 2147483647
Distinct values4294967296
RepresentationTwo’s complement
Scalar semanticsCopy

The byte count describes value representation, not register width, stack slots, alignment, structure padding, or a universal FFI ABI. Shared policies live in the Integer reference. 

Integer.min_value(i32);  // -2147483648
Integer.max_value(i32);  // 2147483647
Integer.bit_width(i32);  // 32
Integer.byte_width(i32); // 4
Integer.is_signed(i32);  // true

2. Value Range & Bit Representation

i32 has exactly 32 value bits. The highest bit carries negative weight; there is no separate negative zero. Every bit pattern is valid, but representation does not imply wrapping arithmetic.

3. Literals & Type Inference

An expected i32 type constrains literals to -2147483648…2147483647. Decimal, binary, and hexadecimal spellings describe numeric values, not reinterpretations of signed bits.

The valid minimum literal -2147483648 is distinct from negating an already typed minimum, which overflows. Numeric 0xffffffff exceeds the signed maximum; it does not silently mean -1.

Without contextual typing, an unsuffixed integer literal defaults to i32. Values outside that range require an explicit expected type; literal magnitude must not silently select a larger type.

4. Value Copying & Storage

Copying, passing, or returning i32 duplicates a scalar value without allocating a heap object. Both copies remain independently usable.

This does not make owning Vector<i32> or tensor storage implicitly copyable. Fixed arrays follow the array-copy contract and may copy many elements. Slices and views borrow existing storage rather than duplicate elements.

5. Type Conversion

Typed numeric values do not receive implicit casts.

DestinationConversion requirement
Signed destinationsAll values fit in i64; conversion stays explicit.
Unsigned destinationsNegative values fail for every unsigned destination. Nonnegative values must also fit its maximum.
usize / isizeCheck the actual target width and destination range.
Floating-point destinationsEvery value is exact in f64. No corresponding all-values guarantee holds for f16, bf16, or f32.

Integer.convert checks representability; widen preserves a value in a wider destination. bitcast, wrapping_convert, and saturating_convert explicitly request different semantics. Floating-point conversion back follows the common fraction, NaN, infinity, and range policies.

6. Arithmetic Boundary Values

Ordinary integer arithmetic returns the same integer type and checks overflow, unsigned underflow, and division by zero. A runtime failure safely stops execution; it does not return Result. Use lexical checked(expression) or a named Integer.checked_* API to receive Result<T, IntegerError>, then handle it or propagate it explicitly with ?. This boundary is the same in debug/release and AOT/JIT execution. Wrapping and saturating operations remain explicit alternatives. See Checked Arithmetic for covered operations and the separate open edge cases.

Integer.checked_add(2147483647:i32, 1:i32);    // overflow
Integer.wrapping_add(2147483647:i32, 1:i32);   // -2147483648
Integer.saturating_add(2147483647:i32, 1:i32); // 2147483647
Integer.unsigned_abs(-2147483648:i32);         // 2147483648:u32
Integer.abs_diff(-2147483648:i32, 2147483647:i32); // 4294967295:u32

Negating or taking a signed absolute value of -2147483648 overflows, as does -2147483648 / -1. Division by zero fails. The proposed minimum-value remainder rule gives -2147483648 % -1 = 0; backend handling is required and the rule remains a draft decision.

7. Bitwise Operation Characteristics

Bit counts inspect exactly 32 bits. Leading and trailing zero counts of zero are 32; its one-count and unsigned bit length are 0. The all-ones pattern has 32 one-bits.

Strict shift counts are 0…31. Invalid counts return an error. Checking the count is separate from deciding whether lost left-shift bits are permitted. Rotations reduce counts modulo 32, preserving displaced bits.

Arithmetic right shift gives -3 >> 1 = -2, while truncating division gives -3 / 2 = -1.

8. string & Byte Representation

These encoding APIs return Array<byte, 4> and their fixed-width inverse APIs accept the same type. byte is distinct from numeric u8; use Byte conversions explicitly instead of relying on an implicit conversion.

Numeric parsing enforces i32 range; textual values above 2147483647 fail. Parsing all-ones hexadecimal digits fails numerically, although reinterpreting the matching unsigned bits yields -1.

Encoding of 0x12345678Byte sequence
Big-endian encoding[0x12, 0x34, 0x56, 0x78]
Little-endian encoding[0x78, 0x56, 0x34, 0x12]

Integer.to_be_bytes / to_le_bytes and their inverse functions use exactly 4 bytes. Byte order is explicit for storage and transport; native endianness is not a portable file format. Byte reinterpretation and numeric conversion remain distinct. 

i32 value = 4660;
Array<byte, 4> bytes = Integer.to_be_bytes(value);
i32 decoded = Integer.from_be_bytes(i32, bytes);

Use an explicit wider destination for wider results. Successful arithmetic never silently changes the operand type.

10. Arrays, Tensors & Execution Targets

Array<i32, N> and Tensor<i32, Shape, Place> preserve the scalar range. Shape products, allocation bytes, and indexing use checked size arithmetic rather than i32 arithmetic.

CPU AOT, CPU JIT, and GPU paths must share value and error semantics. Storage width does not guarantee native arithmetic, atomics, or speed on every device. Quantization additionally requires scale, zero point, and accumulation rules; an integer tensor alone provides none. GPU Pending retains storage through actual completion; CPU visibility requires the appropriate transfer and synchronization.

11. Int32-Specific Functions

No i32-only functions are currently proposed. Use the common Integer. namespace with i32 values or an explicit destination. This page specializes boundaries and return consequences; it does not redefine the entire API. External references inform comparisons, not proof of an Aevix implementation.
