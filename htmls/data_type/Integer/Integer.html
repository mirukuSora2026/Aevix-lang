1. Overview

Language design draft. This reference describes the proposed Aevix integer model. The API catalog is not an implementation or a compatibility claim. Declaration syntax and ordinary arithmetic failure boundaries now have chosen rules in Language Grammar; the complete literal-suffix grammar remains open.

Integers represent whole numbers with a fixed, finite range. Aevix proposes signed i8, i16, i32, i64, unsigned u8, u16, u32, u64, and target-sized isize and usize. Signed values use two’s complement. The alias int means i32; float means f64.

For width N, a signed type represents −2^(N−1) through 2^(N−1)−1; an unsigned type represents 0 through 2^N−1. Target-sized integers follow the target’s address model. Their width must not be assumed in serialized data or shared CPU/GPU interfaces.

This page defines common behavior. The Int8 reference documents i8 boundaries and specialized results.

2. Declaration & Initialization

Type inference accepts a literal when its value fits the required integer type. Without a constraining context, an integer literal defaults to int, or i32. The compiler reports an error if the value cannot fit that default; it does not silently choose a wider type.

Values are immutable by default. Mutation requires the chosen explicit mut declaration, such as mut i32 value = 0;. Common operations use namespace functions such as Integer.checked_add(a, b); integer instance methods are excluded from this design.

3. Integer Literals

Decimal literals and explicit binary, octal, and hexadecimal notation are proposed. Prefix and suffix spellings are not yet final. A literal denotes a numeric value, rather than an instruction to reinterpret a bit pattern.

A negative minimum value must remain expressible: the compiler evaluates the sign and literal magnitude before checking the destination range. It must not first require the positive magnitude to fit that signed type.

Compile-time mathematical evaluation may use a wider internal representation. This does not add arbitrary-precision runtime integers, alter typed expression widths, or permit out-of-range initialization.

4. Arithmetic Operations

Already-typed operands do not undergo implicit numeric promotion. Ordinary arithmetic uses matching integer types. Widen explicitly before an operation when the destination width is insufficient; widening the result afterward cannot undo an earlier overflow.

The chosen ordinary integer arithmetic policy checks failures and uses a safe stop when a runtime operation fails. Ordinary operators produce the matching integer type; they do not automatically return Result. The named checked APIs return Result<T, IntegerError>, and the chosen lexical checked(expression) form returns a Result for its directly written integer arithmetic. The failure boundary is explicit and does not change with expected type, AOT/JIT mode or optimization profile. See Checked Arithmetic. The exact termination and cleanup policy of a safe stop remains open.

Truncated division rounds toward zero. Its remainder follows the dividend’s sign. Euclidean division instead produces a nonnegative remainder smaller than the divisor’s mathematical magnitude. Floor division and Euclidean division differ when the divisor is negative.

5. Comparison & Bitwise Operations

Equality and ordering compare matching typed numeric values and produce bool. Already-typed operands do not acquire implicit numeric conversions; an explicit value-preserving conversion makes cross-type intent clear. Untyped literals may receive their contextual type. Bitwise operations work on the fixed-width representation.

Shift count validation and information preservation are separate. A valid count lies from zero through width minus one. A count-checked left shift may still discard high bits; an exact shift also checks that reversing it preserves the original value. Signed right shift extends the sign bit; logical right shift inserts zeros. Rotations preserve every bit and reduce their count modulo the width.

6. Type Conversion

Proposed function Contract
Integer.convert(T, x) Checked integer conversion; returns Result<T, IntegerError> and rejects an unrepresentable value.
Integer.widen(T, x) Returns T when every source value fits the destination; otherwise the type combination is rejected.
Integer.saturating_convert(T, x) Clamps an integer to the destination range.
Integer.wrapping_convert(T, x) Produces the destination-width modular representation; may change the value.
Integer.bitcast(T, x) Same-width signed/unsigned reinterpretation; preserves bits, not necessarily value.

Type arguments above are descriptive notation. Floating-point conversion needs separate rounding, exactness, NaN, and infinity contracts; these integer-to-integer functions do not silently choose them.

7. Overflow & Underflow

Policy Result
Ordinary checked operators Integer result on success; safe stop on runtime arithmetic failure.
checked(expression) / named checked APIs Result: success value or an explicit recoverable error.
Wrapping Modular result at the fixed width.
Saturating Nearest representable boundary.
Overflowing Wrapped result plus an overflow flag.

These are different operations, not optimization settings. Subtracting below an unsigned minimum is also overflow for checked arithmetic. IntegerError is a proposed shared error type. Indicative errors include Overflow, DivisionByZero, InvalidShiftCount, NotDivisible, and DomainError.

Division of a signed minimum by −1 overflows. Standalone remainder for that input is proposed to return zero; a combined quotient/remainder operation still fails. Wrapping or saturation does not define division by zero.

Constant folding preserves the public contract: a constant checked call can fold to Err. An invalid typed literal or required constant value is a compile-time diagnostic. Optimization must not convert a documented error value into undefined behavior.

8. Performance & Memory

An integer is a plain copyable value. Scalar storage does not require an independent heap allocation or reference count. Its representation size does not dictate register use, structure padding, calling conventions, or stack placement. Copying an entire array is a separate aggregate policy and can have substantial cost.

Scalar checked results can be represented without heap allocation. Checks and error handling still have real costs; the compiler may remove a check only when it preserves the specified behavior. Byte conversion returns a fixed array and does not allocate a heap buffer. Text formatting distinguishes allocating output from writing into caller-provided storage.

9. Proposed Function Reference

Complete proposed catalog. These names and contracts describe the current design, not an implemented compiler or library. Every function uses Integer.; there are no integer instance methods.

T is any integer type, S a signed type, and U its same-width unsigned counterpart. A and B may differ; D is a destination, F a supported float, and N the source byte width. Type arguments, explicit returned-reference lifetime annotations, defaults, tuple labels, and supporting view protocols remain conceptual notation.

IntegerError is a proposed shared error-value type for arithmetic, domains, bounds, conversion, parsing, buffer capacity, and allocation. Its final enum layout is open. Ordering and FormatOptions are proposed library types. Checked calls return Result independently of the chosen safe-stop behavior of ordinary operators.

9.13. Endian bytes and bounded buffers Core

Raw serialization uses byte, the opaque octet type documented in Byte, rather than the numeric integer u8. There is no implicit conversion between them: use Byte.from_u8 or Byte.to_u8 explicitly for each octet when a numeric value is needed. Numeric bit-word APIs retain their documented unsigned integer types.

N is T’s byte width. Fixed arrays preserve every bit; signed decoding uses two’s complement. Buffer operations do not allocate.

Integer.to_be_bytes(T x) Array<byte, N> Fixed big-endian representation.
Integer.from_le_bytes(T, Array<byte, N> bytes) T Little-endian decoding; incorrect fixed length is a type error.
Integer.from_be_bytes(T, Array<byte, N> bytes) T Big-endian decoding; incorrect fixed length is a type error.
Integer.read_le(T, Slice<byte> bytes, usize offset= 0) Result<T, IntegerError> Requires N bytes at offset; InvalidOffset or BufferTooSmall otherwise.
Integer.read_be(T, Slice<byte> bytes, usize offset= 0) Result<T, IntegerError> Same bounds contract, big-endian decoding.
Integer.write_le(T x, MutSlice<byte> buffer, usize offset= 0) Result<usize, IntegerError> Prechecks full capacity; failure leaves the buffer unchanged. Success writes and returns N bytes.
Integer.write_be(T x, MutSlice<byte> buffer, usize offset= 0) Result<usize, IntegerError> Same capacity contract, big-endian encoding.

Applicability and implementation boundaries

Arguments use matching types except explicitly heterogeneous conversion and comparison. Signed-only functions reject unsigned type arguments; Integer.wrapping_neg deliberately accepts unsigned modular negation. Integer.unsigned_abs and Integer.abs_diff return unsigned values; wide carry functions use boolean carry or borrow bits.

Bit-range and buffer-offset validation must not overflow the validation calculation itself. Invalid typed literals are compile-time diagnostics; valid constant checked calls may fold to Err. A zero divisor never receives a fabricated wrapping or saturating value. Failure propagation does not roll back earlier side effects.

Parsing errors should distinguish empty input, invalid radix or digit, and out-of-range values. Mathematical-value formatting differs from optional fixed-width bit-pattern formatting: negative hexadecimal output is not automatically a raw bit dump. Atomic operations belong in Atomic<T> documentation. Backend, GPU, FFI, and allocator coverage require implementation and validation before release.

10. Examples

The following calls illustrate proposed notation. Assume a and b are i32 values 40 and 2; Err names an error value rather than an exception. 

Integer.checked_add(a, b);    // Ok(42)
Integer.convert(i64, a);      // Ok(40)
Integer.bit_width(i32);       // 32
Integer.div_rem_trunc(a, b);  // Ok((20, 0))

A size computation should validate multiplication before allocation. The expression below denotes a checked computation, not a finalized declaration or error propagation syntax. 

Integer.checked_mul(element_count, element_size);
// Handle Overflow before allocating the resulting byte count.

11. Compilation & Parallel Execution

AOT and JIT must preserve arithmetic policy, error results, and evaluation order. Specialization may remove checks under validated guards. Backend lowering must guard division, shifts, and other operations that could otherwise produce undefined behavior or poison.

Checked arithmetic cannot be freely reassociated: an intermediate overflow can distinguish mathematically equivalent expressions. Parallel reductions need an explicit accumulation width, ordering policy, and failure contract. Integer storage support, arithmetic support, and atomic support are separate GPU capabilities. FFI adapters must match the external ABI; Aevix aliases do not redefine a foreign language’s int.
