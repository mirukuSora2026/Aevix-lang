1. Basic Information

u16 is a unsigned, fixed-width integer. “UInt16” names this reference; the page does not introduce another code alias.

Design draft. Function names and examples describe intended Aevix behavior. They do not establish final grammar, a working compiler, or runtime validation.

PropertyType behavior
Code typeu16
Width16 bits; 2 bytes
Range0 through 65535
Distinct values65536
RepresentationUnsigned binary
Scalar semanticsCopy

The byte count describes value representation, not register width, stack slots, alignment, structure padding, or a universal FFI ABI. Shared policies live in the Integer reference. 

Integer.min_value(u16);  // 0
Integer.max_value(u16);  // 65535
Integer.bit_width(u16);  // 16
Integer.byte_width(u16); // 2
Integer.is_signed(u16);  // false

2. Value Range & Bit Representation

u16 has exactly 16 value bits. Each bit contributes a nonnegative power of two. The highest bit remains part of the value rather than a sign. Negative values are outside the type’s range.

Bit patternNumeric value
00000000000000000
00000000000000011
100000000000000032768
111111111111111165535

3. Literals & Type Inference

An expected u16 type constrains literals to 0…65535. Decimal, binary, and hexadecimal spellings describe numeric values, not reinterpretations of signed bits.

Neither -1 nor 65536 can initialize this type. Numeric 0xffff is valid when the expected type is u16.

Without contextual typing, an unsuffixed integer literal defaults to i32. Values outside that range require an explicit expected type; literal magnitude must not silently select a larger type.

4. Value Copying & Storage

Copying, passing, or returning u16 duplicates a scalar value without allocating a heap object. Both copies remain independently usable.

This does not make owning Vector<u16> or tensor storage implicitly copyable. Fixed arrays follow the array-copy contract and may copy many elements. Slices and views borrow existing storage rather than duplicate elements.

5. Type Conversion

Typed numeric values do not receive implicit casts.

DestinationConversion requirement
Signed destinationsAll values fit in i32, i64, and i128; same-width i16 accepts only 0…32767.
Unsigned destinationsAll values fit in u32, u64, and u128; smaller destinations require a range check.
usize / isizeCheck the actual target width and destination range.
Floating-point destinationsEvery value is exact in f32 and f64. f16 and bf16 can round; not every value is exact. Some high values also exceed finite f16 range.

The implemented 0.2 conversion is Integer.convert<D>(value), returning Result<D, IntegerError>. It preserves the mathematical value when the destination range contains it. Out-of-range narrowing and negative-to-unsigned conversion return IntegerError.OutOfRange; they do not truncate, wrap, reinterpret the sign bit, or stop the program. Even an all-values-safe widening remains explicit and uses the same Result API. Handle the result or propagate its error with ? from a compatible Result-returning function.

For floating destinations use Float.convert<D> or Float.convert_exact<D>; for an exact float-to-integer conversion use Float.to_integer_exact<D>. The common catalog’s widen, bitcast, wrapping_convert, and saturating_convert describe separate proposed operations and are not implemented 0.2 alternatives to Integer.convert<D>. See the implemented numeric profile.

6. Arithmetic Boundary Values

Ordinary integer arithmetic returns the same integer type and checks overflow, unsigned underflow, and division by zero. A runtime failure safely stops execution; it does not return Result. Use lexical checked(expression) or a named Integer.checked_* API to receive Result<T, IntegerError>, then handle it or propagate it explicitly with ?. This boundary is the same in debug/release and AOT/JIT execution. Wrapping and saturating operations remain explicit alternatives. See Checked Arithmetic for covered operations and the separate open edge cases.

Integer.checked_sub(0:u16, 1:u16);    // underflow
Integer.wrapping_sub(0:u16, 1:u16);   // 65535
Integer.saturating_sub(0:u16, 1:u16); // 0
Integer.is_negative(42:u16);          // false

65535 + 1 overflows. Division by zero fails. Unsigned values have no negative branch. Conversion to same-width i16 checks its smaller positive range; a wider signed type such as i128 represents every u16 value.

7. Bitwise Operation Characteristics

Bit counts inspect exactly 16 bits. Leading and trailing zero counts of zero are 16; its one-count and unsigned bit length are 0. The all-ones pattern has 16 one-bits.

Strict shift counts are 0…15. Invalid counts return an error. Checking the count is separate from deciding whether lost left-shift bits are permitted. Rotations reduce counts modulo 16, preserving displaced bits.

Unsigned right shift fills high positions with zero. For example, 3 >> 1 = 1.

8. string & Byte Representation

These encoding APIs return Array<byte, 2> and their fixed-width inverse APIs accept the same type. byte is distinct from numeric u8; use Byte conversions explicitly instead of relying on an implicit conversion.

Numeric parsing enforces u16 range; textual values above 65535 fail. Negative numeric text fails rather than wrapping to a large unsigned value.

Encoding of 0x1234Byte sequence
Big-endian encoding[0x12, 0x34]
Little-endian encoding[0x34, 0x12]

Integer.to_be_bytes / to_le_bytes and their inverse functions use exactly 2 bytes. Byte order is explicit for storage and transport; native endianness is not a portable file format. Byte reinterpretation and numeric conversion remain distinct. 

u16 value = 4660;
Array<byte, 2> bytes = Integer.to_be_bytes(value);
u16 decoded = Integer.from_be_bytes(u16, bytes);

10. Arrays, Tensors & Execution Targets

Array<u16, N> and Tensor<u16, Shape, Place> preserve the scalar range. Shape products, allocation bytes, and indexing use checked size arithmetic rather than u16 arithmetic.

CPU AOT, CPU JIT, and GPU paths must share value and error semantics. Storage width does not guarantee native arithmetic, atomics, or speed on every device. Quantization additionally requires scale, zero point, and accumulation rules; an integer tensor alone provides none. GPU Pending retains storage through actual completion; CPU visibility requires the appropriate transfer and synchronization.

11. UInt16-Specific Functions

No u16-only functions are currently proposed. Use the common Integer. namespace with u16 values or an explicit destination. This page specializes boundaries and return consequences; it does not redefine the entire API. External references inform comparisons, not proof of an Aevix implementation.
