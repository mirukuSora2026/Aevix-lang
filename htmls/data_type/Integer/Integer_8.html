1. Basic Information

0.2 implementation scope. The integer primitives, including i128/u128, and int = i32 need no import. Literals, matching-type arithmetic, comparisons, bit operations and Integer.convert<D>(value) are implemented. That conversion accepts only integer inputs/destinations and returns Result<D, IntegerError>, with OutOfRange on failure. Use the implemented Float.convert/convert_exact for an integer-to-float conversion. Named arithmetic, parsing, formatting and byte-codec functions in the broader catalog remain proposals. See the 0.2 implementation profile; other catalog entries remain design contracts.

i8 is a signed, fixed-width integer with an eight-bit value representation. “Int8” names this reference page; an int8 code alias has not been approved. The default int alias remains i32.

Design draft. The policies and Integer. function spellings below are proposals. Examples illustrate intended behavior; they do not claim a working compiler, final grammar, or validated runtime.

Property i8 behavior
Code type i8
Value representation 8 bits; 1 byte
Signed range -128 through 127
Distinct values 256
Representation Two’s complement
Value semantics Copy

One byte describes the value representation. It does not promise one-byte registers, stack slots, alignment, containing structures, or a universal foreign-function ABI. See the common Integer reference for shared contracts. 

Integer.min_value(i8);  // -128
Integer.max_value(i8);  // 127
Integer.bit_width(i8);  // 8
Integer.byte_width(i8); // 1
Integer.is_signed(i8);  // true

2. Value Range & Bit Representation

The highest bit has weight -128; the remaining bits contribute nonnegative powers of two. Every eight-bit pattern represents one valid i8 value. There is no separate negative zero.

Bit pattern Signed value
00000000 0
01111111 127
10000000 -128
11111111 -1

The same bits may denote a different unsigned value: 11111111 is 255 as u8. Two’s complement specifies representation; it does not make ordinary arithmetic wrap automatically.

3. Literals & Type Inference

An expected i8 type constrains a numeric literal to this range. Decimal, hexadecimal, and binary spellings describe numeric values unless an explicit bit reinterpretation is requested. Therefore numeric 0xff means 255 and cannot initialize i8 directly. 

i8 low = -128;   // valid minimum literal
i8 high = 127;   // valid maximum literal
i8 bad = 128;    // compile-time range error
i8 hex = 0xff;   // compile-time range error
int ordinary = 12;   // int aliases i32

The minimum literal is accepted as a signed value. Negating an already typed -128:i8 is a separate arithmetic operation and may fail; literal checking must not confuse these cases.

4. Value Copying & Storage

Copying an i8 duplicates its value without a heap allocation or ownership transfer. Changing the copy does not change the original. Passing or returning an i8 follows the same scalar rule. 

i8 original = 12;
i8 copy = original; // both values remain usable

This property does not make every container copyable. Vector<i8>, owning tensors, and boxed storage follow their ownership rules. Array<i8, N> copying follows the array contract and may copy many elements. A slice or tensor view borrows storage; it does not duplicate its elements.

5. Type Conversion

Typed numeric values never gain an implicit cast merely because a destination looks large enough. Use an explicit conversion operation. Widening preserves the signed mathematical value; bit reinterpretation preserves the bits.

Conversion Value rule
i8 → i16 / i32 / i64 / i128 / isize Every value fits in supported targets whose destination width is at least eight bits; signed widening preserves negative values.
i8 → u8 / u16 / u32 / u64 / u128 / usize Only nonnegative values convert successfully. A wider unsigned destination still cannot represent a negative value.
Other integers → i8 Successful conversion requires -128 ≤ value ≤ 127.
i8 → f16 / bf16 / f32 / f64 Every i8 value is exactly representable in all four formats; the conversion remains explicit.

The implemented 0.2 conversion is Integer.convert<D>(value), returning Result<D, IntegerError>. It preserves the mathematical value when the destination range contains it. Out-of-range narrowing and negative-to-unsigned conversion return IntegerError.OutOfRange; they do not truncate, wrap, reinterpret the sign bit, or stop the program. Even an all-values-safe widening remains explicit and uses the same Result API. Handle the result or propagate its error with ? from a compatible Result-returning function.

For floating destinations use Float.convert<D> or Float.convert_exact<D>; for an exact float-to-integer conversion use Float.to_integer_exact<D>. The common catalog’s widen, bitcast, wrapping_convert, and saturating_convert describe separate proposed operations and are not implemented 0.2 alternatives to Integer.convert<D>. See the implemented numeric profile.

6. Arithmetic Boundary Values

Ordinary integer arithmetic returns the same integer type and checks overflow, unsigned underflow, and division by zero. A runtime failure safely stops execution; it does not return Result. Use lexical checked(expression) or a named Integer.checked_* API to receive Result<T, IntegerError>, then handle it or propagate it explicitly with ?. This boundary is the same in debug/release and AOT/JIT execution. Wrapping and saturating operations remain explicit alternatives. See Checked Arithmetic for covered operations and the separate open edge cases.

Integer.checked_add(127:i8, 1:i8);    // overflow
Integer.wrapping_add(127:i8, 1:i8);   // -128
Integer.saturating_add(127:i8, 1:i8); // 127
Integer.unsigned_abs(-128:i8);       // 128:u8
Integer.abs_diff(-128:i8, 127:i8);   // 255:u8

-(-128), signed abs(-128), and -128 / -1 cannot produce an i8 result. Dividing by zero also fails. The proposed remainder rule gives -128 % -1 = 0; this requires deliberate backend handling and remains a draft decision. Wrapping and saturating behavior must be requested explicitly, including at this minimum boundary.

7. Bitwise Operation Characteristics

Bit counts inspect exactly eight bits. For zero, leading and trailing zero counts are 8; its one-count and unsigned bit length are 0. Signed inputs are interpreted as their fixed-width bit patterns where the common function permits them.

A strict shift count must lie in 0…7. Negative or oversized counts return an error rather than inheriting hardware masking. Count validation is separate from bits lost by a left shift; the common shift contract determines whether that loss is checked or explicitly permitted. 

Integer.shift_right(-3:i8, 1); // successful Result containing -2
// Arithmetic right shift rounds downward; -3 / 2 instead yields -1.

Rotation uses counts modulo eight: rotating by eight leaves the value unchanged. Rotation keeps displaced bits, unlike shifting. reverse_bits reverses all eight positions; swap_bytes leaves a one-byte value unchanged.

8. string & Byte Representation

These encoding APIs return Array<byte, 1> and their fixed-width inverse APIs accept the same type. byte is distinct from numeric u8; use Byte conversions explicitly instead of relying on an implicit conversion.

Numeric parsing reads a signed mathematical value. Parsing decimal "127" into i8 succeeds; "128" fails. Parsing "ff" with radix 16 denotes 255 and fails, while "-80" denotes -128.

A byte reinterpretation is different: interpreting the single byte 0xff as i8 yields -1. A numeric conversion from 255:u8 to i8 must still fail.

Integer.to_le_bytes and to_be_bytes each produce the same single byte for i8; their inverse operations consume exactly one byte. Endianness changes byte order, so it cannot distinguish a one-byte representation. Formatting -1:i8 numerically is not automatically a request for the hexadecimal bit pattern ff. 

i8 value = -1;
Array<byte, 1> bytes = Integer.to_be_bytes(value);
u8 numeric = Byte.to_u8(bytes[0]); // 255; explicit numeric view
i8 decoded = Integer.from_be_bytes(i8, bytes);

9. Return Types of Common Functions

Successful value-preserving arithmetic returns i8. Wider mathematical results need an explicitly wider destination or a specialized return type; they do not silently change this scalar’s type.

Function family i8-specific consequence
min_value / max_value i8
unsigned_abs / abs_diff u8, covering 128 and 255 respectively
Strict shift operations Result<i8, …> under the draft common contract
Bit counts and width metadata The common count type; counts range from 0 to 8, rather than returning i8 by inheritance.
Byte encoding A one-byte array under the common byte contract

10. Arrays, Tensors & Execution Targets

Array<i8, N> stores fixed-width signed elements. Tensor<i8, Shape, Place> adds shape and placement; those properties do not enlarge an element’s range. Allocation sizes, dimension products, and indexing use checked size arithmetic, not i8 arithmetic.

CPU AOT, CPU JIT, and GPU execution must preserve the same i8 value and error policies. Eight-bit storage does not guarantee native eight-bit arithmetic, atomic support, or a particular GPU speed. A backend may use wider instructions while preserving the observable i8 behavior. For comparison, Vulkan exposes 8-bit shader support as a feature with separate storage-class restrictions.

A raw i8 tensor is not automatically quantized: scale, zero point, accumulation width, and conversion rules belong to quantization metadata. A GPU Pending retains the required storage until actual completion. Completion alone does not establish CPU visibility; transfer and synchronization follow the common memory contract.

11. Int8-Specific Functions

No i8-only functions are currently proposed. Use the shared Integer. namespace with i8 values or an explicit i8 destination. This page specializes ranges, boundary examples, storage representation, and return consequences; it does not redefine the entire integer API.

The linked external references informed comparison of arithmetic and target behavior. They specify their own languages and backends; they do not establish that the proposed Aevix compiler or runtime has implemented these guarantees.
