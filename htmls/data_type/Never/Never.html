1. Overview

Design draft. These are proposed Aevix APIs, not claims that a compiler or standard library implements them. Parameter modes are chosen: T value, &T value, and &mut T value. Type-pack notation, callable types, explicit returned-reference lifetime spelling, and error enums remain descriptive where marked. Namespace functions are used throughout; there are no value-method aliases.

never has no valid values. It expresses an impossible variant or a computation that never returns normally. It is different from unit, which has one value, and from return-position void, which allows ordinary completion.

2. No construction or default value

There is no Never.new, zero initializer, default value, parse function, or valid bit pattern constructor. A function advertised as returning never must diverge or transfer control out of normal execution; it cannot fabricate a value.

Unsafe or foreign code that falsely claims to produce never violates its contract. The compiler may remove code based on genuine impossibility, so such a false declaration is a correctness boundary.

3. Control flow and explicit returns

For non-void functions, every normally terminating path explicitly returns a value. A path proven to diverge does not require an impossible return statement. This exception does not allow a reachable fallthrough in a function returning i32, unit, or another ordinary value type.

An infinite loop, process termination, or a declared non-returning foreign call can have a diverging control-flow effect only under their actual contracts. The word never does not itself guarantee cleanup, termination, or a particular runtime error policy.

4. Impossible generic variants

Result<T, never> can only contain Ok(T). Result<never, E> can only contain Err(E). Optional<never> can only be None. These properties let generic APIs represent infallibility without inventing a dummy error. 

Result<i32, never> success = Result.ok(7);
i32 value = Result.into_ok(success);
Optional<never> no_value = Optional.none<never>();

5. Function reference

T value passes a value: Copy types are copied, and owning non-Copy values move without a deep clone. &T value is a shared read borrow; &mut T value is an exclusive modification borrow. Calls use x, &x, or &mut x respectively. Already borrowed references and view values are passed directly; adding another & changes the type. *ref accesses the referent. Ordinary &mut x requires a mut owner; mut T value alone makes a by-value parameter locally mutable and does not modify the caller. Overlapping active borrows are checked until last use; disjoint regions may be split safely and no borrow outlives its source. Synchronized interior mutation follows its own type contract. Fn(A) -> B describes a callable; returned-reference lifetime relationships remain documented in prose.

The eliminator is useful to type-check an impossible match branch. It is not a trap API, an escape hatch for missing return values, or a constructor that a caller should attempt to invoke.

6. Containers and inhabitedness

A zero-length Array of never can have no elements to construct. An Array of never with positive length cannot be safely fully initialized. A zero-length Slice of never can describe an empty borrow only when its source and alignment contract are valid; it does not enable a nonempty read.

A Vector of never can be empty. Safe append cannot receive a valid never element. Generic operations must not access uninitialized memory just because a variant or length was expected to be impossible.

7. Layout and representation boundaries

This document does not promise a portable byte size, alignment, or calling convention for never. A compiler may remove an uninhabited enum variant or use an available niche, but such optimizations are not a stable serialization or FFI contract.

A pointer or reference representation is not itself proof of a valid never referent. A safe borrow always requires an initialized valid value of its referent type.

8. Cleanup and resource lifetimes

Divergence does not define one universal destructor policy. An endless computation retains its live resources; an aborting process may not run destructors; unwinding, if supported, follows its separately specified cleanup rules.

Asynchronous device failure must retain in-flight resources until quiescence is established even if a normal result cannot be delivered. An impossible type does not allow a borrow to end before the underlying access ends.

9. Foreign non-returning calls

A foreign noreturn annotation must be validated against the actual implementation and calling convention. A function that returns despite an imported non-returning contract creates a boundary violation. It is not an ordinary Result error.

Use Result<T, E> for recoverable failure. Use never only when no normal value can exist; the compiler should reject a fabricated constructor rather than insert a hidden default.
