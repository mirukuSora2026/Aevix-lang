1. Fixed Length, Not Dynamic Capacity

0.2 implementation scope. Fixed array declarations, canonical Array<T, N> types, matching-length literals, repeated literals [value; N], indexing and supported iteration are implemented without an import. Repetition evaluates value once and requires Copy. Array owners move by default; the named construction/algorithm functions in the Array catalog remain proposals. See the 0.2 implementation profile; other catalog entries remain design contracts.

Language design draft. “Static Array” means fixed compile-time length. The actual type is Array<T, N>; there is no second Static_Array runtime type or implicit storage-duration rule.

A fixed array owns precisely N initialized element slots throughout its lifetime. It has no spare capacity, push, pop, reserve, or resize operation. To change logical length, construct a different array type or use Vector. Borrowing fewer elements creates a Slice, not a shorter owner.

The common Array reference defines ownership, callbacks, errors, and the complete namespace. This page expands size-dependent behavior and lists specialized forms of those same functions.

Chosen array declaration spelling

The declaration head i32 values[5] denotes a fixed array of five i32 elements. The length is fixed; this does not select process-lifetime storage, implicit zero initialization or pointer decay. Initializers use square-bracket element lists. The inline forms in the table are declaration heads; typed local declarations without initializers follow definite-assignment checks.

Declaration headChosen meaningBoundary or related rule
i32 values[5]Five-element fixed array.The canonical type is Array<i32, 5>; fixed parameters pass an array value without pointer decay.
i32 grid[2][3]Fixed two-dimensional array: two rows of three i32 elements each, with both extents known at compile time.Mixed suffixes compose Array and Vector in outer-to-inner order, as explained below.
i32 values[][]Two-dimensional nested dynamic arrays; each row owns its dynamic storage and may have a different length.Dynamic construction yields Result<Vector<Vector<i32>>, CollectionError>; a single array parameter uses the canonical type.
i32 values[](2)Exactly the same two-dimensional nested dynamic array type as i32 values[][]. Parentheses specify rank, not axis lengths.The rank must be a positive compile-time integer constant; complete constant-expression grammar remains open.

Each empty bracket adds one nesting level. The rank shorthand accepts a positive compile-time integer constant, including a suitable const value. Rank is fixed in the type while each dynamic level may vary in length. These owners move under the collection rules. Nested growable vectors and a rectangular Tensor have different shape and storage contracts: no single allocation, globally contiguous buffer or automatic GPU transfer is promised. Existing Array<T, N> signatures below remain proposed API notation while the declaration spelling above is chosen.

Canonical array types and parameter contexts

Array suffixes are shorthand for complete types. Read suffixes from left to right as outer to inner containers: T name[N] means Array<T, N>, and an empty bracket means Vector<T>. Thus T grid[R][C] means Array<Array<T, C>, R>, while T grid[][] and T grid[](2) mean Vector<Vector<T>>. These canonical type names may appear in return types, Result, generic arguments and whole-array references.

Mixed fixed/dynamic suffixes are permitted for ordinary array declarations. T rows[R][] means Array<Vector<T>, R>; T rows[][C] means Vector<Array<T, C>>. Fixed extents remain compile-time constants; a literal containing any dynamic level produces Result<CollectionType, CollectionError>. The rank shorthand stands for repeated empty brackets only, and is not mixed with other suffixes in the initial grammar.

In function parameters, exactly one trailing empty bracket, T values[], is reserved for the chosen final variadic parameter. Receive one dynamic array with Vector<T> values, a complete nested canonical type for a multidimensional array, or a borrowed &Vector<T>/Slice<T>. Repeated-empty-bracket, rank and mixed suffix parameters must use their canonical type in the initial grammar. Fully fixed suffix parameters denote an Array value and follow the ordinary Copy-or-move rules; arrays remain move-by-default. There is no pointer decay.

A reference written in the base element type belongs to each element: &i32 values[5] denotes five shared-reference elements. Borrow an entire fixed array with &Array<i32, 5> values, or modify one through &mut Array<i32, 5> values. All referent lifetimes remain checked.

Literal type context and partial construction

An expected array declaration, canonical type or Result payload supplies element/container context. Without such a context, a nonempty bracket literal defaults to a fixed Array whose length is the written element count. Its element type follows the existing typed-value and numeric-literal rules. A context-free empty literal cannot determine its element type. Ragged rows require an explicit compatible nested dynamic context rather than an automatic hidden promotion to Vector.

rsn fixed_values = [1, 2, 3];
Result<Vector<i32>, CollectionError> dynamic_values = [1, 2, 3];

The first value is Array<i32, 3>; the second stores the Result of dynamic construction. An explicit zero-length fixed array has a known type, while a typed empty dynamic literal still has Result type even if it needs no allocation. On normal construction failure, destroy every successfully constructed element and row exactly once. This is not rollback of earlier input moves or side effects.

Square-bracket initializers and allocation failure

Array initializers use [...]. A fixed declaration's element count must exactly match its length or compilation fails. A nested dynamic initializer may contain different row lengths. A dynamic array literal constructs a Result; callers must handle that Result or use the existing ? operator in a compatible Result-returning function. The error carrier for dynamic literal construction is the existing CollectionError family.

i32 values[3] = [1, 2, 3];

Fixed multidimensional declarations repeat the compile-time extents in outer-to-inner order. Every initializer level must match its declared extent. This example has two rows, each with three elements, and needs no dynamic element-buffer allocation:

i32 grid[2][3] = [[1, 2, 3], [4, 5, 6]];

Both the row count and each row length are checked at compile time. A fixed extent does not mean persist storage. Mixed forms such as grid[2][] compose fixed and dynamic containers and use fallible construction.

The next examples are independent fragments inside compatible Result-returning functions. Their declared array types supply element and rank context; ? extracts the successful array or returns the compatible error.

i32 grid[][] = [[1, 2], [3, 4, 5]]?;
i32 grid[](2) = [[1, 2], [3, 4, 5]]?;

Nested bracket sublists participate in one recursive literal-construction operation. Their allocation failures flow into the outer construction Result, with already initialized rows cleaned once; a question mark at every sublist is not required. This does not implicitly unwrap an ordinary Result-valued element expression.

The two grid forms denote the same nested dynamic type. The fixed primitive array needs no dynamic element-buffer allocation. Array syntax does not remove failures in element expressions or authorize implicit cloning. See Error Propagation for the existing same-error-type Result contract.

Rejected example. The initializer has only two elements for a fixed length of three.

i32 values[3] = [1, 2];

2. Compile-Time Extent & Type Identity

Array<i32, 4> and Array<i32, 8> are distinct types. N must be a nonnegative compile-time usize value. A runtime input cannot become an extent merely because JIT specialization happens to observe a constant.

Type-level sums, products, and differences are checked before a type is formed. Concatenation, splitting, and reshaping must fit target object limits. A runtime vector can be converted only after checking its current length; failure must preserve the original owner in the conversion error.

Shape equality here is structural. Two-dimensional Array<Array<T, C>, R> contains R row arrays of C elements. Flattening has R*C elements, but does not attach Tensor placement, strides, device capabilities, or symbolic Tensor dimensions.

3. Complete Initialization & Empty Arrays

Every safe value has exactly N initialized elements; fixed length does not mean automatic zero initialization. Default construction calls T’s Default operation. Repetition requires explicit Copy or Clone semantics, and index generators construct each element independently.

Length zero is valid and has no first or last element. Element callbacks are not invoked by an index generator at N=0. Ordinary argument expressions are still evaluated before a function call; zero output length does not erase their external side effects.

A fallible generator or clone constructor destroys only the elements successfully produced before Err. The output does not escape partially initialized. These cleanup obligations also apply when a callback uses resources or returns an error after several successful elements.

4. Contiguity, Alignment & Zero-Sized Elements

Element slots are contiguous with native stride size_of(T). The value’s element payload is N times that size; padding within T remains present. A nested array’s linear element order is row-major. Neither raw padding nor native layout is a wire-format contract.

For N=0 or zero-sized T, payload byte length may be zero while the value retains alignment, identity, length, and element lifecycle semantics. The actual ABI representation of an empty object is not promised to equal every foreign compiler’s empty-array representation.

Proposed bounds require logical lengths no larger than isize.MAX and nonzero payload sizes within the target object bound. A type fitting those limits does not guarantee that a particular stack frame can be materialized. Explicit Box or Vector placement provides a separate fallible allocation path.

5. Move, Copy, Clone & Placement

Owning fixed arrays move by default even when T is a scalar Copy type. The old binding becomes unavailable after ownership transfer. An optimizer may elide storage movement, but large inline arrays and whole-array swaps must not be documented as unconditionally constant-time.

Array.copy requires Copy elements and explicitly duplicates all N values. Array.clone requires Clone and follows its element behavior, including potentially shared handles or nested allocations. Neither a memcpy of resource owners nor a universal deep clone is implied.

Inline ownership describes storage containment, not mandatory stack placement. An array can be a field or sit inside a Box. Moving an array to another function does not transfer its contents to a GPU or transform it into a shared reference.

6. Bounds, Constant Evaluation & Borrowing

Indices are usize values. Read access borrows an element; write access requires exclusive permission. Fixed length does not permit an out-of-range read, and it does not permit simultaneous overlapping write views.

A constant call to get can fold to None; a constant checked access can fold to Err. A malformed extent or impossible type-level reshape is a compile-time diagnostic. The compiler should preserve those different public contracts instead of treating every known failure as a runtime trap.

Bounds-check removal is an optimization based on proof. AOT and JIT must agree on valid indices and failure values. The source owner must remain alive and cannot be moved while an element, iterator, or derived view still borrows it.

7. Nested Shapes & Ownership Transformations

Static concat consumes two owners and forms N+M elements. Owned split returns disjoint owners whose lengths sum to N. Zip and unzip require matching extents and transfer each element once; they do not invent aliasing copies.

Flatten and reshape preserve row-major order. Reshape requires the target product to equal N, including valid zero dimensions. Transpose changes the mapping of positions and may require O(R*C) moves; a strided transpose belongs to TensorView rather than a contiguous Array view.

Compile-time dimensions do not justify unlimited unrolling or code expansion. Optimization may choose loops or specialize shapes. Callback order, drop safety, exact integer size arithmetic, and observable errors remain language contracts.

9. Type-First Examples

The following construction and ownership transfer illustrate the chosen type-first declaration order. Constructor spelling and explicit returned-reference lifetime annotations remain draft; parameter borrow forms are chosen. 

i32 fill = 0;
Array<i32, 4> zeroes = Array.from_copy(i32, 4, &fill);
Array<i32, 4> duplicate = Array.copy(&zeroes);
Array<i32, 4> moved = zeroes;
usize count = Array.len(&moved);

After the move, zeroes is no longer an owning binding. Duplicate is an independent fixed array; moved still has extent four. No example silently calls a Vector growth operation or creates an extra shared owner.

10. Parallelism, FFI & Related Types

Disjoint borrowed ranges may be processed in parallel only with appropriate element and callback thread-safety constraints. Fixed extents simplify proofs but do not make arbitrary captured state race-free. Reduction order must be specified when checked arithmetic can fail.

FFI requires explicit size, alignment, element layout, borrowing lifetime, and allocator ownership contracts. A native array containing string handles, references, or padded records is not automatically a C-compatible element buffer.

An array of char holds Unicode scalar values, not encoded text bytes. See string and byte; byte remains distinct from u8. Device transfer, unsafe raw pointer adoption, and foreign allocation release are separate explicit facilities, not implied by these signatures.
