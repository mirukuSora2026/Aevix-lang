1. Dynamic Length & Separate Ownership

0.2 implementation scope. Dynamic/nested array literals, indexing, iteration, Vector.len, Vector.capacity, Vector.reserve and Vector.push are implemented without an import. Use the canonical Vector scope for exact Result and ownership contracts. Other forwarded catalog functions are proposals. See the 0.2 implementation profile; other catalog entries remain design contracts.

Array-family guide. The Vector reference is the single canonical catalog for Vector signatures, returned errors, ownership, and costs. This page preserves Array-family navigation and existing links; it does not define a second API.

Vector<T> owns a contiguous buffer whose length can change at runtime. Unlike fixed Array<T, N>, its capacity can grow through explicit fallible operations.

2. Length, Capacity & Checked Growth

Length counts initialized elements; capacity counts reserved slots. Reserve does not initialize elements, and clear does not automatically release capacity. Read the canonical length and checked-growth contract and growth guide.

3. Move, Clone & Consuming Errors

Passing or assigning a Vector owner moves ownership by default. Explicit copy or clone creates separate storage, and consuming failures must state whether they return the original input or clean partially processed values. See move, clone, and error ownership.

4. Borrowing & Reallocation

Shared and exclusive references use &T and &mut T. Taking &mut owner requires a mut owner binding; existing borrowed views are passed directly. Conflicting live borrows forbid owner moves, structural changes, and reallocation even when spare capacity exists. See borrowing and invalidation.

5. Failure Guarantees & Partial Work

Allocation, bounds, and callback errors follow each canonical function row. Preflight failure can preserve an owner, while some bulk or consuming callbacks have only the documented partial-progress guarantee. No general rollback is implied. See failure and partial-initialization rules.

6. Empty, Zero-Sized & Resource Elements

Empty buffers and zero-sized elements still have logical lengths, borrow restrictions, callback counts, and possible cleanup effects. See empty, zero-sized, and resource elements.

8. Type-First Examples

The following declarations use the chosen type-first syntax. Fallible allocation remains explicit as a Result; a Vector move does not clone its buffer.

Vector<i32> items = Vector.new(i32);
usize count = Vector.len(&items);
Result<Vector<i32>, CollectionError> duplicate = Vector.copy(&items);

See canonical examples and the error-handling rules for ? propagation.

9. Algorithmic Cost & Observation

Buffer growth may relocate all existing elements, even when end insertion is amortized O(1). Copy, clone, callbacks, and element cleanup retain their costs. The authoritative per-function costs are in the canonical API; see also algorithmic cost and observation.

10. Parallelism, Text & Interoperability

Disjoint write views can support parallel work only with compatible element traits and safe captured state. Shared owners, interior mutability, and foreign aliases require their own synchronization; a Vector type alone does not make T race-free.

CPU/GPU transfer is explicit and separate from Vector move or clone. Kernels and asynchronous work must keep buffers alive, validate layout and shape, and respect device capabilities. No GPU allocation or kernel support is promised here.

Vector<char> contains Unicode scalar values; it is not UTF-8 storage. Use string for text. byte is distinct from u8. FFI needs explicit allocator ownership, length/capacity, element representation, and borrow duration; native metadata is not a stable C++ or Swift ABI.
