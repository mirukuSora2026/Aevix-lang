1 . Array Family Overview

Language design draft. These are proposed Aevix contracts, not implemented compiler or standard-library guarantees. Declarations are type first and values are immutable by default. Borrow, callback, const-parameter, and mutation annotations in signatures are descriptive notation.

The family separates three jobs: Array<T, N> owns exactly N elements with a compile-time length; Vector<T> owns a runtime-length growable buffer; Slice<T> borrows a contiguous range. Static Array, Vector, and Slice expand those contracts. A fixed array never gains capacity or grows in place.

Array and Vector owners move by default, including arrays of copyable integers. Moving transfers responsibility for destruction; it is not a clone. A moved-from binding cannot be used as an owner. Copying a fixed array must be explicit, and cloning requires the element’s Clone contract.

Chosen array declaration spelling

The declaration head i32 values[5] denotes a fixed array of five i32 elements. The length is fixed; this does not select process-lifetime storage, implicit zero initialization or pointer decay. Initializers use square-bracket element lists. The inline forms in the table are declaration heads; typed local declarations without initializers follow definite-assignment checks.

Declaration headChosen meaningBoundary or related rule
i32 values[5]Five-element fixed array.The canonical type is Array<i32, 5>; fixed parameters pass an array value without pointer decay.
i32 grid[2][3]Fixed two-dimensional array: two rows of three i32 elements each, with both extents known at compile time.Mixed suffixes compose Array and Vector in outer-to-inner order, as explained below.
i32 values[][]Two-dimensional nested dynamic arrays; each row owns its dynamic storage and may have a different length.Dynamic construction yields Result<Vector<Vector<i32>>, CollectionError>; a single array parameter uses the canonical type.
i32 values[](2)Exactly the same two-dimensional nested dynamic array type as i32 values[][]. Parentheses specify rank, not axis lengths.The rank must be a positive compile-time integer constant; complete constant-expression grammar remains open.

Each empty bracket adds one nesting level. The rank shorthand accepts a positive compile-time integer constant, including a suitable const value. Rank is fixed in the type while each dynamic level may vary in length. These owners move under the collection rules. Nested growable vectors and a rectangular Tensor have different shape and storage contracts: no single allocation, globally contiguous buffer or automatic GPU transfer is promised. Existing Array<T, N> signatures below remain proposed API notation while the declaration spelling above is chosen.

Canonical array types and parameter contexts

Array suffixes are shorthand for complete types. Read suffixes from left to right as outer to inner containers: T name[N] means Array<T, N>, and an empty bracket means Vector<T>. Thus T grid[R][C] means Array<Array<T, C>, R>, while T grid[][] and T grid[](2) mean Vector<Vector<T>>. These canonical type names may appear in return types, Result, generic arguments and whole-array references.

Mixed fixed/dynamic suffixes are permitted for ordinary array declarations. T rows[R][] means Array<Vector<T>, R>; T rows[][C] means Vector<Array<T, C>>. Fixed extents remain compile-time constants; a literal containing any dynamic level produces Result<CollectionType, CollectionError>. The rank shorthand stands for repeated empty brackets only, and is not mixed with other suffixes in the initial grammar.

In function parameters, exactly one trailing empty bracket, T values[], is reserved for the chosen final variadic parameter. Receive one dynamic array with Vector<T> values, a complete nested canonical type for a multidimensional array, or a borrowed &Vector<T>/Slice<T>. Repeated-empty-bracket, rank and mixed suffix parameters must use their canonical type in the initial grammar. Fully fixed suffix parameters denote an Array value and follow the ordinary Copy-or-move rules; arrays remain move-by-default. There is no pointer decay.

A reference written in the base element type belongs to each element: &i32 values[5] denotes five shared-reference elements. Borrow an entire fixed array with &Array<i32, 5> values, or modify one through &mut Array<i32, 5> values. All referent lifetimes remain checked.

Literal type context and partial construction

An expected array declaration, canonical type or Result payload supplies element/container context. Without such a context, a nonempty bracket literal defaults to a fixed Array whose length is the written element count. Its element type follows the existing typed-value and numeric-literal rules. A context-free empty literal cannot determine its element type. Ragged rows require an explicit compatible nested dynamic context rather than an automatic hidden promotion to Vector.

rsn fixed_values = [1, 2, 3];
Result<Vector<i32>, CollectionError> dynamic_values = [1, 2, 3];

The first value is Array<i32, 3>; the second stores the Result of dynamic construction. An explicit zero-length fixed array has a known type, while a typed empty dynamic literal still has Result type even if it needs no allocation. On normal construction failure, destroy every successfully constructed element and row exactly once. This is not rollback of earlier input moves or side effects.

Square-bracket initializers and allocation failure

Array initializers use [...]. A fixed declaration's element count must exactly match its length or compilation fails. A nested dynamic initializer may contain different row lengths. A dynamic array literal constructs a Result; callers must handle that Result or use the existing ? operator in a compatible Result-returning function. The error carrier for dynamic literal construction is the existing CollectionError family.

i32 values[3] = [1, 2, 3];

Fixed multidimensional declarations repeat the compile-time extents in outer-to-inner order. Every initializer level must match its declared extent. This example has two rows, each with three elements, and needs no dynamic element-buffer allocation:

i32 grid[2][3] = [[1, 2, 3], [4, 5, 6]];

Both the row count and each row length are checked at compile time. A fixed extent does not mean persist storage. Mixed forms such as grid[2][] compose fixed and dynamic containers and use fallible construction.

The next examples are independent fragments inside compatible Result-returning functions. Their declared array types supply element and rank context; ? extracts the successful array or returns the compatible error.

i32 grid[][] = [[1, 2], [3, 4, 5]]?;
i32 grid[](2) = [[1, 2], [3, 4, 5]]?;

Nested bracket sublists participate in one recursive literal-construction operation. Their allocation failures flow into the outer construction Result, with already initialized rows cleaned once; a question mark at every sublist is not required. This does not implicitly unwrap an ordinary Result-valued element expression.

The two grid forms denote the same nested dynamic type. The fixed primitive array needs no dynamic element-buffer allocation. Array syntax does not remove failures in element expressions or authorize implicit cloning. See Error Propagation for the existing same-error-type Result contract.

Rejected example. The initializer has only two elements for a fixed length of three.

i32 values[3] = [1, 2];

2. Element Type, Length & Layout

T is one element type; N is a nonnegative compile-time usize constant and participates in type identity. Different lengths are different fixed-array types. Nested arrays are row-major values, not automatically tensors or SIMD registers.

Elements occupy consecutive element slots with stride equal to the native size of T. Padding inside T remains padding; arbitrary object bytes are not a portable serialization. An owning array contains its element storage, but enclosing storage may be a local, a field, or an explicit Box. A fixed size does not mean a global/static variable.

The proposed target limit bounds every logical length by isize.MAX. For nonzero-sized T, total representation bytes must additionally fit the target object bound. Zero-sized T uses zero payload bytes but retains logical length, alignment, callback counts, and drop obligations. Empty arrays are valid without a dereferenceable first element.

3. Ownership, Initialization & Destruction

Safe constructors publish only fully initialized arrays. They track initialized output elements separately from raw storage; an early returned error destroys the initialized prefix exactly once. No safe API exposes spare uninitialized slots or permits fabricated length metadata.

Clone duplicates according to T’s semantics: cloning a shared handle may retain a shared resource. It is not a universal deep-copy guarantee. Copy is limited to types approved for value duplication; resource owners cannot become safe through a byte copy.

Array destruction releases every owned element once. The exact element destruction order and unwind syntax still require a language specification. Returned errors must maintain initialization safety; process termination cannot promise cleanup. Callbacks’ external side effects are never automatically rolled back.

4. Borrowing, Access & Mutability

Read borrows may coexist. A write borrow excludes overlapping read or write access, while disjoint subranges can be borrowed separately through checked splitting. All borrowed results expire with the owner and cannot escape its lifetime.

Array.get returns Optional for ordinary absence; Array.at returns Result for a bounds diagnostic. Neither reads an unchecked location. A returned element is borrowed; moving it out of a still-initialized array requires a replacement or consuming transformation.

Parameters use the chosen forms T value, &T value, and &mut T value. Taking &mut owner requires a mut owner binding. Existing references and borrowed views are passed directly; known exclusive reference or MutSlice parameters reborrow them under the function reborrow rule.

Slice<T> denotes a read view; MutSlice<T> is the descriptive exclusive writable view type used across this documentation. A write reborrow suspends conflicting use of its source capability.

5. Errors, Callbacks & Cost

Callback labels Transform, TryTransform, RefTransform, and TryRefTransform are descriptive function contracts, not the Map<K, V> collection type. Their final callable-type spelling remains a library design detail. Vector and Slice API signatures are maintained only in the Vector catalog and Slice catalog.

CollectionError, BoundsError, and named ownership-preserving errors are proposed library error types. InputError<T> returns an unused moved input after a rejected replacement; OwnerError<C> returns a failed consuming conversion’s original owner. Callback-returned E is preserved by try-functions.

Bounds-only failures precheck before mutation. Constructors clean partial output. In-place cloning/replacement and callback mutations may leave valid partial changes where their row says so; they are not transactions. Comparator requirements include transitivity and a total order. Unsorted binary-search input violates the algorithm contract without granting memory unsafety.

Complexities count element operations. A move of large inline T, Clone, Drop, comparison, or callback can add substantial work. Fixed-array moves and whole-array swaps can touch O(N) elements; optimizers may elide movement but the language does not promise it. AOT and JIT must preserve visible callback order and errors.

6. Complete Proposed Array API

These individually named functions cover fixed-size arrays. Algorithms accept explicit callbacks; callback type names in signatures are descriptive aliases. Generic names do not promise universal traits: equality needs Eq, sorting needs a total comparator, and clone/copy have separate requirements.

Core literal and callback grammar remains under design. All API rows state observable ownership, failure, and cost contracts rather than claiming existing implementation.

7. Type-First Examples

Assume values is an existing read-accessible Array<i32, 3>. The declarations below illustrate namespace access and explicit duplication; every executable statement ends with a semicolon. 

Array<i32, 3> values = [1, 2, 3];
usize count = Array.len(&values);
Optional<&i32> first = Array.first(&values);
Array<i32, 3> duplicate = Array.copy(&values);
Result<Vector<i32>, CollectionError> dynamic_copy = Array.to_vector_clone(&values);

The last operation allocates a separate Vector; it does not change the original fixed length. The parameter borrow forms are chosen; error-type spelling and explicit returned-reference lifetime annotations remain proposed. Array construction literals will receive a separate grammar specification.

8. Parallelism, Devices & FFI

A shared read view is parallel-safe only when T supports safe shared access. Disjoint write views prevent overlapping mutation, but captured shared state and interior mutability still require their own synchronization. Splitting ownership does not automatically make arbitrary T thread-safe.

Array/Vector moves transfer ownership on the same storage model; they do not transfer bytes to a GPU. Tensor conversion and explicit device transfer must validate element layout, shape, target capabilities, and asynchronous buffer lifetime. No backend support is implied by this draft.

FFI borrows must describe length, alignment, initialization, permission, and who releases the allocation. Empty and zero-sized buffers cannot be dereferenced simply because a pointer exists. Ordinary arrays are not promised to be ABI-compatible with every C++ template instantiation.

9. Text, Characters & Bytes

An Array<char, N> contains Unicode scalar values, not N UTF-8 bytes or N user-perceived graphemes. Use the lowercase string reference for text encoding and string operations.

byte is distinct from u8; neither an array cast nor a view silently changes element identity. Follow the Byte reference for explicit byte/numeric conversion. Contiguous storage alone does not validate UTF-8, pointer provenance, endianness, or external record layout.

10. Design Status & Reference Scope

The catalog is an Aevix design proposal. It intentionally uses move-by-default owners, explicit duplication, checked sizes, and error values rather than inheriting another language’s assignment, exception, or copy-on-write policy.

The listed primary references were checked for fixed extents, contiguity, borrowing, initialization, reallocation, algorithm preconditions, and copy cost. They are research material, not proof of Aevix implementation, ABI compatibility, measured performance, or GPU qualification.
