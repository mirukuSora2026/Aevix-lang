1. Atomic Access Is a Protocol

0.2 implementation scope. Atomic and memory-order support types are specialist library designs, outside both the default prelude and the implemented 0.2 type/API subset. Their eventual use requires explicit imports; no built-in 0.2 module is supplied by this catalog. Import examples on this design page describe intended library boundaries, not an available 0.2 backend or package. See the 0.2 implementation profile; other catalog entries remain design contracts.

Atomic<T> is a non-Copy cell for a supported Copy integer or bool value. It prevents tearing for operations within its declared access width and memory scope; it is not an arbitrary object lock or a lifetime manager. Ordinary immutable bindings can expose explicitly synchronized interior updates through this type. Uncoordinated raw or mixed-size accesses remain forbidden. A scalar’s bit width alone does not establish native atomic support.

Design draft. APIs, memory-order and error records, and trait names describe intended Aevix contracts. Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. unit is a value type distinct from void. No native implementation, fairness, or benchmark claim is implied.

2. Loads, Stores, and Read-Modify-Write

The five draft orders are Relaxed, Acquire, Release, AcqRel, and SeqCst. Loads accept Relaxed/Acquire/SeqCst; stores accept Relaxed/Release/SeqCst. RMW operations accept all five. A known invalid constant order is a compile-time diagnostic; a dynamic invalid order is AtomicError with no operation performed. Relaxed makes one cell operation atomic but does not publish unrelated data. See Memory Order for synchronization boundaries.

3. Compare-Exchange Is Not Ordinary Equality

CAS reports whether this call changed the cell plus the observed value. A mismatch is a normal outcome rather than an invalid-order error. Weak CAS may fail spuriously and must be used in a correct retry loop. Failure is a load, so Release and AcqRel are invalid failure orders. This draft accepts Relaxed, Acquire, or SeqCst for that load. Equality compares the supported cell value representation; no universal floating NaN CAS policy is implied.

4. Explicit Modular, Checked, and Saturating Updates

Named fetch_add/fetch_sub use fixed-width modular integer arithmetic and return the old value. They do not silently replace the checked ordinary Integer arithmetic contract. Separate checked and saturating calls advertise their policies. An overflow return means this call performed no arithmetic write; another thread may still have changed the cell. Retry callbacks can run multiple times, so side effects, allocation, and reentrant updates must not be assumed exactly once.

5. Storage, Progress, and Waiting

The target manifest separately declares cell types, alignment, load/store, RMW, memory scope, and host waiting. A supported operation can require an explicit emulation profile; it must not silently claim lock freedom. Lock-free does not mean wait-free or fair. Float atomics, vector atomics, GPU system scope, and cross-device operations are optional extensions with separate contracts. Waiting can wake spuriously; notification does not itself publish protected state.

7. Cell Lifetime and Non-Atomic Access

An atomic borrow keeps the cell alive. Ownership extraction and get_mut require genuine exclusivity, not a count snapshot or a guess that other workers have finished. Mixing overlapping atomic widths, writing through a foreign non-atomic alias, or freeing a waited-on cell violates the safe abstraction. Shared<Atomic<T>> can retain storage, but its refcount does not replace the selected atomic ordering protocol or a task join.

8. Examples and Related Contracts 

u32 initial_count = 0;
Atomic<u32> count = Atomic.new(initial_count);
Result<u32, AtomicError> observed = Atomic.load(&count, MemoryOrder.Relaxed);
Atomic.is_supported(u64, Target.current());

Target and MemoryOrder are draft support descriptors. Examples contain no implicit float conversion or hidden heap allocation. See capability profiles, Shared threads, and Mutex. References inform this independent memory-model proposal; compiler and device correctness require later implementation verification.
