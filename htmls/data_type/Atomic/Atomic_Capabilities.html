1. A Target Manifest, Not a Type-Name Guess

A target capability descriptor identifies which Atomic<T> cells and operations the selected backend can implement. Copy is necessary for the initial scalar domain but is not sufficient: arbitrary Copy records, char, opaque byte, and float do not automatically become atomic cells. The initial catalog selects supported integer and bool forms. Additional forms need their own representation and operation contracts.

2. Atomic Alignment and Storage

Atomic cell alignment can differ from the corresponding ordinary integer alignment. Reinterpreting an arbitrary byte slice or packed foreign field as an atomic reference is not a safe constructor. Cell storage must remain initialized and alive for all operations and waiters. A target may implement a narrow cell through wider hardware operations internally, but the public abstraction still forbids conflicting partially overlapping access views.

3. Native, Lock-Free, and Wait-Free

Native describes an implementation technique. Lock-free describes system-wide progress under the specified model, while wait-free adds a bound on each operation’s steps. A compare-exchange loop is not automatically wait-free and can starve under contention. This draft publishes capability flags rather than copying another language’s availability guarantees wholesale. A fallback using locks must be selected explicitly and must not report is_lock_free as true.

4. Floating and Vector Extensions

Floating atomics require a selected set of operations, representation equality for CAS, NaN and signed-zero rules, and an arithmetic rounding profile. A target supporting atomic integer bits does not thereby promise native floating addition. SIMD and arbitrary-record atomicity need separate width and alignment capabilities. The current baseline provides no generic safe reinterpretation shortcut that turns a float reference into a concurrently aliased integer atomic.

5. Host Parking and Notifications

Waiting and notification may require OS parking support or a separately selected runtime profile. Wakeups can be spurious and wait predicates must be rechecked. Notification is not data publication. A cell with live waiters cannot be moved or released through conflicting ownership. Timeout results do not prove that another thread completed an operation, and no fairness or scheduler deadline is guaranteed.

6. Device Scope and Visibility

GPU atomic support is declared by operation and memory scope. A device atomic update is not automatically visible to host code, another device, or an unrelated queue. Transfers, fences, events, and coherency rules belong to the execution backend. Host atomics do not become valid on device-only buffers merely because pointer widths match. AOT and JIT must honor the same selected capability and memory model.

7. Queries and Unsupported Operations

Atomic.capabilities, is_supported, is_lock_free, and required_alignment are defined once in Atomic. Unsupported constant instantiations produce compilation diagnostics; dynamic configuration cannot silently weaken an operation. Memory Order describes order domains. Sources inform the proposal, not a universal claim of hardware support or independently proven concurrent algorithm correctness.

A baseline supported cell can be loaded without implying that every width, floating operation, or device scope has the same capability. 

u32 initial_count = 0;
Atomic<u32> counter = Atomic.new(initial_count);
Result<u32, AtomicError> current = Atomic.load(&counter, MemoryOrder.Relaxed);
