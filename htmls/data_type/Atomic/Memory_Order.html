1. Atomicity and Happens-Before Are Different

An atomic cell has a per-location modification order. Observing one of its values does not automatically establish visibility of every other memory location. A release/acquire protocol needs the appropriate reads-from or release-sequence synchronization relation. Ordinary shared non-atomic mutation remains prohibited without a valid happens-before edge and ownership capability. A processor’s apparently strong behavior is not a portable substitute for the language contract.

2. Relaxed Atomic Operations

Relaxed accesses retain atomicity and cell modification-order rules. They are useful when the only required result concerns that independent cell, such as an approximate diagnostic count. They do not publish a newly initialized object or make an unrelated flag-and-data protocol correct by themselves. A loop observing a changed relaxed flag cannot infer that all earlier non-atomic writes are visible.

3. Release, Acquire, and Their RMW Halves

A release write can publish preceding operations to a corresponding acquire observation in a correctly constructed protocol. An Acquire RMW has acquire semantics on its load half and relaxed behavior on its store half; Release has the opposite split. AcqRel supplies both roles. These relationships do not prevent every application race or make arbitrary multi-object invariants transactional.

4. Sequential Consistency Is Not a Global Lock

SeqCst adds the specified total-order constraints for sequentially consistent operations while retaining the ordinary acquire/release relationships appropriate to each operation. It is not a mechanism to make unsynchronized non-atomic fields safe, reserve object lifetime, or acquire an OS mutex. Replacing an algorithm’s every operation with SeqCst cannot repair invalid references, missed reclamation, or a broken compare-and-exchange loop.

5. Invalid Orders and Validation

Loads cannot perform a release store, and stores cannot acquire a value they do not read. Failed CAS is a load and cannot use Release or AcqRel. The common operation signatures define errors for dynamic invalid choices and diagnostics for known invalid constants before touching storage. Helpers below expose validation for configuration builders; they do not execute an atomic access or prove that a larger protocol is correct.

Conceptual signatureReturnsDomain, errors, and cost

6. Fences and Memory Scopes

A fence only participates in synchronization through the specified surrounding atomic accesses; it is not a blanket flush-all command. A compiler fence addresses the selected compiler/same-thread interruption profile and does not replace a hardware interthread fence. Host, device, workgroup, and system scopes are different capabilities. An order name alone does not establish visibility across a GPU transfer or foreign memory mapping.

7. Retry Loops, ABA, and Reclamation

CAS can observe the same bit pattern after a value changed away and back, an ABA problem for protocols using identity. Memory ordering does not keep a reclaimed node alive. Use an explicitly designed reclamation mechanism and valid ownership rather than an untyped atomic address. Atomic defines callable operations; Capabilities separates target support. No lock-free pointer container is silently included in this draft.

Validation does not perform an atomic access or establish a reads-from relation. 

bool load_ok = Atomic.valid_load_order(MemoryOrder.Acquire);
bool store_ok = Atomic.valid_store_order(MemoryOrder.Release);
bool failure_ok = Atomic.valid_failure_order(MemoryOrder.Relaxed);
