1. Dynamic Length & Separate Ownership

Language design draft. Vector is the runtime-length growable owner. It is distinct from fixed Array<T, N>; this catalog describes proposed contracts, not implemented APIs.

Vector<T> owns an initialized prefix in a separate contiguous buffer. Length can change at runtime. Capacity counts available element slots; it is not a second length and does not mean spare slots contain valid T values.

Assignments and function transfers move the owner by default, even for Copy elements. A separate buffer is duplicated only by explicit copy/clone APIs. No implicit copy-on-write sharing or hidden per-element reference counting is part of this proposal.

2. Length, Capacity & Checked Growth

The invariant is 0 <= length <= capacity <= the target’s supported element bound. Push adds one initialized element. Reserve changes capacity without creating any elements; resize changes length and must initialize additions or drop removals.

Every length sum, byte-size product, and allocation layout is checked before use. The proposed logical bound is isize.MAX; nonzero element bytes must also fit the target object bound. Allocator failure is separate from mathematical size overflow.

Growth may reserve more than requested. reserve_exact avoids deliberate excess but does not control allocator rounding. Automatic shrinking is excluded; clear and truncate retain capacity. Explicit shrink requests can fail or leave more capacity than the requested minimum.

3. Move, Clone & Consuming Errors

Moving a Vector transfers its separate-buffer ownership handle; it does not traverse or clone elements. This is O(1) metadata under the proposed model, not a public promise about field order or foreign ABI layout. Live borrows still restrict owner movement.

Clone requires T: Clone and creates a separate Vector buffer. Element Clone may copy a shared handle rather than recursively isolate a resource. Copy requires T: Copy but still allocates a new dynamic buffer; it is explicit and linear.

When a fallible operation consumes an input, its error contract explains ownership. InputError<T> carries an unused element. OwnerError<C> carries an intact failed conversion source. A consuming try_map may return a callback error after earlier elements were consumed; it cleans them rather than reconstructing the original input.

4. Borrowing & Reallocation

Read element references, slices, and iterators depend on the vector owner and current buffer. Reallocation can invalidate physical addresses; insertion and removal can also change which element an index denotes even without reallocation.

Safe structural or capacity-changing mutation requires exclusive access to the owner and is forbidden while conflicting borrows are live. Reserving enough capacity does not grant permission to mutate through a live shared borrow. iter_mut and split views grant disjoint access instead of unrestricted aliases.

Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. MutSlice<T> is an exclusive writable contiguous view and is passed directly without an extra address-of operator.

5. Failure Guarantees & Partial Work

Reserve and elementary insertion preflight sizes and allocation before moving existing elements. Their returned failures preserve the vector; rejected moved inputs are returned in their errors. New output constructors drop only their initialized prefix if construction fails.

Bulk cloning and fallible in-place callbacks have the basic guarantee where documented: completed appended values or processed removals may remain. Every owned element stays initialized and is dropped exactly once; no blanket rollback promise applies.

Sorting requires a consistent total comparator; floating values need an explicit NaN ordering. Stable sorting may allocate scratch; unstable sorting avoids heap scratch. Interrupted comparisons can leave a permutation of initialized elements, not the original order. Unwind syntax is undecided, and process termination cannot promise finalization.

6. Empty, Zero-Sized & Resource Elements

An empty vector may retain allocated capacity. A zero-sized T can have a positive logical length without payload allocation; capacity is logical and is not required to use Rust’s usize.MAX convention. Target count limits still apply.

Zero payload size does not erase construction, iteration, callbacks, identity, or Drop effects. Clearing a vector of resource-like zero-sized values may still require O(length) element finalization. Complexity rows count element operations, with Clone, Drop, large inline moves, and comparator costs added.

Safe APIs never expose uninitialized capacity as T values or allow arbitrary set_len/raw-pointer adoption. Those would require separately specified unsafe or FFI facilities with allocator, alignment, initialized-length, and destruction contracts.

7. Complete Proposed Vector API

Canonical Vector catalog. Maintain signatures, ownership guarantees, returned errors, and costs here. The Array-family Vector guide links to these rows instead of maintaining duplicate contracts.

Transform<T, U>, TryTransform<T, U, E>, and RefTransform<T, U> are descriptive callback contracts, not the Map<K, V> collection type. Their final callable-type spelling remains a library design detail.

All callable names are individually listed. By-value owning parameters move their inputs; shared and exclusive reference parameters use &T and &mut T. CollectionError, BoundsError, BuildError<E>, InputError<T>, and transformation-error carriers are proposed error-value types rather than implementation claims.

Lengths, offsets, and counts are usize unless a fixed-array const parameter is shown. SearchResult and iterator callback names describe library protocols whose exact grammar remains open.

8. Type-First Examples

Each owner is immutable by default. Metadata and explicit copy operations borrow owners at their call sites; fallible allocation remains visible in Result. 

Vector<i32> items = Vector.new(i32);
Vector<i32> empty = Vector.new(i32);
usize empty_count = Vector.len(&empty);
Result<Vector<i32>, CollectionError> duplicate = Vector.copy(&items);
Result<Array<i32, 4>, CollectionError> fixed_copy = Vector.to_array_copy(4, &items);

Use a mut binding before taking &mut owner for reserve, push, or removal. Such a borrow excludes overlapping access until its last use; extra capacity does not waive this rule. The chosen ? operator propagates a compatible error from a Result-returning function; see the error-handling rules.

9. Algorithmic Cost & Observation

End insertion is amortized O(1) element work across ordinary geometric growth, with O(length) relocation on a particular growth operation. It is not guaranteed constant latency. Front or middle insertion/removal shifts a suffix; swap_remove changes order to avoid that shift.

Reserve strategies, sorting implementation, iterator fusion, and JIT specialization must preserve callback order, returned errors, and ownership. A benchmark is needed before any CPU/GPU throughput claim. Fixed-array conversion may move every inline element; it is not a free metadata cast.

10. Parallelism, Text & Interoperability

Disjoint write views can support parallel work only with compatible element traits and safe captured state. Shared owners, interior mutability, and foreign aliases require their own synchronization; a Vector type alone does not make T race-free.

CPU/GPU transfer is explicit and separate from Vector move or clone. Kernels and asynchronous work must keep buffers alive, validate layout and shape, and respect device capabilities. No GPU allocation or kernel support is promised here.

Vector<char> contains Unicode scalar values; it is not UTF-8 storage. Use string for text. byte is distinct from u8. FFI needs explicit allocator ownership, length/capacity, element representation, and borrow duration; native metadata is not a stable C++ or Swift ABI.

11. Related Array Types & Research Scope

Use Static Array when the extent belongs in the type, Slice to borrow without ownership, and Array for shared family rules.
