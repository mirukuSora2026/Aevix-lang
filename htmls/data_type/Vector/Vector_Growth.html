1. Length, Capacity, and Relocation

Growth concerns the initialized logical prefix and a separately reserved allocation. A capacity count is not a list of initialized values. The compiler checks target object bounds and size products before layout or allocator requests. Geometric growth is permitted but neither a specific factor nor an allocator-specific size is public ABI. An empty owner may retain storage; zero-sized elements still have logical counts and destructor effects.

2. Borrow Capabilities Outlive Capacity Guesses

Reserving enough capacity does not suspend the ownership rules. A shared slice, element reference, or iterator remains a live borrow even if a caller predicts that the next insertion will not allocate. Structural mutation may move elements or change which index denotes an element. Exclusive access must be established before growth or insertion; a raw address observation is not a capability to bypass the borrow checker.

3. Preflight and Input Recovery

Elementary growth operations validate counts and reserve storage before moving old elements or consuming the new input irreversibly. Size or allocation failure preserves the old vector and returns rejected moved inputs in the documented carrier. Caller code must retain and inspect the error rather than assume an element vanished. Bulk callbacks have separate basic guarantees and may leave completed work visible. No blanket transaction promise extends to callback side effects.

4. Shrinking and Empty Buffers

Clear and truncate retain capacity under the shared Vector contract. Shrink requests are explicit, may relocate storage, and need exclusive access. Allocator rounding may leave more capacity than requested; a successful request is not proof of exact heap footprint. Dropping initialized elements can execute user destructors, so shrinking logical length is not always constant time. A buffer containing sensitive bytes has no automatic secure-erasure guarantee.

5. Element Identity and Iterator Invalidation

An iterator borrows the owner and current element range. Insert, remove, sort, or retain can alter element positions even when the allocation address stays fixed. In-place algorithms require an exclusive capability and do not promise stable element identity. Disjoint mutable iteration allows each yielded borrow only within its declared protocol. A callback must not reenter the same vector through a conflicting captured alias.

6. Tasks, Devices, and Address Stability

An owned capture can move a vector into a detached host task if its elements satisfy transfer bounds. A scoped task may borrow only while its scope guarantees completion before owner access resumes. GPU submission is separate from a CPU vector move; it requires a placement-aware transfer and completion lease. Do not resize or release borrowed storage while submitted work still accesses it. A user Pending handle’s destructor alone is not the lifetime proof.
