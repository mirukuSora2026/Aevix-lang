Implemented 0.2 CPU profile

Read the implemented SIMD profile for the exact imports, supported lane counts, checked operations, masks, and fixed-array access available in 0.2. The broader API catalog below remains a design draft; it is not a list of compiler-supported functions.

1. Portable is a behavior contract

A portable profile promises a defined result for supported scalar types, lane counts and operations. It does not promise that a vector equals one hardware register, that all lanes execute simultaneously, or that a particular instruction set exists. Lowering can use scalar code or several vectors. A stricter NativeRequired profile can reject targets that lack the requested native support, while keeping numerical meaning unchanged.

CPU and GPU profiles are separate capability sets. A value accepted by a Cpu profile may not be supported inside a selected GPU kernel. Capability reports distinguish scalar type support, width/lane support, operation support and strict floating behavior. Runtime dispatch can select among already compatible implementations, not silently replace strict arithmetic with a relaxed approximation.

2. Compiler specialization and observation

The compiler may specialize N, scalar type, known alignment and target features. It may remove redundant checks when doing so preserves observable failures and active memory accesses. AOT and JIT share the same result and error contract. Dispatch metadata and compile options are part of compiled identity, avoiding a cache hit that uses an incompatible numeric profile.

A lowering report can describe native widths, fallback fragments and feature requirements. Such a report is diagnostic data, not a stable schedule or timing contract. Vendor compiler versions may choose different instruction sequences without changing the program meaning. Performance claims require measurements on the actual target and workload.

3. Floating-point portability limits

The strict scalar floating profile controls NaN classification, signed zero, infinities, rounding and subnormal handling. Float vectorization cannot silently flush subnormals or reassociate reductions. Explicit FMA uses fused semantics even on a target that needs a slower implementation or an unsupported-capability report. Approximate reciprocal and math instructions belong in a named optional profile.

Logical reduction order is separate from selected vector width. A left-to-right accumulator must remain left-to-right even if the compiler divides the input into fragments. A requested tree order may have target-dependent tree structure only when its policy explicitly permits that variation. Exact cross-target NaN payload reproduction is not implied by ordinary numeric operations.

4. Memory, alignment and FFI

A Simd value has no default stable C vector ABI. Passing it to native code requires an adapter that names the target ABI and verifies width, alignment and feature requirements. The portable interchange route is explicit Array conversion or an initialized Slice buffer. A repr or layout annotation would be a separate language decision rather than inferred from lane count.

Ordinary load/store accepts element-aligned slices without a hidden stronger native alignment precondition. An aligned fast path takes a validated alignment witness tied to the allocation and offset. A foreign alignment claim must be checked or lie behind an explicit unsafe boundary. The witness does not prove bounds or exclusive ownership.

AlignmentError is a proposed standalone library error for invalid alignment, incompatible allocation identity or checked address overflow. Alignment validation does not require an otherwise unrelated SIMD lane-count parameter.

5. Representation conversions are values

bitcast operates on a target-independent logical bit sequence: scalar lane representations are concatenated in lane order with least-significant bit first within each lane, then partitioned into destination lanes. Total bit widths must match. This defines a value conversion independently of host byte endianness; serialization into bytes still needs an explicit endian format.

All source and destination scalar bit patterns must be valid for the selected numeric types. Mask and bool are excluded because their representation is not an arbitrary numeric bitstring. The conversion never creates aliased references or a pointer with a new alignment assumption. Foreign ABI bitcasts require a separately named target adapter.

6. Capabilities are queries, not benchmarks 

CapabilityReport support = Simd.supports<f32, 4>(target, SimdOperation.Add, SimdProfile.Portable);
Result<SimdPlan, SimdCompileError> plan = Simd.plan<f32, 4>(target, SimdProfile.Portable);

target is an existing validated target descriptor. The returned plan reports a possible lowering and feature requirements; it does not reserve future runtime resources or guarantee native execution. A program may retain the portable profile and accept scalar fallback, or explicitly require native features and handle a capability error.

8. Reference scope

All interfaces here are proposals. Rust portable SIMD documentation is explicitly experimental and is used only as an official comparison source. LLVM vector IR is a lowering vocabulary; its poison and undefined-behavior preconditions are not safe Aevix contracts. The language must validate every condition required by its own observable semantics.
