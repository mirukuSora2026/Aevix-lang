Implemented 0.2 CPU profile

Read the implemented SIMD profile for the exact imports, supported lane counts, checked operations, masks, and fixed-array access available in 0.2. The broader API catalog below remains a design draft; it is not a list of compiler-supported functions.

1. Fixed lanes with a scalar meaning

Simd<T, N> is a proposed fixed-lane value type. N is a positive compile-time lane count and T is a supported scalar numeric type. It is distinct from a dynamically allocated Vector<T>, a matrix tensor, or an automatically parallel host task. A value contains exactly N logical lanes; no heap allocation is implied by constructing or copying that value.

An initial portable profile targets fixed-width integer lanes and f32/f64, with smaller floating formats gated by capabilities. A supported value may lower to one native vector, several vectors or scalar code. Neither the source type nor a capability report proves one-instruction execution, a register ABI or a particular speedup. These are original Aevix contracts informed by public vector interfaces, not an adopted foreign API.

2. Values, masks and lane errors

V denotes Simd<T, N>, W a result Simd<U, N>, and Mask<N> a logical lane mask. Mask is a proposed library value whose lane semantics are bool; its native memory representation is not Array<bool, N>. SimdError<N> is a proposed error record with a cause and failing-lane mask for checked numeric operations, or an index/bounds/alias error for memory operations. No function uses an invalid lane as LLVM poison visible to safe code.

Borrowed Slice and exclusive MutSlice values retain ordinary ownership rules. Array<T, N> is the fixed-size array type; from_array and to_array describe logical values rather than bitcasting an array to a vector ABI. Generic parameter support and target lane sets are compile-time capabilities. Unsupported operations are diagnosed without silently weakening the scalar contract.

3. Lane arithmetic and overflow

Each numeric lane follows the corresponding scalar semantics. Checked integer operations report all failing lanes without exposing a partial result. Wrapping and saturating operations are separately named. A shift count is checked against the lane width; it is not silently masked by hardware. Signed minimum divided by minus one and integer division by zero remain errors. Floating divide follows IEEE behavior for zero, NaN and infinity in the strict profile.

Fused multiply-add is explicit. Float min/max variants state whether they propagate NaNs and how signed-zero ties are resolved. Numeric equality treats NaNs as unequal and signed zeros as equal; representation equality is a different operation. AOT and JIT cannot infer permission to reassociate, flush subnormals or change rounding merely because values are vectorized.

4. Checked memory operations

A contiguous load reads exactly N elements from the selected start; a store writes exactly N. Safe APIs validate lengths and address arithmetic before access and do not impose hidden native alignment assumptions on an ordinary Slice. Gather validates active indices; scatter validates active indices and rejects duplicate active destinations before any write. This avoids an unspecified race or hidden last-lane policy.

Masked-off memory lanes are not accessed, not bounds-checked as active lanes, and never require forming an invalid address. A masked load supplies explicit fallback values. A mask does not relax alias rules: an immutable source borrow and overlapping exclusive destination borrow still cannot coexist. Scatter duplicate validation is a semantic cost and may use bounded scratch space or a checked allocation for large N.

5. Selection does not make evaluation lazy

Simd.select chooses between two values that have already been computed. It cannot protect a preceding division by zero or an out-of-bounds gather. The masked_divide function instead promises to evaluate arithmetic only for active lanes and to preserve explicit fallback lanes. A compiler must not speculatively introduce an observable error in an inactive lane.

Mask logical operations are lane-wise. all, any and count inspect logical lanes; they do not expose register bit encodings. Explicit bitset conversion specifies lane i as bit i and rejects set bits beyond N. Host-side mask serialization has its own format; a vendor native mask register is not a portable byte representation.

6. Reduction order and conversion

Integer reduction uses the named checked/wrapping accumulator contract. Floating reduction selects an explicit accumulator type and order. The strict left-to-right order processes lane 0 through N-1 after conversion to the accumulator; a tree order requires an explicit option and may change bits. A dot product also states whether multiplication is fused, separately rounded or widened.

Numeric casts and representation bitcasts are separately named. cast_checked validates representability and any selected rounding policy; bitcast requires equal total bit width and defined scalar lane representations. It does not allow a raw reference reinterpretation that violates alignment, ownership or validity. SIMD values can be stored using logical arrays for FFI; an explicit target ABI adapter is required for native vector calling conventions.

10. Values with no hidden dynamic allocation 

Simd<f32, 4> bias = Simd.splat<f32, 4>(0.5);
Simd<f32, 4> input = Simd.from_array<f32, 4>([1.0, 2.0, 3.0, 4.0]);
Simd<f32, 4> shifted = Simd.float_add(input, bias);
Mask<4> active = Simd.less(input, shifted);

These statements use immutable values by default. A destination buffer would need an explicit mut declaration before exclusive store access. No result states that four lanes execute in one instruction on the current CPU or that the same host ABI is used on a GPU.

11. Mask, portability and scalar references

Simd is a semantic vector value, not an automatic threading model. A host Task may process Simd values and a GPU kernel may use supported lane operations, but scheduling, storage placement and vectorization are separate decisions. Autovectorization may use Simd-like lowering for ordinary code only when it preserves the same scalar behavior.
