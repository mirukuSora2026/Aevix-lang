Import and first use

This page describes the implemented 0.2 compiler profile. The larger catalogs in the design reference include future APIs; a function listed there is not automatically available in this profile.

SIMD types require an explicit import. A selective import exposes the chosen names directly. With import simd;, write simd.Simd and simd.SimdMask.

import simd { Simd, SimdMask };

i32 main() {
    i32 values[4] = [1, 2, 3, 4];
    Simd<i32, 4> a = Simd.from_array(&values);
    Simd<i32, 4> b = Simd.splat<i32, 4>(8);
    return Simd.sum(Simd.add(a, b));
}

The example returns 42. SIMD values and masks implement copy semantics and do not allocate a heap buffer. Transfers to and from arrays copy lane values explicitly.

Supported lane types

The lane count is a compile-time constant. Accepted counts are 2, 4, 8, and 16, with at most 128 bits in a numeric vector.

Element typeAccepted lane counts
i8, u82, 4, 8, 16
i16, u162, 4, 8
i32, u32, f322, 4
i64, u64, isize, usize, f642

SimdMask<N> has one logical boolean per lane. Its packed representation is not an Array<bool, N> layout. Comparisons produce masks; selection requires the same lane count on the mask and both alternatives.

f16, bf16, char, byte, and bool are not numeric SIMD element types in this profile. Wider vectors are rejected rather than silently changing their storage or allocation requirements.

Implemented operations

All operations use positional arguments. V below is one Simd<T, N> type and M is SimdMask<N>. Values supplied to arithmetic and mask functions have matching types.

Borrowed array access

Load and store accept fixed arrays and an offset measured in elements. Both verify that the complete lane range fits before accessing memory. Store requires an exclusive mutable loan. The array must already be initialized, and ordinary ownership and borrowing rules still apply.

import simd { Simd };

i32 main() {
    mut i32 buffer[5] = [0, 0, 0, 0, 0];
    Simd<i32, 4> value = Simd.splat<i32, 4>(7);
    Simd.store(&mut buffer, 1, value);
    Simd<i32, 4> loaded = Simd.load<i32, 4>(&buffer, 1);
    return Simd.sum(loaded);
}

Unaligned element offsets are supported. Failed bounds checks stop execution safely. Slice-based, gather/scatter, masked memory, and fallible Result-returning transfers remain outside this initial profile.

Numeric behavior

Integer add, subtract, and multiply check every lane for overflow. Integer divide checks every divisor for zero and rejects signed-minimum divided by minus one. A failing lane stops execution before an invalid value is exposed. Integer sum checks each addition in its ordered fold, including intermediate overflow.

Floating operations follow f32/f64 behavior without reassociation or fast-math flags. Division may produce infinity or NaN; the square root of a negative lane produces NaN. Equality and ordering comparisons are false for NaN; inequality is true. Sum uses the documented lane order and may differ from a reassociated reduction.

Select is an ordinary eager function: both alternatives are evaluated before lane selection. A false mask does not suppress overflow, division, or other effects that occur while computing an alternative.

Portability and scope

The compiler emits LLVM fixed-vector operations for CPU execution. The backend may choose native vectors or lower an operation to several instructions. The source type promises lane semantics, not a particular instruction count, register ABI, or speedup.

The 128-bit ceiling keeps the profile within the current portable allocation-alignment contract. AOT supports the project's ARM64 and x86-64 backend targets; JIT executes only on its running host. Cross-target object generation is not a substitute for native execution testing.

GPU execution, 256/512-bit values, explicit target feature dispatch, saturating or wrapping vector arithmetic, and the rest of the larger design catalog are not implemented by this profile.
