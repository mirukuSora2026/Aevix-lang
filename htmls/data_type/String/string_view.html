1. A Borrowed UTF-8 View

0.2 implementation scope. String literals have allocation-free string_view type. Implemented view operations are string.view, byte_len, scalar_count, is_empty, as_bytes, equals and checked slice_bytes. A view retains its source loan. Borrowed validation via string.view_utf8 remains a proposal; string.from_utf8 instead validates bytes and allocates an owned string. See the 0.2 implementation profile; other catalog entries remain design contracts.

Language design draft. Contracts, helper types, and function spellings below are proposals. They do not claim an implemented compiler, finalized grammar, or validated runtime. Examples use type-first declarations, default immutability, and semicolon-terminated statements.

string_view is the proposed spelling for a lifetime-checked read view into valid UTF-8 storage. It replaces no scalar type and does not own, allocate, normalize, or retain a reference count for the source. Its logical representation is an address and byte length, while its ABI and concrete size remain unspecified. The view may cover an owner, immutable literal storage, or a validated borrowed byte slice.

This is a text-specific borrowing contract rather than an unchecked pointer pair. UTF-8 validity and source lifetime are established before constructing the value. Copying the view copies only its descriptor and preserves the same borrowing restrictions. See the owning string reference for the complete namespace and array views for the related storage model.

2. Lifetime & Owner Mutation

The owner must remain alive throughout every use of the view. A function cannot return a view into a local owner that is being destroyed. A view stored inside another object carries the same lifetime obligation; it does not prolong ownership. Background jobs cannot retain it beyond a scope unless the runtime and type system prove the owner remains valid.

An outstanding read view prevents conflicting writes, including reallocation and in-place edits. Even edits that keep the address unchanged may change textual boundaries or semantic positions. The compiler tracks this relationship instead of trusting a programmer to remember invalidation rules. An owned copy is the explicit way to retain a small substring independently, at the cost of copying its bytes.

3. Byte Ranges & Scalar Boundaries

View length counts bytes. A half-open range may be in bounds yet invalid as text because an endpoint points into a multibyte scalar. Safe constructors reject that range. Scalar-index slicing scans to the requested scalar boundaries and remains a borrow; grapheme-index slicing belongs to the optional Unicode module.

Moving to the nearest scalar boundary is not equivalent to preserving a user-perceived character. Combining marks and emoji sequences can span multiple scalars. Integer offsets also carry no intrinsic source identity: applying an offset obtained from another view requires a fresh range and boundary check. The end offset is a valid boundary but does not designate a scalar to remove or read.

4. Construction & Validation

string.view borrows already validated text in constant time. string.view_utf8 instead borrows arbitrary bytes and validates the full range before returning text. The underlying byte storage is read-borrowed for the resulting view’s lifetime, preventing mutation that would break UTF-8. Empty input succeeds.

Unchecked conversion and arbitrary raw-pointer constructors are excluded from the safe catalog. FFI wrappers must establish length, readability, lifetime, and encoding before building a view. The view is not required to end with NUL, and embedded NUL remains part of its byte count. Copying into a caller buffer copies bytes without silently adding a terminator.

6. Equality, Ordering & Optional Data

A view and owner use the same exact UTF-8 equality contract. Equal contents do not imply equal addresses or shared ownership. Neither comparison nor view creation performs Unicode normalization. Empty text is distinct from an absent optional value. Absence of a search match is represented by Optional; malformed input or invalid slicing is represented by Result.

The proposed descriptor can be passed to generic read-only string functions without copying. It does not expose spare capacity, writable bytes, or a resizable container interface. A separate mutable text-view design would need additional invariants and is not introduced here.

7. Examples 

string_view text = "café";
Result<string_view, TextError> suffix = string.slice_bytes(text, 2, 5);
Optional<usize> location = string.find(text, "fé");
Result<string, TextError> independent = string.from_view(text);

Every example statement ends with a semicolon. The borrowed literal is valid for its storage lifetime. The owning constructor returns a result because copying can allocate; it is not a free cast.

8. Targets & Comparison Sources

AOT and JIT must preserve lifetime and validation checks. Compiler-elided copies do not change whether the source operation semantically creates an owner. A GPU representation requires explicit storage accessibility and supported operations; a CPU address cannot simply be embedded in a device view. Unicode library support remains separately declared.

C++ string views inform the non-owning surface, while Rust UTF-8 views inform validity and checked boundaries. Swift’s separate code-unit views provide another comparison point. These references specify their own behavior; this proposed lifetime guarantee requires independent Aevix implementation and validation.
