1. Encoding Is an Explicit Boundary

0.2 implementation scope. The general encoding namespace and UTF-16/UTF-32/transcoding APIs below remain proposals. The implemented UTF-8 entry point is string.from_utf8(Slice<byte>), which returns Result<string, TextError> with owned text. string.as_bytes borrows existing valid text. The proposed string.view_utf8 validator is not a 0.2 alias for the owning constructor. See the 0.2 implementation profile; other catalog entries remain design contracts.

Language design draft. Contracts, helper types, and function spellings below are proposals. They do not claim an implemented compiler, finalized grammar, or validated runtime. Examples use type-first declarations, default immutability, and semicolon-terminated statements.

encoding. is a proposed library namespace for validated import and export. Internal string storage remains UTF-8. UTF-16 and UTF-32 code-unit arrays are external representations rather than additional text primitives. Borrowing existing UTF-8 uses string.view_utf8; encoding to a new array makes a visible copy.

Encoding, DecodeError, EncodeError, EncodingError, Decoder, Encoder, and ConversionProgress, DecodeReport<T>, and TranscodeReport<T> are supporting library proposals. Each error family includes allocation or capacity failure wherever its operation may allocate or write. Conversion never silently falls back to a system code page.

Related references: char, byte, and arrays.

Report records carry output and replacement counts. A transcode report also records source progress; selecting a lossy policy never hides whether substitution occurred.

2. Scalar Validity & Error Policy

UTF-8 validation rejects overlong sequences, surrogate encodings, isolated continuation bytes, truncated sequences, and values above U+10FFFF. UTF-16 rejects unpaired surrogates. UTF-32 requires every code unit to encode a scalar. Noncharacters and unassigned scalars are not automatically malformed encodings; protocol-level restrictions are separate checks.

Strict decoding reports the first malformed sequence with its byte or code-unit position. Lossy decoding is explicitly named and replaces maximal ill-formed subparts with U+FFFD while reporting replacement counts. It is unsuitable when original bytes must be preserved for signatures, audit records, or binary protocols. These rules follow the distinctions in the Unicode core encoding definitions.

3. Code Units, Byte Order & BOMs

A Slice<u16> contains numeric code units, independent of byte serialization order. UTF-16LE and UTF-16BE byte streams explicitly choose little or big endian; UTF-32 has the analogous distinction. UTF-8 has no endian variant. Raw byte reinterpretation cannot replace decoding or endian conversion.

BOM handling is a separate option: preserve, require-and-consume, or detect under an explicitly allowed set. A fixed-endian API preserves an initial U+FEFF as text by default; it does not silently remove it. Detecting a BOM identifies only a possible prefix, not the encoding of arbitrary BOM-free bytes. Compare the Unicode BOM FAQ.

6. Streaming Boundaries & Progress

A transport chunk may end inside a UTF-8 sequence, UTF-16 surrogate pair, or serialized code unit. A decoder keeps encoding-specific bounded carry state between calls; it does not retain a borrowed pointer to a temporary chunk. Empty input is not end-of-stream. Only an explicit finish operation decides whether pending bytes form a truncated sequence.

Caller-buffer operations report consumed input bytes and written output bytes. OutputFull means the caller must provide more output space; it is not malformed input. Decoding emits complete UTF-8 scalars only, and the caller must preserve any reported partial progress. Strict errors report the original stream position. Stateful objects require exclusive mutation and cannot be shared concurrently without synchronization.

A strict streaming error includes consumed/written progress and places the converter in a failed state; recreate it before retrying. After finish begins, only further finish calls may drain output until Finished. These are explicit state-machine proposals, avoiding silent reuse after partial failure.

7. Streaming Converter Functions

Proposed progress statuses are InputExhausted, NeedMoreInput, OutputFull, and Finished. Setup can allocate; chunk operations use preconfigured state and caller buffers. Additional legacy encodings require explicit optional backend support.

8. Examples & Execution Targets 

string_view text = "café";
Result<Vector<u16>, EncodeError> wide = encoding.encode_utf16(text);
Result<Vector<byte>, EncodeError> network = encoding.encode_utf16_be(text);
Result<Vector<byte>, EncodeError> c_text = encoding.to_c_utf8(text);
Result<string_view, TextError> checked = string.view_utf8(input_bytes);

The input byte slice is an already borrowed external buffer. UTF-16 output is encoded data, not a different owner type. Strict import does not normalize, fold case, or discard valid control characters. AOT and JIT preserve these boundary rules. GPU conversion is available only for explicitly supported formats and memory spaces; CPU locale or codec support does not establish device support.

ICU streaming conversion provides a comparison for split input and output buffers. Implementation checks should cover every chunk boundary, malformed tails, buffer exhaustion, BOM policy, allocation failure, and round-trip scalar preservation. These are required validation targets, not recorded test results.
