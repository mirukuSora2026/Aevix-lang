1. Overview

0.2 implementation scope. Tuple<...> is in the prelude. Implemented calls are Tuple.make, len, is_empty, get<I>, get_mut<I> and copy. Access uses an explicit tuple borrow and a compile-time valid index; copy requires every field to be Copy. Clone, reverse, map, apply and Array conversion functions below remain proposals. See the 0.2 implementation profile; other catalog entries remain design contracts.

Catalog status. The scope note identifies the implemented subset; other listed APIs remain proposed Aevix contracts. Parameter modes are chosen: T value, &T value, and &mut T value. Type-pack notation, callable types, explicit returned-reference lifetime spelling, and error enums remain descriptive where marked. Namespace functions are used throughout; there are no value-method aliases.

A tuple groups a known number of possibly different types. Tuple<i32, bool> contains one i32 and one bool; changing either type or the number of fields creates a different tuple type. Named domain records belong in Struct when field names carry meaning.

2. Declarations and construction

Type-first declarations make the full product type visible. Tuple.make moves non-Copy inputs. There is no hidden heap allocation for the product itself, although a field can own an allocation. 

Tuple<i32, bool> status = Tuple.make(7, true);
usize fields = Tuple.len(&status);
bool empty = Tuple.is_empty(&status);

3. Static access and heterogeneous types

A field index is a compile-time argument. A runtime integer cannot select arbitrary heterogeneous fields and return a single unconstrained type. A dynamic alternative requires an explicit enum, a homogeneous Array, or an application-defined visitor.

Field, Prefix, Suffix, Reverse, Repeat, and count are explanatory type-pack notation in this catalog, not additional primitive types or finalized syntax.

4. Ownership, borrows, and mutation

This draft keeps tuple owners move by default, with Tuple.copy requiring Copy on every field and Tuple.clone requiring Clone. A clone follows each field contract; cloning Shared does not recursively duplicate the referenced object.

Field borrows cannot outlive the containing tuple. An exclusive field borrow conflicts with any access that aliases that field. Provably disjoint field borrows may coexist. A move of the whole tuple is forbidden while any field borrow remains live.

5. Type-changing transformations

Concatenation, reversal, push, pop, and split construct new static product types. They are not dynamic-capacity container operations and do not resize a tuple in place. Compiler specialization can inline field moves; the semantic work still scales with field contents.

Mapping uses a tuple of appropriately typed callbacks. A single callback cannot be assumed to accept all unrelated field types. Tuple.try_map uses one shared error type so its output type remains statically known.

6. Function reference

T value passes a value: Copy types are copied, and owning non-Copy values move without a deep clone. &T value is a shared read borrow; &mut T value is an exclusive modification borrow. Calls use x, &x, or &mut x respectively. Already borrowed references and view values are passed directly; adding another & changes the type. *ref accesses the referent. Ordinary &mut x requires a mut owner; mut T value alone makes a by-value parameter locally mutable and does not modify the caller. Overlapping active borrows are checked until last use; disjoint regions may be split safely and no borrow outlives its source. Synchronized interior mutation follows its own type contract. Fn(A) -> B describes a callable; returned-reference lifetime relationships remain documented in prose.

7. Partial construction and failure

A tuple becomes observable only after every field is initialized. If a clone or fallible mapping fails, completed outputs are destroyed once, remaining owned inputs are destroyed once, and no reference to an uninitialized field escapes. A borrowed source remains valid.

CloneError is a descriptive fallible-clone error contract and must preserve allocation failure information. Destructors must not introduce an unmodeled recoverable failure during cleanup. Explicit resource-close operations carry such errors as Result values.

8. Layout, cost, and zero-sized fields

The compiler may insert alignment padding. Field offsets, ordering in memory, calling convention, and tail padding require a target layout specification; the default product layout is not a portable C struct ABI. Safe code cannot inspect padding as initialized bytes.

Arity must be representable as target usize, and the complete layout must satisfy target size and alignment limits. An invalid static layout is rejected at compile time; it is not silently turned into a heap object. Type-pack queries require compiler support; namespace spelling alone does not make every helper a primitive instruction.

Zero-sized fields still have type, lifetime, and destructor semantics. A tuple containing a zero-sized resource may perform nonzero cleanup work. A tuple is not always cheap to copy merely because its field count is small.

9. Devices and foreign interfaces

A tuple is device-compatible only if every field and required operation is supported by the selected target. A tuple containing a host string or lock cannot be silently lowered into a GPU kernel. Explicit transfers operate on the supported contents and preserve lifetimes.

C++ std::tuple and Python tuple do not share an Aevix tuple ABI. Bindings adapt field by field or use an explicitly specified record layout. Python tuple elements remain managed Python objects at that boundary.

10. Examples and choosing a container

Catalog example. This fragment also uses proposed functions identified in the scope note; it is not a complete 0.2 program.

Tuple<i32, bool> pair = Tuple.make(12, false);
Tuple<i32, bool> duplicate = Tuple.copy(&pair);
Tuple<bool, i32> reversed = Tuple.reverse(duplicate);
Array<i32, 2> numbers = Tuple.to_array<i32>(Tuple.make(3, 5));

The Array conversion is valid because both fields are exactly i32. A tuple of i8 and i32 requires explicit conversion before becoming a homogeneous Array. Use Array for repeated same-type elements and Vector for runtime growth.
