1. A borrowed tensor descriptor

TensorView<T, S, P> grants read access to elements through a validated shape, origin and stride descriptor. It owns no element buffer and cannot outlive the storage loan. MutTensorView<T, S, P> is a candidate exclusive descriptor; it grants mutation only when each logical location identifies a distinct initialized element. These are library ownership forms, not an escape from the core borrow checker.

The owner cannot move, resize, transfer away, deallocate or expose conflicting mutable access while a view is live. Multiple read views may coexist. A GPU view is a device-side access capability and metadata handle; it does not authorize host dereference. Passing a view into an asynchronous submission extends its loan to the operation scope until quiescence.

2. Strides, origin and bounds

A stride is measured in elements in this draft. Signed strides permit reversed traversal when origin and the complete reachable span remain inside the same allocation. All offset computations are checked. Empty views have no element access; their descriptor still has valid allocation identity and a canonical in-bounds or one-past origin. Safe APIs do not form out-of-bounds pointers even for a lane that will later be masked off.

Logical byte length differs from the physical span occupied by a strided view. Padding, reversed order and skipped elements make them diverge. A foreign descriptor must supply allocation size, element width, alignment and lifetime evidence; raw strides alone cannot establish memory safety. GPU backend restrictions can reject a valid abstract view if the operation cannot lower that layout.

3. Aliasing and mutation

Broadcasting with a repeated address, overlapping sliding windows and arbitrary repeated gathers are read-only. An exclusive view requires a proof of injectivity or a checked construction that establishes it. Bounds safety alone does not prevent two logical elements from racing on the same physical location. A failed alias proof returns LayoutError rather than choosing a potentially racy kernel.

Splitting an exclusive view is safe only when both returned views are disjoint. The parent exclusive borrow remains consumed while the children exist. Combining views must verify a shared allocation relationship and compatible loans, not merely adjacent integer addresses. The safe catalog deliberately avoids a general unchecked from-pointer constructor.

4. Reshaping versus copying

A view reshape succeeds only when the existing traversal order can represent the target without moving elements. Transposition usually preserves storage while changing strides, and may prevent a later flatten_view. A requested materialization copies logical elements into a fresh owner with the named contiguous order. contiguous_copy always creates an independent owner, even if input was already contiguous.

No function silently chooses between returning an alias and an independent owner based on runtime layout. This makes mutation behavior and allocation visible. A compiler can remove a copy when it proves observational equivalence, but the public ownership result and failure semantics remain those of the requested operation.

5. Iteration and asynchronous leases

Element iteration over Cpu storage follows logical lexicographic order unless an explicit order descriptor says otherwise. An iterator borrows the view and owner. A mutable iterator yields nonoverlapping exclusive element references and cannot return a second reference to an element already loaned. Generic view iterators cannot run CPU loads over device-only storage.

Submitting a kernel with a borrowed view registers the allocation, metadata and lifetime lease before the device can access them. Losing the user Pending handle does not end that lease. The enclosing device scope must establish quiescence before borrowed storage can leave scope. Device loss that leaves quiescence unknown cannot be downgraded to a normal error that immediately frees the buffer.

6. Descriptor-only operations 

// Given a validated read-only Cpu tensor owner named image.
Result<TensorView<f32, Shape<3, 2>, Cpu>, ShapeError> transposed = Tensor.transpose_view(&image, 0, 1);
Result<TensorView<f32, Shape<6>, Cpu>, LayoutError> flat = Tensor.flatten_view(&image);
// Given a separate initialized, injective owner named prepared_owner.
mut Tensor<f32, Shape<2, 3>, Cpu> writable = prepared_owner;
MutTensorView<f32, Shape<2, 3>, Cpu> editable = Tensor.view_mut(&mut writable);

The static types here illustrate a 2-by-3 input. A compiler may reject an incompatible declared result before execution. Dynamic input uses a dynamic view descriptor and retains checked results. Neither statement copies element storage or converts its placement.

8. Design boundary and related pages

All signatures are proposed library contracts. AOT and JIT preserve the same validation, lifetime and numeric semantics. An optimization may remove a proven redundant operation, but must preserve observable errors and synchronization boundaries. Supporting descriptor types and generic shape spellings remain design candidates; parameter passing uses the approved value, &T and &mut T forms. Returned-reference lifetime notation remains conceptual.
