1. Placement is a checked capability

P distinguishes placement classes such as Cpu and Gpu. DeviceId identifies an actual allocation context and device. The same Gpu marker can describe incompatible devices, so queue submission checks concrete identity and supported memory access. Unified virtual addressing, unified physical memory and coherent host access are separate backend capabilities; none follows from the word unified in the programming model.

The goal is one typed shape and operation model. It does not erase transfer costs or assume every CPU scalar operation is native on every GPU. Storage support, arithmetic support, synchronization support and atomic support are queried separately. A target can store f64 yet lack the requested f64 operation profile or offer poor throughput.

2. Submission and failure ordering

Tensor.submit accepts a typed TensorOp descriptor, validates shapes and capabilities, registers resource leases, then submits work. Submission can include explicit specialization and allocation and therefore returns Result. A successful submission returns Pending<Out>; it does not return a ready tensor. The selected queue and operation determine execution placement, with no implicit fallback transfer to Cpu.

An adapter must handle partial submission carefully. If a backend reports failure after accepting any work, resource leases remain retained until quiescence is established. A simple error return cannot imply that no device access occurred. SubmitError may carry a receipt or recovery state so a device scope can drain accepted work safely. This is a required contract, not a claim that all backends already implement it.

3. Transfers and staging

A transfer explicitly names destination device and policy. Upload keeps source storage stable for the required interval; download keeps the device source live and the host destination inaccessible to conflicting access until completion. Pageable host memory may require staging. The caller chooses a staging policy and can inspect whether bytes were copied into a pinned staging owner.

A true asynchronous transfer may require registered or pinned memory. Passing a stack slice is allowed only when the selected adapter can retain its scoped loan and satisfy backend lifetime requirements, otherwise it returns an unsupported-storage error. Zero-copy mapping is a named capability with synchronization obligations, not a promise that transfer_async transfers zero bytes.

4. Queues and visibility

A queue defines ordering only for operations covered by its declared semantics. Cross-queue consumers require explicit dependency tokens and the appropriate visibility operation. An event records a particular generation of submitted work; recycling an event object cannot let an old token certify a newer submission. Queue idle and successful completion are different reports.

Host readability requires a completed producer, the necessary memory visibility/cache operations and a host-accessible allocation. Waiting on a device computation does not download device-only memory. A mapped shared buffer can avoid a bulk transfer but still requires an acquire operation and exclusive ownership transfer. See Pending_Visibility for the complete boundary.

5. Precision and compiler specialization

AOT and JIT may specialize shape, layout and device capabilities while preserving the same scalar and error semantics. The strict profile does not silently reassociate reductions, flush subnormals or narrow accumulators. Requested relaxed math is explicit in operation options and remains reflected in the compiled operation identity and cache key.

Compilation reports can describe selected lowering and required capabilities; they do not prove hardware speed or timing. A fallback that changes placement requires an explicit policy and a cost-visible transfer path. Kernel launch bounds and address arithmetic must remain checked even when MLIR or LLVM internal operations have weaker preconditions.

6. Explicit allocation and dependency handles 

Result<Pending<Tensor<f32, Shape<2, 3>, Gpu>>, SubmitError> initialization = Tensor.zeros_async<f32, Shape<2, 3>>(&queue);
// Given a validated operation descriptor and already borrowed input descriptors on queue.device.
Result<Pending<Tensor<f32, Shape<2, 3>, Gpu>>, SubmitError> calculation = Tensor.submit(&queue, operation, inputs);

The values above are submission results and must be handled before Pending functions are called. Awaiting them through the later control-flow syntax has the same completion contract as the explicit Pending functions. No example implies that a GPU tensor can be immediately read through Cpu indexing.

8. Design boundary and related pages

All signatures are proposed library contracts. AOT and JIT preserve the same validation, lifetime and numeric semantics. An optimization may remove a proven redundant operation, but must preserve observable errors and synchronization boundaries. Supporting descriptor types and generic shape spellings remain design candidates; parameter passing uses the approved value, &T and &mut T forms. Returned-reference lifetime notation remains conceptual.
