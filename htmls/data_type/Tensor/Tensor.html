Import required. Tensor is a specialist library type. Add import tensor { Tensor }; before declarations to use its short name. Other specialist names used by a program also need their own permitted import routes. The catalog examples below focus on API fragments; they do not imply automatic type availability.

1. A typed owner for multidimensional data

Tensor<T, S, P> is the proposed owning multidimensional container. T is the element type, S describes shape, and P describes a placement class. A value owns initialized storage and shape/layout metadata. Assignment moves that ownership; a large element buffer is never copied merely because the value is passed to a function. This reference is an original Aevix design contract, not an implemented compiler or a promise that any listed operation is supported by every backend.

Shape<2, 3> denotes a statically known shape. Cpu and Gpu are candidate placement markers, not physical device identities. A tensor on one GPU cannot be passed to another GPU queue solely because both types contain Gpu. Runtime device identity, allocation context, and queue compatibility remain validated. Views borrow storage and do not create another owner.

2. Reference notation and supporting records

In signatures, X is a catalog variable for an already borrowed input: &Tensor<T, S, P> or TensorView<T, S, P>. O is the inferred owning result tensor, V is a read-only TensorView, and M is an exclusive borrowed input: &mut Tensor<T, S, P> or MutTensorView<T, S, P>. Owners are passed with &owner or &mut owner; existing views are passed directly, without an extra reference layer. These letters are documentation variables, not additional language types. S2 is a requested shape. TensorError, ShapeError, LayoutError, AllocationError, DeviceError and SubmitError are proposed library error records. TensorError distinguishes shape, bounds, overflow, allocation, alias, unsupported-operation and scalar-arithmetic failures.

TensorOp<Inputs, Out>, ReductionSpec<A>, AxisList, Layout, DeviceId, Queue and Capabilities are proposed library descriptors. A TensorOp declares input/output types and operation parameters; it is not a newly settled lazy expression primitive. A reduction spec names accumulator type A, output conversion, axis retention and accumulation order. Parameters follow the approved grammar: T value passes a Copy value by copy and an owning non-Copy value by move; &T value shares a read borrow; &mut T value grants an exclusive write borrow. Calls use x, &x or &mut x respectively. A mutable owner binding is required to create &mut access. Returned-reference lifetime notation remains descriptive.

Slice<T>, MutSlice<T>, TensorView, MutTensorView, ShapeLike and the catalog X/M arguments already carry their borrowing capabilities and are passed directly. Borrow lifetimes follow overlapping storage and last use. mut T value changes only a callee-local by-value parameter; it does not substitute for &mut T. Synchronized interior-mutation types follow their own rules.

3. Static facts, dynamic checks and empty shapes

Provably incompatible static shapes are compile-time errors. Runtime dimensions produce checked Result values. Every dimension product, byte-size calculation, stride multiplication and reachable address span must be representable before storage or pointer access. Rank zero contains one scalar element. An extent of zero makes the element count zero, including when other extents are large; descriptor validation still checks each dimension and byte-size calculation without relying on integer overflow.

Broadcasting aligns trailing dimensions. An aligned pair is compatible when the extents are equal or one extent is 1. The result uses the non-singleton extent: broadcasting 0 with 1 produces 0. Broadcasting 0 with 2 is invalid. An omitted leading dimension behaves as 1. Broadcasting is a read-only view operation and must not fabricate an exclusive view of repeated storage.

4. Views, explicit copies and mutation

Shape does not imply contiguity. A view carries extents, strides, an origin and a validated storage span. Slicing, transposition and compatible reshaping only create borrowed descriptors. Advanced selection, concatenation and explicit materialization create output storage. A reshape request that needs data movement returns a layout error; the caller chooses a copy operation. No ordinary indexing operation secretly moves a GPU buffer to the host.

Mutation requires an exclusive borrow. Mutable views must be injective over their logical indices: overlapping windows, zero strides over non-singleton extents and repeated indices cannot yield a general mutable view. An _into function validates shape, indexing and prohibited aliasing before starting writes. A later scalar-arithmetic or device execution failure does not imply rollback; caller-owned destinations may be partially changed and must follow their reported validity state. Newly allocated output is exposed only after successful initialization.

5. Arithmetic precision and reproducibility

Element operations use the scalar type contract, including integer overflow rules, NaN, infinity and signed zero. Reduction precision and accumulation order are separate from storage type. The strict profile specifies a logical lexicographic order and explicit accumulator conversion; a tree or relaxed order must be requested in ReductionSpec and may produce different floating-point bits. No backend may silently use narrower accumulation, flush subnormals or enable fast math merely because code uses a GPU or JIT.

Explicit fma performs one fused multiply-add per element. A compiler may fuse operations only when the selected numeric contract permits the same result. A reproducible mode constrains operation order and scalar behavior; it does not by itself promise identical transcendental implementations on every target. Unsupported numeric capabilities are diagnosed or returned as errors rather than silently changing meaning.

6. CPU results and explicitly submitted device work

Ready arithmetic functions in this catalog are instantiated for Cpu storage. Metadata and safe view functions are placement-independent and cannot read device elements on the host. Device arithmetic uses the same typed operation description through Tensor.submit and returns Pending<Out>. This makes queue submission, synchronization and failures visible. Device output can be ready for another device operation without becoming host-readable.

Allocation, upload, download, staging and materialization are separate operations. Ownership and borrow leases remain live until queued work becomes quiescent, even if a Pending handle is dropped. Completion, successful execution, cache visibility and transfer to host storage are distinct guarantees. See the Pending reference for resource retention and fatal device-loss behavior.

12. Cost-visible examples

The following statements illustrate the approved type-first declaration and borrowing grammar. They do not unwrap Result implicitly. A Result must be handled before its payload can be borrowed, moved or submitted; the later control-flow reference defines that handling syntax. 

Result<Tensor<f32, Shape<2, 3>, Cpu>, TensorError> matrix = Tensor.zeros<f32, Shape<2, 3>>();
Result<Tensor<f32, DynamicShape<1>, Cpu>, TensorError> samples = Tensor.linspace<f32>(0.0, 1.0, 4, true);
// Given a validated Cpu tensor owner named source and a borrowed shape descriptor named target_shape.
Result<TensorView<f32, Shape<3, 2>, Cpu>, TensorError> reshaped = Tensor.reshape_view(&source, target_shape);

13. Scope and related types

Autodiff, sparse formats, distributed tensors, compiler fusion heuristics and vendor-specific matrix instructions belong in optional libraries or later profiles. They do not change the core owner, shape or cost contract. A compiler can eliminate a proven redundant copy, but may not invent an observable transfer or weaken borrowing to do so. Backend adapters must validate foreign descriptors rather than importing undefined behavior from an IR operation into safe Aevix.
