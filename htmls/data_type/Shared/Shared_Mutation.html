1. Sharing Does Not Grant Write Access

A shared owner exposes read access by default. A mut binding allows changing that handle; it does not automatically make the shared T writable. Interior mutability must be mediated by a synchronization primitive or another explicitly safe abstraction. Neither two equal values nor two unequal addresses establish the aliasing capability required for a write.

2. Establishing Uniqueness

The common get_mut operation needs exclusive access to the requesting handle and no other strong or weak handles. Its implementation coordinates this decision with concurrent promotion and reference-count updates. Reading counts and then returning &mut T would contain a race. A returned mutable borrow suspends conflicting handle operations for its lifetime. The conservative condition is part of the library contract, not merely a debug assertion.

3. An Explicit Allocation and Clone Boundary

make_mut advertises that it may allocate and call T: Clone. The returned error preserves the original handle and value when allocation or cloning fails. On success, the handle can point at a distinct cloned allocation; no other existing strong handle is redirected. This is a deliberate cost and identity change. User Clone behavior may share nested resources, so it cannot be advertised as recursive isolation.

4. Weak Observers Stay with Their Allocation

When weak handles exist, this draft chooses a clone into new control storage rather than treating an old weak reference as a future reference to an arbitrary new value. Old weak handles remain tied to old identity. If the requesting handle was the last strong owner of the old value, moving to the clone can make those weak handles permanently expired. If old strong owners remain, promotion still targets that old value.

5. Locks and Atomic Fields

Shared<Mutex<T>> and Shared<RwLock<T>> keep storage alive, while lock guards regulate actual data access. Atomic fields require their own valid memory orders and type capabilities. Atomic reference counting is not a release/acquire publication protocol for arbitrary later field mutations. Contention, fairness, callback reentrancy, and lock ordering remain separate concerns. No shared-owner operation establishes automatic deadlock prevention.

6. Recovery and Callback Effects

Simple preflight failures preserve the owner. Calling an allocating payload clone may execute user code and cannot reverse external side effects that code already performed. A strong extraction operation returns an intact handle when uniqueness is unavailable. Error carriers state whether they contain an owner, value, or only a callback error; callers must not assume every failed transformation can reconstruct consumed data.

7. Common Functions and Typed Handles

The individual Shared.get_mut, Shared.make_mut, Shared.try_unwrap, and cloning signatures are defined once in Shared. Weak Graphs explains back-edges and Mutex describes guards. This page adds operational consequences without introducing another mutation namespace or a raw reference-count manipulation API.

Construction and payload trait queries are explicit; neither grants a mutable borrow through a shared handle.
