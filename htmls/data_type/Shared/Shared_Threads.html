1. Transfer and Shared-Access Bounds

Shared<T> is transferable and shareable only when its pointee and allocator/resource contract satisfy the corresponding Send/Sync-style bounds. These are descriptive safety traits whose final spelling remains a language decision. Atomic ownership metadata cannot make an unsynchronized interior field safe or change the thread affinity of an external handle. A unique Box similarly inherits its payload’s transfer constraints.

2. Ownership Is Not Data Publication

Creating another strong handle retains lifetime. Publishing initialized data and communicating later mutations still need an appropriate synchronization edge: a channel, a lock, task joining, or correct atomics. Count snapshots do not establish visibility of arbitrary fields. Shared immutable data can be read concurrently when T supports it, but calling a method that mutates interior state must retain that method’s synchronization obligations.

3. Scoped and Detached Captures

Scoped tasks may borrow only under a parent scope that tracks actual completion before any captured borrow expires. Detached tasks need owned captures or appropriately retained owners with valid transfer bounds. Putting a borrowed Slice into Shared does not extend its referent lifetime. A shared handle can itself leak in a cycle; that cannot become a use-after-free in an otherwise safe execution.

4. GPU and Foreign Completion

A host Shared handle neither uploads memory nor converts a CPU pointer into a kernel buffer. Device resource wrappers use placement-aware capabilities and completion leases. A cancellation request or discarded Pending handle does not prove a device has stopped. Buffers and code required by in-flight work remain retained until the backend proves completion, while host visibility may need additional synchronization or transfer.

5. Atomic Costs and Progress

Handle cloning increments a shared atomic count and dropping decrements it. Those operations can contend on cache lines and can trigger payload finalization when ownership ends. The document does not promise one instruction, wait freedom, universal lock freedom, or a particular cross-target implementation. Refcount overflow is handled explicitly and cannot wrap. Diagnostic counts are snapshots whose values can change immediately on another thread.

6. Finalization and External Resources

Reference cycles, intentionally retained handles, and process exit can prevent cleanup. This design promises safe lifetime management under its contracts, not eventual release of every file, callback registration, GPU object, or heap allocation. Resources requiring a particular release thread need an owning adapter that enforces it. A generic T destructor may not be correct on an arbitrary worker thread merely because a counter is atomic.

7. Related Synchronization Contracts

See Shared, Memory Order, Mutex, and RwLock. The contracts preserve the selected Aevix semantics across AOT and JIT without claiming external driver correctness or measured concurrency performance. No unchecked FFI adoption or ordinary safe raw-count editing is provided.

These capability queries concern the complete payload type; creating a Shared handle is still a separate fallible operation. 

bool scalar_transfer = Shared.is_sendable(i32);
bool locked_access = Shared.is_shareable(Mutex<i32>);
