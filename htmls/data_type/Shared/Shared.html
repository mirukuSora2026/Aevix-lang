1. Atomic Shared Ownership

0.2 implementation scope. Shared is a specialist library design, outside both the default prelude and the implemented 0.2 type/API subset. Their eventual use requires explicit imports; no built-in 0.2 module is supplied by this catalog. Import examples on this design page describe intended library boundaries, not an available 0.2 backend or package. See the 0.2 implementation profile; other catalog entries remain design contracts.

Shared<T> owns one strong reference to a value and atomic control state. Moving a handle transfers that reference without incrementing it; explicit clone creates another strong handle without cloning T. Last-strong destruction finalizes the payload, while weak handles can keep control information alive. The model has no tracing collector. Shared cycles can leak values and external resources even though dangling dereferences remain forbidden.

Design draft. Functions, traits, error carriers, and callback notation specify intended contracts, not implemented APIs. Variables and parameters are type first; bindings are immutable by default. Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. unit is a value type, distinct from return-position void.

2. Construction and Count Overflow

Allocating constructors return explicit errors and recover unused moved input on preflight failure. Cyclic construction exposes only a weak handle until T is initialized, preventing a read of partial state. Strong and weak counters cannot wrap to zero. This draft makes handle-clone overflow a RefCountError instead of silently saturating or prematurely destroying live storage. Handle cloning is allocation-free but performs atomic synchronization work.

3. Read Access and Trait Bounds

Shared access normally exposes only &T. Reference counting does not make a non-thread-safe T safe to share, make an external object reentrant, or synchronize its mutable fields. Thread transfer and shared reading require the documented Send/Sync-style bounds. Mutability can live behind Mutex, RwLock, or appropriate atomics, whose guards and ordering rules remain necessary. Moving a Shared handle does not upload a tensor or make a host value device-addressable.

4. Exclusive Access and Copy-on-Write

get_mut must establish exclusive access atomically and account for weak promotion; a strong_count result of one is not such a proof. Explicit make_mut may allocate and clone T. Under this conservative draft it clones when any other strong or weak handles exist, rather than implicitly detaching weak observers through an undocumented optimization. The requesting handle then denotes a new allocation; observers of the old allocation remain attached to the old identity.

CollectionError for make_mut and clone_value includes payload CloneError and allocation failure; an error preserves this handle and its prior allocation identity. Clone may still have external side effects that no ownership API can reverse.

5. Extraction and Failure Ownership

try_unwrap consumes a handle and atomically claims the value only when no other strong owner exists. A failed claim returns that handle. Weak references may remain but cannot resurrect a value after its strong count reaches zero. Fallible into_box and unwrap_or_clone specify input recovery on returned preflight or clone failure. A clone of T can retain its own shared resources, so extraction through Clone is not a promise of deep isolation.

7. Cycles, Tasks, and Asynchronous Resources

Weak back-edges can break known ownership cycles, but neither a lint nor reference counting proves global leak freedom. Cleanup may also be bypassed by process termination or intentionally retained ownership. Task and GPU resource safety cannot depend only on a user-visible handle’s destructor. A structured scope or runtime-owned completion lease must keep actual data alive until work has truly stopped, even when a notification handle is lost.
