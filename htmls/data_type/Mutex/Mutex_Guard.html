1. The Guard Is the Access Proof

A guard represents an acquired lock capability, not an owned copy of T. Borrowing fields requires retaining that capability, and dropping or explicitly unlocking it ends access. Moving a derived reference elsewhere cannot detach it from the guard lifetime. The lock owner remains borrowed until all relevant guards and waiters end. The safe profile provides no raw guard-forgetting escape that grants unprotected references.

2. Thread Affinity and Suspension

The default guard is non-Send and must be released on its acquiring execution context. It cannot cross await in the safe async profile, be handed to a GPU kernel, or be captured by detached work. This conservative rule respects backends whose unlock operations have thread affinity. A Shared owner retains storage only; it does not allow copying or fabricating guard capabilities.

3. Mapped Field Guards

Mapping consumes the original guard and retains its same underlying lock lease. A projection callback returns a field borrow tied to the input, not a reference into unrelated temporary storage. The mapped guard controls only its exposed projection, but the underlying full lock remains held. Fallible mapping returns the original guard if the field is absent. No allocation is needed for the borrow transformation.

5. Release, Exceptions, and Leaks

Normal guard destruction releases the lock. Unwinding follows the selected poison policy before release. Forced process termination cannot promise finalization, and leaking a held capability can prevent progress without creating permission to access data unsafely. Unlocking is not a durable disk flush or arbitrary GPU fence. Pointee references must be unusable before release; an API returning R from a guarded callback enforces that non-escape rule.

6. Reader/Writer Boundaries

Readers do not own a future right to upgrade. Reacquiring exclusive access while retaining a read capability may deadlock, especially with queued-writer policies. A mutex is non-reentrant by default; taking the same mutex recursively from a destructor or callback can deadlock. No automatic global lock order is inferred.

7. Related Common and Recovery Contracts

The Mutex common catalog defines acquisition and owner access. Poison recovery explains why an error can carry a held guard. Mapped guard support records and callback bounds are descriptive proposals, not hidden compiler syntax. No lock-free or deadlock-free property is implied by the existence of a safe guard type.

Successful acquisition and poison-error acquisition both retain an unlock obligation. The Result must be inspected before protected access. 

Mutex<i32> gate = Mutex.new(0);
Result<MutexGuard<i32>, LockError<MutexGuard<i32>>> acquired = Mutex.lock(&gate);
