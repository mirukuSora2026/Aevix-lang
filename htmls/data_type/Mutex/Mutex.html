1. Protected Data and Access Capabilities

Mutex<T> serializes access to one initialized T. A guard proves exclusive access and keeps the lock borrow alive. Sharing the mutex can be valid for a transferable T even when direct shared T access would be invalid. No reentrant acquisition, global lock ordering, fairness, or deadlock-freedom guarantee is implied.

Design draft. APIs, memory-order and error records, and trait names describe intended Aevix contracts. Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. unit is a value type distinct from void. No native implementation, fairness, or benchmark claim is implied.

2. Acquisition, Blocking, and Guard Lifetime

Acquisition returns a guard tied to the lock owner. A guard’s normal destruction or explicit unlock releases its capability; references derived from that guard cannot remain usable afterward. A blocked call may wait indefinitely under contention or a deadlock. Timeout and try operations state non-success explicitly. The lock cannot be moved or destroyed while borrowed guards or waiters need it.

3. Defined Advisory Poisoning

Default policy is PoisonOnUnwind. Unwinding while an exclusive guard is held marks the default poison state. Returning an ordinary Result error without unwinding does not automatically poison the lock. Poisoning warns that a higher-level invariant may be incomplete; it is not memory-safety validation. A poisoned acquisition returns an error carrying its already acquired guard. Releasing that error releases the guard; explicitly recovering it retains access without silently clearing poison.

4. Mutation and Moved-Input Failure

Convenience get_cloned is an explicit potentially allocating clone performed under the selected access mode. set and replace recover unused moved replacements when acquisition fails. User destructors and callbacks can run while access is held and may reenter other locks, so their costs and deadlock risks remain visible. A returned callback error does not reverse mutations already performed. Allocation or application errors are distinct from advisory poison state.

LockCloneError is the combined convenience error for get_cloned: it distinguishes lock/system/poison errors from fallible payload CloneError, including its allocation cause. It never silently unwraps a failed clone. Guard-returning lock operations retain their distinct LockError<Guard> contract.

5. Threads, Tasks, and Await Boundaries

Guards are non-Send by default in this draft and cannot cross an async suspension in the safe profile. Release before await or device submission instead of capturing a guard in detached work. The owning lock may be stored in Shared when trait/resource bounds permit it. A host lock neither synchronizes arbitrary device memory nor proves a foreign resource is reentrant. Borrowed data must not escape a synchronous protected callback.

7. Costs, Priorities, and Unsupported Features

A lock can park an OS thread, spin briefly, allocate runtime waiting state, or use a target-specific backend according to its published profile. This is not a lock-free primitive. Priority inversion and starvation depend on scheduling and policy. Unsupported timed operations or target/thread profiles produce capability diagnostics instead of silently moving work or changing poison semantics. No native layout or constant-size OS handle ABI is promised.

8. Examples and Specialized Rules 

Mutex<i32> gate = Mutex.new(0);
Mutex.is_poisoned(&gate);
Mutex.poison_policy(&gate);

See guard operations and poison recovery for specific lifetime and repair contracts. Shared retains the owner but does not acquire data access. Error carriers are proposed library records. The primary lock reference informs this independent design without importing all its platform behavior.
