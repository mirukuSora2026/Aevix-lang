1. Observe Without Retaining the Value

Weak<T> identifies shared control state without holding a strong owner of T. An empty handle identifies no allocation; an expired handle can still retain control bookkeeping after T has been destroyed. Weak does not expose &T directly. To read the payload, acquire a live Shared owner through upgrade and keep that returned owner for the whole borrow.

Design draft. Functions, traits, error carriers, and callback notation specify intended contracts, not implemented APIs. Variables and parameters are type first; bindings are immutable by default. Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. unit is a value type, distinct from return-position void.

2. Promotion and Races

Promotion atomically succeeds only while a positive strong count can be incremented. A count of zero cannot be resurrected. Refcount overflow is a returned error in this draft; an expired object is instead an Ok(None) outcome. Checking is_expired or strong_count and later accessing the value is not safe promotion. Another thread may drop the final owner between those observations.

3. Control State Versus Payload Lifetime

After last-strong destruction, weak control storage may remain until the last weak handle is released. It must contain enough identity and count state to reject future promotion safely. Keeping a weak reference does not promise the old T’s fields remain initialized or its external resources remain open. An implementation may retain allocation backing storage, but the value is still dead and cannot be dereferenced.

4. Cycles and Resource Leaks

A weak back-edge can break a known cycle in a graph whose forward ownership is strong. It is a design tool, not automatic cycle detection or an absolute leak-freedom proof. Strong cycles elsewhere, forgotten ownership, and external callback registrations can still retain resources. A Weak cached observer may expire at any time; application logic must handle absent data without manufacturing a replacement reference.

5. Threads, Tasks, and Borrowed Data

Weak inherits relevant thread/resource bounds. Promoting it retains the Shared allocation, not a separately borrowed referent stored inside T. For example, a Weak of an owner containing Slice does not make the slice’s source live longer. Scoped tasks and device submissions still require their own completion and placement contracts. Weak promotion is not an asynchronous join, a memory transfer, or proof that arbitrary mutable fields are synchronized.

7. Identity and Copy-on-Write

Weak handles attach to allocation identity. Explicit Shared.make_mut may redirect its requesting owner to a new cloned allocation; an old Weak is not silently retargeted. It can remain valid for old strong owners or become expired when the old last strong handle leaves. Application graphs depending on stable identity must account for this explicit mutation behavior rather than treating equal cloned values as the same object.

8. Examples and Related Owners 

Weak<i32> missing = Weak.new(i32);
Result<Optional<Shared<i32>>, RefCountError> observed = Weak.upgrade(&missing);
Weak.is_empty(&missing);

See Weak Graphs for ownership design and Shared for strong construction. Namespace calls are individually defined above. Borrowing, counter safety, and application validity are different guarantees; no weak handle provides unchecked access to an expired or partly constructed object.
