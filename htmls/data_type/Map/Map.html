1. Hashed map

Map<K, V> owns at most one value for each equivalence class of keys. Its default representation is hashed, with a per-instance randomized policy and no stable traversal order. It is a host owning collection, not an implicit concurrent table or GPU dictionary. Insertion may grow buckets; moving the handle transfers ownership of every entry without cloning.

Design draft. This is an Aevix contract proposal, not an implementation claim. Callback, iterator, trait, and error-carrier names are descriptive. Parameters use T value by value, &T value for a shared borrow, and &mut T value for an exclusive borrow. Calls pass owners as x, &x, or &mut x; taking &mut owner requires a mut binding. Existing references and borrowed views are passed directly. Callback aliases, error records, and returned-reference lifetime notation remain design descriptions. Bindings are immutable unless declared mut; unit is a value type.

2. Key equality and hashing

Equal keys must produce equal hashes under the map’s policy. Both equality and hash meaning must stay stable while a key is stored. Public APIs expose stored keys through shared borrows only. Interior mutation, external global state, and unsafe code can still violate this rule; wrong lookups or diagnostic failure are possible, but the safe implementation must preserve initialization, bounds, and alias safety. Floats require an explicit lawful equality/hash policy rather than silently treating NaN as an ordinary equal key.

3. Ownership and entry identity

Lookups borrow; removal returns ownership. Values may be edited through a unique borrow while keys remain fixed. Any live value reference, entry capability, drain, or mutable iterator constrains structural mutation even when spare capacity exists. No raw pointer stability, insertion order, or key address stability is part of the contract. Canonical key identity matters when equal keys carry different descriptive metadata.

4. Failure guarantees

CollectionError includes size overflow, allocation, seed initialization, and fallible cloning where applicable. InsertError retains unused incoming key and value on duplicate rejection or growth preflight failure. Such preflight errors leave existing entries unchanged. User hash/equality callbacks must be lawful and must not reenter a borrowed map; if a callback unwinds, memory safety and initialized ownership remain, but callback effects are not rolled back. Bulk construction cleans partial output and leaves its borrowed source intact.

6. Order and complexity

Expected constant-time lookup is a workload and hash-distribution expectation, not a worst-case guarantee or collision-proof security claim. Worst-case lookup and insertion can inspect a linear number of entries. Rehashing and full traversal may inspect capacity, including empty buckets; oversized sparse maps therefore have observable scan cost. Hashing long strings, equality, cloning, and destruction add their own work. Use an ordered map when sorted traversal or key ranges are required.

7. Examples

These complete expressions retain the construction Result for explicit caller handling. They do not unwrap an allocation error or imply that a Result itself is a map. 

Result<Map<i32, i32>, CollectionError> scores = Map.with_capacity(i32, i32, 32);
Result<Map<string, i32>, CollectionError> names = Map.new(string, i32);

8. Targets and related collections

Sharing a map across threads still requires synchronized access and Send/Sync-compatible key, value, and hash policy bounds. A host lock does not publish a table to a device. Serialize explicit fields or transform to device-supported arrays rather than copying a host handle or relying on bucket layout. See OrderedMap, entry capabilities, Set, Vector, and string.
