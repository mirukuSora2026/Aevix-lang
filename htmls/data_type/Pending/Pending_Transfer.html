1. A transfer is work with memory obligations

An asynchronous transfer explicitly names source, destination, logical byte or element count, device identities and policy. Its Pending handle tracks work already accepted for submission. Upload, download and device-to-device copy are distinct paths even when they share a generic transfer operation. Unified addressing does not establish coherent access, equal devices or zero transfer cost.

The transfer registry retains allocation owners or scoped loans before the backend can access them. Source read loans prevent conflicting writes; destination exclusive loans prevent reads and overlapping writes until the transfer completes and required visibility is established. Dropping an observation handle cannot end DMA lifetime requirements.

2. Lengths, layout and initialized elements

Element transfers require equal logical shape and compatible element representation unless an explicitly named conversion is requested. Byte transfers validate byte counts, allocation spans, alignment restrictions and overlap policy using checked arithmetic. Tensor logical byte length can differ from a strided storage span; a simple contiguous copy cannot blindly use one in place of the other.

A strided transfer either uses a supported gather/scatter path or requires an explicit materialization/staging operation. No adapter may silently expose padding bytes as initialized values. Empty transfers perform no element access but still validate identities, descriptors and completion-token semantics. Caller-provided destinations may be partially written on a late backend failure.

3. Pinned memory and explicit staging

Some backends require pinned or registered host memory for true asynchronous DMA. An ordinary pageable slice can require a staging copy or a synchronous step. TransferPolicy states whether staging is allowed, required or forbidden; a plan reports the intended path and estimated bytes before submission. A plan is not a reservation or proof of actual overlap.

Pending.pin_copy creates an initialized pinned staging owner with an explicit allocation and copy. It is retained until the backend no longer reads it. Registering an existing host buffer needs lifetime and backend registration guarantees and is a fallible explicit operation. Registration does not turn arbitrary stack memory into independently owned storage.

4. Borrowed host storage and scoped submission

A borrowed host buffer can participate only when its DeviceScope proves that the storage remains valid until transfer quiescence. Exclusive host access is unavailable while a device writes or reads in a conflicting way. A task suspension or cancellation request does not shorten this interval. The registry cannot rely only on a user-defined destructor for safety.

A detached transfer requires owned resources, including any metadata and pinned registration owner. Failed detach returns the original operation handle. If submission partially succeeds, the error retains a recovery receipt and all accepted work remains registered. Ordinary failure is not evidence that the source can immediately be freed.

5. Download completion and host access

Downloading into a new Cpu owner exposes that owner only after successful initialization and required host visibility. Downloading into caller storage retains an exclusive loan and reports output validity on failure. Waiting for a device kernel alone is not a download, and acquiring a host mapping is valid only for storage that actually supports host access.

A mapping capability may avoid a bulk copy while still requiring invalidate/acquire operations and ownership transfer. Coherent host memory can remove a cache operation only when the adapter has the required capability proof. It cannot remove completion ordering or conflicting-access restrictions.

6. Planning and named transfer paths 

// source/destination and host_source/device_source are already borrowed transfer-buffer views.
Result<TransferPlan, DeviceError> plan = Pending.plan_transfer(source, destination, transfer_policy);
Result<Pending<TransferOutput>, SubmitError> upload = Pending.upload(&scope, &queue, host_source, transfer_policy);
Result<Pending<HostBuffer<f32>>, SubmitError> download = Pending.download<f32>(&scope, &queue, device_source, host_policy);

source, destination, scope and queue are existing validated values. The examples do not unwrap results, assume a native pointer ABI or allow a borrowed buffer to escape its enclosing scope.

8. Backend boundary

The device adapter must map these proposed contracts onto actual queue, event, cache and allocation rules. CUDA and Vulkan sources demonstrate why asynchronous naming, event completion and memory visibility cannot be treated as one universal guarantee. The documentation specifies required behavior; it does not prove a working implementation on any device.
