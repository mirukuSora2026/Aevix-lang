1. Already-submitted work with retained resources

0.2 implementation scope. The Pending and device-completion APIs described here are specialist library designs, outside both the default prelude and the implemented 0.2 type/API subset. Their eventual use requires explicit imports; no built-in 0.2 module is supplied by this catalog. The implemented host CPU facility is parallel.for_each, which does not create a Task or Pending value. See the 0.2 implementation profile; other catalog entries remain design contracts.

Pending<T> is the proposed move-only result handle for device work that has been accepted for submission and will produce T. It is distinct from a host Task<T> and from an unstarted lazy future. Its registry entry retains all required buffers, metadata, compiled code, queue and device context until the device can no longer access them. A user handle is an observation/result capability, not the only owner of those safety obligations.

Dropping, forgetting or discarding a Pending handle does not free in-flight resources. Scoped borrowed inputs keep their loans until the enclosing device scope proves quiescence. Owned detached submissions can be retained by the device runtime independently. This is a design requirement, not an existing backend implementation or guarantee that all hardware supports cancellation.

2. Supporting records, ownership and errors

Queue, DeviceScope, CompletionToken, DeviceReady<T>, HostReady<T>, DeviceStatus, WaitStatus, DependencySet and TransferPolicy are proposed library types. Shared observation uses &Pending<T> and exclusive result take uses &mut Pending<T>. Calls spell &operation or &mut operation explicitly; the latter requires a mut owner binding. Pending<T> by value moves its owning handle. DeviceReady certifies successful producer completion for device use; it does not make storage host-addressable. HostReady certifies host accessibility plus required visibility, while retaining its ownership or mapping loan.

SubmitError covers validation/allocation/compile/admission errors and can retain a recovery receipt when any work was partially accepted. DeviceError distinguishes failed but quiescent work from device/session loss with unresolved quiescence. Invalid result take and unsupported synchronization are recoverable errors when no unsafe resource release follows. Fatal backend loss is not automatically an ordinary Result that lets borrowed memory leave scope.

SpawnInputError<Pending<T>> preserves the device handle if a host bridge cannot register. A successful bridge returns Task<Result<DeviceReady<T>, DeviceError>>; host scheduling failure, device failure and host accessibility remain separate.

Queue submission borrows &Queue and an existing device scope through &DeviceScope; these registries have synchronized interior state. HostReadBuffer, HostWriteBuffer, DeviceReadBuffer and DeviceWriteBuffer are already borrowed buffer capabilities, so callers pass those views directly. A HostMap owns its mapping lease; obtaining host_slice borrows &HostMap, and host_slice_mut borrows &mut HostMap from a mut binding. Existing references are passed directly without another &.

3. Completion, success and visibility are different

Status separates Submitted, Running, Completed, FailedQuiescent and QuiescenceUnknown phases. Cancellation requested is an orthogonal flag. Completed means the backend proved the work no longer accesses its leases; the outcome still needs a success/failure check. is_complete returns true only for proven quiescent terminal work, including a quiescent failure, and false for unknown quiescence.

A successful result can be ready for another device operation while remaining invisible or inaccessible to the host. Host access requires completion, necessary memory-domain/cache operations and host-accessible storage. Waiting on a kernel does not download a device-only tensor. A memory mapping must retain its allocation and cannot overlap active exclusive device access.

4. Registration and lifetime safety

Submission validates shape, allocation span, alias rules and device identity before registration. Resource leases are registered before the device can see addresses. If submission partly succeeds and then fails, the runtime preserves all leases needed by accepted commands and supplies recovery tracking. Returning an error is not proof that no operation began.

Loan release is independent of handle destructors. A DeviceScope borrowing stack or collection storage cannot return until use is quiescent. If device loss makes quiescence unknown, the runtime must retain/quarantine owned allocations and establish safe quiescence before releasing borrowed loans, or follow its explicitly fatal termination policy. It must not resume safe code with potentially accessed storage deallocated.

5. Ordering and dependency generations

Queue order covers only the operations and memory scopes declared by that queue profile. Cross-queue use requires an explicit completion dependency plus a memory visibility/ownership transition where needed. An execution-order edge alone does not always make writes visible. A CompletionToken identifies one recorded submission generation and cannot be reused as proof for later work after an underlying event object is recycled.

Dependencies retain producer registry state and relevant device context. Incompatible devices, impossible ordering or known dependency cycles return a checked error. A token is not a host pointer, a blanket fence for unrelated memory or proof that an entire device is idle. Importing a foreign event requires an adapter contract identifying exactly what it orders.

6. Cancellation, timeout and abandonment

Cancellation requests are best-effort and capability-dependent. They may cancel work not yet launched or request a cooperative device path. They do not prove completion, undo writes or make borrowed buffers reusable. A cancellation acknowledged as stopped must still establish quiescence. Timeout limits the observer wait; in-flight work and registry leases remain live afterward.

discard_result abandons observation while work remains tracked. Detach is explicit and requires independently owned resources; borrowed device scopes cannot be escaped by discarding a handle. Device errors can leave caller-provided outputs partially written or invalid according to an output-validity report. No generic rollback guarantee follows from Result.

9. Observation does not transfer memory 

// Given an accepted device submission owner named operation.
Result<bool, DeviceError> complete = Pending.is_complete(&operation);
Result<CompletionReport, DeviceError> completion = Pending.wait(&operation);
// Given a separate owned submission handle named owned_operation.
Result<DeviceReady<Tensor<f32, Shape<2, 3>, Gpu>>, DeviceError> output = Pending.wait_take_device(owned_operation);

The output remains a Gpu tensor. Host scalar access requires an explicit download or an allowed host mapping/acquire path. A query that returns false does not permit reuse of source/destination buffers. A Result error must be interpreted together with quiescence and registry policy, not assumed to release an in-flight loan.

10. Explicit movement and memory visibility

Pending exposes runtime costs that a unified programming model cannot erase: submission, staging, ordering, synchronization and ownership transfer. It does not promise hardware overlap, cancellation, real-time completion or zero-cost scheduling. AOT/JIT may optimize command construction while preserving these visible boundaries.
