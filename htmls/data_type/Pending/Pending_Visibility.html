1. Four separate questions

A consumer must distinguish whether a producer stopped accessing resources, whether it succeeded, whether its writes are visible to the consumer domain and whether that consumer can address the storage. A completed failure can be quiescent without valid output. Successful device-ready storage can remain inaccessible to a host pointer. These facts cannot be compressed into one unchecked ready bool.

CompletionToken is a retained generation-specific dependency capability. DeviceReady<T> pairs a successful output with device-use readiness. HostReady<T> additionally proves supported host access and the required acquire/cache operations while retaining ownership or a mapping loan. None is a universal fence for unrelated allocations or future submissions.

2. Execution order and memory dependencies

Queue order determines when commands execute under a selected queue profile. A memory dependency also makes relevant writes available and visible to specified consumers. Cross-queue or cross-device use requires an explicit adapter-supported dependency and memory-domain transition. An execution-only event is insufficient for a read-after-write dependency if visibility has not been established.

A dependency names producer generation, allocation accesses, consumer queue/domain and relevant access modes. Reusing a native event object requires a fresh token generation. Importing an external token needs a documented producer scope and ownership lifetime; a raw integer event handle cannot prove those facts. Dependency cycles and incompatible device identities are checked errors when detectable.

3. Host acquire and mappings

Host acquire is permitted only for host-accessible output. It waits or checks the required successful completion, performs backend cache invalidation or domain operations when needed and grants a host-access loan or owner. Device-only allocations return UnsupportedHostAccess; the caller requests an explicit download. A shared virtual address alone is insufficient.

Mapping retains the allocation and prohibits conflicting device access for its mapped loan. Releasing the host map can require an explicit release/flush operation before subsequent device reads. A coherent memory capability can remove certain cache steps while leaving ordering and loan exclusivity intact. Safe APIs must not expose an uninitialized or partial failed output as an ordinary initialized Slice.

4. Failure and unknown quiescence

A quiescent execution error reports that no further accesses from the failed work can occur, together with output validity. Resource cleanup and borrowed-loan release can then follow the declared report. Device or session loss may leave quiescence unknown. In that case a normal error return must not authorize deallocation, mutation or scope exit for memory the device may still access.

The adapter must establish safe quiescence, retain/quarantine owned storage or use an explicitly fatal termination policy before borrowed storage could be released. Returning to safe code with a dangling device reference is forbidden. A timeout or cancellation request cannot be used as a substitute for this proof, even if a user no longer cares about the result.

5. Host tasks and visibility evidence

A host Task waiting for Pending can integrate device completion with a scheduler. It retains the same device resource leases and does not invent host coherence. A Task producing a Gpu tensor may carry a successful device-ready value while still requiring download before Cpu indexing. Error layers remain distinct: task scheduling/lifecycle failure surrounds the device Result.

Locks and host atomics do not automatically establish device memory visibility. Shared<T> reference counting retains memory but does not flush GPU caches or permit concurrent mutation. Device-scope completion, host acquire and explicit release define the legal handoff points. The exact target barriers are an adapter responsibility, not an implicit consequence of a language-level bool.

6. Readiness is typed evidence 

// Given an accepted submission whose output is host-accessible.
mut Pending<HostBuffer<f32>> pending_host_output = prepared_host_output;
Result<Optional<HostReady<HostBuffer<f32>>>, DeviceError> readable = Pending.acquire_host(&mut pending_host_output);
// Existing producer token is moved into a dependency on the borrowed destination queue.
Result<QueueDependency, DeviceError> ordered = Pending.after(&consumer_queue, producer_token);

An absent readable value means output is not available for taking. A successful ordered dependency schedules the declared producer-to-consumer relation; it does not give immediate host access to either allocation.

8. Backend boundary

The device adapter must map these proposed contracts onto actual queue, event, cache and allocation rules. CUDA and Vulkan sources demonstrate why asynchronous naming, event completion and memory visibility cannot be treated as one universal guarantee. The documentation specifies required behavior; it does not prove a working implementation on any device.
