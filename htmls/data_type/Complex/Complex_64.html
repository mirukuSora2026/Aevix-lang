1. Basic Information

Complex<f64> stores a real f64 component and an imaginary f64 component. The pair carries 128 bits of value payload and has two independently rounded components. There is no combined 128-bit significand.

Property Binding
Code type Complex<f64>
Each component f64; 64 bits
Value payload 128 bits / 16 bytes
Normal precision 53 significant binary digits per component
Component max finite magnitude 1.79769313 × 10^308
Component min positive normal 2^-1022
Component min positive subnormal 2^-1074
Component epsilon 2^-52
Consecutive exact component integers −9007199254740992 through +9007199254740992
Status Default component format

The shared API is Complex. The component encoding is defined in f64. The default complex alias is proposed to select this type.

2. Type-First Declarations & Construction

The type appears before the variable name. Literal components are checked and rounded in the expected f64 context, avoiding an unintended conversion through a different format. An already typed f64 value can be passed directly; a value in another component format requires an explicit conversion. An imaginary literal suffix is not required by this design. 

import complex { Complex, ComplexError };

Complex<f64> value = Complex<f64>.new(3.0, 4.0);
f64 real = value.real;
f64 magnitude = Complex<f64>.norm(value);
Complex<f64> copy = value;

All statements end with semicolons. The copied scalar has independent component values. No allocation is required for this assignment, construction, component extraction, or conjugation.

3. Range & Magnitude Boundaries

Both components may independently reach the finite limits of f64. That square region is not a circular bound on the magnitude: a representable pair can have a Euclidean norm greater than the largest representable f64. The pair remains a valid finite complex value even when a magnitude-returning function overflows.

Complex.norm uses a scaled evaluation to avoid an unnecessary square overflow. norm_squared intentionally returns the squared magnitude in f64, so it may overflow much earlier. The proposed checked norm reports a non-finite result rather than pretending the pair itself was invalid. Division likewise uses a scaled algorithm, not an unconditional real²+imag² denominator.

4. Precision, Rounding & Accumulation

Every integer component in [−9007199254740992, +9007199254740992] is exact. This guarantee applies separately to real and imaginary values; it does not guarantee exact complex multiplication or an exact norm. At and above the precision boundary, adding a unit may round back to the same component.

Core component arithmetic uses the requested Float profile. A multiply-add rewrite, a wider temporary, or a parallel reduction tree can change the result. Use explicit accumulator format and order for reductions. A wider accumulator is optional and explicit; strict execution cannot infer that a different result is interchangeable.

5. Signed Zero, Infinity & NaN

f64 has signed zeros, infinities, NaNs, and subnormals, and either component can hold any of them. is_finite requires both components to be finite. is_nan and is_infinite can both be true for one pair. Numeric equality ignores zero signs and rejects equality involving NaN; bit equality remains available.

Branch-sensitive functions preserve the side selected by signed zero. For a negative real value, sqrt with +0 imaginary approaches the positive imaginary root, while −0 selects the negative imaginary root. Conjugation must toggle that sign even when the numerical imaginary value is zero. Text transport may lose payload detail; raw component bits do not.

6. Conversions & Return Types

Complex.convert_exact validates both destination components; a failure cannot return half a pair. Rounded conversion explicitly chooses a Float rounding policy. Changing f64 to another component format is never an implicit promotion. Conversion to a real scalar requires a zero imaginary component; conversion to an integer additionally checks finiteness, rounding, and range.

Operation Specialized result
Complex.new / add / conjugate Complex<f64>
Complex.real / imag / norm / phase f64
Complex.checked_div Result<Complex<f64>, ComplexError>
Complex.to_bits (u64, u64)
Complex.to_be_bytes Array<byte, 16>
Complex.to_string Result<string, ComplexError>

Converting a pair to an integer does not silently discard the imaginary value. A signed imaginary zero is allowed and contributes no integer sign. Any explicit lossy operation must be named by the caller.

7. Bytes, Layout & Foreign Functions

Canonical wire storage is 16 bytes: real component first, imaginary component second, with each component encoded in the requested byte order. Big-endian does not mean reversing the entire pair. A dynamic-buffer decoder checks the whole pair before reading; checked writes leave the destination unchanged on a bounds error.

The wire width is distinct from a foreign ABI. The language does not promise a matching C complex, C++ template specialization, vendor GPU vector, register pair, or alignment merely because all use similar numbers of bytes. An FFI binding validates the complete target layout and calling convention. A byte view also cannot grant mutable access that breaks exclusive borrowing.

8. Arrays, SIMD & GPU Execution

Array<Complex<f64>, N> and Vector<Complex<f64>> own contiguous scalar pairs. A tensor adds shape and placement without enlarging an element’s component range. Owners move by default. Converting interleaved pairs to separate real and imaginary buffers is a visible O(n) operation unless the compiler removes a wholly unobservable temporary.

A target may provide scalar component instructions without a native complex division or transcendental implementation. Math-library capability and its accuracy profile are checked independently of storage support. Parallel output requires disjoint writable regions. GPU completion, transfer, and CPU visibility remain separate steps.

9. Format-Specific Function Bindings

No second format-specific function namespace is introduced. The full catalog stays in Complex.; this page specializes its component type, range, wire width, and execution requirements. The principal branch and checked-error policies are identical across formats, while the rounding grid and supported target implementations differ. 

Complex<f64> conjugated = Complex<f64>.conjugate(value);
Result<Complex<f64>, ComplexError> divided =
    Complex<f64>.div(value, Complex<f64>.one());

This page is a proposed language reference, not proof that the compiler, foreign library, or GPU backend implements the type. Unsupported capabilities are diagnosed instead of silently selecting another representation.
