1. Basic Information

Complex<T> is a pair of floating-point components representing real + imaginary × i, with i² = −1. The component format T determines range and rounding. Complex numbers extend the real number system, but they do not have a compatible mathematical total order.

Design draft. APIs below specify intended Aevix behavior. They do not claim a compiler implementation, backend support, or a frozen foreign ABI. The generic spelling is the unambiguous reference form; complex is the proposed convenience alias for Complex<f64>. Width-suffixed aliases such as c64 are deliberately not assigned here.

Reference type Component format Value payload Status
Complex<f16> f16 × 2 32 bits / 4 bytes Explicit low-precision capability
Complex<bf16> bf16 × 2 32 bits / 4 bytes Explicit low-precision capability
Complex<f32> f32 × 2 64 bits / 8 bytes Core proposed format
Complex<f64> f64 × 2 128 bits / 16 bytes Default alias candidate 
f32 initial_real = 3.0;
f32 initial_imag = 4.0;
Complex<f32> z = Complex.new(initial_real, initial_imag);
f32 magnitude = Complex.norm(z); // approximately 5
Complex<f32> conjugated = Complex.conjugate(z);
complex default_value = Complex.zero(Complex<f64>);

2. Declarations, Ownership & Costs

Variable declarations place the type first and end with a semicolon. Components inherit static typing; contextual literal checking happens directly in the expected format. Constructing a scalar complex value does not allocate and scalar assignment copies its two components. Bindings are immutable by default; mutation requires an explicit writable binding or exclusive borrow.

Copying a scalar does not make an owning Array, Vector, or Tensor implicitly clone its storage. Those containers move by default; explicit cloning and CPU/GPU transfers expose their costs. A conjugation operation returns a value rather than mutating its argument.

The value payload is two components. Alignment, register use, stack slots, and containing-structure padding depend on the target. A numerical pair is not automatically ABI-compatible with a foreign complex scalar. FFI bindings validate component format, ordering, alignment, call convention, and ownership independently.

3. Numerical Model & Error Values

Strict execution preserves the Float component format, signed zero, subnormals, explicit rounding points, and branch selection. AOT and JIT must use the same requested numerical profile. Reassociation, contraction, flush-to-zero, wider intermediates, and fast-math approximation require an explicit profile; GPU storage support alone does not provide a complex math library.

The baseline uses round-to-nearest, ties-to-even for core component arithmetic. Transcendental implementations publish their accuracy and non-finite case tables in the selected target profile. The Annex-G-compatible profile is the proposed interoperability baseline for special values; a target without that profile rejects the unchecked instantiation. The finite-only checked API remains a separate, precise error-value contract.

ComplexError includes NonFiniteInput, NonFiniteResult, DivideByZero, Pole, Domain, ZeroMagnitude, Inexact, OutOfRange, ImaginaryPartPresent, InvalidText, InvalidOptions, BufferTooSmall, AllocationFailed, LengthMismatch, Aliasing, and UnsupportedCapability. Underflow to a finite subnormal or zero is valid arithmetic; exact conversion can still reject lost information.

4. Principal Branches & Signed Zero

A multi-valued mathematical inverse needs a selected branch. sqrt, ln, and non-integer powers use the principal branch, with the negative real axis as the logarithmic cut. Signed imaginary zero distinguishes approach from above or below the cut: the two representations must not be merged by a strict optimizer.

Function Cut or exceptional input Selected behavior
ln / sqrt / non-integer power Negative real axis; ln also zero pole Sign of imaginary zero selects the side; ln phase in [−π, π]
asin / acos Real rays outside [−1, 1] Principal inverse; endpoint poles/limits follow selected special-value profile
atan / asinh Imaginary rays beyond ±i Principal inverse; atan has poles at ±i
acosh Real axis below 1 Principal result with nonnegative real part
atanh Real rays outside [−1, 1] Principal inverse; poles at ±1
ln1p Real axis at and below −1 Translated principal logarithmic cut 
Complex<f64> above = Complex.new(-4.0, 0.0);
Complex<f64> below = Complex.new(-4.0, -0.0);
Complex.sqrt(above); // +0 + 2i
Complex.sqrt(below); // +0 - 2i
Complex.same_bits(above, below); // false

5. Complete Function Catalog

Each function is listed once in the groups below with its result and failure contract. T, Z, U, N, the integer type parameter I, writable views, callbacks, and options are conceptual signature notation; variable examples use type-first declarations. Shared scalar contracts belong here; the per-format pages specialize limits and return types.

Core calls are allocation-free unless they explicitly return string or another owning container. Ordinary operators use the matching typed scalar operation; they do not silently convert between component formats. The catalog intentionally omits a generic min/max, bitwise complex arithmetic, and a meaningful numeric less-than relation.

9. Arithmetic & Scaling

Core arithmetic returns the source complex type. Component +, −, ×, ÷ round in T. General complex division and magnitude use scaled algorithms to avoid unnecessary intermediate overflow; exact reproducibility depends on the explicitly selected numerical profile.

Complex.mul(Z a, Z b) Z Complex product; any FMA contraction must be selected by profile.
Complex.div(Z a, Z b) Z Scaled complex quotient. Zero denominator and special inputs follow the selected non-finite profile; use checked_div for an error value.
Complex.reciprocal(Z value) Z Scaled 1/value; avoids materializing a naively squared denominator.
Complex.square(Z value) Z value × value, with documented profile rounding.
Complex.scale(Z value, T factor) Z Multiplies both components by a real factor.
Complex.unscale(Z value, T divisor) Z Divides both components by a real divisor.
Complex.add_real(Z value, T scalar) Z Adds only to the real component.
Complex.sub_real(Z value, T scalar) Z Subtracts only from the real component.
Complex.scale_pow2(Z value, i32 exponent) Z Scales both components by 2^exponent with one rounding per component; may overflow or underflow.
Complex.mul_add(Z a, Z b, Z c) Z Complex a×b+c; no claim of a single correctly rounded complex operation or implicit hardware complex FMA.

10. Checked Arithmetic & Errors

All checked operations reject non-finite inputs before evaluation, report a zero denominator explicitly, and reject non-finite outputs. Finite rounding and finite underflow remain valid; Inexact is not an arithmetic error. Every function below allocates no heap storage.

Complex.checked_sub(Z a, Z b) Result<Z, ComplexError> Component subtraction; same finite-result policy.
Complex.checked_mul(Z a, Z b) Result<Z, ComplexError> Complex multiplication; checks the final component results.
Complex.checked_div(Z a, Z b) Result<Z, ComplexError> DivideByZero when both b components are ±0; otherwise scaled division.
Complex.checked_reciprocal(Z value) Result<Z, ComplexError> Rejects complex zero; scaled reciprocal.
Complex.checked_scale(Z value, T factor) Result<Z, ComplexError> Finite components and finite factor; finite-result check.
Complex.checked_unscale(Z value, T divisor) Result<Z, ComplexError> Finite nonzero real divisor; zero gives DivideByZero.
Complex.checked_sqrt(Z value) Result<Z, ComplexError> Principal square root; finite inputs include negative real values.
Complex.checked_ln(Z value) Result<Z, ComplexError> Complex zero is Pole; other finite values use the principal logarithm.
Complex.checked_exp(Z value) Result<Z, ComplexError> Finite input and finite exponential output required.
Complex.checked_pow(Z base, Z exponent) Result<Z, ComplexError> Exponent zero returns one, including 0^0. Other zero-base cases require a strictly positive real exponent; negative real exponent is Pole and nonzero imaginary exponent is Domain.

11. Magnitude, Phase & Polar Coordinates

Lengths use the Euclidean plane. The value has no mathematical less-than ordering. These scalar outputs are rounded in T and carry no hidden output allocation.

Conceptual signature Returns Contract and cost
Complex.norm(Z value) T Scaled hypot(real, imag), nonnegative; may overflow if the true magnitude exceeds max(T).
Complex.norm_squared(Z value) T real²+imag². May overflow even when norm is representable; not a substitute for norm in robust algorithms.
Complex.l1_norm(Z value) T |real|+|imag|; may overflow.
Complex.phase(Z value) T atan2(imag, real), in [−π, π]. Signed zero selects a side of the negative-real cut; follows atan2 at the origin.
Complex.to_polar(Z value) (T, T) (norm(value), phase(value)); no shared-allocation object.
Complex.distance(Z a, Z b) T Euclidean distance; computed component differences may themselves overflow.
Complex.normalize(Z value) Result<Z, ComplexError> Finite nonzero value required. Scaled normalization avoids a needless intermediate norm overflow; ZeroMagnitude for zero.
Complex.project(Z value) Z Riemann-sphere projection: any infinity maps to (+∞, signed imaginary zero); otherwise preserves components.

14. Equality & Explicit Ordering

Complex values support equality, not an intrinsic ordered-number relation. Comparator helpers are deliberately named for their purpose; numeric equality never treats a NaN component as equal to itself; raw representation equality and total ordering remain separate operations.

Conceptual signature Returns Contract and cost
Complex.equal(Z a, Z b) bool Both components compare numerically equal; ±0 compare equal and any NaN comparison is false.
Complex.not_equal(Z a, Z b) bool Logical negation of equal.
Complex.same_bits(Z a, Z b) bool Both raw component representations match, including zero signs and NaN payloads.
Complex.total_compare(Z a, Z b) Ordering Lexicographic Float.total_compare on (real, imag); a deterministic representation order, not mathematical magnitude ordering.
Complex.is_close(Z a, Z b, T rel_tol, T abs_tol) Result<bool, ComplexError> Finite nonnegative tolerances required. Equal infinities compare close; other non-finite pairs do not. Finite values use |a−b| ≤ max(abs_tol, rel_tol×max(|a|,|b|)) with scaled evaluation.

Complex.convert(D, Z value, Rounding mode) Result<Complex<D>, ComplexError> Rounds each component once; overflow/non-finite conversion behavior follows explicit Float conversion policy.
Complex.from_integer_exact(T, I value) Result<Z, ComplexError> Integer must be exactly representable in T; imaginary part +0.
Complex.from_integer(T, I value, Rounding mode) Result<Z, ComplexError> Explicit rounded integer-to-real conversion; imaginary +0.
Complex.to_real_exact(Z value) Result<T, ComplexError> Imaginary component must be ±0; otherwise ImaginaryPartPresent. Copies real bits.
Complex.to_integer_exact(I, Z value) Result<I, ComplexError> Imaginary zero, finite integral real part, and destination range required; both zero signs become integer zero.
Complex.to_integer(I, Z value, Rounding mode) Result<I, ComplexError> Imaginary zero required; finite real part rounded with range validation before conversion.

16. Bits, Bytes & Explicit Layout

Canonical bytes always store real first, imaginary second. Endianness applies within each component; it never swaps component order. Wire functions do not establish C/C++ ABI compatibility.

Complex.to_be_bytes(Z value) Array<byte, 2*N> Encodes each component big-endian, real before imaginary.
Complex.from_le_bytes(T, Array<byte, 2*N> bytes) Z Fixed-width little-endian decode.

17. Parsing & Formatting

The Cartesian grammar is locale-independent: optional parentheses around a+bi, with explicit signed imaginary component and Float decimal grammar for each component. Whitespace is accepted only around the whole value. Polar text is not silently interpreted as Cartesian text.

Conceptual signature Returns Contract and cost
Complex.parse(T, string_view text) Result<Z, ComplexError> Parses the whole input; rejects trailing data and malformed separators. Component non-finite tokens follow ParseOptions defaults.
Complex.parse_with(T, string_view text, ComplexParseOptions options) Result<Z, ComplexError> Explicit non-finite-token, whitespace, and component grammar policy; no hidden locale lookup.
Complex.to_string(Z value) Result<string, ComplexError> Round-trip Cartesian text; AllocationFailed reported. NaN text does not retain arbitrary payloads.
Complex.format(Z value, ComplexFormatOptions options) Result<string, ComplexError> Explicit Cartesian or polar notation, component precision, and sign policy; allocation and invalid options can fail.
Complex.format_into(Z value, MutSlice<byte> output, ComplexFormatOptions options) Result<usize, ComplexError> Writes valid UTF-8, returns bytes written; validates capacity before committing, unchanged on BufferTooSmall.
Complex.parse_polar(T, string_view radius, string_view radians) Result<Z, ComplexError> Parses two real fields and delegates to from_polar; rejects negative radius.

18. Optional Bulk Operations

These optional library functions require explicit target execution and output storage. They are not primitive scalar instructions. MutSlice is already an exclusive writable view and is passed directly. The owner parameter forms &T and &mut T are chosen; explicit returned-reference lifetime annotations remain descriptive. Length, alias, and capability checks complete before writing.

Conceptual signature Returns Contract and cost
Complex.map_into(Slice<Z> input, MutSlice<Z> output, PureFn operation) Result<unit, ComplexError> Equal lengths; independent pure scalar callback. Explicit O(n), no output allocation.
Complex.conjugate_into(Slice<Z> input, MutSlice<Z> output) Result<unit, ComplexError> Elementwise conjugation; input and output borrows must be disjoint. Use conjugate_in_place for one writable buffer.
Complex.multiply_into(Slice<Z> a, Slice<Z> b, MutSlice<Z> output) Result<unit, ComplexError> Equal lengths; disjoint borrows required. O(n) computation.
Complex.dotu(Slice<Z> a, Slice<Z> b, AccumulationPolicy policy) Result<Z, ComplexError> Σ a[k]×b[k], with no conjugation. Explicit accumulator format and evaluation order; length/capability errors reported.
Complex.dotc(Slice<Z> a, Slice<Z> b, AccumulationPolicy policy) Result<Z, ComplexError> Σ conjugate(a[k])×b[k]. Same explicit reduction policy.
Complex.from_split_into(Slice<T> real, Slice<T> imag, MutSlice<Z> output) Result<unit, ComplexError> Zips separate component arrays; equal lengths and disjoint writable storage required; O(n) writes.
Complex.to_split_into(Slice<Z> input, MutSlice<T> real, MutSlice<T> imag) Result<unit, ComplexError> Materializes separate real/imaginary arrays; disjoint destinations; O(n). No zero-copy strided scalar view is promised.

19. CPU, GPU & Data Layout

Arrays of complex values use interleaved component pairs unless another explicit storage layout is chosen. Separate real and imaginary arrays can improve a particular SIMD or GPU access pattern, but converting between interleaved and split layout is an O(n) materialization. A compiler may eliminate an unobservable temporary; it may not hide an observable device transfer or replace the requested accumulator format.

Parallel writes require disjoint exclusive output borrows. Device submission retains input and output ownership until actual completion; a Pending value alone is not CPU visibility. Transfer direction, synchronization, math-library availability, supported formats, and atomic operations are checked separately. Complex addition is not automatically an atomic two-component transaction.

FFT planning, transforms, matrix decompositions, convolution, special scientific functions, and automatic differentiation belong to explicitly selected libraries, not scalar Complex methods. Their plans, workspaces, execution order, and allocations need their own contracts. This page does not invent device-native support merely by listing scalar operations.
