1. The scope boundary is a lifetime proof

A task scope defines the interval in which child work may access captured borrowed storage. The borrowed environment must outlive that interval. Every child accepted by the scope is registered before it can run. Scope completion closes admission and waits until accepted children can no longer access those loans. A child handle is a way to observe a result, not the source of the lifetime guarantee.

A scope borrowing a local array cannot be returned, detached or stored in a longer-lived container. Moving a Task handle does not move the borrowed storage into an owner. The compiler rejects an escaping relationship even when the code intends to join later. Runtime tracking independently handles accepted work after a handle is forgotten.

2. Normal return, early return and unwinding

Normal scope exit is an explicit join boundary. Early return must route through the same required drain before destroying borrowed values. If unwind is part of a selected runtime profile, cancellation may be requested during unwind, but the implementation cannot release borrowed storage until all use has stopped. A second failure during cleanup follows the selected fatal policy rather than inventing a safe Result with live references.

A runtime that cannot establish safe completion must preserve storage or terminate according to its fatal policy. It cannot resume the caller with a dangling child reference. This is a memory-safety requirement and may lead to an unbounded wait. It does not imply that arbitrary application code will cooperate or terminate.

3. Read, exclusive and owned captures

Read-only captures can be shared when their element types satisfy the relevant sharing rules. Exclusive captures transfer a unique loan for the child interval. Splitting a mutable collection into disjoint slices can enable independent tasks, but two index ranges that might overlap are rejected or checked before spawning. Shared<T> retains an allocation and does not automatically establish thread-safe access to T.

Owned captures move values into work and can support explicit detach if they have no hidden environment loans. Scope-owned work is still joined by default even when its captures could outlive the scope. LocalTaskScope permits non-Send values only while execution stays on the compatible local executor; converting it into a migratable task is not implicit.

4. Results, failures and admission closure

Every task result can be taken once. A scope report collects unobserved lifecycle outcomes after all children are safe, without automatically flattening a Result returned by the child. Application errors remain ordinary returned values. Closing admission rejects new spawn attempts; it does not cancel already accepted children or immediately destroy captured data.

Dynamic child creation during closing needs a clear registration linearization point. Either registration succeeds and the child belongs to the drain set, or it fails before work starts. Ordinary spawn consumes its work value and safely destroys unstarted captures on failure; APIs promising reuse return a typed ownership-preserving error payload. No unregistered task may start and borrow scope data. A report that summarizes failures can allocate during normal operation; required safety cleanup must not depend on a successful late allocation.

5. Suspension and synchronization

The safe profile forbids carrying a lock guard across an async suspension and handing that guard to device work. Release it before yield, sleep, awaiting a child or submitting a GPU operation. This is compatible with scoped borrowing: a lifetime-safe capture can still cause deadlock if it holds a resource another child needs.

A blocking join inside an executor worker can deadlock a single-thread scheduler. The runtime must diagnose incompatible blocking contexts or require an explicitly blocking executor boundary. Awaiting the same task from multiple observers does not permit multiple moves of T; observation and exclusive take remain different operations.

6. A scope is an obligation-bearing value 

Result<TaskScope, SpawnError> opened = Task.open_scope(&executor, scope_options);
// After handling opened as active_scope and preparing lifetime-safe work.
Result<Task<i32>, SpawnError> child = Task.spawn<i32>(&active_scope, borrowed_work);
// At the required explicit boundary, after resolving handle ownership.
Result<ScopeReport, ScopeError> report = Task.close_scope(active_scope);

TaskScope is tracked specially by lexical rules and the runtime registry; writing a destructor that joins a list of handles is insufficient by itself. The example does not choose how future scope-body syntax will spell that boundary.

8. Design requirements and sources

These contracts require both compiler lifetime analysis and runtime tracking. They are not inferred automatically from a user handle destructor, a Rust thread interface or Tokio behavior. The referenced systems provide comparison points; Aevix deliberately specifies its own structured default and error-as-value policy. No implementation, bounded shutdown guarantee or deadlock freedom is claimed.
