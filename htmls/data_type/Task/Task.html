1. A handle to host work in a lifetime scope

Task<T> is the proposed move-only handle for scheduled host computation producing one value of type T. A task is not a dedicated operating-system thread, a device queue event or an unstarted lazy future. Scheduling can allocate and fail. Once accepted by a scope, work and its captured resources remain tracked independently of whether the caller retains the user-facing handle.

Structured execution is the default: borrowed captures cannot outlive their storage, and a scope cannot finish while any child might still access its loans. Explicitly detached work requires owned or otherwise independently valid captures. These are design requirements for the compiler and runtime; this documentation does not assert that an executor or cancellation implementation already exists.

2. Supporting records and two layers of error

TaskScope, LocalTaskScope, Executor, Work<T>, CancellationSource, CancellationToken, TaskStatus, JoinSet<T> and Duration are proposed library types. Work<T> describes a callable or suspended computation producing T; final closure and async syntax is outside this reference. Task observation uses &Task<T>; exclusive result-handle access uses &mut Task<T>. Calls spell &job or &mut job explicitly; creating the latter requires a mut owner binding. Task<T> by value moves the owning handle. SpawnError distinguishes allocation, closed scope, executor unavailable and capture-safety failures.

TaskError represents cancellation, recoverable runtime failure, consumed result or an explicitly supported caught-unwind report. Process abort, fatal memory corruption and unrecoverable runtime termination do not become ordinary Result values. If a task returns Result<U, E>, joining gives Result<Result<U, E>, TaskError>: application failure and task lifecycle failure stay separate. No implicit flattening loses the distinction.

SpawnInputError<Input> is a proposed ownership-preserving scheduling error carrying the original input handle when registration fails. No child may start before input ownership and resource registration are accepted. ScopeError, JoinError, ScopeReport and RaceOutcome are proposed library records; a race outcome contains its selected terminal outcome and explicit unfinished loser handles. Work submission errors that consume user work retain it in a typed error payload when reuse is promised.

Ordinary spawn functions consume their Work value. Failed admission safely destroys unstarted work and its captures, releasing scoped loans; non-generic SpawnError does not promise to return those moved captures. Already-running input handles supplied to map, then or from_pending instead use SpawnInputError<Input> to preserve their observation and result capability.

Scope registration and observation borrow &TaskScope; closing a scope consumes TaskScope. Scope/executor registries and cancellation sources support synchronized interior operations, so these APIs do not require a mutable binding merely to request cancellation or register work. An existing reference is passed directly without adding another &. &mut Task accesses the original handle; mut Task by value would only make a moved callee-local handle mutable.

3. The scope owns the obligation to finish

Task.scope accepts an explicit structured scope body. Closing its registration set prevents new children; joining drains all accepted work and owned cleanup before borrowed storage can be released. Scope completion is an observable join boundary, including when source syntax later makes it part of a block. The compiler rejects paths that escape a live borrowed scope without that boundary.

The runtime registration set and lexical rules must remain safe even when a handle is dropped, moved away, forgotten or never joined individually. Handle destruction is not the sole safety mechanism. Early return and unwinding must route through a defined drain/termination policy before borrowed storage is destroyed. A noncooperative task may delay scope completion indefinitely; safety does not imply termination or bounded latency.

4. Capture safety, migration and locks

A multithread executor requires captures and outputs to satisfy the relevant transfer/share traits. Shared<T> reference counting only retains memory; it does not make an arbitrary T thread-safe. An exclusive borrowed slice may be captured by one scoped task while disjoint slices are captured by others, with the loan unavailable to its parent until joined. A local task remains pinned to a compatible local executor and cannot silently migrate.

In the proposed safe profile, lock guards are non-Send by default, cannot cross suspension and cannot be submitted to a GPU. Release a guard before waiting, yielding or handing work to a device. Structured tasks prevent invalid lifetime escape; they do not prevent deadlock, lock-order bugs, starvation or algorithmic races mediated by explicitly synchronized state.

5. A cancellation request is not completion

Cancellation is cooperative. A request signals a token or task state and can prevent not-yet-started work when supported, but does not prove running code has stopped, release its loans, undo writes or kill a host thread. A task may complete normally while racing a request. join and await_result report its actual terminal outcome only after required cleanup and captured-resource release.

Timeout means the observation interval expired. It leaves work tracked and its resource obligations live; a timeout function does not silently cancel or detach the task. A race returns the winner and retains explicit handles for unfinished losers. Cancellation propagation and waiting for cancellation acknowledgment are separately named operations.

6. Execution and cost model

Host async suspension can free an executor worker to run other tasks; a blocking function occupies a thread. spawn_blocking uses an explicit blocking pool and obeys the same ownership boundary. Scheduling, task state, cancellation checks and synchronization have real costs. Task is a runtime abstraction and makes no zero-overhead or parallel-speedup claim.

AOT and JIT share task ordering, borrowing and result contracts. Scheduling is nondeterministic unless an optional scheduler policy provides stronger guarantees. Numeric work inside a task retains its scalar profile: creating parallel tasks does not authorize an unordered floating reduction. A task that bridges a Pending device result retains device leases but does not replace the Pending visibility contract.

10. Scheduling without implicit unwrapping 

// Existing scope and prepared_work satisfy their capture and lifetime constraints.
Result<Task<i32>, SpawnError> scheduled = Task.spawn<i32>(&scope, prepared_work);
// Given a separate handle; exclusive observation requires a mut binding.
mut Task<i32> observed_job = prepared_job;
Result<Optional<i32>, TaskError> available = Task.try_take(&mut observed_job);
// Another validated handle named job is consumed by join.
Result<i32, TaskError> outcome = Task.join(job);
// A job whose ordinary output is Result keeps the lifecycle layer.
Result<Result<i32, ParseError>, TaskError> parsed = Task.join(parse_job);

All values are immutable unless mut is written explicitly. The approved &mut Task<T> form exclusively borrows a mut handle, while &Task<T> observes without consuming it. Non-void work functions must explicitly return their result on every normally terminating path; the examples avoid fixing a closure grammar.

11. Host tasks and device completion

Task is the host scheduling and structured-lifetime abstraction. Pending represents already-submitted device work. A successful Task<Tensor<..., Gpu>> can carry a device tensor owner, but only its declared Pending dependency proves that a producer finished; the Task type alone grants no host mapping. Structured parallel iteration and collections can build on Task without changing these boundaries.
