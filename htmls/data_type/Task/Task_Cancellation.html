1. A request changes intent

A CancellationSource owns permission to request cancellation. CancellationToken is a retained read-only notification capability handed to work. A request tells code to stop at a cooperative boundary and perform required cleanup; it does not erase already executed effects or prove termination. The source and token are proposed library types with fallible state allocation when needed.

A task may finish normally between a cancellation query and request, or after noticing a request while it performs cleanup. The actual join outcome is authoritative. A cancellation flag and terminal phase are separate pieces of state, so a completed successful task can also report that cancellation was requested too late.

2. Token trees and notification

A child token receives cancellation propagated from its parent. Cancelling a child does not cancel the parent or siblings. A shared clone of a token observes the same request state. The contract specifies request visibility after the requesting operation returns for the selected synchronization profile; it does not promise every independent child observes the transition simultaneously while propagation is in progress.

Waiting for a token to be requested only acknowledges notification. It does not wait for every task using the token to stop. Task or scope joins provide the completion boundary. A notification wait must retain token state and register wakeups without a lost-wakeup race; repeatedly polling a bool in a busy loop is not the intended API.

3. Checkpoints and blocking work

check_cancel is an explicit cooperative checkpoint returning a cancellation value. Yield, timer and I/O integrations can also expose request handling through their named contracts. A CPU-bound loop that never checks cancellation may run indefinitely. Running blocking work generally cannot be safely force-killed, so cancellation remains a request even when the host scheduler can remove not-yet-started jobs.

A suspended operation is safe to cancel only when its own contract explains cleanup and side effects. Dropping a wait object does not automatically cancel the underlying operation. If I/O or GPU work was accepted externally, its lifetime obligations continue until completion or a proven safe abort. A host cancellation token cannot certify device quiescence.

4. Timeout and racing outcomes

A timeout limits how long an observer waits, not how long work can continue. A timed-out task remains in its scope and retains captured loans. A function that requests cancellation on timeout must name that policy and still return a handle or await eventual completion. A deadline is monotonic-time based; clock precision and scheduler latency prevent a strict real-time bound.

Race returns the winning terminal outcome together with unfinished loser handles. A loser that has already performed writes cannot be rolled back by cancelling it. Deterministic bias or tie-breaking belongs to an explicit selection policy; scheduler arrival order alone is not deterministic application semantics.

5. Graceful shutdown is a sequence

Graceful shutdown closes admission, sends requests, allows cleanup and joins tracked work. Each step can fail or wait for a noncooperative child. A timeout during shutdown must preserve ownership and scope obligations; it cannot free borrowed memory merely to meet a deadline. Detached owned work may follow a separate runtime shutdown policy because it does not borrow the caller stack.

Unrecoverable process failure and fatal runtime termination are outside ordinary TaskError recovery. A supported caught unwind is reported only after the runtime has established safe cleanup of the task state. The API must not advertise every panic, allocator catastrophe or foreign thread termination as safely recoverable.

6. Request and completion remain explicit 

Result<CancellationSource, CancellationError> created = Task.cancel_source();
// Given a validated source and task handle; cancellation uses synchronized interior state.
Result<CancelRequest, CancellationError> requested = Task.cancel_request(&source);
bool finished = Task.is_finished(&job);
Result<i32, TaskError> outcome = Task.join(job);

The bool finished may be false after a successful request and can become stale immediately. join consumes the result handle and establishes completion; requested is not a substitute for it.

8. Design requirements and sources

These contracts require both compiler lifetime analysis and runtime tracking. They are not inferred automatically from a user handle destructor, a Rust thread interface or Tokio behavior. The referenced systems provide comparison points; Aevix deliberately specifies its own structured default and error-as-value policy. No implementation, bounded shutdown guarantee or deadlock freedom is claimed.
