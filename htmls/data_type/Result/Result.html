1. Overview

0.2 implementation scope. The prelude supplies Result<T, E>, Result.ok(value), Result.err(error), Result.is_ok(&value) and is_err. Variant construction, switch and owned postfix ? propagation with exactly the same error type are implemented. Mapping, conversion, unwrap and iterator helpers in the broader catalog remain proposals. See the 0.2 implementation profile; other catalog entries remain design contracts.

Catalog status. The scope note identifies the implemented subset; other listed APIs remain proposed Aevix contracts. Parameter modes are chosen: T value, &T value, and &mut T value. Type-pack notation, callable types, explicit returned-reference lifetime spelling, and error enums remain descriptive where marked. Namespace functions are used throughout; there are no value-method aliases.

Result is a tagged value carrying either success T or failure E. Returning an error is normal control flow. Its mere construction does not throw, unwind, log, terminate, or transfer control to a caller. The caller handles the active variant or explicitly propagates it.

2. Declarations and variants

Success and error payloads can have different types and ownership. Type-first declarations provide constructor context. Neither variant requires a wrapper allocation; the active payload can itself own allocated resources. 

Result<i32, i32> success = Result.ok(12);
Result<i32, i32> failure = Result.err(404);
bool failed = Result.is_err(&failure);

3. Handling and explicit returns

A Result-returning function is non-void. Ordinary successful completion explicitly returns its Result value; the chosen postfix ? may explicitly spell an Err-only early return. A final expression is not an implicit return, and a diverging path does not need an impossible return. See Error Propagation.

This catalog keeps named Result APIs alongside the chosen postfix ? and lexical checked(expression) syntax. Ordinary integer arithmetic still produces its scalar type and uses a checked safe-stop contract. The chosen future checked(expression) form makes directly written integer arithmetic failures into Result values; 0.2 does not implement that wrapper. Implemented postfix ? either extracts success or returns the same error type from the current Result-returning function. The checked-expression wrapper remains a chosen design rule; ordinary safe-stop operators and same-error-type postfix propagation are implemented in 0.2. A declared API retains the explicit errors stated in its contract.

Discarded Result expressions produce a warning

The chosen default language policy calls for a warning on an ignored Result-valued expression statement. The 0.2 compiler currently accepts that statement without a warning; the diagnostic is planned work, not a shipped check. It is not implicit success, unwrapping or error propagation, and does not by itself make the program ill-typed. This initial policy adds no discard keyword or forced handling syntax. A stored or returned Result remains an ordinary value; callers must explicitly inspect, transform or propagate it before using its success payload.

Both success and error payloads retain ordinary ownership cleanup when a discarded temporary ends. API-catalog examples that show a fallible call by itself demonstrate its spelling and would produce this warning once the planned diagnostic is implemented; they do not demonstrate successful error handling. Additional unused-variable/data-flow diagnostics remain separate tooling work.

4. Ownership and borrowed errors

An owned Result moves its active payload. Shared or exclusive projections borrow only the active variant and keep the source alive. Replacing the tag is forbidden while such a projection remains live. Result has no None state to leave behind during a take.

Replace installs a complete new Result and returns the previous one. Clone returns a nested Result because cloning can fail independently of whether the original value was Ok or Err. It never mistakes a cloned original Err for a cloning failure.

5. Composition and error types

Map changes a success type, map_err changes an error type, and and_then sequences a fallible operation with the same E. If two operations have different errors, map them into an explicit application enum before sequencing. A generic hidden exception union is not inserted.

Eager and/or/zip inputs have already executed. And_then and or_else call their branch only when needed. Zip specifies left error priority, not parallel first-to-complete failure. Recovery that discards an error is named and documented.

6. Function reference

T value passes a value: Copy types are copied, and owning non-Copy values move without a deep clone. &T value is a shared read borrow; &mut T value is an exclusive modification borrow. Calls use x, &x, or &mut x respectively. Already borrowed references and view values are passed directly; adding another & changes the type. *ref accesses the referent. Ordinary &mut x requires a mut owner; mut T value alone makes a by-value parameter locally mutable and does not modify the caller. Overlapping active borrows are checked until last use; disjoint regions may be split safely and no borrow outlives its source. Synchronized interior mutation follows its own type contract. Fn(A) -> B describes a callable; returned-reference lifetime relationships remain documented in prose.

7. Collection and allocation errors

CollectError<E> is a proposed library enum that distinguishes an input error E from CollectionError size/allocation failure. The two cases are never conflated or forced into a user error type. Collection stops at the first sequential failure; already accumulated owned elements are safely destroyed.

CloneError and collection error names describe draft support contracts. A cleanup destructor does not silently emit another recoverable Result. Operations such as flushing or closing a resource expose explicit fallible APIs before ownership destruction.

8. unit, never, and nested variants

Result<unit, E> means fallible completion with no success payload. It is not void and still needs an explicit returned value. Result<T, never> is statically infallible; into_ok extracts its success without a panic-on-error shortcut.

Transpose changes the nesting of Optional and Result with a precise state mapping. Flatten accepts the same inner and outer error type only. No implicit error conversion is introduced by either helper.

9. Parallel work and completion

A Result value is not a synchronization primitive. Receiving an Err from a GPU submission attempt differs from observing completion of already submitted work. Pending and Task contracts define when resources and borrowed buffers are safe to release.

Parallel reductions must define failure selection, integer overflow, and cancellation. They cannot reinterpret a poisoned or partially initialized accumulator as a valid success value. Shared mutable error storage needs atomic or lock protection.

10. Layout, FFI, and diagnostics

Result layout is not automatically C-compatible. A foreign status code plus output pointer, C++ expected, Python exception, or nullable object needs an explicit binding contract for ownership and error conversion. Python exceptions become error values only at the adapter boundary.

Payload niches and tag elision are compiler optimizations, not stable wire formats. Diagnostic formatting follows payload traits and may allocate; no automatic log is emitted simply because Err is constructed or destroyed.

11. Examples and intentional discard 

Result<i32, never> infallible = Result.ok(7);
i32 known = Result.into_ok(infallible);
i32 fallback = Result.unwrap_or(Result.err<i32, i32>(404), 0);
Optional<i32> kept = Result.ok_optional(Result.ok<i32, i32>(9));

Fallback recovery consumes the handled error. ok_optional intentionally removes error information; use it only when that loss is part of the application contract. There is no general panic-on-Err unwrap in this proposed safe catalog.
