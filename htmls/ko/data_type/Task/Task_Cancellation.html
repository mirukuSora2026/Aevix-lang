0.3 개발 프로필. import하는 task 모듈은 자식마다 네이티브 스레드 하나를 사용하며, 컴파일러가 전달 특성과 효과를 검사하고 완전히 소유한 캡처·결과만 허용하는 Task<T>/TaskScope 부분집합을 제공합니다. 독립적인 취소 기능도 구현되었으며, 관측 권한을 버린 뒤에도 어휘적 Scope가 작업을 유지합니다. 대여·정적 뷰, 중첩 스코프, 작업자 내부의 spawn, 풀, detach는 이 프로필에 포함하지 않습니다. 아래의 더 넓은 표는 설계 계약입니다. 동기 CPU 작업은 0.3에 유지하고, Awaitable·실행 중단 API와 async 기반은 0.4로 옮깁니다. 자세한 내용은 현재 소스·실행 지원 범위.

1입니다. 요청이 인텐트를 변경함

CancellationSource는 취소를 요청할 수 있는 권한을 가지고 있습니다. CancellationToken은 작업에 할당된 읽기 전용 알림 기능입니다. 요청은 코드에 협동 경계에서 중지하고 필요한 정리를 수행하도록 지시합니다; 이미 실행된 효과를 지우거나 종료를 증명하지 않습니다. 소스와 토큰은 필요할 때 오류 상태 할당이 가능한 라이브러리 유형입니다.

작업은 일반적으로 취소 쿼리와 요청 사이에서 또는 요청이 정리를 수행하는 동안 요청을 알아 차린 후에 완료 될 수 있습니다. 실제 결과는 권위적입니다. 취소 플래그와 터미널 단계는 별개의 상태이므로, 완료된 작업은 취소가 너무 늦게 요청되었음을 보고할 수도 있습니다.

2입니다. 토큰 트리 및 알림

자식 토큰은 부모로부터 전달된 취소를 받습니다. 자식을 취소해도 부모 또는 형제는 취소되지 않습니다. 토큰의 공유 클론은 동일한 요청 상태를 관찰합니다. 이 계약은 선택된 동기화 프로파일에 대한 요청 동작 반환 후 요청 가시성을 지정합니다; 모든 독립된 자식이 전파가 진행되는 동안 동시에 전환을 준수할 것을 약속하지 않습니다.

토큰이 요청되기를 기다리는 것은 알림만 인식합니다. 토큰을 사용하는 모든 작업이 중지되기를 기다리지 않습니다. Task 또는 스코프 조인은 완료 경계를 제공합니다. 알림 대기는 손실된 웨이크업 레이스 없이 토큰 상태를 유지하고 웨이크업을 등록해야 합니다; 바쁜 루프에서 bool를 반복적으로 폴링하는 것은 의도된 API가 아닙니다.

3입니다. 체크 포인트 및 차단 작업

check_cancel 은 취소 값을 반환하는 명시적 협동 체크포인트입니다. 수율, 타이머 및 I/O 통합은 또한 지정된 계약을 통해 요청 처리를 노출시킬 수 있습니다. never가 취소를 확인하는 CPU 바운드 루프가 무기한으로 실행될 수 있습니다. 일반적으로 차단 작업을 안전하게 강제 종료할 수 없으므로 취소는 호스트 스케줄러가 아직 시작하지 않은 작업을 제거할 수 있는 경우에도 요청으로 남아 있습니다.

중단된 작업은 자체 계약이 정리 및 부작용을 설명하는 경우에만 취소하는 것이 안전합니다. wait 개체를 삭제해도 기본 작업이 자동으로 취소되지는 않습니다. I/O 또는 GPU 작업이 외부에서 수락된 경우 수명 의무는 완료 또는 입증된 안전한 중단까지 계속됩니다. 호스트 취소 토큰은 장치 quiescence를 인증할 수 없습니다.

4입니다. 타임아웃 및 레이싱 결과

시간 초과는 관찰자가 얼마나 오래 기다릴 수 있는지를 제한하는 것이지 얼마나 오래 작업이 지속될 수 있는지를 제한하는 것이 아닙니다. 시간 초과 작업은 그 범위에 남아 있으며 캡처 된 대여을 유지합니다. 시간 초과 시 취소를 요청하는 함수는 해당 정책의 이름을 지정하고 return를 핸들로 지정하거나 최종 완료를 기다려야 합니다. 마감 시한은 단조 시간 기준입니다. 클럭 정밀도와 스케줄러 지연 시간은 엄격한 실시간 제한을 방지합니다.

레이스는 미완성 패자 핸들과 함께 우승 터미널 결과를 반환합니다. 이미 쓰기를 수행 한 패자는 그것을 취소하여 롤백 할 수 없습니다. 결정론적 편향(deterministic bias) 또는 타이 브레이킹(tie-breaking)은 명시적 선택 정책(explicit selection policy)에 속하며, 스케줄러 도착 순서만으로는 결정론적 애플리케이션 의미론이 아니다.

5입니다. 우아한 종료는 시퀀스입니다.

우아한 종료는 입학을 닫고, 요청을 보내고, 정리를 허용하고, 추적 된 작업에 참여합니다. 각 단계는 비협조적 인 어린이를 기다리거나 실패 할 수 있습니다. 종료시 타임아웃은 소유권과 범위 의무를 보존해야 합니다; 그것은 단지 기한을 맞추기 위해 빌린 메모리를 자유롭게 할 수 없습니다. 분리 된 작업은 호출자 스택을 빌리지 않기 때문에 별도의 런타임 종료 정책을 따를 수 있습니다.

복구할 수 없는 프로세스 오류 및 치명적인 런타임 종료는 일반 TaskError 복구 외부에 있습니다. 지원되는 풀림은 런타임이 작업 상태의 안전한 정리를 설정한 후에만 보고됩니다. API는 모든 패닉, 할당자 재앙 또는 외부 스레드 종료를 안전하게 복구 가능한 것으로 광고해서는 안 됩니다.

6입니다. 요청 및 완료는 명시적 

Result<CancellationSource, CancellationError> created = Task.cancel_source();
// Given a validated source and task handle; cancellation uses synchronized interior state.
Result<CancelRequest, CancellationError> requested = Task.cancel_request(&source);
bool finished = Task.is_finished(&job);
Result<i32, TaskError> outcome = Task.join(job);

bool 완료는 성공적인 요청 후에 false일 수 있으며 즉시 정체될 수 있습니다. join은 결과 핸들을 소비하고 완료를 설정합니다. request는 그것을 대신하지 않습니다.

8입니다. 설계 요구 사항 및 소스

이러한 계약에는 컴파일러 수명 분석과 런타임 추적이 모두 필요합니다. 사용자 핸들 소멸기, Rust 스레드 인터페이스 또는 Tokio 동작으로부터 자동으로 유추되지 않습니다. 참조된 시스템은 비교점을 제공합니다; Aevix는 의도적으로 자체 구조화된 기본값과 오류-값 정책을 지정합니다. 구현, 제한된 종료 보증 또는 교착 상태의 자유는 주장되지 않습니다.
