1입니다. 개요

0.2 구현 범위. prelude가 제공하는 타입: Result<T, E>, Result.ok(value), Result.err(error), Result.is_ok(&value) 및 is_err. variant 생성·switch와 소유 값에 대한 후위 ? 전파가 구현되어 있습니다. 전파 시 오류 타입은 정확히 같아야 합니다. 더 넓은 카탈로그의 매핑·변환·unwrap·반복자 보조 함수는 아직 제안입니다. 자세한 내용: 0.2 구현 프로필; 나머지 카탈로그 항목은 설계 계약입니다.

카탈로그 상태. 지원 범위 알림은 구현된 부분집합을 밝히며 다른 API는 제안된 Aevix 계약입니다. 선택된 매개변수 형식: T value, &T value, 및 &mut T value. 타입 팩·호출 가능 타입·반환 참조의 명시적 수명 표기·오류 enum은 표시된 곳에서 설명용으로 남습니다. 모든 연산은 네임스페이스 함수를 사용하며 값 메서드 별칭은 없습니다.

Result는 성공 T 또는 실패 E를 담는 태그 값입니다. 오류 반환은 정상적인 제어 흐름입니다. 생성만으로 throw·스택 되감기·로그·종료·호출자로의 제어 이전이 일어나지 않습니다. 호출자가 활성 variant를 처리하거나 명시적으로 전파합니다.

2입니다. 선언 및 변형

성공·오류 payload는 서로 다른 타입·소유권을 가질 수 있습니다. 타입 우선 선언은 생성자 문맥을 제공합니다. 어느 variant에도 래퍼 할당은 필수가 아니지만 활성 payload가 할당된 자원을 소유할 수는 있습니다. 

Result<i32, i32> success = Result.ok(12);
Result<i32, i32> failure = Result.err(404);
bool failed = Result.is_err(&failure);

3입니다. 처리 및 명시적 반환

Result 반환 함수는 non-void입니다. 일반적인 성공 경로에서는 Result 값을 명시적으로 반환합니다. 선택된 후위 ? 로 Err인 경우에만 조기 반환을 명시할 수 있습니다. 마지막 식은 암시적 반환이 아니며 끝나지 않는 경로에는 불가능한 반환이 필요하지 않습니다. 자세한 내용: 오류 전파.

이 카탈로그는 선택된 후위 ? 와 어휘적 checked(expression) 문법과 함께 이름 있는 Result API를 유지합니다. 일반 정수 산술은 여전히 스칼라 타입을 결과로 만들며 검사된 안전 중단 계약을 사용합니다. 향후 선택된 checked(expression) 형식은 직접 작성한 정수 산술 실패를 Result 값으로 만듭니다. 0.2에는 이 래퍼가 구현되어 있지 않습니다. 구현된 후위 ? 는 성공 값을 꺼내거나 현재 Result 반환 함수에서 같은 오류 타입을 반환합니다. checked 식 래퍼는 선택된 설계 규칙으로 남습니다. 일반 안전 중단 연산자와 같은 오류 타입의 후위 전파는 0.2에 구현되어 있습니다. 선언된 API에는 해당 계약에 명시한 오류가 그대로 적용됩니다.

폐기된 Result 표현식은 경고를 생성합니다.

선택된 기본 언어 정책은 Result 값의 식 문장을 무시하면 경고하도록 합니다. 현재 0.2 컴파일러는 경고 없이 허용합니다. 이 진단은 계획된 작업이며 배포된 검사가 아닙니다. 무시는 암시적 성공·unwrap·오류 전파가 아니며 그 자체로 프로그램의 타입을 잘못되게 만들지도 않습니다. 초기 정책에는 discard 키워드나 강제 처리 문법이 없습니다. 저장·반환한 Result는 일반 값으로 남으며 성공 payload를 사용하기 전에 명시적으로 검사·변환·전파해야 합니다.

버린 임시값의 수명이 끝날 때 성공·오류 payload 모두 일반적인 소유권 정리를 따릅니다. 실패 가능한 호출만 단독으로 보여 주는 API 예제는 표기를 설명합니다. 계획된 진단을 구현하면 경고가 나며 성공적인 오류 처리 예제가 아닙니다. 추가 미사용 변수·데이터 흐름 진단은 별도 도구 작업입니다.

4입니다. 소유권 및 빌린 오류

소유 Result는 활성 payload를 이동합니다. 공유·배타적 투영은 활성 variant만 대여하고 원본을 살아 있게 유지합니다. 그 투영이 살아 있는 동안 태그를 바꿀 수 없습니다. Result에는 take 뒤에 남길 None 상태가 없습니다.

replace는 완전한 새 Result를 설치하고 이전 값을 반환합니다. clone은 원본이 Ok·Err인지와 별개로 실패할 수 있어 중첩 Result를 반환합니다. 복제한 원본 Err를 복제 실패로 오해하지 않습니다.

5입니다. 구성 및 오류 유형

map은 성공 타입을, map_err는 오류 타입을 바꾸며 and_then은 같은 E의 실패 가능 연산을 연결합니다. 연산 둘의 오류가 다르면 연결 전에 명시적인 애플리케이션 enum으로 매핑합니다. 숨은 제네릭 예외 합집합을 삽입하지 않습니다.

즉시 평가하는 and·or·zip 입력은 이미 실행된 값입니다. and_then·or_else는 필요한 분기에서만 호출합니다. zip이 정하는 것은 왼쪽 오류 우선순위이며 병렬로 먼저 끝난 실패가 아닙니다. 오류를 버리는 복구는 이름과 문서에 명시합니다.

6입니다. 함수 참조

T value 는 값을 전달합니다. Copy 타입은 복사하며 소유 non-Copy 값은 깊은 clone 없이 이동합니다. &T value 는 공유 읽기 대여이고 &mut T value 는 배타적 변경 대여입니다. 호출 시 각각 x, &x, 또는 &mut x 를 사용합니다. 이미 대여한 참조·뷰 값은 직접 전달하며 &를 하나 더 붙이면 타입이 바뀝니다. *ref 는 참조 대상을 읽고 씁니다. 일반적인 &mut x 에는 mut 소유자가 필요합니다. mut T value 만으로는 값 매개변수가 함수 안에서 변경 가능해질 뿐 호출자의 값을 변경하지 않습니다. 겹치는 활성 대여는 마지막 사용까지 검사합니다. 서로 겹치지 않는 영역은 안전하게 나눌 수 있으며 대여는 원본보다 오래 살 수 없습니다. 동기화된 내부 변경은 해당 타입의 계약을 따릅니다. Fn(A) -> B 는 호출 가능한 값을 설명하며 반환 참조의 수명 관계는 본문으로 문서화합니다.

7입니다. 수집 및 할당 오류

CollectError<E> 는 입력 오류 E와 CollectionError 크기·할당 실패를 구분하는 제안된 라이브러리 enum입니다. 두 경우를 혼동하거나 사용자 오류 타입에 억지로 넣지 않습니다. 수집은 순차적인 첫 실패에서 멈추고 이미 모은 소유 요소를 안전하게 정리합니다.

CloneError·컬렉션 오류 이름은 보조 계약의 초안입니다. 정리 소멸자가 또 다른 복구 가능한 Result를 조용히 내지는 않습니다. flush·자원 닫기 같은 연산은 소유권 소멸 전에 명시적인 실패 가능 API를 제공합니다.

8. unit, never 및 중첩된 변형

Result<unit, E> 는 성공 payload 없는 실패 가능 완료를 뜻합니다. void가 아니므로 명시적인 반환 값이 필요합니다. Result<T, never> 는 정적으로 실패하지 않습니다. into_ok는 오류 시 panic하는 지름길 없이 성공 값을 꺼냅니다.

transpose는 정확한 상태 매핑에 따라 Optional·Result의 중첩을 바꿉니다. flatten은 안쪽·바깥쪽 오류 타입이 같을 때만 허용합니다. 어느 보조 함수도 암시적 오류 변환을 추가하지 않습니다.

9입니다. 병렬 작업 및 완료

Result 값은 동기화 수단이 아닙니다. GPU 제출 시도의 Err를 받는 것과 이미 제출한 작업의 완료를 관측하는 것은 다릅니다. 자원·대여 버퍼를 안전하게 해제할 시점은 Pending·Task 계약이 정의합니다.

병렬 축약은 실패 선택·정수 오버플로·취소를 정의해야 합니다. poison 상태나 부분 초기화된 누적기를 유효한 성공 값으로 재해석할 수 없습니다. 공유 변경 오류 저장소에는 원자 연산이나 잠금 보호가 필요합니다.

10입니다. 레이아웃, FFI 및 진단

Result의 메모리 배치는 자동으로 C와 호환되지 않습니다. 외부 상태 코드와 출력 포인터, C++ expected, Python 예외나 nullable 객체에는 소유권·오류 변환을 명시한 바인딩 계약이 필요합니다. Python 예외는 어댑터 경계에서만 오류 값이 됩니다.

payload의 미사용 표현 활용과 태그 생략은 컴파일러 최적화이며 안정적인 전송 형식이 아닙니다. 진단 포매팅은 payload 특성을 따르며 할당할 수 있습니다. Err를 만들거나 정리했다는 이유만으로 자동 로그가 출력되지는 않습니다.

11입니다. 예 및 의도적 폐기 

Result<i32, never> infallible = Result.ok(7);
i32 known = Result.into_ok(infallible);
i32 fallback = Result.unwrap_or(Result.err<i32, i32>(404), 0);
Optional<i32> kept = Result.ok_optional(Result.ok<i32, i32>(9));

대체 복구는 처리한 오류를 소비합니다. ok_optional은 오류 정보를 의도적으로 제거하므로 그 손실이 애플리케이션 계약에 포함될 때만 사용합니다. 이 안전한 카탈로그 제안에는 일반적인 panic-on-Err unwrap이 없습니다.
