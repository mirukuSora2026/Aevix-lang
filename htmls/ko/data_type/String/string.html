1입니다. UTF-8 텍스트 소유

언어 설계 초안. 아래 계약·보조 타입·함수 표기는 제안입니다. 컴파일러 구현, 확정된 문법이나 검증된 런타임을 주장하지 않습니다. 예제는 타입 우선 선언, 기본 불변성과 세미콜론으로 끝나는 문장을 사용합니다.

구현된 0.2 부분집합. 현재 0.2 프로필 에는 byte_len, scalar_count, is_empty, view, as_bytes, equals, from_view, from_utf8, slice_bytes, append, push_char, clear가 나열되어 있습니다. 핵심 실패 가능 텍스트 연산은 TextError를 반환합니다. 바이트 소유권 인수와 고급 알고리즘을 비롯한 나머지 행은 아직 제안입니다. 텍스트 입력 s는 string_view 또는 소유 string의 명시적 대여를 뜻합니다.

string 은 연속적이고 올바르게 인코딩된 UTF-8 버퍼를 소유합니다. 이동은 소유권을 이전하며 내용 복제에는 명시적이고 실패 가능한 복사를 사용합니다. 값은 기본적으로 변경할 수 없습니다. 변경 연산에는 배타적 쓰기 대여가 필요합니다. 빈 텍스트는 유효한 값이며 값 없음은 Optional<string>로 나타냅니다. 텍스트 안의 U+0000도 유효하며 버퍼를 끝내지 않습니다.

char 는 유니코드 스칼라 하나이며 화면에 보이는 문자 하나와 같지 않습니다. byte 는 불투명한 8비트 저장 단위로, 수치 타입 u8 와 구분됩니다. UTF-8 텍스트는 읽기 전용 바이트를 제공하지만 임의의 바이트 오프셋을 텍스트 인덱스로 바꾸지는 않습니다. 기본 소유권은 메모리 모델을 따르며 자동 참조 카운트나 copy-on-write를 암시하지 않습니다.

관련 참조 문서: char, byte, 및 배열.

2입니다. 소유권, 실패 및 명백한 비용

s, needle와 카탈로그의 다른 텍스트 입력은 소유자의 읽기 대여 또는 string_view를 받습니다. 뷰는 원본 수명을 유지하므로 소유자보다 오래 살거나 충돌하는 변경 뒤까지 유지될 수 없습니다. 검색 결과 오프셋은 변경되지 않은 원본을 가리킵니다. 재할당·삭제·대체·변경은 저장한 위치의 정숫값이 여전히 범위 안이어도 해당 위치를 무효화할 수 있습니다.

dst 은 소유자의 배타적 변경 대여를 뜻합니다. 읽기 뷰가 살아 있으면 겹치는 저장소에 쓸 수 없습니다. 별도로 명세된 별칭 안전 연산이 아니라면 자기 자신 덧붙이기와 겹치는 대체에는 명시적 임시 복사가 필요합니다. 모든 변경 연산은 확정 전에 범위를 검증하고 필요한 용량을 확보합니다. 오류를 보고하면 원래 내용은 바뀌지 않습니다. 성공한 연산 뒤에도 용량이 절대 바뀌지 않는다는 뜻은 아닙니다.

TextError, BoundaryError, PatternError, OwnedUtf8Error, FormatArgs, 및 Iterator<T> 는 제안된 라이브러리 보조 타입이며 새 기본 타입이 아닙니다. 오류는 잘못된 인코딩, 경계·범위 오류, 금지된 빈 패턴, 용량 오버플로, 할당 실패와 포매팅 실패를 다룹니다. 소유권을 받는 UTF-8 검증이 실패하면 거절한 바이트 버퍼를 다음 타입에 담아 반환합니다: OwnedUtf8Error. 할당할 수 있는 모든 연산의 반환 타입은 Result.

제안하는 상위 수준 비용 모델: n 는 원본 바이트 수, k 는 출력 바이트 수, p 패턴 크기에 따라 달라집니다. “순회”라는 표기는 모든 검색이 선형 시간이라는 보장이 아닙니다. 콜백 실행과 패턴 준비 비용은 별도입니다. 반복자는 원본과 저장해 둔 패턴을 대여합니다. 텍스트를 비우거나 용량을 줄이는 작업은 보안 목적의 메모리 삭제가 아닙니다.

3입니다. 지표, 매칭 및 실행 목표

범위는 끝을 포함하지 않는 바이트 범위입니다. 안전한 바이트 슬라이싱은 범위와 UTF-8 스칼라 경계를 모두 검사합니다. 스칼라 순번에는 순회가 필요하며 자소 군집 순번에는 분할도 필요합니다. 문자를 반환하는 기본 s[i] 연산은 없습니다. 바이트를 살펴볼 때는 as_bytes를 사용하며 다른 텍스트 뷰를 만들려면 검증이 필요합니다. 스칼라 경계를 맞춰도 자소 군집을 나눌 수 있습니다.

기본 동등성·순서 비교는 정규화·로캘 조정·대소문자 접기 없이 UTF-8 바이트를 비교합니다. 리터럴 텍스트 검색에 성공하면 스칼라 경계에 맞는 바이트 오프셋을 반환합니다. 다음 연산은 빈 검색어를 허용합니다: contains, find, 및 rfind. 앞의 두 연산은 0에서, 역방향 검색은 바이트 길이에서 일치합니다. 개수 세기·일치 반복·대체·구분자 분할은 진행을 명확히 하기 위해 빈 패턴을 거절합니다. 구분자 없음과 빈 필드의 의미는 아래 각 함수가 정합니다.

ASCII 대소문자·공백 보조 함수는 의도적으로 범위를 제한합니다. 유니코드 정규화, 자소 군집 분할, 로캘 대소문자 처리와 정렬은 선택적 Unicode 모듈의 기능입니다. 인코딩 입출력의 담당 기능: Encoding. CPU 라이브러리 지원이 네이티브 GPU 지원을 뜻하지는 않습니다. AOT와 JIT는 검증·수명 규칙을 보존합니다. 장치 텍스트 연산에는 선언된 기능과 명시적 데이터 전송이 필요합니다.

비교 레퍼런스 포함 Rust UTF-8보기, 텍스트 작업 이동, 및 Java의 대조 텍스트 API. 그들의 인덱싱 및 할당 정책은 자동으로 채택되지 않습니다.

9입니다. 분할, 라인 및 매치 반복

13입니다. 예제 및 디자인 경계 

string_view text = "café";
Result<string_view, TextError> word = string.slice_bytes(text, 0, 5);
Result<string_view, TextError> invalid = string.slice_bytes(text, 4, 5); // Err(TextError.InvalidBoundary);
bool same = string.equals(text, "café");

미래 카탈로그 예제. 아래의 검색, 반복 및 반복기 호출은 0.2 구현의 일부가 아닌 제안된 API입니다.

Optional<usize> hit = string.find(text, "fé"); // Byte offset 2;
Result<string, TextError> repeated = string.repeat(text, 2);
Result<Iterator<string_view>, PatternError> fields = string.split("a,,b", ",");

이 초안에서 텍스트 리터럴은 변경할 수 없는 정적 UTF-8 저장소를 다음 타입으로 대여하며 string_view 할당하지 않습니다. 리터럴 텍스트에서 소유 string 을 만들려면 명시적이고 실패 가능한 소유 생성자가 필요합니다. 전체 문법을 설계 중이더라도 이 초안의 할당 규칙은 일관되게 유지합니다. 언어 표기와 네임스페이스는 항상 소문자 string.

계획된 0.3 문법: print/println의 + 출력 조합 은 중간 소유 string 없이 대여한 텍스트와 출력 가능한 값을 결합합니다. 인식된 출력 호출에 적용되며 일반 string 값 식에는 적용되지 않습니다. 소유 문자열 연결은 명시적이고 실패 가능한 연산으로 유지합니다. 위 카탈로그만으로 구현을 주장하지는 않습니다. 원시 문자열 리터럴 계획 도 string_view를 만들며 암시적인 string 할당을 추가하지 않습니다.

생성·비교·연결에서 정규화를 수행하지 않습니다. C 호환 NUL 종료는 명시적 인코딩 연산입니다. 정규식 엔진·파서·파일 경로·로캘 자원 로딩·안전한 삭제는 별도 API입니다. 일반 텍스트 이스케이프로 HTML·SQL·셸·JSON 각각에 필요한 처리를 대신할 수는 없습니다.
