1입니다. 3개의 뚜렷한 실패 채널

채널의미처리 중
Result<T, E>복구 가능한 실패는 일반적인 형식화된 값입니다. Optional 부재는 별도의 success/absence 모델입니다.완전한 스위치, return를 Result 검사하거나, postfix를 사용 ?.
보안된 런타임 중지잘못된 액세스 또는 오버플로우 정수 명령이 실행되기 전에 안전하지 않은 작업이 거부됩니다.사전 조건을 수정하거나 별도로 구현 된 checked/optional API를 선택하십시오.
컴파일러/공구 진단소스 문법, 유형, 소유권, 모듈, 백엔드 또는 호스트 도구 실패.진단 또는 환경을 고치십시오; 프로그램 과실 가치는 건설되지 않습니다.

Aevix에는 현재 언어 수준 throw / try / catch 예외 메커니즘이 없습니다. 컴파일러 내부의 C++ 예외는 구현 세부 사항이며 Aevix 예외 유형이 아닙니다.

현재 0.3의 공통 Error interface 계획 opt-in borrowed inspection이라고도 합니다. 그것은 오류를 크기 Result 페이로드로 만들지 않으며, 모든 E가 인터페이스를 구현하거나, 암시 적으로 상자를 사용하거나, 오류를 변환하거나, 예외 풀기를 추가해야합니다. 분리되는 try/error-scope 디자인은 0.4 일 남아 있습니다.

2입니다. 오류 유형 카탈로그

69 카탈로그 오류 이름과 참조된 API 시그니처을 탐색합니다. 카탈로그는 숫자, 텍스트, 컬렉션, 소유권, 참조 카운트, 동기화, Tensor/SIMD, 작업 및 장치 오류를 다룹니다. 0.2 작업 프로필 지원 명시적으로 가져온 CPU SIMD 및 범위 CPU parallel.for_each 검증 된 Scalar Workers와 함께. 일반 Task API, Tensor 및 GPU 실행은 지원되지 않으며 카탈로그 오류 기록은 설계 계약으로 남아 있습니다.

3입니다. 0.2 오류 캐리어 구현

0.2 프로필에는 아래 오류 타입의 일부 기능이 구현됐습니다. 이 오류 컨테이너가 존재한다고 해서 같은 카탈로그 이름에 연결된 모든 API를 실행할 수 있는 것은 아닙니다. 구현 범위 현재 플랫폼 범위를 기록한다; 네이티브 Windows 실행은 확립된 증거 밖에 남아있다.

운송인변형 및 페이로드0.2 사용
CollectionErrorAllocationFailure; 크기 오버플로우.동적 배열 할당 및 크기 오류.
InputError<T>AllocationFailure 및 SizeOverflow, 각각은 공개 T 입력을 전달합니다.Vector.push 및 Box.new는 문서화된 사전 비행 실패 시 사용되지 않은 입력을 유지합니다.
RangeErrorInvalidStep; 카운트 오버플로우.잘못된 0 단계 및 usize에 맞지 않는 count입니다.
IntegerError아웃오프랜지.Integer.convert 대상 범위 실패; 일반 오버플로는 여전히 실행을 중지합니다.
FloatErrorOutOfRange; NonFinite; 정확하지 않습니다.rounded/exact 플로팅 및 정확한 float-to-integer 변환 구현.
TextError할당 실패; 크기 초과; InvalidUtf8; InvalidBoundary.UTF-8 소유자 construction/mutation 및 텍스트 경계 검사를 구현했습니다.
BoundsErrorOutOfBounds; 역방향 범위.검사된 Slice.slice 및 Slice.slice_mut; 일반 인덱싱은 가드 스톱을 사용합니다.
ComplexError제로디바이저.가져온 Complex.div 및 Complex.reciprocal는 0 분모를 거부합니다.

위의 7개의 핵심 캐리어가 자동으로 제공됩니다. ComplexError는 수입한에 의해 공급됩니다 complex module; 이것은 전주 실수가 아니다. Box는 요구합니다 import memory { Box };, 및 import memory { Box, InputError }; 표준 InputError 유형을 다시 내보냅니다. AllocError 및 AllocationError CollectionError의 별칭이 아닌 고유한 디자인 이름으로 남습니다. 자세히 보기 0.2 구현 프로필 지원 연산을 확인하세요.

동적 할당 예제, 구현 된 최소 프로필 :

Result<Vector<i32>, CollectionError> make_values() {
    i32 values[] = [1, 2, 3]?;
    return Result.ok(values);
}

문자는 소유 Vector를 할당합니다. postfix ?는 실패시 정확히 CollectionError를 전파한다; 성공은 반환된 Result로 값을 이동시킨다. 이 예제에서는 고정 Array 리터럴에 대한 암시적 할당을 도입하거나 전체 Vector API 카탈로그를 약속하지 않습니다.

4입니다. 명시적인 취급 및 전파

Result<i32, i32> fetch(bool available) {
    if (available) return Result.ok(42);
    return Result.err(404);
}

Result<i32, i32> compute(bool available) {
    i32 value = fetch(available)?;
    return Result.ok(value + 1);
}

Result.ok 및 Result.err는 return 컨텍스트에서 캐리어 유형을 추론합니다. 오류 유형은 두 기능 모두에서 정확히 동일합니다. 성공적인 브랜치는 그 값을 명시적으로 반환한다. 베어 정수는 유효한 피연산자가 아니며 다른 오류 유형이 자동으로 변환되지 않습니다.

5입니다. 청소 및 소유자 복구

일반 오류 전파는 완전히 초기화된 소유 값에 대한 범위 정리를 따릅니다. 구현된 array/Box 경로는 구축된 소유 값을 정리하고 문서화된 실패에 대해 사용되지 않은 입력을 유지합니다. 더 넓은 컬렉션 디자인은 또한 초기화된 접두어 정리를 필요로 하지만, 이러한 계약은 모든 카탈로그 API의 구현을 설정하지 않습니다. InputError<T>와 같은 소유자 보존 오류는 사전 비행 실패 시 허용된 입력을 명시적으로 전달합니다. 이는 범용 롤백이 아닌 API별 보증입니다. 이미 완료된 콜백으로 이동한 값은 자동으로 재구성할 수 없습니다.

정상적인 소유권 정리는 성공적인 플러싱, 저장 또는 폐쇄를 약속하지 않습니다. 이러한 오류가 있는 작업에는 파괴 전에 명시적 Result 반환 API가 필요합니다. 트랩, 중단, 프로세스 킬 및 강제 종료는 정상 범위 또는 persist 정리를 보장하지 않습니다.

6입니다. 런타임 및 컴파일러 오류

모든 실패 범주, 컴파일러 내부 예외 유형, CLI 종료 동작 및 persist 초기화 실패를 읽습니다. 진단 텍스트 및 운영 체제 신호 번호는 안정적인 공공 오류 열거형 또는 휴대용 ABI가 아닙니다.
