0.2 구현 현황. 상수 제네릭 크기, 뒤쪽 매개변수의 기본값, 투명한 타입 별칭, numeric.Floating 은 구현되어 있습니다. 아래 절에서는 구현된 기능과 남아 있는 설계 제한을 구분합니다.

1입니다. 형식 매개 변수는 선언에 속한다

제네릭 선언은 타입 이름 뒤에 타입 매개변수를 적습니다. 선언 내부의 필드·메서드 서명은 이 타입들을 사용할 수 있습니다. 구체적으로 사용할 때는 각 매개변수를 지정한 타입으로 대체하며, 실행 중 변수의 타입이 바뀌는 것은 아닙니다.

struct Pair<T> {
    public T first;
    public T second;
};

Pair<i32> numbers = Pair<i32> {
    first = 10,
    second = 20
};

왼쪽 선언은 변수 이름 앞에 변수의 타입을 적습니다. 오른쪽 생성식은 같은 구체 struct를 명시하며, 앞서 선택한 필드 이름 지정 초기화 구문을 사용합니다. 필드의 이름·타입·누락·중복·접근 권한을 검사합니다.

2입니다. 일반적인 구조체는 필드 규칙을 유지합니다.

Pair<f64> coordinates = Pair<f64> {
    first = 1.5,
    second = 2.5
};

Pair<string> make_words(string initial_first, string initial_second) {
    return Pair<string> {
        first = initial_first,
        second = initial_second
    };
}

이 예제는 앞 절의 제약 없는 Pair를 사용합니다. coordinates에서는 T가 f64이고 make_words에서는 string입니다. 제네릭이 아닌 구체 함수는 이미 소유 중인 string을 받아 반환할 Pair로 이동합니다. 리터럴이나 대여한 string_view를 소유 string으로 변환하지 않습니다. 소유 string 필드는 struct가 이동할 때 함께 이동하며, 같은 제네릭 이름을 사용한다고 해서 Copy 필드가 되지는 않습니다.

struct 필드는 기본적으로 private입니다. 이 예제에서는 외부의 필드 이름 지정 생성이 가능하도록 필드를 명시적으로 public으로 선언합니다. 필수 필드가 private인 제네릭 타입은 일반 struct와 같은 접근 제한 아래에서 내부 팩토리 로직을 사용합니다. 제네릭 메서드의 매개변수는 일반 제네릭 함수와 마찬가지로 메서드 이름 뒤에 둡니다.

3입니다. 열거형은 각 변형 페이로드를 파라미터화할 수 있다.

enum Outcome<T, E> {
    Success {
        public T value;
    };

    Failure {
        public E error;
    };
};

Outcome<string, i32> make_success(string initial_value) {
    return Outcome<string, i32>.Success {
        value = initial_value
    };
}

Outcome<string, i32> failure = Outcome<string, i32>.Failure {
    error = 7
};

T와 E는 서로 다른 타입 매개변수입니다. make_success는 제네릭이 아닌 구체 함수로, 이미 소유 중인 string 매개변수를 Success 페이로드로 이동합니다. 두 항목 모두 상위의 구체 enum 타입인 Outcome<string, i32>를 만듭니다. 항목 이름은 기본적으로 public이고 페이로드 필드는 기본적으로 private입니다. 이 예제의 페이로드는 외부 생성이 가능하도록 명시적으로 public으로 선언합니다.

일반적인 switch의 빠짐없는 분기 검사, 일부 페이로드 필드 바인딩, case별 스코프, 소유권 규칙은 그대로 적용됩니다. 이 선언은 항목의 형태가 비슷하다는 이유만으로 내장 Result/Optional의 ? 연산자를 Outcome에 확장하지 않습니다. 제네릭 enum에 Copy를 명시적으로 적용한다면 모든 항목의 페이로드를 검사해야 합니다.

4입니다. 인터페이스는 자신의 계약을 파라미터화할 수 있다.

interface Reader<T> {
    public T read(&Self self);
};

struct Reading implements Reader<i32> {
    i32 stored;

    public Reading new(i32 initial_value) {
        return Reading { stored = initial_value };
    }

    public i32 read(&Reading self) {
        return (*self).stored;
    }
};

Reading reading = Reading.new(42);
i32 value = reading.read();

Reader<i32>에서 T는 i32로 해석됩니다. 이와 별개로 이 구현에서 Self는 Reading으로 해석됩니다. T는 계약의 타입 인자를 나타내고, Self는 구체적인 수신자 타입을 나타냅니다. 이 public 구현은 필수 일반 메서드를 제공하며, 기본 본문이 없으므로 override를 붙이지 않습니다.

일반 호출의 구현은 정적으로 선택됩니다. 구체 제네릭 인터페이스에는 일반적인 dyn 메서드 호출 가능 규칙이 적용됩니다. 타입 인자는 선언된 뒤쪽 기본값으로 타입을 완성할 수 있을 때만 생략할 수 있으며, 이는 인터페이스 상속을 추가하지 않습니다. 함수 호출의 추론과 오버로드 규칙은 다음 문서에서 별도로 정합니다: 함수와 호출.

5입니다. 구체적인 논쟁은 일반적인 유형 검사를 결정합니다.

확인계약
인수 목록콘크리트는 공급 인자를 순서대로 사용한다; 선언된 후행 기본값은 생략된 파라미터를 완성할 수 있다.
필드 형식치환 후, 각 초기화 값은 선언된 필드 유형과 일치해야 합니다.
계약대체 후 인터페이스 구현은 필요한 시그니처과 일치해야 합니다.
접근 권한형식 인수가 public/private 제한을 우회하지 않습니다.
기능 요구 사항공급된 유형에 의해 제약 조건이 충족되어야 하는 곳을 선택합니다.

허용되지 않는 예제. 확정된 규칙을 의도적으로 위반한 예제입니다.

// Rejected: second resolves to i32 and a string_view literal cannot initialize it;
Pair<i32> invalid = Pair<i32> {
    first = 1,
    second = "two"
};

서로 다른 구체 인스턴스화 사이의 암묵적 변환은 도입하지 않습니다. 정확한 공변성·반공변성 및 서브타이핑 정책은 미정입니다. 타입이 지정되지 않은 숫자 리터럴은 기존 리터럴 규칙에 따라 이미 선언된 숫자 필드 타입으로 결정될 수 있습니다.

6입니다. 컨테이너는 여전히 기본적으로 이동됩니다.

Pair<i32> original = Pair<i32> {
    first = 10,
    second = 20
};
Pair<i32> moved = original;

제약 없는 Pair 선언에는 타입 전체에 대한 Copy 명시가 없습니다. 구체적인 i32 필드가 Copy여도 struct 대입은 소유권을 이동합니다. 제네릭 치환이 컨테이너를 암묵적으로 Copy로 만들지는 않습니다.

허용되지 않는 예제. 확정된 규칙을 의도적으로 위반한 예제입니다.

// Rejected: original was moved in the preceding example;
Pair<i32> reused = original;

컨테이너가 Copy를 명시하면 컴파일러는 선택된 Copy 규칙에 따라 관련 구체 필드 타입을 검사해야 합니다. 두 요소를 함께 적는 헤더는 다음과 같습니다: struct CopyPair<T> implements Copy where T implements Copy: 컨테이너는 필드 타입 제약보다 앞에서 Copy를 명시합니다. 조건부 구현 선언은 이 프로필에 포함되지 않습니다.

7입니다. 대여 및 변동성은 여전히 명확합니다.

mut Pair<i32> editable = Pair<i32> {
    first = 10,
    second = 20
};
editable.first = 30;

&Pair<i32> view = &editable;
i32 observed = (*view).first;

일반적인 소유 바인딩에 대입하려면 mut이 필요합니다. 공유 참조는 복제 없이 같은 struct를 읽으며 필드를 쓸 수 없습니다. 타입 매개변수를 대체해도 불변 바인딩에 권한이 추가되거나 구체 타입에 필요한 할당이 숨겨지지 않습니다.

대여한 필드가 있는 제네릭 값은 각 원본의 수명을 지켜야 합니다. 수명 매개변수 구문과 제네릭 반환 참조의 수명 표기는 미정입니다. 꺾쇠괄호의 타입 인자는 참조가 수명을 벗어나도 된다는 포괄적 허가가 아닙니다.

8입니다. 정적 전문화로 소스 계약 유지

0.2 컴파일러는 제네릭 본문을 계약에 따라 검사하고 타입·상수 인자의 정규화된 구체 특수화를 생성합니다. AOT와 JIT는 같은 검사를 사용합니다. 이 구현은 안정적인 제네릭 ABI, 고정된 딕셔너리 배치, 향후 공유 코드 컴파일 전략을 보장하지 않습니다.

제네릭 선언 자체가 GPU 사용 가능성, 압축된 배치, 벡터화, 런타임 비용 없는 동작을 보장하지는 않습니다. 연산과 구체 표현의 실제 비용은 유지되며, 할당·복사·장치 전송은 명시적으로 표현합니다.

9입니다. 열린 일반적인 결정 및 관련 참조

  • 제네릭 함수·메서드는 이름 뒤에 매개변수를 둡니다. 호출에서는 앞부분을 명시한 목록을 추론이나 기본값으로 완성할 수 있습니다. 자세한 내용은 다음 문서를 참조하세요: 제네릭 함수.
  • 제네릭 타입 인자는 선언된 뒤쪽 기본값을 생략할 수 있습니다. 임의의 필드 값으로 컨테이너 타입을 추론하는 기능, 와일드카드 인자, 공변성·반공변성 확장은 지원하지 않습니다.
  • const usize 매개변수, 뒤쪽 타입·값 매개변수의 기본값, 투명한 비제네릭 타입 별칭은 구현되어 있습니다. Shape 매개변수, 수명 매개변수 구문, 제네릭 별칭 선언, 연관 타입은 이 프로필에 포함되지 않습니다.
  • 타입의 implements 목록은 where보다 앞에 옵니다. 타입·함수 제약은 주어를 반복한 요구 사항을 쉼표로 구분하며, 조건부 구현 선언은 지원하지 않습니다.
  • dyn 뷰는 호출 가능한 비제네릭 메서드를 노출합니다. 제네릭 메서드는 정적 호출로 유지되며, 제네릭 ABI/FFI 배치 보장은 이 프로필에 포함되지 않습니다.
