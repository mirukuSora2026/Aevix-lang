1입니다. 형식 우선 선언에서 persist 사용하기

persist i32 protocol_revision = 1;

i32 read_limit() {
    persist i32 limit = 64;
    return limit;
}

선언된 형식이 바인딩 이름보다 앞에 있습니다. 모듈 수준 선언에는 프로그램 입장의 앞에 초기화된 가공 수명 저장이 있다; 기능에 있는 선언은 그 외침 후에 그것의 저장을 돌려보내고 첫번째 도달에 초기화한다 유지한다. 스토리지를 유지한다고 해서 일반적인 불변의 바인딩이 쓰기 가능해지는 것은 아닙니다.

이 참조는 선택된 persist T name = value; 형식. 그것은 const, mut, 시정 및 persist 수식어구의 모든 조합 또는 순서를 침전하지 않는다.

2입니다. 선언당 하나의 저장소 ID

상황저장소 규칙
두 개의 서로 다른 persist 선언각각에는 그것의 유형이, 분리되는 범위에 있는 이름 및 처음 가치가 일치할 때라도, 그것의 자신의 저장 신원이 있다.
한 지역 선언의 반복된 범위그 선언에 속하는 성공적으로 초기화된 값을 재사용합니다.
루프가 한 로컬 선언에 반복적으로 도달함선언은 각 반복에 대한 새로운 영구 셀이 아닙니다.
여러 스레드가 하나의 선언에 도달하나의 초기화를 조정하고 그 결과 저장소를 액세스 안전 규칙의 적용을 받습니다.
프로세스가 종료되고 다시 시작됩니다.새로운 프로세스가 새로 초기화 된 저장소를 얻습니다. 디스크 복원이 암시되지 않습니다.

저장된 값은 그 타입의 소유권 및 차입 요건을 유지하며, 그 영구적인 장소는 이동에 의해 초기화되지 않은 채로 둘 수 없다는 추가적인 규칙이 있다. Persist는 암묵적 클론, 참조 카운트된 핸들, 직렬화 형식 또는 가비지 컬렉터가 아닙니다.

저장된 값은 초기화 상태를 유지해야 합니다.

필드 또는 요소 중 하나를 포함한 persist 장소는 초기화되지 않은 상태로 이동하거나 둘 수 없습니다. Copy 값을 읽어들이면 복사하고, 다른 접근은 저장된 값을 빌려온다. 소유권을 추출하는 작업은 성공을 노출하기 전에 완전한 교체를 설치해야하며 일반적인 동기화 및 대여 요구 사항을 충족해야합니다. 이 규칙은 동기화되지 않은 변경에 대한 새로운 대체 API 또는 권한을 도입하지 않습니다.

허용되지 않는 예제. 이 non-Copy Result를 반환하면 저장된 소유자가 영구적 인 위치에서 벗어나게됩니다.

Result<Box<i32>, InputError<i32>> take_owner() {
    persist Result<Box<i32>, InputError<i32>> retained = Box.new(7);
    return retained;
}

이니셜라이저는 둘러싸는 기능에서 전파될 수 없습니다.

persist 초기화는 저장된 값을 완료하거나 초기화-오류 중지 정책을 따라야 합니다. 우편 번호 ? 이니셜라이저 내부에서는 주변 함수로부터 반환되는 것이 금지되어 있으며, 값이 미완성인 다른 비로컬 종료도 마찬가지입니다. Result 자체를 저장하여 예상 오류를 전체 값으로 유지합니다. 이니셜라이저가 사용할 수 있는 함수 ? 자신의 몸 안에 : 반환 된 Result는 초기화에 대한 일반적인 입력입니다.

Result<i32, IntegerError> invalid_initializer() {
    persist i32 saved = checked(2147483647 + 1)?;
    return Result.ok(saved);
}

이니셜라이저는 enclosing 함수로부터 Err를 반환함으로써, 자신의 first-reach guard를 초기화 상태로 둘 수 없다. 이 제한은 재시도 또는 중독 상태 복구 정책을 추가하지 않습니다.

3입니다. 긴 저장 시간이 이름의 범위를 넓힐 수 없음

로컬 persist 이름은 여전히 어휘 블록과 중첩된 범위에서만 볼 수 있으며, 보이는 외부 이름은 그림자를 칠 수 없습니다. 이 값은 해당 블록의 끝에 해제되지 않지만, 그 로컬 식별자는 이후에 임의 코드에서 액세스할 수 없게 됩니다. Public/private는 이미 선택한 모듈에 적용되며 로컬 변수를 내보내는 방법이 아닌 선언 경계를 입력합니다.

i32 read_revision() {
    {
        persist i32 retained_revision = 3;
        i32 observed = retained_revision;
    }
    return 3;
}

허용되지 않는 예제. 그 함수에 다음의 추가는 그것의 렉시컬 범위 밖의 이름을 사용할 것이다.

i32 read_revision() {
    {
        persist i32 retained_revision = 3;
    }
    return retained_revision;
}

또한 영구 저장 기간은 다른 곳에서 빌린 데이터의 수명을 연장하지 않습니다. persist에 저장된 참조는 전체 소스 수명 제약을 충족해야 합니다. returned-reference lifetime 문법은 별도의 설계 문제로 남아있다.

4입니다. 로컬 초기화는 호출의 입력을 직접 캡처할 수 없습니다.

로컬 persist 초기화는 런타임 함수 매개 변수 또는 일반 로컬 변수에 직접 의존하지 않을 수 있습니다. 언어는 선언에 먼저 도달했기 때문에 첫 번째 호출자의 입력이 영구적으로 선택되는 것을 거부합니다. 동시 호출에서, 이것은 또한 어느 스레드가 초기화에서 승리하든지 입력을 선택하는 것을 피한다.

예를 거부합니다. 두 초기화는 모두 call-local runtime 값에 직접적으로 의존한다.

i32 from_parameter(i32 input) {
    persist i32 saved = input;
    return saved;
}

i32 from_local() {
    i32 ordinary = 10;
    persist i32 saved = ordinary;
    return saved;
}
i32 offset(i32 input) {
    persist i32 fixed_offset = 10;
    return input + fixed_offset;
}

허용된 예제는 이니셜라이저 외부에서 일반 함수 결과의 매개 변수를 사용합니다. 직접 의존성 제한은 완전한 전이 순도 분석의 약속이 아닙니다: 호출 뒤에 숨겨진 효과는 런타임 persist 초기화 검사를 포함한 자체 규칙에 의해 처리됩니다.

5입니다. 제네릭 함수 locals는 concrete type 인수를 사용합니다.

제네릭 함수 안에 있는 persist는 해당 함수의 타입 인수의 각 콘크리트 조합에 대해 별도의 스토리지 인스턴스를 가지고 있습니다. 동일한 조합으로 반복되는 호출은 인스턴스를 재사용합니다. 다른 조합은 persist의 자체 유형이 동일하더라도 다른 인스턴스를 선택합니다.

i32 marker<T>(T value) {
    persist i32 stamp = 7;
    return stamp;
}

i32 first = marker<i32>(10);
i32 second = marker<i32>(20);
i32 third = marker<f64>(2.5);

처음 두 호출은 동일한 i32 인스턴스를 참조하고, 세 번째는 f64 인스턴스를 참조합니다. 이 그림의 모든 return 7, 따라서 반환된 숫자는 저장소 ID 검사 API가 아닙니다. 도달하지 않은 인스턴스는 로컬 값을 성공적으로 초기화하지 못했습니다.

여러 유형의 매개 변수로, 전체 주문 튜플 문제. 일반적인 함수 유형 추론 및 명시적 인수는 일반적인 규칙을 유지합니다. 이 스토리지 정책은 const, Shape 또는 수명 일반 매개 변수 구문을 추가하지 않습니다.

6입니다. AOT 및 JIT 버전은 하나의 언어 수준 ID를 유지합니다.

AOT 컴파일 및 선택적 JIT 전문화는 하나의 함수 및 하나의 구체적인 유형-논쟁 조합에 대해 여러 코드 버전을 생성할 수 있습니다. 그들은 여전히 동일한 영구 저장소에 액세스합니다. 코드 버전을 생성하거나 교체해도 다른 초기화 실행이 생성되지 않거나 초기화된 값이 재설정되지 않습니다.

이것은 semantic requirement입니다. Symbol naming, runtime registries, code-cache implementation, dynamic-library loading, 그리고 hot reload는 여기에서 선택되지 않는다.

7입니다. 관련 규칙 및 열린 경계

  • 일반적인 형식 멤버 persist 및 스레드 로컬 저장소 규칙이 선택되지 않습니다.
  • 나머지 수정자 조합과 영구 저장소 검사 API는 도입되지 않습니다.
  • 빌린 필드와 반환 참조 수명 표기은 저장 기간과 별도로 유지됩니다.
