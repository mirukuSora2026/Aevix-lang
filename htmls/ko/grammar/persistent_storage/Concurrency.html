1입니다. 하나의 스레드가 로컬 persist를 초기화

i32 protocol() {
    persist i32 revision = 3;
    return revision;
}

여러 스레드가 초기화되기 전에 리비전에 도달하면 정확히 한 스레드가 초기화 시도를 수행합니다. 다른 사람들은 그 시도가 끝나기를 기다리고 있습니다. 성공 후, 그들은 모두 동일한 완전 한 저장 된 값을 사용 하 여, 그들의 액세스 형식 및 대여 규칙을 만족 제공. 샘플은 Copy 스칼라를 반환하므로 모든 호출자에게 영구 소유 리소스를 전송하지 않습니다.

첫 번째 초기화 주장initializer를 시작합니다.현재 시도를 기다립니다.
값을 만듭니다.불완전한 값을 사용할 수 없습니다.부분 필드나 자리 표시자 값을 관찰하지 마십시오.
성공적으로 완료완성된 값과 초기화 성공을 게시합니다.초기화된 값을 안전하게 다시 시작하고 액세스합니다.

언어는 성공적인 출판에 필요한 동기화가 필요합니다. 사용자가 선택할 수 있는 메모리 순서 API, 스토리지 상태 검사 API 또는 필수 잠금 구현은 이 규칙에 의해 도입되지 않습니다.

2입니다. 초기화 조정은 나중에 사용하는 잠금 장치가 아닙니다.

일단 초기화가 성공하면, 첫 번째 도달 가드는 더 이상 값에 대한 임의의 동작을 보호하지 않습니다. 스레드 간에 값을 공유하려면 일반적인 안전 공유 계약을 충족해야 합니다. 공유 상태가 변경될 수 있는 경우 수정을 위해서는 Atomic, Mutex 또는 RwLock와 같은 명시적인 동기화 유형이 필요합니다.

접근 패턴선택한 요구 사항
적절히 공유 가능한 불변 값 읽기해당 유형의 안전한 동시 읽기 및 대여 요구 사항을 유지하십시오.
동시에 스칼라 업데이트명시 적으로 적절한 원자 또는 동기화 추상화를 사용합니다.
복합 자원을 동시에 수정필요한 액세스 보증과 함께 명시적 잠금 또는 동기화 추상화를 사용합니다.
동기화되지 않은 접근과 경쟁할 때 일반적인 가변 값 사용안전하지 않은 공유 수정을 거부합니다; 초기화 조정으로는 충분하지 않습니다.
저장된 소유 값에 접근그것을 빌리거나 Copy 값을 복사하십시오. 밖으로 이동하고 영구적 인 장소를 초기화하지 마십시오; 추출은 완전히 안전한 교체가 필요합니다.

선택한 규칙은 동기화 비용을 표시합니다. 모든 persist 유형을 공유 가능으로 인증하거나, 새 Sync/Send-like 인터페이스 이름을 추가하거나, 일반 단일 스레드 또는 스레드 로컬 가변 영구 바인딩에 대해 여전히 열려 있는 정책을 선택하지 않습니다.

개별적으로 제안된 사항 보기 Atomic, Mutex 및 RwLock APIs입니다. 그들의 정확한 생성자 및 동작 시그니처은 이 장에 의해 완결되지 않는다.

3입니다. Err을 포함하는 Result는 완전한 초기화된 값이다.

persist Result<i32, i32> configuration_status = Result.err(7);

이니셜라이저는 일반적으로 오류 페이로드가 7인 Result를 구성합니다. 스토리지 초기화가 성공했습니다. Result를 읽거나 처리하는 것은 기존 소유권, 대여 및 Result 규칙을 따르며, 초기화에 대한 암시적인 재시도는 없으며 저장된 Err만으로도 프로그램을 중단하지 않습니다.

상황초기화 상태결과
함수는 저장을 위해 정상적으로 구성된 Err를 반환합니다.성공적으로 초기화되었습니다.프로그램은 그것의 정규적인 Result API를 사용하여 저장한 과실을 취급할지도 모른다.
Optional 값은 일반적으로 부재를 저장합니다.성공적으로 초기화되었습니다.부재는 일반적인 가치이며, 미완성 이니셜라이저의 증거가 아닙니다.
이니셜라이저가 런타임 초기화 주기에 도달실행 실패.진단 및 중지; 불완전한 값은 게시되지 않습니다.
이니셜라이저 내부에서 발생하는 일반적인 안전 실패실행 실패.복구 가능한 Result를 발명하는 대신 선택한 초기화-오류 중지 경계를 따르십시오.

Result 반환 작업은 의도적으로 리소스 준비 오류를 저장된 값으로 만들 수 있습니다. API 선택은 초기화 자체를 중단하는 실행 오류와 다릅니다. Persist 액세스에는 새로운 암시적 Result 래퍼가 없습니다.

4입니다. 초기화 주기가 무기한 상호 대기 상태가 되어서는 안 됩니다.

정적으로 확인된 value-initialization cycle은 컴파일 타임 에러이다. 실행을 통해서만 발견된 종속성의 경우, 초기화 주기를 생성하는 Aevix 관리형 액세스는 초기화 실행 오류로 진단되고 프로그램을 중지합니다. 이 규칙은 몇 가지 관리 persist 값을 포함하는 주기뿐만 아니라 재귀적인 첫 번째 범위 초기화도 포함합니다.

예를 들어 A를 초기화하려면 B가 필요하고 B를 초기화하려면 미완성 A가 다시 필요한 경우 이니셜라이저는 일부 값을 게시하거나 단순히 영원히 기다릴 수 없습니다. 서로 다른 스레드에서 관리되는 초기화가 동일한 순환 종속성을 형성하면 일반 대기가 충분하지 않습니다.

불투명한 외래 코드와 관련 없는 잠금은 언어가 관리되는 persist 액세스에서만 추론할 수 없는 대기를 도입할 수 있습니다. 선택된 사이클 규칙은 모든 외부 교착 상태에 대한 검출기로 광고되어서는 안됩니다.

5입니다. 안전 규칙은 무엇을 요할 수 있는가?

첫 번째 reach는 초기화를 실행하고 다른 thread와 맞설 수 있다. never가 완료한 이니셜라이저를 기다리는 스레드는 차단된 상태로 유지될 수 있습니다. 후속 액세스는 필수 안전성과 가시성을 유지해야 하며, 향후 컴파일러 또는 런타임이 해당 변환이 유효한 경우 중복 검사를 제거할 수 있도록 해야 합니다.

벤치 마크, 특정 빠른 경로 또는 절대적인 제로 오버 헤드 약속이 사양에서 다음과 같습니다. 명시적인 공유 동기화는 필요한 경우 경쟁 및 메모리 순서을 포함하여 선택한 작업의 실제 비용을 유지합니다.

6입니다. 실패 및 복구 경계

선택한 초기화 실행 실패 정책은 진단 더하기 프로그램 중지입니다. 호출자에게 재시도 토큰을 제공하거나 예외 문법을 선택하거나 일반 종료 정리가 중지 된 후에 실행된다는 것을 보장하지 않습니다. 예상 준비 실패를 처리하는 데는 명시적인 Result 베어링 이니셜라이저 API를 사용하여 완성된 Result를 저장하고 검사할 수 있습니다.

  • 상세한 고장 진단, 부분 건설 청소 및 안전 정지 풀림 메커니즘은 구현 및 설계 작업으로 남아 있습니다.
  • 일반적인 자동 재시도 모드 또는 새로운 영구 액세스 복구 API가 승인되지 않았습니다.
  • 성공적인 초기화는 나중에 FFI 경주를 검증하거나 빌린 데이터 수명을 연장하지 않습니다.
