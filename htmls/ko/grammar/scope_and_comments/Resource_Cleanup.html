선언전체 자료형연산자와 표현식제어 흐름

1. 결정적인 소유권 정리

스코프가 정상 종료되면 Aevix는 초기화 역순으로 그 스코프가 아직 소유한 값을 해제합니다. 현재 소유 값은 각 타입 계약에 따라 정확히 한 번 정리합니다. Copy 스칼라는 자원 해제가 필요 없으며, 소유 컨테이너는 원소를 파괴하고 저장 공간을 해제할 수 있습니다.

설계 문서. 확정된 언어 규칙은 직접 설명하고, 미정 정책과 권고안은 따로 표시합니다. 이 예제들이 컴파일러·런타임·진단 시스템의 구현을 뜻하지는 않습니다.

이는 소유권 규칙이지 추적형 가비지 수집의 일정이나 접근 가능한 모든 자원의 무조건적인 해제 보장이 아닙니다. 이동한 값, 남아 있는 Shared 소유자, 지속 저장소, 강한 순환 참조, 디바이스 사용 권한에는 각각의 수명 조건이 있습니다.

2. 초기화의 역순

성공적으로 초기화한 소유 값만 정리 대상이 됩니다. 부분 생성 실패는 API 계약에 따라 초기화된 부분을 정리합니다. 지역 정리는 가장 최근에 초기화한 살아 있는 소유 값부터 먼저 초기화한 값으로 진행하며 이미 이동해 나간 값은 두 번 정리하지 않습니다.

{
    Result<Box<i32>, InputError<i32>> first = Box.new(1);
    Result<Box<i32>, InputError<i32>> second = Box.new(2);
}

두 번째 Result를 첫 번째보다 먼저 정리합니다. Ok 분기는 Box를 소유하고 오류 분기는 문서화된 복구 페이로드를 소유합니다. 이 예제는 할당 성공을 가정하지 않습니다. 컨테이너 내부 원소의 정확한 파괴 순서는 그 컨테이너 계약에 속하며 지역 변수 순서로 임의 결정하지 않습니다.

3. 블록 끝과 제어 흐름의 종료

종료 방식정리 의무이후의 제어 흐름
블록 닫기그 영역이 아직 소유한 지역 값을 해제합니다.블록 다음을 계속 실행합니다.
break가장 가까운 반복문·switch 대상을 향해 나가면서 통과한 영역을 정리합니다.대상 다음에서 계속 실행합니다.
continue벗어난 반복 본문의 영역을 정리합니다.해당 반복문에 정의된 다음 반복 단계를 수행합니다.
return넘겨주는 반환 소유 값을 제외하고 벗어나는 지역 영역을 정리합니다.선언된 결과를 호출자에게 넘깁니다.
?를 통한 Result 전파대응하는 명시적 오류 반환과 같은 정리를 수행합니다.바깥 함수에서 오류를 반환합니다.
void leave_loop() {
    while (true) {
        Vector<i32> scratch = Vector.new(i32);
        break;
    }
    return;
}

scratch 소유 값은 break 경로에서 해제됩니다. 각 case와 default도 독립된 스코프이므로 분기를 나갈 때 초기화 역순으로 아직 소유한 지역 값을 정리합니다. 바깥 소유자나 반환 결과로 이동한 값은 그 목적지를 따릅니다. 허용된 return, 바깥 반복문의 continue, 발산 경로, Result 전파 뒤에도 case 끝의 break는 명시합니다: ?. 도달할 수 없는 필수 마지막 break는 그 자체로 오류나 경고가 아니며 두 번째 정리 동작으로 실행되지도 않습니다. 정상 return·continue·Err는 실제로 나가는 영역만 정리합니다. 끝나지 않는 실행은 정상 종료가 아니며 안전 정지 시 정리는 별도로 미정입니다. 자세한 내용은 case 종료.

4. 이동과 반환되는 소유 값

이동은 정리 의무를 이전합니다. 이전 위치는 사용할 수 없게 되고 목적지가 현재 소유자가 됩니다. 반환 페이로드는 호출자가 받는 결과로 이동합니다. 호출자가 사용하기 전에 함수 정리가 같은 페이로드를 파괴해서는 안 됩니다.

Vector<i32> transfer_owner() {
    Vector<i32> original = Vector.new(i32);
    Vector<i32> destination = original;
    return destination;
}

소유 값의 이동은 할당된 내용을 clone하지 않습니다. 명시적 clone은 새로운 정리 의무를 만들 수 있으며 할당하거나 실패할 수 있습니다. AOT·JIT 최적화에서도 값 의미와 관찰 가능한 해제 동작을 보존해야 합니다.

다음 상황에서 소비하는 enum switch, switch (move event)는 직접 소유한 enum을 받습니다. 값 바인딩은 소유 페이로드 필드를 분기 지역이나 바깥 목적지로 이동할 수 있습니다. 소비된 항목이 계속 소유한 데이터는 분기를 벗어날 때 한 번 정리합니다. 읽기·수정 모드는 원본 소유자를 유지합니다. 사용자 정의 정리와 부분 필드 이동의 조합은 아직 설계가 열려 있습니다.

5. Result 오류도 정상 종료입니다

반환한 Err와 ?가 전파한 오류는 정리 관점에서 일반 함수 완료 경로입니다. 앞선 대입, 끝난 콜백, 외부 IO를 되돌리지는 않습니다. checked 산술 표현식과 Result 타입은 별도의 오류 경계를 유지합니다.

Result<i32, IntegerError> calculate(i32 left, i32 right) {
    Vector<i32> scratch = Vector.new(i32);
    rsn total = checked(left + right)?;
    return Result.ok(total);
}

계산이 성공하든 IntegerError를 전파하든 scratch는 정상 스코프 종료까지 그 지역에서 소유합니다. 여기에 ?가 있다는 이유로 관련 없는 호출 함수의 트랩이나 실패가 복구 가능한 Result가 되지는 않습니다.

6. 대여 종료는 소유 값 해제가 아닙니다

대여는 일시적인 접근 권한이지 소유권 복제가 아닙니다. 공유·독점 대여가 끝나면 남은 제한 아래에서 원래 소유 값을 다시 사용할 수 있습니다. 소유 값의 할당을 파괴하지는 않습니다. 마지막 사용 분석은 접근 권한에 관한 것이며 관찰 가능한 스코프 정리 규칙을 조용히 바꾸지 않습니다.

mut i32 number = 1;
{
    &mut i32 target = &mut number;
    *target = 2;
}
i32 observed = number;

대여한 인수, Slice, MutSlice, string_view에도 같은 구분이 적용됩니다. 대여한 뷰의 지역 바인딩이 끝나도 다른 곳에서 소유한 원소는 해제하지 않습니다. 반환·캡처한 대여는 완전한 원본 수명 제약을 계속 따릅니다.

7. 참조 횟수를 세는 소유권

Shared 핸들을 해제하면 강한 참조 하나가 줄어듭니다. 핸들 하나가 스코프를 나갈 때마다가 아니라 마지막 강한 소유자가 놓을 때 페이로드를 정리합니다. Weak 관찰자는 제어용 정보를 유지할 수 있지만 파괴된 페이로드를 살려두거나 강한 소유권으로의 승격 성공 없이 읽을 수는 없습니다.

강한 소유권 순환은 메모리와 외부 자원을 유지할 수 있습니다. 알려진 순환은 Weak 역방향 참조로 끊을 수 있지만 언어가 절대적인 메모리 누수 방지를 보장하지는 않습니다. Shared 핸들의 clone과 페이로드의 clone은 소유권·비용 계약이 다릅니다. 자세한 내용은 Shared 및 Weak.

8. 실패 가능한 flush와 close의 명시

데이터 커밋이나 외부 자원 flush처럼 성공 여부가 프로그램에 중요하다면 자동 정리 전에 명시적인 Result API가 필요합니다. 호출자가 아직 복구를 선택할 수 있을 때 결과를 처리하세요. 이미 끝난 스코프에 자동 정리가 복구 가능한 Err를 반환할 수는 없습니다.

정리 계약은 소멸자가 복구 가능한 오류를 내보내거나 스택 풀기를 하는 것을 허용하지 않습니다. 이는 정리 동작의 요구 사항이지 모든 외부 디바이스·IO가 항상 성공한다는 보장이 아닙니다. 사용자 정의 소멸자 선언 구문과 강제 검사 방식은 아직 설계하지 않았으며, 새 close·drop·소멸자 함수 문법을 도입하지도 않습니다.

버퍼 출력의 커밋, 원격 작업 성공, 애플리케이션 상태의 트랜잭션 복구를 자동 정리만으로 증명할 수는 없습니다.

9. 처리 중인 GPU 자원

Pending 결과 핸들이 끝나도 수락된 디바이스 작업은 계속 추적될 수 있습니다. 런타임은 디바이스가 더 이상 접근할 수 없을 때까지 소유 버퍼·코드·큐 상태·필요한 자원 사용 권한을 유지해야 합니다. 사용자 핸들을 버렸다는 사실은 완료의 증거가 아니며 반드시 디바이스를 기다리는 것도 아닙니다.

대여한 지역 저장소에는 더 강한 종료 제약이 있습니다. 디바이스 접근이 계속될 수 있다면 선언 스코프가 저장소를 해제하거나 재사용해서는 안 됩니다. 대여한 지역 값을 끝내기 전에 접근 종료가 증명되어야 합니다. 언어 구문이 대기를 넣을지 미완료 대여 상태의 종료를 거부할지는 아직 미정이며 어느 쪽도 암묵적으로 선택하지 않습니다.

시간 초과, 취소 요청, Pending 핸들 폐기, 제출 오류 반환만으로 접근 종료가 확인되지는 않습니다. 완료 여부가 불명확한 상태에서 대여 메모리를 해제한 채 안전한 코드로 돌아가는 것은 정당화할 수 없습니다.

참고: Pending 및 Task 에서 완료 추적을 설명합니다. 소유권 유지와 호스트의 메모리 가시성은 별도 의무입니다.

10. 비정상 종료와 지속 저장소의 경계

복구 가능한 checked 구문 밖의 일반 정수 안전 실패는 안전 정지이지 정상 오류 반환이 아닙니다. 이 문서는 안전 정지, 프로세스 abort, 외부 프로세스 종료 뒤에 지역 정리가 실행된다고 보장하지 않습니다. 정상 스코프 종료 보장을 모든 종료 상황에 대한 보장으로 표현해서는 안 됩니다.

지속 저장소는 프로세스 수명 계약을 따릅니다. 정상 종료에서는 언어가 추적하는 스레드·Task·GPU 자원 사용을 마친 뒤 초기화 완료의 역순으로 성공적으로 초기화된 persist 값을 해제합니다. persist 정리는 다른 persist에 접근할 수 없습니다. 치명적인 초기화 오류는 실행을 중단하며 이 정상 종료 보장이 적용되지 않습니다. 자세한 규칙은 지속 저장소 종료. 일반 렉시컬 스코프를 나가도 프로세스 수명의 persist 저장소는 해제하지 않습니다.

11. 설계 범위와 관련 문서

확정 규칙에는 초기화 역순 정리, 이동·반환의 소유권 전달, 정상 이탈 시 정리, 컴파일러가 관리하는 Drop이 포함됩니다. Drop 구현은 public void drop(&mut Concrete self)를 사용하며 필드 정리 전에 한 번 실행합니다. Copy와 함께 구현하거나 명시적으로 호출할 수 없습니다. Drop 소유자에서 non-Copy 필드를 꺼내 이동하는 것은 금지하지만, 소유자 전체 이동은 허용합니다. 정리에 쓰이는 대여는 정리가 끝날 때까지 유효해야 합니다. 실패 가능한 flush와 close는 명시적 Result API로 처리합니다. 이는 컴파일러에서 개발 중인 0.3 확정 계약이며 배포된 0.2 프로필에는 포함되지 않습니다. 대여한 장치 자원의 이탈 동작과 안전 정지 시 정리는 미정이며 GPU 실행은 보류합니다.
