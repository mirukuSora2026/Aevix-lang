1. 우선순위와 비교의 경계

선택된 소스 규칙은 기존 연산자 사이의 관계를 완성합니다. 순위 숫자가 작을수록 더 강하게 결합합니다. 두 피연산자를 모두 평가하는 연산의 평가 순서는 왼쪽부터 오른쪽이며, 우선순위가 부수 효과의 순서를 바꿀 권한을 주지는 않습니다.

설계와 구현 범위. 현재 0.2 구현 프로필 은 지원하는 프런트엔드 기능을 설명합니다. 이런 일반 파싱 요구 사항이 예제의 모든 카탈로그 API를 실행 가능하게 만들지는 않습니다.

순위연산자결합 방식
1. () [] ? ++ --왼쪽부터 이어지는 후위 연산 체인. 각 연산은 피연산자와 저장 위치에 관한 규칙을 유지합니다.
2& &mut * + - ! ~ ++ --오른쪽에서 왼쪽.
3* / %왼쪽에서 오른쪽.
4+ -왼쪽에서 오른쪽.
5<< >>왼쪽에서 오른쪽.
6< <= > >=괄호 없는 비교 연쇄는 허용하지 않습니다.
7== !=괄호 없는 비교 연쇄는 허용하지 않습니다.
8&왼쪽에서 오른쪽.
9^왼쪽에서 오른쪽.
10|왼쪽에서 오른쪽.
11&&왼쪽에서 오른쪽, 단락 평가.
12||왼쪽에서 오른쪽, 단락 평가.
13.. ..=비결합. 필요하면 양 끝의 표현식을 괄호로 묶습니다.
14condition ? first : second오른쪽에서 왼쪽, 선택된 분기 하나만 평가.

대입과 복합 대입은 문장입니다. C 방식 for 의 전용 갱신 동작 칸에서 사용할 수 있지만 값 표현식이 되지는 않습니다. Range는 연쇄로 연결하지 않습니다. 다음처럼 쓰지 말고 의도적인 중첩 표현식을 괄호로 묶으세요: a..b..c. 관계 연산과 동등 비교의 우선순위는 서로 다르지만 두 단계에 걸친 괄호 없는 비교 연쇄도 금지됩니다. 괄호로 묶은 비교 결과를 다시 비교하려면 다음처럼 씁니다: (a < b) == expected . 정수 ++ 및 -- 에는 쓰기 가능한 원시 정수 저장 위치가 필요합니다. 결과는 값이므로 그 뒤에 다시 갱신 연산을 붙여도 쓰기 가능한 위치가 생기지 않습니다.

비교는 비트 연산보다 먼저 결합하므로 마스크 검사에는 다음처럼 괄호가 필요합니다: (flags & mask) != 0. 괄호는 묶는 방식을 바꾸지만 선택된 평가 순서와 실패 계약은 그대로 유지합니다.

2. 후위 전파와 조건 선택

후위 ? 는 후위 연산 체인에 속합니다. 삼항 ? : 는 가장 낮은 조건 선택 우선순위에 속합니다. 같은 토큰열은 공백과 무관하게 해석합니다. 이 규칙 아래에서 완전한 구문 해석이 하나만 남으면 사용하고, 여러 개면 표현식을 거부하여 명시적 괄호를 요구합니다. 피연산자 타입은 그 뒤에 검사하며, 파싱을 고르기 위해 타입을 추측해서는 안 됩니다.

작성한 형태결합 방식의미
checked(a + b)? + c(checked(a + b)?) + c검사한 합을 전파한 다음 c의 일반 덧셈을 수행합니다.
result? ? first : second(result?) ? first : second꺼낸 결과는 bool이어야 하며 선택한 값만 평가합니다.
flag ? make_result()? : fallbackflag ? (make_result()?) : fallback선택된 true 분기에서만 호출하고 전파합니다.
flag ? +x : yflag ? (+x) : y물음표는 조건 선택을 시작하고 +는 단항 연산입니다.
Result<i32, IntegerError> choose_from_result(Result<bool, IntegerError> result, i32 first, i32 second) {
    i32 selected = result? ? first : second;
    return Result.ok(selected);
}

분기들은 여전히 같은 타입이어야 하며 전파도 바깥 함수와 정확히 같은 오류형을 사용해야 합니다. 파싱이 하나로 결정되어도 타입·대여·반환 오류가 허용되는 것은 아닙니다.

모호한 토큰열: a ? + b ? + c : d. 가능한 두 해석은 다음과 같습니다: ((a?) + b) ? (+c) : d 및 a ? ((+(b?)) + c) : d. 타입 검사로 한 해석이 거부될 것 같더라도 괄호 없는 형태는 거부합니다. 원하는 묶음을 직접 쓰세요. 0.2 파서는 타입 검사 전에 이 모호함을 거부하며, 클로저 파서 검사에서도 전파·내부 삼항식·중첩 클로저 본문을 확인합니다.

3. 제네릭 꺾쇠와 시프트 토큰

타입 문맥에서 <...> 는 타입 인수를 감쌉니다. 중첩 타입 인수 목록을 닫을 때 닫는 >> 토큰은 두 개의 닫는 꺾쇠 구분자로 나뉩니다. 같은 토큰도 표현식 문맥에서는 오른쪽 시프트 연산자로 남습니다.

형태해석
Vector<Vector<i32>>중첩 제네릭 타입. 닫는 구분자 두 개.
identity<i32>(value)정상적인 타입 인수 목록, 뒤따르는 호출 괄호, 정적으로 확인된 호출 대상 이름이 일치하면 제네릭 호출.
a < b표현식 문맥의 일반 관계 비교.
value >> amount표현식 문맥의 일반 오른쪽 시프트.

제네릭 호출은 타입 인수 구문·호출 문맥·해결된 이름의 정적 종류로 구분합니다. 임의의 실행 중 값을 타입으로 재해석하거나 실행 중 값에 따라 다른 파싱을 고르지 않습니다. 타입·호출 대상 경로가 계속 모호하면 명시적인 묶음이나 접근 가능한 명확한 타입 경로를 요구하며, 변환이나 import를 만들어내지 않습니다. 함수 제네릭 인수는 앞부분만 명시하고 나머지를 추론이나 뒤쪽 기본값으로 채울 수 있습니다. 자세한 내용은 0.2 제네릭 구현 프로필. 제네릭 타입 생성에는 별도로 문서화된 명시적 타입 인수 규칙이 적용됩니다.

4. 제한된 컴파일 타임 타입 피연산자

문서화된 내장 intrinsic은 특정 인수 위치를 다음으로 지정할 수 있습니다: 컴파일 타임 타입 피연산자. 카탈로그가 지정한 그 위치에서만 다음과 같은 타입을 허용합니다: i64 . 호출의 일반 괄호 안에 쓰더라도 컴파일 타임에 해결되며, 실행 중 일급 타입 값으로 표현되지 않습니다.

intrinsic 호출타입 피연산자
Integer.convert(i64, source)변환 대상 정수형 i64.
Vector.new(i32)Vector의 원소형 i32.
Array.from_copy(i32, 4, &fill)Array의 원소형 i32. 다른 피연산자는 각각 문서화된 계약을 유지합니다.
Box.payload_size(i32)조회하는 페이로드 타입 i32.
i32 source = 12;
Result<i64, IntegerError> widened = Integer.convert(i64, source);
usize payload_bytes = Box.payload_size(i32);

intrinsic 카탈로그의 타입 피연산자 표시는 그 intrinsic의 메타데이터이며 일반 값 매개변수 선언이 아닙니다. 이 규칙은 다른 문서화된 내장 항목도 해당 위치를 명시했을 때만 적용됩니다. 모든 식별자를 타입 피연산자로 취급하지 않습니다. 사용자 함수는 일반 값 매개변수를 유지하고, 제네릭 인수는 <...> 를 사용해 추론하거나 앞부분을 명시하거나 뒤쪽 기본값으로 채울 수 있습니다. 다음을 전달하는 것은 i32 일반 정수 값 매개변수에 허용되지 않습니다. 컴파일 타임 타입 피연산자는 제네릭 인수 추론과 별개인 intrinsic 규칙이며 일반 리플렉션, 암묵적 할당, clone을 도입하지 않습니다.

5. Range와 숫자 토큰의 경계

렉서는 ..= 를 다음보다 먼저 인식합니다: ... 소수점을 사용하는 십진 실수 리터럴에는 소수점 양쪽에 숫자가 필요합니다. 0.5 및 1.0 는 이 형태이며 다음은 아닙니다: .5 및 1. . 따라서 0..10 는 정수 0, Range .., 정수 10, 및 0..=10 는 양 끝을 포함하는 Range 토큰을 사용합니다.

부호 있는 최솟값 리터럴은 기대하는 부호 있는 타입에 대해 부호와 크기를 함께 검사합니다. i8 minimum = -128; 는 먼저 양수 128이 i8에 들어갈 것을 요구하지 않고 허용됩니다. 이미 타입이 정해진 최솟값의 부호 반전은 별도의 산술 연산이며 해당 오버플로 계약을 유지합니다.

이 최소 토큰 규칙만으로 모든 진법·접미사·구분자·지수 형태·유니코드 식별자·문자열 및 문자 이스케이프를 확정하지는 않습니다. API 카탈로그의 다른 숫자 표기 후보를 이 페이지가 자동으로 채택하지도 않습니다.

6. 문장 본문과 else의 결합

다음 else 는 가장 가까운 짝 없는 다음 문장에 연결됩니다: if. bool 조건의 괄호는 계속 필수입니다. 실행 가능한 일반 문장 하나는 본문 중괄호를 생략할 수 있지만, 선언을 본문으로 쓰려면 명시적 블록이 필요합니다. 중괄호 없는 선언 하나에 특별한 스코프를 만들어주지 않습니다.

예를 들어 if (outer) if (inner) action(); else fallback(); 에서 else는 inner에 연결됩니다. outer에 붙이려면 중괄호를 쓰세요. 선언 본문은 다음처럼 작성합니다: if (ready) { i32 value = 1; } . 선언 이름과 정리는 그 명시적 블록을 따릅니다.

실행되는 선언·대입·호출 문장·return은 모두 세미콜론으로 끝납니다. 함수나 제어 흐름 블록의 닫는 중괄호에는 세미콜론을 추가하지 않습니다. 타입 선언은 기존에 정한 다음 끝맺음을 유지합니다: };.

7. case 종료에는 break를 명시합니다

작성한 모든 case와 default는 끝에 명시적인 다음 문장을 유지합니다: break;. 그 앞의 return, 반복문의 continue, 발산 경로나 Result ? 는 각자의 제어 흐름·소유권 계약 아래에서 허용됩니다. 어떤 것도 마지막에 써야 하는 break를 대신하지 않습니다. 필수 break에 도달할 수 없어도 그 이유만으로 오류나 경고를 만들지 않습니다. 이 제한된 예외로 일반적인 도달 불가능 코드 정책이 정해지는 것은 아닙니다.

i32 first_or_zero(i32 value) {
    switch (value) {
        case 1:
            return 10;
            break;
        default:
            break;
    }
    return 0;
}

이 예제의 Result에서 ? 는 Err일 때만 조기 반환하며 성공 경로는 작성된 break까지 계속됩니다. Optional 전파도 None에서 조기 반환합니다. return·continue·전파된 Err는 실제로 나가는 영역을 정확히 한 번 정리합니다. 끝나지 않는 실행은 정상 스코프 종료가 아니며 안전 정지 시 정리는 별도로 미정입니다. 스칼라와 enum switch에 같은 규칙이 적용됩니다. 관련 문서는 Switch 및 Enum Switch.

8. 구현과 남은 제한

파서는 중첩 제네릭의 닫는 기호, 비교 연쇄 거부, 혼합된 물음표를 포함해 허용·거부·모호한 토큰열을 테스트합니다. 더 넓은 형식 문법의 검사 범위는 구현 과제로 남습니다. 현재 예제 모음이 제안된 모든 카탈로그 표현식의 지원을 증명하지는 않습니다.

전체 리터럴·식별자 문법, 일반 캐스트, None의 오류 변환, 사용자 정의 연산자 오버로딩, 다음 내부에서의 세부 ? 효과는 checked(...) 별도 설계 작업입니다. 소유한 Optional의 전파와 검사하는 정수 시프트·인덱싱은 다음 프로필에서 구현되어 있습니다: 0.2 구현 프로필. 이 페이지는 일반 Task나 GPU 실행을 추가하지 않습니다.
