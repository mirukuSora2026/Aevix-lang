문법 개요선언자료형

1. 명시적인 혼합 산술 모델

0.2 구현 범위. 안전 검사를 수행하는 일반 정수 연산자는 구현되어 있습니다. 다음 checked(expression) 구문과 이 페이지의 이름 있는 checked 산술 API는 선택된 설계 계약이며, 실행 가능한 0.2 기능이 아닙니다. 이미 구현된 Integer.convert 및 Float 변환은 각자의 명시적 Result 계약을 유지합니다. 자세한 내용은 숫자 타입 구현 프로필.

선택된 설계는 편리한 일반 정수 산술과 복구 가능한 checked 산술을 함께 제공합니다. 평가 전에 구문으로 실패 방식을 정합니다. 반환형·최적화 설정·타입 추론 결과가 두 방식을 조용히 바꾸지는 않습니다.

형태성공 결과산술 실패
a + b스칼라 T.정적으로 확정된 실패는 진단하고 실행 중 실패는 안전 정지합니다.
Integer.checked_add(a, b)Ok(T) 에서 Result<T, IntegerError>.Err를 반환합니다.
checked(a + b * c)Ok(T) 에서 Result<T, IntegerError>.직접 작성한 산술 중 처음 실패한 연산이 이 checked 표현식의 Err가 됩니다.

checked는 모든 오류를 잡는 런타임 함수가 아니라 언어 구문입니다. Result는 이 표현식의 결과를 나타내며, 그 오류를 바깥 함수에서 반환하는 것은 별도의 명시적 작업입니다. 모든 예제는 설계 예제로, Aevix 컴파일러에서 컴파일한 예제가 아닙니다.

일반 산술은 선언된 숫자 타입을 반환합니다

i32 add(i32 first, i32 second) {
    return first + second;
}

표현 가능한 입력에 대해 add는 i32를 반환합니다. 수학적인 합이 i32 범위를 넘으면 실행 중 안전 실패로 실행을 멈춥니다. Debug와 release 빌드의 동작은 같아야 합니다. 복구 불가능한 종료의 세부 사항은 미정이며, 이 페이지는 강제 정지 시 스택 풀기나 자원 정리를 보장하지 않습니다.

부호 없는 뺄셈에서 0보다 작아지는 경우도 같은 검사 정책의 오버플로입니다. 부호 있는 최솟값을 -1로 나눈 결과는 해당 타입에 들어가지 않습니다. 0으로 나누거나 나머지를 구하는 것은 산술 실패입니다. 부호 있는 최솟값의 -1에 대한 나머지는 Integer API 초안의 검토 항목이며 이 페이지에서 새로 확정하지 않습니다.

2. checked(expression)과 적용되는 연산

Result<i32, IntegerError> calculate(i32 first, i32 second, i32 third) {
    return checked(first + second * third);
}

checked 범위는 그 안에 직접 작성된 지원 정수 산술의 실패를 IntegerError 값으로 바꿉니다. 성공 결과에는 i32 타입인 최종 표현식 값이 들어갑니다. Result가 함수 반환형과 같다면 그대로 반환할 수 있으므로 unwrap이나 전파 연산자가 필요 없습니다.

초기 예제는 같은 타입의 정수 스칼라 결과를 사용합니다. 정수가 아니거나 영역이 섞인 표현식에 checked를 적용했을 때의 일반 결과 형태는 미정입니다. 괄호가 표현식의 경계를 정하며, 이 버전은 checked 문장 블록을 도입하지 않습니다.

적용 연산과 대응하는 명시적 API

직접 작성하는 구문이름 있는 API초기 실패 계약
a + bInteger.checked_add(a, b)결과가 T에 들어가지 않으면 오버플로.
a - bInteger.checked_sub(a, b)부호 없는 언더플로를 포함한 오버플로.
a * bInteger.checked_mul(a, b)곱이 T에 들어가지 않으면 오버플로.
a / bInteger.checked_div(a, b)0인 나눗수 또는 부호 있는 최솟값을 -1로 나누는 경우.
a % bInteger.checked_rem(a, b)0인 나눗수. 부호 있는 나머지의 예외 경계는 아직 미정.
-value 부호 있는 정수에 적용Integer.checked_neg(value)부호 있는 최솟값의 부호를 반전하면 오버플로.
++value value++ --value value--직접 작성하는 checked 구문다음 정수를 저장하기 전에 검사하며, 첫 실패는 Err를 반환합니다.

단항 +는 지원하는 숫자 값을 그대로 유지합니다. 비트 연산이 임의 오류 포착으로 바뀌지는 않으며, checked 구문과 시프트 실패의 최종 관계는 아직 미정입니다. 제안된 Integer API 카탈로그 에는 명시적 변환, 파싱, wrapping, saturating 함수도 있습니다. 이 함수들은 각자의 계약을 유지합니다.

i32 first = 10;
i32 second = 20;
Result<i32, IntegerError> explicit_sum = Integer.checked_add(first, second);
Result<i32, IntegerError> expression_sum = checked(first + second);

3. 평가 순서와 중간 실패

Result<i32, IntegerError> combine(i32 first, i32 second, i32 third) {
    return checked(first + second * third);
}

first, second, third를 차례로 한 번씩 평가합니다. second * third를 계산한 다음 first를 더합니다. 곱셈이 실패하면 덧셈은 실행하지 않습니다. 첫 실패는 선택된 평가 순서에 따라 결정해야 하며, 더 빠르다는 이유로 구현이 임의의 뒤쪽 실패를 선택해서는 안 됩니다.

실패하면 checked 표현식의 남은 작업을 건너뜁니다. 바깥 함수에서 자동으로 반환하지는 않습니다. Result를 바인딩하거나 그대로 반환하고, 명시적 API로 확인하거나 별도로 승인된 후위 물음표를 사용하세요.

중간 오버플로도 실패입니다

i8 first = 120;
i8 second = 10;
i8 third = 10;
Result<i8, IntegerError> outcome = checked(first + second - third);

첫 덧셈의 결과는 i8 범위 밖인 130입니다. 무한 정밀도의 수학적 재배열로 최종 결과가 120이 될 수 있어도 이 표현식은 Err를 생성합니다. 뺄셈은 실행하지 않습니다. 최적화의 재결합이나 JIT 특수화로 이 정의된 실패를 성공으로 바꿔서는 안 됩니다.

피연산자를 암묵적으로 넓히지 않습니다. 더 넓은 정수형으로 계산하려면 표현식에 들어가기 전에 문서화된 명시적 변환을 수행하세요. outcome에 rsn을 사용하면 Result 타입만 추론하며 산술의 비트 폭은 바뀌지 않습니다.

4. 정적 검사도 Result의 실패를 보존합니다

i8 first = 120;
i8 second = 10;
rsn outcome = checked(first + second);

컴파일러가 계산을 미리 결정하면 outcome은 Result<i8, IntegerError>의 일반 Err 값입니다. checked 안에서 증명된 오버플로는 일반 산술의 컴파일 거부가 아니라 해당 표현식의 값 계약에 속합니다.

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: ordinary statically guaranteed i8 overflow;
i8 invalid_sum = 127 + 1;

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: the literal itself cannot be an i8 operand;
Result<i8, IntegerError> invalid_literal = checked(128);

checked는 유효하지 않은 타입 지정 리터럴, 타입 불일치, 해결되지 않은 이름, 구문 오류, 잘못된 대여를 고치지 않습니다. 이런 오류는 여전히 컴파일 타임 진단입니다. 이름 있는 checked API를 상수 접기할 때도 그 Result 계약을 유지해야 합니다.

5. 구문으로 정해지는 경계이며 트랩 포착이 아닙니다

i32 ordinary_add(i32 first, i32 second) {
    return first + second;
}

Result<i32, IntegerError> outer(i32 first, i32 second) {
    return checked(ordinary_add(first, second) + 1);
}

checked 안에 직접 작성된 + 1만 적용 대상입니다. ordinary_add 내부의 일반 덧셈이 실패해도 outer가 그 안전 정지를 Err로 바꾸지 않습니다. 최적화로 호출을 인라인해도 같습니다. 코드 생성 방식에 따라 소스의 경계가 이동해서는 안 됩니다.

명시적 checked 함수 호출은 자체 Result를 반환합니다. checked가 이를 암묵적으로 unwrap하거나 임의의 중첩 래퍼를 평탄화하지는 않습니다. 별도의 단계로 오류 전파 를 checked 표현식 바깥에 사용하세요.

6. 증가 연산 검사와 롤백 금지

mut i8 counter = 127;
Result<i8, IntegerError> outcome = checked(counter++);
i8 unchanged = counter;

outcome은 Err이고 unchanged는 127입니다. 후위 증가가 이전 값을 반환하는 것은 검사한 변경을 성공적으로 저장한 뒤뿐입니다. 요청한 변경을 수행하지 않은 채 오버플로에서 Ok(127)를 만들어서는 안 됩니다.

mut i8 counter = 4;
Result<i8, IntegerError> before = checked(counter++);
Result<i8, IntegerError> after = checked(++counter);

before는 4, after는 6을 담고 counter는 6입니다. 전위 감소는 새로 저장한 값을, 후위 감소는 이전 값을 반환합니다. 쓰기 가능한 저장 위치는 한 번만 평가합니다. 지역 참조 바인딩 자체가 불변이어도 독점 참조는 대상 수정을 허용할 수 있습니다.

앞서 성공한 작업은 롤백하지 않습니다

mut i8 counter = 1;
i8 large = 127;
Result<i8, IntegerError> outcome = checked(counter++ + large);
i8 retained_update = counter;

증가 연산이 성공해 2를 저장합니다. 이후 이전 값 1에 큰 값 127을 더하면서 오버플로가 납니다. outcome은 Err지만 retained_update는 2입니다. checked는 산술 오류의 경계이지 트랜잭션이 아닙니다. 앞선 함수 호출, 끝난 수정, 소유권 이동은 유지됩니다.

실패한 연산은 자신의 결과를 저장하지 않습니다. 이 보장은 실패한 변경에만 해당하며 앞서 성공한 연산을 되돌리지 않습니다. 스코프 종료 시 자동 자원 정리는 별도의 소유권 규칙입니다.

7. 기대 타입으로 실패 방식을 바꾸지 않습니다

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: ordinary addition returns i32, not Result;
Result<i32, IntegerError> wrong_mode(i32 first, i32 second) {
    return first + second;
}
Result<i32, IntegerError> explicit_mode(i32 first, i32 second) {
    return checked(first + second);
}

Result 반환형을 썼다고 일반 +를 복구 가능한 checked 구문으로 재해석해서는 안 됩니다. 마찬가지로 Result를 일반 정수에 대입해도 값을 암묵적으로 꺼내지 않습니다. 적절한 문맥에서 명시적 후위 ?나 Result API가 필요합니다.

8. 부동소수점 동작은 별도입니다

f64 first = 1.0;
f64 second = 2.0;
f64 ordinary = first + second;
rsn finite_result = Float.checked_add(first, second);

부동소수점 NaN과 무한대는 Float 계약을 따릅니다. 정수 checked 구문이 모든 부동소수점 특수 값을 산술 오류로 만들지는 않습니다. 유한 결과 검사 계약이 필요하면 명시적 checked Float API를 사용하고, 실수의 나머지는 Float.fmod 같은 함수를 사용하세요.

checked라는 이름만으로 부동소수점 트랩, Tensor 전체의 오류 처리, 할당 실패 포착, GPU 동기화를 도입하지 않습니다. 이런 동작은 각자의 API를 통해 선택해야 합니다.

9. checked와 명시적 전파 결합

Result<i32, IntegerError> calculate_stepwise(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = checked(sum * third)?;
    return Result.ok(value);
}

각 checked 표현식은 Result를 반환합니다. 후위 ?는 성공한 스칼라를 꺼내거나 같은 IntegerError를 바깥 함수에서 반환합니다. 성공 경로는 여전히 Result.ok(value)를 명시적으로 반환합니다.

Result<i32, IntegerError> calculate_whole(i32 first, i32 second, i32 third) {
    return checked((first + second) * third);
}

checked(...) 안의 ? 구문과 세부 효과 규칙은 미정입니다. 이 예제들은 그런 중첩을 사용하지 않습니다. 함수에서 반환하는 ?를 checked 범위가 잡는다고 정의한 적은 없습니다.

10. 비용·소유권·컴파일

  • 스칼라 Result는 별도의 힙 할당 없이 표현할 수 있습니다. 이 구문이 최종 ABI나 메모리 배치를 확정하지는 않습니다.
  • 필요한 검사, 태그, 오류 분기에는 명령어 비용이 들 수 있습니다. 컴파일러는 값·부수 효과·실패 동작을 보존할 때만 검사를 제거합니다.
  • AOT와 JIT는 같은 의미 계약을 사용합니다. 최적화가 wrapping, 실패 생략, checked 구문 경계의 변경을 허용하지는 않습니다.
  • 정상적인 스코프 종료와 Err 전파는 초기화 역순으로 아직 소유한 자원을 정리합니다. 이동된 값은 새 소유자가 관리합니다.
  • 안전 정지 시 정리는 미정입니다. 복구 가능한 checked 산술은 롤백이나 숨은 GPU 대기를 보장하지 않습니다.

성공 페이로드가 없는 Result 반환 작업에는 다음을 사용하며 Result<unit, E>, 반환 위치의 void를 담는 컨테이너는 사용하지 않습니다. 자세한 내용은 unit과 void.

11. 아직 결정되지 않은 사항과 관련 문서

  • 최종 IntegerError enum 표현, 페이로드, 공개 진단 이름. Overflow와 DivisionByZero는 실패 개념을 나타내며 승인된 enum 선언 구문을 뜻하지 않습니다.
  • 제안된 checked 나머지의 경계와 checked 구문에서 시프트 실패를 처리하는 방식은 별도 설계 작업입니다. 0.2의 일반 시프트는 이미 개수를 검사하고, 왼쪽 시프트의 상위 비트를 버리며, 부호 있는 오른쪽 시프트와 없는 경우를 구분합니다. 자세한 내용은 구현된 시프트 규칙.
  • 선택된 부호·크기 범위 검사 이후의 부호 없는 단항 - 허용 범위와 전체 리터럴 문법.
  • 일반 checked 표현식의 결과 형태, 중첩 checked 평탄화, checked 문장 블록, checked 피연산자 내부의 ?.
  • 종료·스택 풀기·강제 정지 시 정리와 사용자 정의 산술 오버로딩.
