1. 후위 ? 연산자와 첫 번째 전체 예제

0.2 구현 범위. 소유한 Result와 Optional의 전파가 구현되어 있으며, 다음 범위 안에서도 사용할 수 있습니다: 반환형을 명시한 클로저 본문. Result의 Err는 오류형이 같은 Result 반환으로만, Optional의 None은 Optional 반환으로만 전달됩니다. 아래의 checked 산술과 더 넓은 API 카탈로그는 별도의 설계 범위입니다. 자세한 내용은 다음을 참고하세요: 구현 프로필.

Result<T, E> 피연산자에 후위 ?를 적용하면 성공 시 T 페이로드를 얻습니다. 오류 시에는 현재의 Result<U, E> 반환 함수에서 즉시 오류 Result를 반환합니다. 성공형 T는 바깥 함수의 성공형 U와 달라도 되지만, 오류형 E는 정확히 같아야 합니다.

피연산자의 결과표현식의 결과제어 흐름
Ok(value)추출한 T 값.주변 코드의 평가를 계속합니다.
Err(error)이 경로에서는 성공 값이 생성되지 않습니다.현재 함수에서 E를 담은 Err를 반환합니다.

이 설계는 기존 반환 규칙에 명시적인 오류 반환 표기 하나를 추가합니다. 정상적으로 끝나는 non-void 경로는 여전히 return을 써야 하며, 마지막 표현식을 암묵적으로 반환하지 않습니다. 아래 Result 예제는 선택된 계약을 설명합니다. 카탈로그에만 있는 API를 예제로 사용했다고 해서 그 API의 구현을 뜻하지는 않습니다.

추출한 값을 타입이 명시된 선언에 사용하기

Result<i32, IntegerError> calculate(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = checked(sum * third)?;
    return Result.ok(value);
}

덧셈이 실패하면 calculate는 즉시 오류를 반환하고 곱셈을 건너뜁니다. 곱셈이 실패하면 그 오류를 반환합니다. 둘 다 성공하면 값을 명시적으로 감싼 뒤 반환합니다. Result.ok는 성공 값을 생성할 뿐, 그 자체로 반환하지는 않습니다.

rsn으로 추출한 페이로드의 타입도 추론할 수 있습니다: rsn sum = checked(first + second)?; 는 이 문맥에서 i32로 추론됩니다. 타입 추론은 오류형이나 반환 규칙을 바꾸지 않습니다.

2. 바깥 함수의 오류형은 같아야 합니다

Result<bool, IntegerError> positive_sum(i32 first, i32 second) {
    i32 sum = Integer.checked_add(first, second)?;
    return Result.ok(sum > 0);
}

피연산자의 성공형은 i32이고 함수의 성공형은 bool입니다. IntegerError가 정확히 같으므로 허용됩니다. 암묵적 오류 변환, 자동 From 방식 변환, 오류 계층에 따른 강제 변환, clone은 없습니다. 다른 오류형을 전파하려면 문서화된 Result API로 명시적으로 매핑해야 합니다. 다음 계획은 0.3의 공통 Error interface 계획 대여를 통한 오류 보고를 추가합니다. 이를 구현해도 정확한 오류형 일치 규칙은 바뀌지 않으며 오류를 자동으로 박싱하지도 않습니다.

리터럴이나 Result 생성자는 ? 적용 전에 이미 완전한 Result<T, E>로 결정되어 있어야 합니다. ?가 빠진 성공형·오류형을 임의로 채우거나 일반 숫자를 Result로 바꾸지는 않습니다.

3. Result 직접 반환과 ?는 서로 다른 경로입니다

Result<i32, IntegerError> direct_sum(i32 first, i32 second) {
    return checked(first + second);
}

Result<i32, IntegerError> extract_sum(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    return Result.ok(sum);
}

direct_sum은 호환되는 래퍼를 그대로 반환합니다. extract_sum은 래퍼를 소비해 스칼라를 꺼낸 뒤 성공 값을 생성하여 명시적으로 반환합니다. 둘 다 오류를 값으로 유지합니다. 이후 작업에 페이로드가 필요 없다면 직접 반환하면 됩니다.

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: ? extracts i32 on success, but the function returns Result;
Result<i32, IntegerError> missing_success_wrapper(i32 first, i32 second) {
    return checked(first + second)?;
}

전파는 호환되지 않는 명시적 반환 표현식을 조용히 Ok로 감싸지 않습니다. 성공 경로에도 일반 타입 규칙이 그대로 적용됩니다.

4. checked는 Result를 만들고 ?는 전달합니다

Result<i32, IntegerError> partly_checked(i32 first, i32 second, i32 third) {
    i32 sum = checked(first + second)?;
    i32 value = sum + third;
    return Result.ok(value);
}

Result<i32, IntegerError> fully_checked(i32 first, i32 second, i32 third) {
    i32 value = checked(first + second + third)?;
    return Result.ok(value);
}

partly_checked의 두 번째 덧셈은 일반 산술이므로 실행 중 실패하면 안전 정지합니다. fully_checked에서는 두 덧셈 모두 checked 안에 직접 작성되어 있어, 처음 실패한 연산이 Result 오류가 된 다음 ?로 전달됩니다. 전파 연산자가 앞선 checked의 범위를 넓히지는 않습니다.

보조 함수의 일반 실패는 바깥 checked 호출에 포착되지 않습니다. 마찬가지로 ?는 안전 정지, 임의의 외부 예외, Result로 표현되지 않은 할당 실패, 명시적인 Result API로 관찰하지 않은 GPU 작업 오류를 잡지 않습니다.

5. 한 번만 평가하며 롤백하지 않는 소유 페이로드

Result<i32, IntegerError> increment_then_add(&mut i32 counter, i32 amount) {
    i32 previous = checked((*counter)++)?;
    i32 value = checked(previous + amount)?;
    return Result.ok(value);
}

각 ?의 피연산자는 한 번만 실행됩니다. 증가 연산이 실패하면 뒤의 덧셈은 실행하지 않습니다. 증가가 성공한 뒤 덧셈이 실패했다면 이미 저장된 증가 결과는 유지됩니다. 오류 반환은 트랜잭션이나 자동 롤백이 아닙니다.

?는 가장 가까운 반복문이나 switch만 나가는 것이 아니라 현재 함수 또는 반환형을 명시한 클로저 본문에서 반환합니다. break나 continue를 뜻하지 않습니다. 같은 문장의 뒤쪽 작업, 나중 인수, 해당 경로의 후속 문장은 건너뜁니다.

페이로드 추출은 소유권을 보존합니다

Result<string, TextError> create_text(string_view source) {
    string owned = string.from_view(source)?;
    return Result.ok(owned);
}

string.from_view는 문서에 명시된 복사·할당을 수행하고 성공 시 소유 string을 반환합니다. ?는 소유한 Result에서 그 페이로드를 이동시킵니다. owned를 반환하면 반환 Result로 이전하며, 바이트를 깊은 복사하지 않습니다.

Err 경로에서는 오류 페이로드가 바깥 함수의 오류 결과로 이동합니다. Copy 페이로드의 스칼라 복사는 힙 작업 없이 구현할 수 있지만, 언어가 소유 페이로드나 오류를 암묵적으로 clone하지는 않습니다. 페이로드 안의 대여는 원래 수명 제한을 유지하며 원본보다 오래 살아남을 수 없습니다.

Result 전파는 소유한 Result를 소비합니다. Optional 전파도 소유한 Optional을 소비합니다. 대여한 래퍼에 ? 적용, 자동 역참조, 오류 대여, 일반화된 전파 trait은 0.2 범위에 포함되지 않습니다.

6. 스코프 정리와 unit 성공 값

Result<unit, TextError> prepare_texts() {
    string first = string.from_view("first")?;
    string second = string.from_view("second")?;
    return Result.ok(Unit.value());
}

두 번째 작업이 Err를 반환하면 first를 정리한 뒤 오류가 함수 밖으로 나갑니다. 성공 반환에서는 초기화 역순에 따라 second, first 순으로 정리합니다. 초기화되었고 아직 소유한 자원만 정리하며, 이동된 자원은 새 소유자에게 속합니다.

이는 Result 값을 통한 일반 함수 종료이므로 선택된 스코프 정리 계약이 적용됩니다. 강제 안전 정지 뒤의 정리까지 보장하지는 않습니다. 자동 정리가 새 정리 오류로 반환 오류를 덮어쓰지도 않습니다. Task와 GPU 대여는 사용 중인 버퍼를 암묵적으로 해제하는 대신 자원 수명·완료 계약을 따라야 합니다.

성공 페이로드가 없는 함수는 unit을 사용합니다

Result<unit, IntegerError> check_addition(i32 first, i32 second) {
    i32 verified = checked(first + second)?;
    return Result.ok(Unit.value());
}

unit은 값이 하나인 일반 타입이므로 Result<unit, IntegerError>가 의미 있습니다. 함수는 성공 unit도 명시적으로 반환해야 합니다. 반환 위치의 void는 저장 가능한 페이로드 타입이 아닙니다. void·정수·never 함수 안에 ?가 있다는 이유로 래퍼 반환 경로가 생기지는 않습니다. Optional 반환 함수는 소유한 Optional의 None을 전파할 수 있지만 None을 Result 오류로 암묵적으로 바꿀 수는 없습니다.

7. 전파와 삼항 선택은 다릅니다

Result<i32, IntegerError> choose_result(bool choose_first, i32 first, i32 second) {
    i32 selected = choose_first ? first : second;
    i32 increased = checked(selected + 1)?;
    return Result.ok(increased);
}
형태목적평가 방식
result?성공 값을 추출하거나 오류를 반환합니다.Result를 한 번 평가하며 함수를 종료할 수 있습니다.
condition ? first : second값을 선택합니다.bool 조건과 선택된 분기 하나만 평가합니다.

공백으로 전파와 삼항 선택을 구분하지 않습니다. 후위 ? 는 후위 연산 체인에 속하며, 삼항 선택은 가장 낮은 표현식 우선순위에서 오른쪽 결합입니다. 완전한 구문 해석이 하나뿐일 때 그것을 사용합니다. 여러 해석이 남으면 피연산자 타입으로 선택하지 않고 거부하여 명시적 괄호를 요구합니다. 자세한 내용은 파싱 규칙 에서 혼합된 형태와 실제로 모호한 토큰열을 확인하세요.

8. 의도적으로 거부되는 사용

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: this function has no Result error return type;
i32 invalid_context(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    return sum;
}

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: IntegerError does not match TextError;
Result<i32, TextError> wrong_error_type(i32 first, i32 second) {
    i32 sum = Integer.checked_add(first, second)?;
    return Result.ok(sum);
}

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: a plain integer is not a Result operand;
Result<i32, IntegerError> wrong_operand(i32 value) {
    i32 extracted = value?;
    return Result.ok(extracted);
}

허용되지 않는 예제. 이 코드는 선택된 규칙을 의도적으로 위반합니다.

// Rejected: the final expression is not an explicit success return;
Result<i32, IntegerError> missing_return(i32 first, i32 second) {
    i32 sum = checked(first + second)?;
    Result.ok(sum);
}

이 목록은 선택된 의미 규칙의 거부 사유이며 구현된 오류 코드가 아닙니다. 성공 반환 누락, 이동한 페이로드 재사용, 대여의 수명 이탈은 ?와 별개로 오류입니다.

9. 아직 결정되지 않은 전파 규칙

  • Optional 전파는 구현되어 있습니다. Some은 페이로드를 꺼내고 None은 현재 Optional 반환 함수나 클로저에서 반환합니다. None의 오류 변환과 추가 래퍼 타입은 지원하지 않습니다.
  • 자동 오류 변환, 대여한 Result 전파, 사용자 확장 전파 프로토콜은 아직 선택되지 않았습니다.
  • 0.2 파서 검사는 클로저 본문과 중첩 클로저에서 선택된 후위 연산과 조건 선택의 파싱 규칙 을 검사하고, 실제로 모호한 물음표 표현식은 거부합니다.
  • checked(...) 안의 ? 구문과 세부 효과는 아직 미정입니다. checked의 범위는 함수 반환을 포착하는 범위가 아닙니다.
  • 0.2에서 클로저가 해당 전파 경로를 가지려면 다음 반환형을 명시해야 합니다: -> Result<T, E> 또는 -> Optional<T> . 후위 ?는 클로저를 만든 함수가 아니라 그 클로저 본문에서 반환합니다. Async/GPU 선언 구문과 추가 래퍼 프로토콜은 이 구현 범위에 포함되지 않습니다.

구현된 핵심 기능은 소유한 Result 또는 Optional을 한 번 소비하고 같은 종류의 래퍼로 조기 반환합니다. Result는 같은 E를 요구하며 Optional은 오류 변환 없이 None을 전달합니다. 정상적으로 끝나는 non-void 경로는 여전히 일반 return을 명시해야 합니다.

10. 출처와 관련 문서

아래 1차 자료는 비교를 위해 사용했습니다. Aevix는 이 페이지에 명시한 규칙을 따르며, 다른 언어의 우선순위·암묵적 오류 변환·빌드 모드 동작을 자동으로 받아들이지 않습니다.

  • Rust Reference — Try 전파 표현식(비교 자료)

Aevix는 오류형의 정확한 일치를 선택했습니다. 비교 자료의 변환 규칙이나 다른 오류 래퍼를 이 설계에 도입한 것은 아닙니다.
