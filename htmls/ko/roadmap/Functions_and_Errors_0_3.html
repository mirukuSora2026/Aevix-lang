기존 동작과 새 작업

이 작업은 기존 0.3 마일스톤에 추가됩니다. 공통 Error 인터페이스와 소유형 AnyError 운반자는 새로운 라이브러리 작업입니다. 선택된 0.3 모델은 Result를 사용하는 공통 오류입니다. try는 0.4 설계 작업으로 유지하며 Java식 throw/catch 스택 되감기는 선택하지 않았습니다. 뒤에 정의된 함수의 호출과 인터페이스 기본 구현의 override는 이미 현재 0.2 컴파일러에서 동작합니다. 0.3에서는 이 계약을 유지하며 문서와 거절 검사를 강화합니다.

기능현재 범위0.3 작업
정의보다 앞에서 함수 호출하기직접 선언을 본문보다 먼저 수집합니다. 로컬 검사에서는 뒤에 정의된 함수 호출과 상호 재귀를 허용합니다.선언 순서가 호출 가능 여부를 바꾸지 않게 유지하고 import·오버로드·제네릭·메서드의 회귀 사례를 확보합니다.
인터페이스 기본 구현의 overrideoverride 키워드와 기본 구현 대체 검사가 존재합니다.규칙을 유지하고 유효한 대상이 없는 모든 위치에서 한정자를 거절합니다.
Result 기반 공통 오류Error와 AnyError는 계획 단계이며 0.2에 포함된 선언이 아닙니다.대여한 Error 검사와 Result<T, AnyError>를 위한 구체적인 소유형 AnyError를 제공하고 명시적으로 변환합니다.
try/catch 문법이 페이지에서 추가하지 않습니다.별도로 계획된 0.4 오류 범위 설계를 유지하며 Java식 스택 되감기는 선택하지 않았습니다.

planned-0.3으로 표시한 코드 블록은 앞으로 추가할 모듈에 의존합니다. 다른 예제는 기존 문법을 설명합니다. 이러한 구분이 릴리스된 배포물이나 모든 백엔드·플랫폼 조합의 동작을 인증하지는 않습니다.

정의보다 앞에서 함수 호출하기

모듈 수준 함수는 같은 모듈에서 나중에 정의한 함수를 호출할 수 있습니다. 타입 메서드도 접근 가능한 타입 안에서 선언 우선 모델을 따릅니다. 별도의 전방 프로토타입은 필요하지 않습니다.

i32 main() {
    return add(1, 2) - 3;
}

i32 add(i32 left, i32 right) {
    return left + right;
}

main은 add의 정의가 아래에 있어도 add를 해석할 수 있습니다. 함수 본문을 검사하기 전에 선언 이름, 제네릭 매개변수, 매개변수 타입, 반환 타입과 제약을 수집합니다. 이미 방문한 함수만이 아니라 전체 선언 집합을 기준으로 호출을 해석합니다.

bool is_even(i32 value) {
    if (value == 0) return true;
    return is_odd(value - 1);
}

bool is_odd(i32 value) {
    if (value == 0) return false;
    return is_even(value - 1);
}

이 상호 재귀 예제는 입력이 음이 아닌 경우를 가정합니다. 선언 수집이 종료를 보장하거나 호출 스택 비용을 없애지는 않습니다.

  • 호출할 수 있는 선언은 일반 가시성·import 규칙으로 결정합니다. 먼저 컴파일했다는 이유만으로 다른 파일이 보이는 것은 아닙니다.
  • 오버로드 선택과 제네릭 제약은 바뀌지 않으며 소스 순서로 승자를 고르지 않습니다.
  • 지역 변수에는 일반적인 블록 선언·초기화 규칙을 적용합니다. 선언이나 초기화 전에 읽을 수 없습니다.
  • 문장은 작성된 제어 흐름 순서대로 실행합니다. persist 초기화에는 별도의 의존성·수명 규칙을 적용합니다.
  • 이 규칙은 모듈·타입 선언에 관한 것이며 중첩 함수나 별도의 프로토타입 문법을 추가하지 않습니다.

명시적 override

기존 override 키워드는 구조체나 enum이 구현한 인터페이스의 일치하는 기본 메서드를 대체할 때 사용합니다. 대체 시에는 이 표기가 필수입니다.

interface Scored {
    public i32 score(&Self self) {
        return 1;
    }
};

struct Player implements Scored {
    public override i32 score(&Player self) {
        return 2;
    }
};

해석된 메서드 이름, 매개변수·수신자 계약, 반환 타입과 제네릭 요구가 일치해야 합니다. 인터페이스 구현 메서드는 계속 public입니다. 구체 타입 호출은 기본적으로 선택된 구현을 정적으로 사용하고, 자격을 갖춘 dyn 호출은 동적 뷰를 통해 같은 대체 구현을 사용합니다.

상황규칙
일치하는 기본 본문 하나를 대체public override를 쓰고 전체 메서드 계약을 충족합니다.
기본 본문이 없는 필수 메서드 구현일반 public 메서드로 작성합니다. 대체할 본문이 없으므로 override를 쓰지 않습니다.
여러 기본 구현의 충돌명시적 override 하나를 제공합니다. 인터페이스 나열 순서에는 우선권이 없습니다.
알 수 없는 이름 또는 호환되지 않는 시그니처override를 거절하며 무관한 메서드를 조용히 추가하지 않습니다.
자유 함수, 필드, 지역 선언 또는 일치하는 기본 구현이 없는 메서드한정자를 거절합니다.

알려진 보강 작업: 현재 0.2 프런트엔드는 모듈 수준 함수, 필드 또는 인터페이스 안에 선언한 메서드에 붙은 override를 대상 없음 오류 없이 허용합니다. 0.3 거절 검사는 이 빈틈을 막아야 합니다. 올바른 인터페이스 예제가 동작한다고 해서 모든 한정자 오용을 이미 진단한다는 뜻은 아닙니다.

기존에 선택한 인터페이스 모델을 유지합니다. 클래스 상속, 기본 가상 호출, super 식이나 Java의 어노테이션 문법을 추가하지 않습니다.

공통 오류 인터페이스

선택된 0.3 모델: Result를 사용하는 공통 오류 처리입니다. 명시적으로 import한 error.Error 인터페이스로 대여한 오류를 살펴보고 구체적인 error.AnyError 타입으로 소유하는 공통 오류를 전파합니다.

제안하는 최소 인터페이스는 할당 없이 code와 message를 읽을 수 있게 합니다. code는 오류 종류를 식별하고 message는 사람이 읽을 요약입니다. 뷰는 오류 소유자나 정적 저장소를 대여할 수 있지만 해당 저장소보다 오래 살 수 없습니다.

public interface Error {
    public string_view code(&Self self);
    public string_view message(&Self self);
};

이는 error.avx에 둘 공개 선언의 제안이며 자동 prelude 타입이 아닙니다. 표준 복구 가능 오류 타입은 구체 필드와 enum variant를 유지하면서 이를 구현할 수 있습니다. 사용자 오류는 기존 인터페이스 규칙에 따라 implements Error로 참여합니다.

import error { Error };
import system;

Result<unit, system.IoError> report(&dyn Error e) {
    system.println(e.code() + ": " + e.message())?;
    return Result.ok(Unit.value());
}

Error는 공통 동작을 정의하고 e는 전달받은 오류 변수입니다. 처리 함수는 기존 오류를 대여하므로 clone·박싱·소비하지 않습니다. 출력도 실패할 수 있으므로 report는 계획된 콘솔 IO Result를 반환합니다.

code나 message를 읽을 때마다 새 소유 string을 포매팅해서는 안 됩니다. 구현은 정적 요약이나 저장해 둔 텍스트의 대여를 사용할 수 있습니다. 상세 포매팅, 원인, 문맥과 선택적 역추적은 저장소·실패 계약을 명시한 별도 API입니다. 컴파일러 진단, 프로세스 종료나 복구 불가능한 안전 중단을 잡아 준다고 약속하는 인터페이스가 아닙니다.

오류 소유와 전파

대여한 &dyn Error 는 즉시 오류를 보고할 때 유용합니다. 임시 오류를 소유하거나 소유자의 수명을 벗어나거나 완전한 구체 Error 값처럼 저장할 수는 없습니다. 인터페이스 이름만으로 다음 타입의 E에 쓸 크기가 정해진 오류 운반자가 되지는 않습니다: Result<T, E>.

선택된 운반자: AnyError는 구체적인 소유 타입이며 다음과 같이 사용할 수 있습니다: Result<T, AnyError>. 호출자가 정확한 계약을 필요로 하는 곳에서는 구체 오류 타입과 명시적인 애플리케이션 enum을 유지합니다. 기존 ? 규칙 은 전파 경계에서 같은 E를 계속 요구합니다. Error를 구현한다고 서로 다른 Result 오류 매개변수를 바꿔 쓸 수 있게 되지는 않습니다.

import error { AnyError };

Result<i32, AnyError> forward(Result<i32, AnyError> operation) {
    i32 value = operation?;
    return Result.ok(value);
}

이 예제는 이미 AnyError로 저장된 오류를 전달하며 다른 오류 타입을 암시적으로 변환하지 않습니다. AnyError는 Error를 구현하고 기본적으로 이동합니다. 애플리케이션 경계에서의 사용은 명시적이며, 타입이 정해진 라이브러리 오류와 그 payload도 계속 사용할 수 있습니다.

명시적으로 선택한 고정 크기 표준 오류 집합에는 인라인 저장을 권장합니다. 해당 오류를 운반자로 바꿀 때 추가 할당이 필요하지 않도록 하기 위해서입니다. 오류 생성 자체에 할당이 없었다거나 InputError<T> 같은 임의의 payload 포함 오류가 인라인에 들어간다고 보장하지는 않습니다. 이런 오류는 타입이 정해진 Result에 두거나 명시적인 실패 가능 패킹을 사용합니다.

다른 오류의 소유형 타입 소거에는 별도의 명시적이고 실패 가능한 변환이 필요합니다. 할당 실패를 표현하면서 원래 오류를 보존해야 하며, 또 다른 래퍼를 재귀적으로 할당하지 않고도 할당 실패를 보고할 수 있어야 합니다. 실패 가능한 패킹은 실패 시 원래 오류를 반환해야 합니다. 이를 실패하지 않는 map_err 콜백이나 자동 ? 변환에 숨길 수 없고 중첩 실패도 자동으로 평탄화하지 않습니다.

0.3의 오류 매핑 기반 은 계속 명시적으로 유지합니다. AnyError는 0.3에 포함하기로 선택했습니다. 구현 전에 생성자 이름, 인라인 variant 집합, 레이아웃, 할당, 실패 시 소유권 표현, 수명과 스레드 간 이전 규칙을 확정합니다. 자동 스레드 간 사용 권한이나 대여 수명 연장은 암시하지 않습니다.

try·catch와의 관계

확정된 결정: 0.3은 Result와 명시적 매핑을 사용하는 공통 오류 모델을 채택합니다. Java식 try/catch는 추가하지 않습니다. 기존 0.4 try 작업은 유지합니다. 공유 오류 인터페이스가 throw 문, 예외 상속, 런타임 스택 되감기나 함수 사이의 오류 포착을 조용히 추가하지는 않습니다.

0.4에서는 Result 실패를 지역적으로 처리하는 방향을 계속 우선합니다. 나중에 Java식 스택 되감기를 선택한다면 컴파일러를 바꾸기 전에 제어를 옮길 수 있는 연산, catch 순서, 정리, FFI를 넘는 전파와 Result와의 관계를 명세해야 합니다.

0.3 구현 완료 조건

  1. 뒤에 정의된 자유 함수, 메서드, 오버로드, 제네릭 함수와 상호 재귀에 대한 공통 사례를 유지합니다. 독립 선언의 순서를 바꿔도 허용되는 호출이 달라져서는 안 됩니다.
  2. 선언 전 지역 변수 사용, import 누락, private 접근, 중복 시그니처와 모호한 오버로드를 거절합니다.
  3. 올바른 override와 dyn 디스패치 사례를 유지합니다. 잘못 놓인 한정자, 기본 구현 누락, 맞지 않는 수신자·결과 계약과 해결되지 않은 기본 구현 충돌은 거절합니다.
  4. error 모듈의 공개 code·message·AnyError 계약을 확정하고 선택된 표준 오류 어댑터를 구현하며 오류·메시지 대여의 수명 이탈을 거절합니다.
  5. 필수 할당 없는 보고, 출력 실패, 명시적 오류 매핑과 Result<T, AnyError> 전파를 검사합니다. 패킹은 소유형 제네릭 payload를 포함하여 변환 실패 시 입력 오류를 보존해야 합니다.
  6. 현재 Result/? 동작과 별도의 0.4 try 결정을 유지합니다. 컴파일러 포팅에서 의존하기 전에 AOT·JIT의 언어 동작을 비교합니다.

주요 참고 자료

이 자료는 각자의 언어를 설명합니다. 이 계획에서는 위에 적은 Aevix의 선언·인터페이스·소유권·Result 규칙이 기준입니다.

  • Java 언어 명세: 선언의 범위 — 메서드의 텍스트상 정의보다 앞에서 호출하는 경우와 비교하기 위한 메서드 멤버 범위 자료입니다.
  • Java 언어 명세: Override — override 의도를 검사하는 방식의 비교 자료입니다. Aevix는 자체 키워드와 인터페이스 규칙을 사용합니다.
  • Java 언어 명세: 예외의 종류 — Exception과 Error는 서로 다릅니다. 공통 수신자가 있다고 모든 실패를 복구할 수 있는 것은 아닙니다.
  • Rust 표준 라이브러리: Error — 공통 오류 동작과 대여 기반 오류 검사의 비교 자료이며 박싱·변환 정책을 자동으로 채택하지는 않습니다.
