계획 상태

셀프 호스팅은 0.5에서 진행할 예정입니다. 이 잠정 계획은 구현 담당 에이전트의 소스 기반 검토와 기존 언어 결정을 종합한 것입니다. 요청한 Claude Opus 5.5 검토는 최종 답변 전에 계정 한도에 도달해 중단되었습니다. 모델 간 합의가 완료된 상태는 아닙니다. 자세한 내용: 검토 상태.

GPU는 0.2 범위에서 제외됩니다. CPU SIMD와 범위가 제한된 병렬 실행은 범위에 포함됩니다. 전체 라이브러리 카탈로그를 구현해야 부트스트랩할 수 있는 것은 아닙니다.

버전목표산출물완료 조건
0.2현재 기반 기능 완성i128/u128, 반정밀도 부동소수점, Complex, 클로저, 제네릭 기본값과 const 크기, 텍스트/Tuple/Slice, CPU SIMD와 병렬 실행, JIT 생명주기, 의존성 검사, PATH 설치 프로그램 및 VSIX.모든 의미 분석·실행 검사를 통과하고, 소유권·오버플로·할당 실패·설치 위치 변경 검사가 계속 유효해야 합니다. 네이티브 실행과 교차 빌드의 근거를 구분해 기록합니다. 성능 작업은 계속 보류합니다.
0.3컴파일러 부분집합과 네이티브 자원 경계 확정검토된 버퍼·핸들 FFI, 사용자 자원 정리, 명시적이고 실패 가능한 close/flush, 오류 매핑, 대여한 Error 인터페이스와 Result용 소유 AnyError 컨테이너, 컬렉션·텍스트·해시·맵·IO·경로·프로세스의 필수 기능, print·println·printf·input을 제공하는 import system, + 출력 조합, 반환문에 한정한 bool→정수 변환, 명시적 Boolean 변환, 필드 축약 표기와 원시 문자열, 정의보다 앞선 호출 유지와 override 진단 강화, 안정적인 ID, 대상 ABI, IR 검증·버전 관리 및 분리 컴파일.소스 프런트엔드는 모듈을 읽고, 심볼·타입 테이블을 유지하고, 진단을 출력하며 Clang을 호출할 수 있어야 합니다. 네이티브 핸들은 정확히 한 번 닫혀야 하며, 부분 IO와 할당 실패는 문서에 명시된 상태를 보존해야 합니다. 콘솔 IO는 EOF, 빈 입력, 인코딩 오류, 부분 출력, flush 실패를 구분하고, 서식 지정 호출은 실행 전에 잘못된 타입을 거부해야 합니다. 편의 문법은 일반 타입 규칙, 명시적 비용, 대여, AOT/JIT 동작을 보존해야 합니다. 선언 순서와 무관한 호출을 유지하고, 잘못된 위치의 override 표시와 유효 범위를 벗어나는 오류 뷰를 거부해야 합니다.
0.4검토된 문법 추가와 함께 컴파일러를 Aevix로 단계적으로 이식소스 저장소, 렉서·파서, 이름·타입·상수·제네릭, CFG·소유권, AIR·검증기, 텍스트 LLVM 출력기, 모듈 로더와 드라이버. do-while 반복문을 추가하고 try·오류 범위 설계를 확정하며, 유용한 다른 제어 흐름 문법을 검토합니다. C++는 stage0으로 유지합니다.Aevix 컴파일러가 실제 컴파일러 모듈을 컴파일하고 네이티브 프로그램을 출력해야 합니다. 파싱·타입 검사·소유권 분석을 C++ 프런트엔드에 다시 위임해서는 안 됩니다. 부트스트랩 전에 승인된 문법의 허용·거절, 정리, 실행 검사가 stage0과 Aevix에서 일치해야 합니다.
0.5부트스트랩과 셀프 호스팅 확립stage0 C++ → stage1 Aevix 컴파일러 → stage1이 빌드한 stage2 → stage2가 빌드한 stage3 순서로 진행한다. stage2/stage3를 비교하고 전체 회귀 검사 모음을 실행한다. 설명하는 표시, 안정적인 기계용 코드, 구조화된 수정안, 편집기 연동을 갖춘 친절한 소스 진단도 추가한다.문서에 명시한 시드로 새 환경에서 부트스트랩에 성공해야 한다. 정규화한 출력을 비교하고 차이를 조사한다. LLVM·런타임·링커 의존성과 대상 환경의 실행 한계를 공개한다. 공통 진단 테스트는 유니코드 위치, 소유권 원인, 결정적인 정렬 순서, 제한된 복구, 오래된 편집기 응답을 다룬다.

0.3과 0.4의 추가 작업

다음 항목은 기존 로드맵에 추가됩니다. 0.3의 네이티브 자원·라이브러리 작업, 0.4의 컴파일러 이식, 0.5의 셀프 호스팅 목표를 대체하지 않습니다. 새로운 API와 문법은 계획이며 현재 0.2 컴파일러의 기능이 아닙니다. 정의보다 앞선 호출과 올바른 인터페이스 override는 이미 지원되며, 0.3에서는 기존 계약을 문서화하고 강화합니다.

버전유지되는 기존 목표추가 작업
0.3네이티브 자원, FFI, 컬렉션과 컴파일러 구현에 필요한 라이브러리.import system 콘솔 IO: print, println, printf, input과 + 출력 조합. 명시적인 오류·버퍼 계약을 바탕으로 제공합니다. 편의 기능: bool의 정수 반환, 명시적 Boolean 변환, 이름이 지정된 필드의 축약 표기, 원시 문자열. 함수와 오류 계약: 정의보다 앞선 호출, override 검사 강화, Result와 함께 사용하는 공통 오류. 대여한 Error로 검사하고 소유 AnyError에 담습니다.
0.4C++를 stage0으로 유지하면서 컴파일러를 Aevix로 이식.추가 문법 연구와 구현: do-while과 try. 다른 후보도 기존 안전성 모델에 맞춰 검토합니다.
0.5문서화된 stage0 → stage1 → stage2 → stage3 셀프 호스팅 부트스트랩.친절한 컴파일러 진단: 소스 발췌와 밑줄, 기대 타입과 실제 타입, 소유권의 시작 지점, 관련 위치, 안정적인 코드, 검토된 수정안, 구조화된 JSON, VSIX 연동을 추가한다. 부트스트랩과 대상 환경의 통과 조건도 계속 충족해야 한다.

선행 작업 순서

안전한 네이티브 자원을 먼저 마련한 뒤 컬렉션·텍스트·해시·IO·프로세스 라이브러리를 구현합니다. 검토된 바이트·오류 경계를 기반으로 system 콘솔 계층을 도입하고, 더 넓은 File·Process 소유권 작업도 유지합니다. 일반적인 암시적 변환 범위를 넓히지 않으면서 승인된 0.3 편의 규칙을 구현한 다음 컴파일러 부분집합을 확정합니다. 새로운 0.4 문법은 Aevix 이식 작업에서 사용하기 전에 stage0과 공유 회귀 검사에 먼저 반영해야 합니다. 소스 저장소와 구문을 의미 분석보다 먼저 이식하고, 네이티브 실행 전에 소유권과 AIR 검증을 이식합니다.

SourceId, NodeId, TypeId와 바이트 범위를 장기 식별자로 사용하고, 조회 중에는 짧게 대여합니다. Vector가 커질 때 요소의 장기 대여를 유지할 수는 없습니다. 안정적인 C++ 객체 주소를 그대로 Vector 참조로 옮기는 방식은 대여 규칙과 충돌합니다.

일반 공개 C FFI에는 기존 스칼라 매개변수·반환값 제한이 유지됩니다. 개발 중인 File/Process 래퍼는 신뢰된 표준 모듈 연산의 별도 닫힌 레지스트리, 비공개 세대 토큰, 범위가 있고 호출 후 보관하지 않는 버퍼를 사용합니다. 이것이 임의의 extern 권한을 주지는 않으며, 주소를 u64로 넘기는 것은 안전한 대안이 아닙니다.

셀프 호스팅의 범위

프런트엔드, 의미 분석, AIR 구성, 컴파일러 드라이버는 Aevix로 작성해야 합니다. C++ 프런트엔드를 감싼 실행기만으로는 목표를 달성한 것이 아닙니다. LLVM, 검토된 플랫폼 shim, 네이티브 런타임, 링커는 외부 의존성으로 남을 수 있습니다.

자체 CPU 백엔드, GPU, 추측 기반 JIT 단계·OSR, 네트워크 패키지 레지스트리, 비동기 실행기, 정규식, 전체 로캘·Unicode 스택이 부트스트랩을 막을 필요는 없습니다.

0.3 구현 전에 결정할 사항

사용자 정의 정리는 확정한 Drop 인터페이스를 사용하며, 등록된 CPU 자원은 타입이 있는 네이티브 경계를 사용합니다. 더 넓은 FFI 자원·버퍼 계약과 안정적인 공개 레이아웃·ABI 보장은 별도의 결정이 필요합니다. 이 기반이 검사하지 않는 포인터나 콜백 권한을 주지는 않습니다.

직렬화된 AIR와 영구 캐시에는 버전을 부여합니다. 캐시 식별 정보에 소스·의존성 내용, 컴파일러·런타임·LLVM 버전, 대상 기능·메모리 배치, 옵션을 포함합니다. 변경 가능한 AST 주소는 영구 ID가 아닙니다.

system 콘솔 함수와 do-while·try 작업은 추가 목표입니다. 정확한 서식 지정 호출 계약과 try 오류 모델은 집중적인 검토가 필요합니다. try를 추가한다고 throw/catch 예외 스택 풀기가 승인되는 것은 아닙니다. 확정된 범위와 제안된 세부 사항은 연결된 버전별 계획을 참고하세요.
